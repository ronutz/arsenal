HTTP's founding simplification is amnesia: every request stands alone, and the server owes it no memory of the last one. That statelessness is why the web scales - any server can answer any request - and why logging in should be impossible. **Cookies** are the retrofit that squares the circle: state lives *in the client* and travels with every request, so the protocol stays stateless while the application remembers. The mechanics fit in one sentence; the consequences fill this article and [its security sequel](/learn/cookie-security-flags).

## The two headers, and who keeps the ledger

A response says `Set-Cookie: session=abc123; Path=/; Max-Age=3600` - one cookie per header line, name, value, and attributes. From then on, every request the browser sends *in scope* carries `Cookie: session=abc123` - names and values only, attributes never echoed back. Two asymmetries hide there, and both matter. First, **the browser keeps the ledger**: the server declared the rules once at set time, but only the client knows what it stored, when it expires, and what else is in the jar - the server just sees what comes back. Second, cookies are per-*request*, not per-session: the browser attaches every in-scope cookie to every matching request, which is the entire performance and security surface in one habit - and the reason session identifiers stay short and [load balancers can ride the mechanism for persistence](/learn/f5-bigip-persistence-cookies).

## Scope: which requests carry it

Attributes at set time define the cookie's territory. **Domain** unset means host-only - the exact origin host, the strictest and best default; `Domain=example.com` widens it to the whole registrable domain including subdomains, which is exactly how a session leaks to a subdomain you forgot you had. **Path** narrows by URL prefix - more etiquette than security, since same-origin pages can reach across paths. The browser computes the intersection on every request: host match, path match, plus the scheme and cross-site rules [the flags article owns](/learn/cookie-security-flags). One more territorial rule earns its mention: the **public suffix list** is why nobody can set a cookie for `.com` or `.com.br` and have it follow you across the internet.

## The send decision, one check at a time

Every time the browser builds a request, it runs the same checks on each stored cookie, and the cookie goes only if it passes all of them ([RFC 6265, section 5.4](https://www.rfc-editor.org/rfc/rfc6265.html#section-5.4)). **Host.** A cookie set without `Domain` is host-only and goes back only to the identical host; with `Domain`, the request's host must domain-match it, which means being identical to it or ending in it right after a dot, and not being an IP address, with both compared in lower case ([sections 5.1.3, 5.3 step 6 and 5.4](https://www.rfc-editor.org/rfc/rfc6265.html#section-5.1.3)). So `Domain=www.example.com` is not the same as leaving `Domain` out: it also reaches `api.www.example.com`. A `Domain` that the host setting the cookie does not itself domain-match makes the browser ignore the cookie entirely ([section 5.3, step 6](https://www.rfc-editor.org/rfc/rfc6265.html#section-5.3)). **Path.** Without `Path`, the cookie's path is the directory of the URL that set it, `/account` for a cookie set by `/account/login`; a request path matches when it is identical to the cookie's path, or begins with it and either the cookie's path ends in a slash or the next character of the request path is one ([section 5.1.4](https://www.rfc-editor.org/rfc/rfc6265.html#section-5.1.4)). So `/account` covers `/account/orders` but not `/accounting`, and `Path=/account/` does not cover `/account` itself; the comparison is character for character, not the URI equivalence of RFC 3986 ([RFC 6265 errata, erratum 3663](https://www.rfc-editor.org/errata/rfc6265)). **Secure.** A `Secure` cookie goes only over a channel the browser considers secure, typically HTTPS. **HttpOnly.** An `HttpOnly` cookie is left out when the cookie string is built for a non-HTTP API ([section 5.4](https://www.rfc-editor.org/rfc/rfc6265.html#section-5.4)), and `document.cookie` returns exactly that string ([HTML Standard, document.cookie](https://html.spec.whatwg.org/multipage/dom.html#dom-document-cookie)); a request that the page's script makes still carries the cookie.

**SameSite.** The last check is not in RFC 6265. It comes from the RFC's revision, draft-ietf-httpbis-rfc6265bis, which the IESG approved on 2 December 2025 and which, when checked on 26 October 2026, was still an Internet-Draft, revision 22 of 1 December 2025, waiting in the RFC Editor's queue with the status "blocked: Final Approval Pending" and no RFC number ([IETF Datatracker](https://datatracker.ietf.org/doc/draft-ietf-httpbis-rfc6265bis/)). On a cross-site request, a cookie that is not `SameSite=None` is left out unless it is `Lax` or has no `SameSite` attribute, the request is an HTTP request with a safe method, and it navigates a top-level window ([draft, section 5.8.3](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis-22#section-5.8.3)); GET is a safe method and POST is not ([RFC 9110, section 9.2.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1)). A cookie with no `SameSite` attribute gets the draft's "Default" enforcement, which that check treats like `Lax` ([section 5.7, step 17](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis-22#section-5.7)), although a browser may waive the safe-method condition for such a cookie when it was created recently, a mode the draft calls Lax-allowing-unsafe, naming two minutes as a reasonable limit ([section 5.6.7.2](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis-22#section-5.6.7.2)). A `SameSite=None` cookie without `Secure` is never stored at all ([section 5.7, step 19](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis-22#section-5.7)). For `document.cookie`, the read counts as cross-site when the page is framed, directly or through other frames, by a page from another site, and then only `SameSite=None` cookies are visible ([section 5.8.2](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis-22#section-5.8.2)).

Two more filters sit outside the cookie's attributes: the Fetch Standard's credentials mode can keep cookies off a request whatever the cookie says ([Fetch Standard, credentials mode](https://fetch.spec.whatwg.org/#concept-request-credentials-mode)), and a browser may leave the `Cookie` header off entirely, for example on third-party requests ([draft, section 5.8.1](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-rfc6265bis-22#section-5.8.1)). Which of the draft's rules a given browser applies, the Default enforcement included, is for that browser's own documentation to say.

## Lifetime: session or persistent

No expiry attribute makes a **session cookie** - it dies with the browsing session, which modern session-restore features quietly stretch far beyond what "session" suggests. `Max-Age` (seconds from now, the modern form) or `Expires` (an absolute date, the legacy form) makes a **persistent cookie** written to disk; when both appear, `Max-Age` wins. Deletion is just the same move with the clock turned back: set the cookie again with `Max-Age=0` or a past `Expires`. And because the ledger is the browser's, "log out" that only clears the server-side session while the cookie lingers is a classic half-measure - the note keeps arriving, now naming a session that no longer exists.

## What cookies are, once you squint

The pattern worth keeping: a cookie is a *server-issued claim stored by the client and replayed on schedule* - which makes it the conceptual ancestor of every bearer credential since. Where the story goes next is defense: `Secure`, `HttpOnly`, `SameSite`, and the `__Host-` prefix are [the sequel](/learn/cookie-security-flags), and they exist because everything this article described - automatic attachment, wide scoping, client-side custody - is precisely what attackers learned to ride.
