Engineers and instructors put code in pictures all the time: a `show` command's output on a slide, a configuration excerpt attached to a ticket, a script in a document that has to look exactly like the terminal. A picture keeps the layout, the colours and the monospace columns, and it pastes anywhere. It also drops three things on the way, and each of them has a rule or a format you can check.

## Text first, when the medium can show text

The Web Content Accessibility Guidelines treat a picture of words as a picture. WCAG 2.2 defines an image of text as "text that has been rendered in a non-text form (e.g., an image) in order to achieve a particular visual effect", and Success Criterion 1.4.5, Images of Text (Level AA), says that if the technology in use can achieve the visual presentation, text is used rather than images of text, unless the image can be customised by the user or the particular presentation is essential. The W3C's Understanding document explains why: people who need a different font size, colour, font or spacing can change real text and cannot change pixels.

For code, that settles most cases. A documentation page, a wiki, a knowledge base article or a ticket system that renders fenced code blocks can show the code as text, monospaced and highlighted, and the reader can copy it, which a picture never allows. Keep the picture for the places that cannot: a slide whose tool does not keep code formatting, a chat that flattens indentation, a printed handout. On a slide, the speaker notes are text, so the code can travel there as well.

An SVG sits in between. An SVG whose code is written as `<text>` elements holds real characters that can be selected and searched. The same file loaded through an `<img>` element is still an image on the page, and it needs a text alternative like any other picture.

## Alt text for code is the code

Success Criterion 1.1.1, Non-text Content (Level A), asks that every non-text content presented to the user has "a text alternative that serves the equivalent purpose". The purpose of a picture of a configuration is the configuration, so the equivalent is the configuration itself, as text: a one-line description of what the picture is, then the code. "Screenshot of router config" serves no purpose a reader can use; the nine lines that were in the screenshot do.

Where the picture had a value masked, the alternative should say so in words rather than reproduce the bullets of the mask. And where the alt text would be long, the guidance above applies twice over: put the code as text next to the picture, and keep the alt text to the description.

## Contrast applies to the picture as well

Success Criterion 1.4.3, Contrast (Minimum), Level AA, covers "text and images of text": at least 4.5:1 between the text and its background, 3:1 for large-scale text. A highlighted line is a second background, so every text colour has to meet the ratio against both the normal background and the highlight: each syntax colour is a separate pair to check, twice. The [colour contrast and format tool](/tools/color-contrast-format) does the arithmetic, and the article on [colour contrast and the WCAG formula](/learn/colour-contrast-wcag-and-css-color-notations) explains it.

## What a screenshot keeps

The third loss is the one that hurts. A picture keeps every character that was on the screen, and it travels like any attachment: copied, forwarded, attached to the next ticket. The secrets that turn up in pictures of configuration and terminal output most often all have documented formats, which is what makes them findable before you publish.

**Private keys in PEM.** RFC 7468 defines the textual encoding: a line `-----BEGIN` followed by a label, base64 data, and a matching `-----END` line. Its section 10 assigns the label `PRIVATE KEY` to PKCS #8 private keys and section 11 assigns `ENCRYPTED PRIVATE KEY` to encrypted ones. OpenSSL's manual still documents its older "traditional" form, `RSA PRIVATE KEY` with `Proc-Type` and `DEK-Info` headers, and OpenSSH writes its keys between `-----BEGIN OPENSSH PRIVATE KEY-----` and the matching end line. A key in a block scalar of a YAML file or in a JSON credentials file, written on one line with `\n` escapes, is the same secret.

**HTTP credentials.** RFC 9110 defines the `Authorization` field as the scheme followed by the credentials. With the Bearer scheme of RFC 6750 the credential is the token itself, and RFC 6750 defines a bearer token as one that "any party in possession of the token" can use. With the Basic scheme of RFC 7617 it is the user name, a colon and the password, encoded in Base64: an encoding, not encryption, so anyone who can read the picture can decode it.

**AWS access keys.** AWS's IAM documentation lists the prefixes of its unique identifiers: `AKIA` for an access key and `ASIA` for a temporary access key issued by AWS STS. An access key ID is half of a credential; the other half is the secret access key, which the AWS CLI's credentials file stores next to it as `aws_secret_access_key`.

**JWTs.** RFC 7519 defines a JWT as a set of claims carried in a JWS or JWE compact serialisation: base64url segments joined by dots, three of them for a signed token and five for an encrypted one. RFC 7515 defines base64url as an encoding of the bytes, so the header and the claims of a signed token are readable by anyone who has it, and while it is valid it is the credential.

**Passwords in URLs.** RFC 3986 says the `user:password` form in a URL's userinfo is deprecated, and that applications should not render as clear text any data after the first colon. Configuration still holds such URLs: F5's own tmsh reference shows a key file imported from `ftp://username:password@server/...`.

**Device configuration.** FortiOS stores secrets in its configuration with the marker `ENC` before the encrypted value, as in `set psksecret ENC ...` in Fortinet's technical tip on copying a pre-shared key between configurations. Encrypted is not harmless: Fortinet's own documentation describes configurations "encrypted with the system default key" and offers private data encryption to replace that key, and the tip exists because people copy those values from one configuration into another. F5's tmsh shows `encrypted-password` for local users and accepts `password` and `passphrase` attributes on monitors, SSL keys and client SSL profiles. Cisco IOS XE writes `username ... secret 9 ...` and `enable secret ...`, and its guide prints its own type 5 example to explain the migration to stronger types. All of these belong to the device, and none belongs in a slide.

## Mask before the picture, and replace the characters

Masking has to happen before the picture is made, and it has to replace the characters rather than cover them. A box drawn over text in an SVG or a PDF hides it from the eye and leaves it in the file, selectable and searchable. A picture that has already been published with a live secret in it is a disclosure: masking the next copy does not withdraw the first one, so the secret has to be changed where it is used.

The [code to image tool](/tools/code-to-image) works in that order. It looks for the formats above before it draws anything, lists what it found with the line and the column, replaces each value with eight bullets unless you untick it, and writes the alt text with the word "masked" where the value was. It names what it looks for and is not a complete scanner: a format it does not know stays in the picture, so read the picture before you publish it.
