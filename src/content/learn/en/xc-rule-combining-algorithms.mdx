A service policy with a `rule_list` holds an ordered list of rules. The **rule combining algorithm** decides how that list is walked, and therefore which rule's action wins when more than one rule could match a request.

## The three algorithms

**FIRST_MATCH** is the default and the one most people reason about. Rules are evaluated sequentially from top to bottom until one matches. That rule's action is applied and evaluation stops. Order in the list is everything: a broad rule near the top can shadow a more specific rule below it, which never gets a chance to run.

**ALLOW_OVERRIDES** evaluates all rules with an ALLOW action before any rule with a DENY action. The practical effect is that if any ALLOW rule matches, the request is allowed, even if a DENY rule would also have matched. Allow wins ties.

**DENY_OVERRIDES** is the mirror image: all DENY rules are evaluated before any ALLOW rule. If any DENY rule matches, the request is denied, regardless of a matching ALLOW. Deny wins ties.

## Why the order matters

Consider two rules: one denies a specific bad ASN (autonomous system number), and one allows everything from a partner country. Under FIRST_MATCH, whichever appears first decides. Under DENY_OVERRIDES, the deny is considered first, so a request from the bad ASN is blocked even if it also comes from the partner country. Under ALLOW_OVERRIDES, the same request is allowed, because the allow is considered first.

Same rules, three different outcomes for the overlapping request. This is why reading a policy without knowing its algorithm can mislead you.

Reduced to two rules, an ALLOW listed first and a DENY listed second, the three algorithms disagree in exactly one case:

| ALLOW rule matches? | DENY rule matches? | FIRST_MATCH | ALLOW_OVERRIDES | DENY_OVERRIDES |
|---|---|---|---|---|
| Yes | Yes | Allow | Allow | **Deny** |
| Yes | No | Allow | Allow | Allow |
| No | Yes | Deny | Deny | Deny |
| No | No | No rule matches | No rule matches | No rule matches |

When no rule matches, the policy does not match: the next service policy is evaluated, and if [no policy matches at all, the request is blocked by default](https://docs.cloud.f5.com/docs-v2/multi-cloud-app-connect/how-to/app-security/service-policy). Swap the two rules and only one cell moves, FIRST_MATCH on the first row, which is the whole argument for knowing the algorithm before reading the order.

## The App Firewall constraint

There is one hard rule to know. If any rule in the policy is configured with an App Firewall (WAF (web application firewall)) action, the combining algorithm **must** be FIRST_MATCH. The overrides modes are not permitted alongside WAF actions, because WAF processing is tied to sequential evaluation. If you see WAF actions on rules, you can assume FIRST_MATCH.

## Where the algorithm lives

The algorithm belongs to the **policy**. F5's [service policy API reference](https://docs.cloud.f5.com/docs-v2/api/service-policy) describes it as the rule combining algorithm "for a policy" that "determines how the list of rules in the policy is evaluated", with FIRST_MATCH as the default, and the [create example](https://docs.cloud.f5.com/docs-v2/platform/reference/api-ref/ves-io-schema-service_policy-api-create) carries it in the policy's own spec as `"algo": "FIRST_MATCH"`. The service policy set is not where it lives: [the set's spec](https://docs.cloud.f5.com/docs-v2/api/service-policy-set) holds a single field, an ordered list of up to 16 references to service policies.

Documented is not the same as configurable, though. The published create schema for a service policy has no field that takes the algorithm (the type is defined, and nothing in the schema points to it), and the console workflow for a custom rule list offers only the order of the rules. Read FIRST_MATCH as what a policy does, and ALLOW_OVERRIDES and DENY_OVERRIDES as documented semantics: if you meet one in an exported object, these are its rules, but the current schema does not confirm that a tenant can still choose one.

For that reason the explainer on this site defaults to explaining top-to-bottom FIRST_MATCH evaluation, and surfaces an explicit algorithm only if the pasted JSON carries one. When you are auditing a real deployment, read the algorithm, if there is one, from the policy object itself, not from the policy set.


## The algorithm decides which mistakes are survivable

Ordering is not only about precedence; it decides **what a misplaced rule costs.**

Under first-match, a broad ALLOW placed above a specific DENY silently disables the DENY, and the configuration still contains both, so a reviewer reading the list sees the protection they expect. The rule is present, correct, and unreachable.

That is why **specific before general** is not style advice. It is the ordering under which an error becomes visible: a specific rule that is wrong stops matching and gets noticed, whereas a general rule placed too early keeps working perfectly while shadowing everything beneath it.

**Read a policy bottom-up when you are looking for what is not being enforced.** Reading top-down tells you what happens; reading upward tells you what can never happen.
