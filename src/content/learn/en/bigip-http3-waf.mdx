HTTP/3 changed the transport under the web: QUIC over UDP instead of TCP, with encryption reaching deeper into the protocol. For a WAF (web application firewall) that grew up parsing TCP streams, that is not a version bump, it is a new listening post. BIG-IP 21.1 is the release where F5's web protection stack takes up position on it.

## What actually ships

Per the 21.1 release notes, WAF inspection of HTTP/3 client-side traffic is now supported, and the coverage is the full protection trio: Advanced WAF security policies, Bot Defense, and L7 DoS protection can all attach to HTTP/3-enabled virtual servers. Two details in F5's wording deserve emphasis. First, security policies of any template type can be associated with an HTTP/3 virtual server, so this is not a special reduced-capability policy mode; the policy you built for HTTP/2 conceptually carries over. Second, F5 explicitly claims the same inspection fidelity as HTTP/1.1 and HTTP/2, naming the classic payload threats, cross-site scripting and SQL (Structured Query Language) injection, as covered. The transport changed; the attack surface the WAF reads did not get a discount. Since the enforcement object is still an ASM policy, everything about reading one still applies, and the [declarative-policy explainer](/tools/f5-awaf-declarative-policy-explainer) works on these policies unchanged.

## The limits, stated as plainly as F5 states them

Three current limitations frame the deployment. Client-side only: the HTTP/3 protection applies where the client connects; the server side of the proxy is not part of this feature. No BADOS (behavioral DoS): behavioural DoS is not supported on HTTP/3, so L7 DoS protection here means the signature and threshold machinery, not the behavioural learning layer. And no HTTP/3 virtual server creation from the WAF UI: the virtual server is built on the LTM side first, then protected.

The fourth caveat is the biggest one and it is architectural: the underlying HTTP/3 implementation on BIG-IP LTM remains experimental, with F5 pointing to [K60235402](https://my.f5.com/manage/s/article/K60235402) for the protocol overview. That overview, last updated in June 2023, traces the path: HTTP/3 and QUIC arrived as an experimental feature in 15.1.0.1, implementing draft 24 of the QUIC transport and HTTP/3 specifications, moved to draft 29 in 15.1.1, and follow RFC 9114 from 15.1.2.1 and 16.1.0.2; it states that BIG-IP supports QUIC and HTTP/3 from 16.1.0, and it carries F5's advice to test experimental features in staging, not in production. The 21.1 release notes are the newer document, and they still call the LTM implementation experimental. Read that dependency correctly: the WAF layer on top is a supported 21.1 feature, but it stands on a transport implementation F5 itself still labels experimental. For production, that argues for HTTP/3 as an addition alongside HTTP/1.1 and HTTP/2 listeners rather than a replacement, letting clients that negotiate HTTP/3 get it while everything else lands on the mature paths.

## The LTM side the protection stands on

The WAF attaches to a virtual server the LTM side has already built, so it helps to know what that virtual server is. F5's 21.1 procedure makes it a Standard virtual server with UDP towards the client, a TCP profile towards the pool, the clientssl-quic profile, the HTTP MRF Router, and a QUIC profile plus an HTTP3 profile; the [protocol profiles article](/learn/bigip-l4-protocol-profiles) walks the composition. K60235402 states the constraints behind that shape: HTTP/3 and QUIC must be used together, QUIC without HTTP/3 being unsupported; QUIC and HTTP/3 are not supported on the server side, which is why the pool side is TCP; and QUIC works only with TLS 1.3, with clientssl-quic as the parent for a custom client SSL profile. Two settings of the new profiles are worth reading before tuning anything. The QUIC profile's `bidi-concurrent-streams-per-connection` and `uni-concurrent-streams-per-connection` set how many bidirectional and unidirectional streams may be outstanding on one QUIC connection ([tmsh reference: ltm profile quic](https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/ltm/ltm_profile_quic.html)); for HTTP/3, K60235402 notes, the unidirectional streams are the control stream that carries SETTINGS, the QPACK encoder and decoder streams, and push. The HTTP3 profile's `header-table-size` is the size of the table HTTP/3 uses to compress headers, 4,096 bytes by default: a larger table compresses better at the cost of more memory ([tmsh reference: ltm profile http3](https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/ltm/ltm_profile_http3.html)). In an iRule, `HTTP::version` returns "3.0" for HTTP/3 from v16.0, though it cannot set it ([HTTP::version](https://clouddocs.f5.com/api/irules/HTTP__version.html)).

Four database variables tune the QUIC side, all listed in K60235402. `quic.preestablished.threshold`, 16384 by default, is the number of new or untrusted QUIC connections, those that have not completed the TLS handshake, that BIG-IP accepts before it sends RETRY packets demanding proof of address from the client. `quic.cmetrics`, enabled by default, encodes congestion control parameters in the resumption token so that later connections start from them. `tmm.quic.log.level` sets the level of QUIC connection events logged to `/var/log/ltm`, Critical by default. And `quic.qlogging`, disabled by default, writes packets and events to `/var/log/trace<TMM_number>.qlog` in the standard qlog format; F5 recommends turning it on only when required and off straight after troubleshooting, because it can be verbose.

## Testing it, and the builds that matter

Test with a client that cannot quietly fall back. curl's `--http3` attempts HTTP/3 but falls back to earlier versions if the QUIC connection fails or is slow, so a passing test can hide a broken listener; `--http3-only` fails instead when no QUIC connection can be established ([curl manual](https://curl.se/docs/manpage.html)).

```
# Fails outright when no QUIC connection can be made: the honest test of an HTTP/3 listener
curl --http3-only -sv https://www.example.com/ -o /dev/null
```

Browsers need to discover the HTTP/3 service, and [K16240003](https://my.f5.com/manage/s/article/K16240003) describes how: an `Alt-Svc` header, inserted by an iRule or an LTM policy on a working HTTP/1.1 or HTTP/2 virtual server, advertises the HTTP/3 virtual server, and a client that receives it may try a QUIC connection to the indicated host and port, continuing on the existing connection if that fails. The article's examples use the `h3-24` token of draft 24; for the published RFC the token is `h3`. That quiet fallback is one more reason for the `--http3-only` test above: a client that stays on its existing connection still gets a working page.

## OpenAPI 3.1 for API Security

The same release lets Advanced WAF's API Security consume OpenAPI Specification 3.1 files through the existing import workflow, no configuration changes required. F5's note carries one scoping clause worth keeping: all OpenAPI 3.1.x files are accepted, but schema features are supported at the major-version level, so 3.1.0 semantics define what the policy builder understands. If your API teams moved to 3.1 for its JSON Schema alignment and webhooks, the spec file they already maintain now drives the positive security model directly, and the perennial workaround of down-converting specs to 3.0 for the WAF can retire.

## Logging: Splunk key-value, now in two sizes

Remote application-security logging gains a format: Splunk Key-Value Pairs Extended, which enriches events with an XML violation_details element carrying additional violation context, while the existing format is renamed Splunk Key-Value Pairs Basic. The operational fine print is a one-way door: configurations using the Extended format cannot be loaded on releases that do not support it, so a UCS or config sync that travels backwards in version must not carry Extended logging profiles.

## Reading the release as one motion

Put the three items together and 21.1's WAF story is about meeting traffic where it is going: the transport clients are adopting (HTTP/3), the contract format API teams are writing (OpenAPI 3.1), and the SIEM (security information and event management) detail level analysts keep asking for (Extended key-value). The [flagship overview](/learn/bigip-21x-whats-new) situates this next to the release's other marquee WAF item, MCP protocol protection, which the [AI and MCP deep-dive](/learn/bigip-ai-mcp) covers in full.
