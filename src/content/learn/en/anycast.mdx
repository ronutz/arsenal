A Domain Name System (DNS) resolver that asks a root server does not care which machine answers. RFC 1546 named that need in 1993: a client "wishes to locate a host which supports a particular service but, if several servers support the service, does not particularly care which server is used" ([RFC 1546, "Motivation"](https://www.rfc-editor.org/rfc/rfc1546)). **Anycast** is the Internet's answer: one address announced from many places, with ordinary routing delivering each packet to one of them. By the end you can define it as the standards do, see how the Border Gateway Protocol (BGP) chooses, say why the [DNS](/learn/dns-family-history) fits it and the Transmission Control Protocol (TCP) strains it, read the root server figures of 2026-10-13, and run one query that shows which instance answered you.

## Where the word comes from, and the words that stuck

RFC 1546, "Host Anycasting Service", came from BBN in November 1993 through the Internet Research Task Force (IRTF) as an experimental memo that proposed no protocol ([RFC 1546, Abstract](https://www.rfc-editor.org/rfc/rfc1546)). Internet Protocol (IP) anycasting is "a service which provides a stateless best effort delivery of an anycast datagram to at least one host, and preferably only one host, which serves the anycast address" ([RFC 1546, "Architectural Issues"](https://www.rfc-editor.org/rfc/rfc1546)). One assumption failed: "this memo assumes that anycast addresses will be a separate class of IP addresses (not yet assigned)" ([RFC 1546, "Anycast Addresses"](https://www.rfc-editor.org/rfc/rfc1546)). None was ever assigned; deployed anycast uses ordinary unicast addresses ([RFC 3258, section 1](https://www.rfc-editor.org/rfc/rfc3258#section-1)).

The vocabulary comes from RFC 4786, "Operation of Anycast Services", Best Current Practice (BCP) 126 of December 2006, still listed with no "Updated by" or "Obsoleted by" entry ([RFC 4786 information page](https://www.rfc-editor.org/info/rfc4786)). Its section 2 fixes four terms ([RFC 4786, section 2](https://www.rfc-editor.org/rfc/rfc4786#section-2)):

- **Service Address**: "an IP address associated with a particular service".
- **Anycast**: "the practice of making a particular Service Address available in multiple, discrete, autonomous locations, such that datagrams sent are routed to one of several available locations".
- **Anycast Node**: "an internally-connected collection of hosts and routers that together provide service for an anycast Service Address".
- **Catchment**: by analogy with a river basin, "the topological region of a network within which packets directed at an Anycast Address are routed to one particular node".

## One prefix from many places: global nodes, local nodes and NO_EXPORT

The mechanism is [BGP](/learn/bgp-primer): "the service is first associated with a stable set of IP addresses, and reachability to those addresses is advertised in a routing system from multiple, independent service nodes" ([RFC 4786, section 1](https://www.rfc-editor.org/rfc/rfc4786#section-1)). On the Internet a host route will not travel, "a consequence of operational policy, and not a protocol restriction", so each node announces a **covering prefix**, "often a 24-bit prefix" for IPv4 ([RFC 4786, section 4.4.2](https://www.rfc-editor.org/rfc/rfc4786#section-4.4.2)). K-root does exactly that for 193.0.14.129, from one autonomous system (AS): "Each node announces prefixes from 193.0.14.0/23 in AS25152" ([RIPE NCC, K-root](https://www.ripe.net/analyse/dns/k-root/)).

Which AS originates the prefix is a point where the documents differ. BCP 126 says nodes "should use the same origin AS for their advertisements, but might have different upstream ASes" ([RFC 4786, section 4.4.4](https://www.rfc-editor.org/rfc/rfc4786#section-4.4.4)); RFC 7094 reports that RFC 6382, not read here, later recommended "per-node unique origin Autonomous System Numbers (ASNs) for globally anycasted critical infrastructure services" ([RFC 7094, section 2.3](https://www.rfc-editor.org/rfc/rfc7094#section-2.3)); K-root, as quoted above, still uses one.

A **Global Node** is "capable of providing service to clients anywhere in the network"; a **Local Node** serves "a local catchment of autonomous systems" and limits its route "using well-known community string attributes such as NO_EXPORT [RFC1997] or NOPEER [RFC3765]" ([RFC 4786, section 4.4.6](https://www.rfc-editor.org/rfc/rfc4786#section-4.4.6)). Fail-over runs "from Local Node to Global Node" ([RFC 4786, section 4.7](https://www.rfc-editor.org/rfc/rfc4786#section-4.7)), which is why "All operators provide service to the entire Internet through at least one global instance" ([root-servers.org FAQ](https://root-servers.org/faq/)).

## Nearest in the routing table, not on the map

The standards define "nearest" by metric, not by distance on a map. IPv6 delivers to the "nearest" interface "according to the routing protocols' measure of distance" ([RFC 4291, section 2.6](https://www.rfc-editor.org/rfc/rfc4291#section-2.6)); the Internet Architecture Board (IAB) expects the "closest" instance "as determined by unicast routing topology metric(s)" ([RFC 7094, section 1](https://www.rfc-editor.org/rfc/rfc7094#section-1)); and BCP 126 warns that "Topological nearness within the routing system does not, in general, correlate to round-trip performance across a network; in some cases, response times may see no reduction, and may increase" ([RFC 4786, section 3.2](https://www.rfc-editor.org/rfc/rfc4786#section-3.2)). The catchment is not a fixed population either: "the population of clients using individual anycast nodes is neither static, nor reliably deterministic" ([RFC 4786, section 1](https://www.rfc-editor.org/rfc/rfc4786#section-1)), and "load distribution between nodes is generally unbalanced in terms of request and traffic load" ([RFC 4786, section 3.1](https://www.rfc-editor.org/rfc/rfc4786#section-3.1)): anycast gives resilience and coarse distribution, not load balancing.

## Why DNS fits and where TCP strains

Anycast is stateless: an internetwork has "no obligation to deliver two successive packets sent to the same anycast address to the same host" ([RFC 1546, "How UDP and TCP Use Anycasting"](https://www.rfc-editor.org/rfc/rfc1546)). Some services, the DNS over the User Datagram Protocol (UDP) first among them, "may even be carried out using a single packet request and a single packet reply (e.g., DNS transactions over UDP transport)", and the routing decision "ought to be stable for substantially longer than the expected transaction time" ([RFC 4786, section 4.1](https://www.rfc-editor.org/rfc/rfc4786#section-4.1)). One packet each way is the ideal case.

TCP breaks the rule before any data flows, "due to the TCP setup handshake" ([RFC 4786, section 4.4.3](https://www.rfc-editor.org/rfc/rfc4786#section-4.4.3)), and stateful transports "will fail probabilistically, but possibly catastrophically, when using anycast addresses in the presence of "normal" routing dynamics" ([RFC 7094, section 3.1](https://www.rfc-editor.org/rfc/rfc7094#section-3.1)). TCP to an anycast address usually works anyway because BGP "usually selects a single, consistent exit for a single destination regardless of whether multiple candidate paths exist". The breaker is Per Packet Load Balancing (PPLB) inside a network, "effectively making the anycast service unavailable"; BCP 126 finds it "reasonable to consider networks making such use of PPLB to be pathological" ([RFC 4786, section 4.4.3](https://www.rfc-editor.org/rfc/rfc4786#section-4.4.3)). Practice runs ahead of theory: for TCP over anycast "there is expanding deployment (e.g., for content distribution networks)", although "such practice is not "safe" in the traditional and architectural sense" ([RFC 7094, section 4.5](https://www.rfc-editor.org/rfc/rfc7094#section-4.5)).

## The root servers today

The DNS use of anycast was written down in April 2002 under another name: RFC 3258 calls it a **shared unicast address**, announced over BGP by an operator that "must have an autonomous system number" ([RFC 3258, section 2.5](https://www.rfc-editor.org/rfc/rfc3258#section-2.5)). Its draft was named draft-ietf-dnsop-hardie-shared-root-server ([IETF Datatracker, RFC 3258](https://datatracker.ietf.org/doc/rfc3258/)), yet the text names no root deployment, and no document read says which root letter went anycast first; the spread is dated instead: "By late 2007, at least 10 of the 13 root name servers were already using IP anycast [RSSAC29]" ([RFC 7094, section 1](https://www.rfc-editor.org/rfc/rfc7094#section-1)).

root-servers.org keeps the current picture: "As of 2026-10-13T12:05:40Z, the root server system consists of 2047 operational instances operated by the 12 independent root server operators" ([root-servers.org](https://root-servers.org/)). Its FAQ settles the arithmetic: "There are 13 Root Server Identifiers (RSI, the letters "A" through "M")" and "(There are 13 RSIs and 12 RSOs because one RSO operates two RSIs.)" ([root-servers.org FAQ](https://root-servers.org/faq/)). Neither page says anycast; the FAQ explains the many sites through global and local instances, pointing to "RFC 4786 (section 4.4.6 in particular)". ISC, on a page dated 2019-07-10 in its metadata, says it plainly: the "anycast" scheme is "used to make the servers collectively behave as one server" ([ISC, F-Root](https://www.isc.org/f-root/)). ## Anycast in IPv6

IPv6 names anycast as an address type yet gives it no range of its own: "Anycast addresses are allocated from the unicast address space, using any of the defined unicast address formats", and when one address is assigned to several interfaces the nodes "must be explicitly configured to know that it is an anycast address" ([RFC 4291, section 2.6](https://www.rfc-editor.org/rfc/rfc4291#section-2.6)). One anycast address is built in: the **Subnet-Router anycast address**, the subnet prefix with the interface identifier set to zero, whose packets "will be delivered to one router on the subnet", and which "All routers are required to support" ([RFC 4291, section 2.6.1](https://www.rfc-editor.org/rfc/rfc4291#section-2.6.1)). Early IPv6 was stricter: anycast addresses "must not be used as source addresses and must not be assigned to IPv6 hosts (i.e., only routers). These restrictions were later lifted in 2006 [RFC4291]" ([RFC 7094, section 2.2](https://www.rfc-editor.org/rfc/rfc7094#section-2.2); the reason is in [RFC 4291, Appendix B](https://www.rfc-editor.org/rfc/rfc4291#appendix-B)). One on-link rule stays: "Duplicate Address Detection MUST NOT be performed on anycast addresses" (RFC 4862 as quoted in [RFC 7094, section 4.5](https://www.rfc-editor.org/rfc/rfc7094#section-4.5)).

## Running it: watch from everywhere, withdraw on failure, hold under attack

An anycast service cannot be watched from one place. BCP 126 wants services "monitored from probes distributed representatively across the routing system", recording which node answered ([RFC 4786, section 5.1](https://www.rfc-editor.org/rfc/rfc4786#section-5.1)). In-band node identification is "strongly recommended for services to be distributed using anycast" ([RFC 4786, section 4.9](https://www.rfc-editor.org/rfc/rfc4786#section-4.9)), and for the DNS "the Name Server ID (NSID) option was defined for this purpose [RFC5001]" ([RFC 7094, section 2.1](https://www.rfc-editor.org/rfc/rfc7094#section-2.1)).

The second habit couples route and service, so that "availability of the service triggers the route advertisement, and non-availability of the service triggers a route withdrawal" ([RFC 4786, section 4.4.1](https://www.rfc-editor.org/rfc/rfc4786#section-4.4.1)). Three documents, best taught together:

| Document | Position |
|---|---|
| [RFC 3258, section 2.3](https://www.rfc-editor.org/rfc/rfc3258#section-2.3) (April 2002) | "it advises instead that the DNS process shutdown so that servers on other addresses are queried", calling this "a choice between performance and operational complexity" |
| [RFC 4786, section 4.4.1](https://www.rfc-editor.org/rfc/rfc4786#section-4.4.1) (December 2006) | "non-availability of the service triggers a route withdrawal" |
| [RFC 7094, section 2.3](https://www.rfc-editor.org/rfc/rfc7094#section-2.3) (January 2014) | "most anycast benefits cannot be realized without route withdrawals" |
| [RFC 7094, section 4.4](https://www.rfc-editor.org/rfc/rfc7094#section-4.4) (January 2014), under attack | "care must be taken not to simply withdraw an anycast route in the presence of a sustained DoS attack, since the result would simply move the attack to another service instance" |

Withdrawal is current practice; RFC 3258's advice is the older trade-off it named itself. The last row is the twist: a failed node is withdrawn, a node under denial of service (DoS) is held, because it "can act as a sink for attack traffic originated within its sphere of influence" ([RFC 4786, section 6.1](https://www.rfc-editor.org/rfc/rfc4786#section-6.1)). Withdrawals must not flap either: nodes need "a minimum delay following a withdrawal before the service can be re-advertised" ([RFC 4786, section 4.4.1](https://www.rfc-editor.org/rfc/rfc4786#section-4.4.1)). A hijacked route, the subject of [BGP: the trust fall](/learn/bgp-and-the-routing-chokepoint), is harder to spot here, since "A rogue Anycast Node might be difficult to detect" ([RFC 4786, section 6.3](https://www.rfc-editor.org/rfc/rfc4786#section-6.3)).

## Public resolvers, and seeing anycast from your own desk

Public resolvers run the same way. Google's FAQ says "Anycast routing directs your queries to the closest Google Public DNS server", that queries "are routed to the nearest location advertising the anycast address used (8.8.8.8, 8.8.4.4, or one of the IPv6 addresses in 2001:4860:4860::)", locations that "change due to network conditions and traffic load" ([Google Public DNS FAQ](https://developers.google.com/speed/public-dns/faq)). On ping it adds: "If Google Public DNS has a ping time of 300 ms, but resolves many names in 1 ms, the overall average response time is 301 ms" (same page). The choice itself is in [public DNS resolvers: what you are actually choosing](/learn/choosing-a-public-dns-resolver).

ISC publishes the query that shows which F-Root instance you reach:

```
dig +norec @f.root-servers.net hostname.bind chaos txt
```

It asks the server "to reveal the name of the particular server which answers the query. The hostname will contain an IATA three letter airport code, allowing the location of the server to be identified" ([ISC, F-Root](https://www.isc.org/f-root/)). The [dig command builder](/tools/dig-command-builder) assembles the line; [following delegation with dig +trace](/learn/dig-trace-and-delegation) covers the root's referral. Run it from the office and from a phone on a mobile network, then compare the airport codes: that is RFC 4786's "probes distributed representatively across the routing system" in miniature.

## What to remember

- Anycast is "the practice of making a particular Service Address available in multiple, discrete, autonomous locations"; the addresses are ordinary unicast.
- The routing system chooses the node; "nearest" means "according to the routing protocols' measure of distance", not distance on a map.
- On the Internet a node announces a covering prefix, often a 24-bit prefix for IPv4; Local Nodes limit propagation with NO_EXPORT and fail over to Global Nodes.
- DNS over UDP fits because a transaction is one packet each way; TCP mostly works because BGP picks one consistent exit, and per-packet load balancing breaks it.
- The root is 13 identifiers, 12 operators and, as of 2026-10-13T12:05:40Z, 2047 operational instances.
- Monitor from many vantage points, withdraw the route when the service fails, hold it under a sustained attack, and make nodes identify themselves with NSID or hostname.bind.
