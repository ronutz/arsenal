Every monitoring product eventually promises a single number, and Zscaler Digital Experience (ZDX - the platform's user-experience monitoring service) delivers one: a score from 0 to 100, computed per user and rolled up per application, location, city, department, and organisation. Single numbers earn either trust or contempt depending on whether the operator knows how they are made - so this article opens the anatomy. Everything below is grounded in Zscaler's ZDX reference architecture and help documentation, verified 2026-07-21; the scale, the bands, the roll-up rules and the score types were re-read on [Zscaler's score page](https://help.zscaler.com/zdx/understanding-zdx-score) on 2026-10-26.

## The instruments: two probe families

ZDX measures from where the experience actually lives - the user's device - through [the Client Connector](/learn/zscaler-client-connector-profiles) this series already dissected, whose telemetry flows through a Telemetry and Policy Gateway into the ZDX analytics engine. The measuring itself belongs to two probe families with cleanly divided labor. **Web Probes** ask *how the application behaves*: they fetch a URL and record **Page Fetch Time** (which, by documented design, requests only the top-level page document, not every embedded asset - a probe, not a replay), **DNS Time**, **Server Response Time** (the time to first byte), and **Availability**. **CloudPath probes** ask *how the network path behaves*: hop-by-hop measurement of the route - latency and loss along the way - the [traceroute instinct](/learn/map-the-path-before-you-troubleshoot) industrialized. The division matters diagnostically: a bad web metric with a clean path points at the application; a bad path indicts the road.

## How the number is made

The documented mechanics reward exact memory. Probes run **every five minutes** for most plans, against every defined application, and each five-minute measurement is given a value from 0 to 100. For the hourly view, ZDX takes **the lowest value observed during the hour** - the score is pessimistic by design, because an experience that was terrible for five minutes was terrible, whatever the average says. Rollups keep the same conservatism, in two documented shapes. An **application's** score is **each user's lowest value over the selected period, averaged**: three users whose lowest values were 42, 76 and 62 give the application 60. **Departments, locations, cities and the organisation** work per time interval instead: the lowest value in each interval becomes that interval's score (for the organisation, the lowest-scoring application), and the intervals are averaged across the selected range. A **user's** own score is their lowest-scoring application. Every score is rounded to the nearest whole number.

The bands carry operational meaning, and Zscaler publishes all three:

| Band | Range | Colour |
|---|---|---|
| Good | 66-100 | Green |
| Okay | 34-65 | Amber |
| Poor | 0-33 | Red |

For Poor scores the dashboard automatically runs root-cause analysis on the worst recent sample, surfacing the factors that likely dragged it down.

The number also depends on how the application is measured. Zscaler documents three score types: a **Synthetic Probe Score**, measured by the Web and CloudPath probes; a **RUM Score**, measured by Real User Monitoring (RUM) in the user's browser, which adds browser metrics such as page load time and Core Web Vitals; and a **Combined Score** built from both. The types use different configurations and metrics, so they can disagree for the same application: compare like with like.

## What is not published, said plainly

Zscaler documents the factors, the probing cadence, the lowest-of-the-hour rule, and the bands - and does **not** publish the exact composite formula that turns raw metrics into the 0-100 value. This series treats that the way [the honesty rules](/learn/zscaler-zero-trust-exchange-architecture) demand: the factors and semantics above are sourced; any claim about precise metric weights would be invention, and the companion tool declines to invent - it classifies and explains what the documentation grounds, and says so. Two more documented calibrations belong in the same drawer: API-retrieved metrics can differ from the dashboard by a small margin because aggregates use approximate functions for performance, and telemetry reporting carries an estimated delay of around twenty minutes - the score is near-real-time, not instantaneous.

## Reading the score like an operator

The anatomy dictates the reading order. A low score is an invitation, not a verdict: open the user, split web metrics from path metrics, and let the division of labor point - DNS Time ballooning is a resolver conversation; Server Response Time climbing with a clean path is the application's problem; path loss at a specific hop is [a network conversation with a street address](/learn/map-the-path-before-you-troubleshoot). And remember the pessimism when reporting upward: an hourly score is the hour's *worst* five minutes, which is exactly what a user remembers about their day, and exactly why the number is built that way.
