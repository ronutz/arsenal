## The scenario

You are given `172.16.0.0/22` and have to fit four segments inside it:

- **Sales**: 500 hosts
- **Engineering**: 200 hosts
- **Link A**: a point-to-point router link, 2 hosts
- **Link B**: a second point-to-point link, 2 hosts

A `/22` holds 1,024 addresses (`172.16.0.0` to `172.16.3.255`). The conceptual rules are covered in [VLSM](/learn/vlsm); here we run them all the way through.

## Step 1: size each segment

Find the smallest block that holds each host count, remembering the two reserved addresses (network and broadcast) in every ordinary block:

- 500 hosts needs 9 host bits (2⁹ − 2 = 510 usable), a `/23`.
- 200 hosts needs 8 host bits (254 usable), a `/24`.
- 2 hosts needs 2 host bits (2 usable), a `/30`.
- 2 hosts needs another `/30`.

Round up to the next power of two: 500 does not fit a `/24` (254 usable), so it takes a `/23`. Before going on, check that the total fits at all: 512 + 256 + 4 + 4 = 776 addresses, against 1,024 in the parent.

## Step 2: sort largest first

Order the segments by block size, biggest first, so each lands on a clean boundary:

1. Sales, `/23` (512 addresses)
2. Engineering, `/24` (256)
3. Link A, `/30` (4)
4. Link B, `/30` (4)

## Step 3: assign the addresses

Allocate in that order, each block starting where the previous one ended:

| Segment | Block | Mask | First host | Last host | Broadcast | Usable |
|---|---|---|---|---|---|---|
| Sales | 172.16.0.0/23 | 255.255.254.0 | 172.16.0.1 | 172.16.1.254 | 172.16.1.255 | 510 |
| Engineering | 172.16.2.0/24 | 255.255.255.0 | 172.16.2.1 | 172.16.2.254 | 172.16.2.255 | 254 |
| Link A | 172.16.3.0/30 | 255.255.255.252 | 172.16.3.1 | 172.16.3.2 | 172.16.3.3 | 2 |
| Link B | 172.16.3.4/30 | 255.255.255.252 | 172.16.3.5 | 172.16.3.6 | 172.16.3.7 | 2 |

Sales fills the first half of the block. Engineering takes the next `/24`. The two router links take four addresses each at the start of the final `/24`.

## Step 4: check every boundary

A block is valid only if it starts on a multiple of its own size. Count each start as an offset from the parent's first address:

- Sales starts at offset 0, a multiple of 512.
- Engineering starts at offset 512 (`172.16.2.0`), a multiple of 256.
- Link A starts at offset 768 (`172.16.3.0`), a multiple of 4; Link B at 772, also a multiple of 4.

None overlaps, because each starts where the previous one ended. This is the property largest-first guarantees: everything placed before a block is a larger (or equal) power of two, so the running total is always a multiple of the next size.

## Step 5: account for what is left

The four segments use 776 addresses, leaving 248 free, from `172.16.3.8` to `172.16.3.255`: 75.8% utilisation. A free range is only useful as blocks that start on their own boundaries, so write the tail that way:

| Free block | Addresses | Fits |
|---|---|---|
| 172.16.3.8/29 | 8 | up to 6 hosts |
| 172.16.3.16/28 | 16 | up to 14 hosts |
| 172.16.3.32/27 | 32 | up to 30 hosts |
| 172.16.3.64/26 | 64 | up to 62 hosts |
| 172.16.3.128/25 | 128 | up to 126 hosts |

8 + 16 + 32 + 64 + 128 = 248, so the whole tail is accounted for. The next segment of up to 126 hosts goes in the `/25`; one of 200 hosts no longer fits anywhere in the parent, however many free addresses the total shows.

## The same plan with /31 links

On point-to-point links between routers, a `/31` holds both ends: RFC 3021 allows "the use of 31-bit subnet masks" on such links, where "the two addresses above MUST be interpreted as host addresses" ([RFC 3021](https://www.rfc-editor.org/rfc/rfc3021)). With Link A at `172.16.3.0/31` and Link B at `172.16.3.2/31`, the plan uses 772 addresses instead of 776, and the free tail becomes `172.16.3.4/30`, `.8/29`, `.16/28`, `.32/27`, `.64/26` and `.128/25`: 252 addresses. Both ends of each link must support it, so check the equipment at each end before numbering a link this way.

## What the wrong order does

Allocate the same four segments smallest first, each starting where the last ended, and the method goes wrong as soon as the first large block arrives:

1. Link A at `172.16.0.0/30`, Link B at `172.16.0.4/30`.
2. Sales, a `/23`, cannot start at `172.16.0.8`: its start must be a multiple of 512, so it jumps to `172.16.2.0`, skipping `172.16.0.8` to `172.16.1.255`.
3. Engineering would start where Sales ends, at `172.16.4.0`, which is outside the parent.

The space for Engineering exists, at `172.16.1.0/24` inside the skipped range, but only by going back to find it, and in a larger plan that backtracking is where overlaps and stranded fragments come from. Largest first never needs it.

## One route for all of it

Because every segment came out of one parent, the rest of the network reaches all four with a single route, `172.16.0.0/22`. That is the reward for keeping a site inside one block, and it holds only while every subnet stays inside it: [route summarisation](/learn/route-summarization) and [supernetting and aggregation](/learn/supernetting-and-aggregation) take the idea further.

## What the site's router does with the summary

On the site's own router the plan becomes routes. The four segments are directly connected, `172.16.0.0/23`, `172.16.2.0/24`, `172.16.3.0/30` and `172.16.3.4/30`, and the router announces the summary, `172.16.0.0/22`, to the rest of the network. The summary also needs a route on the router that announces it, and that route leads nowhere. The CIDR specification makes this a rule: "A router that generates an aggregate route for multiple, more-specific routes must discard packets that match the aggregate route, but not any of the more-specific routes" ([RFC 4632, section 5.1](https://www.rfc-editor.org/rfc/rfc4632)).

A packet for `172.16.3.200`, in the free tail, shows why. The rest of the network sends it to the site, because the /22 covers it. At the site's router no segment matches it, so without a discard route the best match left is the site's default route, which points back to the rest of the network, where the /22 sends the packet straight back; it circles between the two routers until its time to live runs out. The rule exists for exactly this case: the discard route "is necessary to prevent forwarding loops when some addresses covered by the aggregate are not reachable" (as above), and the specification notes that it is usually put in place as a discard, or null, route for the summary (RFC 4632, section 5.2). The allocated addresses are not affected: a packet for `172.16.2.10` still reaches Engineering, because the /24 is a longer match than the /22. How a router chooses between overlapping routes is the subject of [static routes and longest prefix match](/learn/static-routes-and-longest-match).

## Checking your work

This is exactly the allocation the [CIDR calculator](/tools/cidr) produces in VLSM mode: enter `172.16.0.0/22` as the parent and the four host counts, and it returns the same networks, masks, ranges, and the 75.8% utilisation figure, computed entirely in your browser. If a segment does not fit, it is listed separately rather than silently dropped.

## What to remember

- Check the total first: the blocks' sizes, not the host counts, must fit the parent.
- Largest first, each block starting where the last ended, keeps every block on its boundary without backtracking.
- Free space is only as useful as the aligned blocks it splits into; a big enough total can still have no room for one large subnet.
- /31 point-to-point links save two addresses each where both ends support them.
- Everything inside one parent is reachable by one route.
- The router that announces the summary discards what matches only the summary, so unused addresses inside it end there instead of looping.
