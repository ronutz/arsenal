HTTP/2 carries many streams over one connection. That suits the client and strains a proxy built around one request per connection. The [history of the HTTP versions](/learn/http-versions-09-to-3) explains the framing; this article is about what BIG-IP does with it. F5's HTTP/2 full-proxy chapter states the capability plainly: the system can process HTTP/2 requests and responses on both the client and server sides, carrying multiple simultaneous, bidirectional streams "through the use of the BIG-IP system's message-routing proxy, instead of the traditional connection-oriented TCP proxy" ([configuring HTTP/2 full-proxy support](https://techdocs.f5.com/en-us/bigip-15-1-0/big-ip-http2-full-proxy-configuration/http2-full-proxy-configuring.html)).

## What the full proxy is built from

The chapter's steps assemble the virtual server from five parts:

- an HTTP profile on the client side, with the server side set to Use Client Profile or given a profile of its own;
- the clientssl-secure and serverssl-secure profiles, chosen because they disable mid-stream SSL renegotiation, which the chapter calls a requirement for an HTTP/2 full-proxy deployment;
- an HTTP/2 profile on the client side and, through Use Client Profile or a second profile, on the server side, with Enforce TLS Requirements enabled (also required);
- the HTTP MRF Router check box, which the chapter singles out as the setting to make sure you select;
- a pool whose members are HTTP/2-capable web servers.

F5's profile overview, [K04412053](https://my.f5.com/manage/s/article/K04412053), adds the history and one guard rail. Client-side HTTP/2 arrived in 11.6.0 and server-side processing in 14.1.0, when the webacceleration and OneConnect profiles were not supported in full proxy mode; webacceleration support in full proxy mode followed in 15.0.0. Its note under Enforce TLS Requirements says that adding a client SSL profile to an HTTP/2 virtual server raises a configuration error if TLS renegotiation is not disabled and the ECDHE (elliptic curve Diffie-Hellman ephemeral) cipher is not allowed.

The HTTP/2 profile's settings and defaults, from the same chapter and, for the first two rows, from K04412053:

| Setting | Default | What it sets |
|---|---|---|
| Concurrent Streams Per Connection | 10 | Maximum number of concurrent streams BIG-IP advertises to the client in the SETTINGS exchange |
| Connection Idle Timeout | 300 | Seconds an HTTP/2 connection may stay idle before BIG-IP sends GOAWAY to close it |
| Activation Modes | ALPN | What makes BIG-IP handle an incoming connection as HTTP/2 (the alternative is Always) |
| Frame Size | 2048 | Size, in bytes, of the data frames HTTP/2 produces |
| Receive Window | 32 | Size, in kilobytes, of the HTTP/2 flow-control receive window |
| Write Size | 16384 | Size, in bytes, of the SSL records HTTP/2 produces |
| Header Table Size | 4096 | Table size for header compression, which the chapter marks as unused; K04412053 describes it as the maximum size, in bytes, of the dynamic table of HTTP/2 header compression (RFC 7541, section 4.2) |

The two F5 documents disagree on Header Table Size, so check its behaviour on your release before tuning it. K04412053 also dates the activation modes: BIG-IP has not accepted NPN (Next Protocol Negotiation) since 13.1.0, and Always, which runs HTTP/2 in plain text, was developed for debugging only and requires removing the client SSL profiles from the virtual server.

The chapter's Applies To list runs from 15.0.1 to 21.0.0, so confirm each point against the documentation for your release before relying on it on 21.1.

## What it rules out

The same chapter lists the features that are not supported in an HTTP/2 full-proxy deployment: OneConnect, the Hash and SSL persistence types, and connection mirroring in high-availability configurations. Virtual Desktop Infrastructure (VDI) is not supported either, and a virtual server carrying both an HTTP/2 profile and a VDI profile can return ERR_HTTP2_PROTOCOL_ERROR. And the HTTP/2 protocol is not compatible with NTLM. K04412053 adds that load balancing of gRPC calls in HTTP/2 streams is an enhancement F5 is tracking, ID1311961. Each line meets a decision made elsewhere: [connection reuse](/learn/bigip-oneconnect-connection-reuse), [choosing a persistence method](/learn/choosing-a-persistence-method) and [persistence mirroring](/learn/persistence-mirroring-and-ha).

## iRules, one stream at a time

With the MRF router enabled, BIG-IP load balances each HTTP/2 stream individually, and the message-routing framework raises an `MR_EGRESS` event before the request passes through the server-side stack. F5 describes this mechanism in [Bug 2294701](https://cdn.f5.com/product/bugtracker/ID2294701.html), which also shows what does not belong in that event: `HTTP::respond` in `MR_EGRESS` fails with "Can't execute in the current context". The record lists 17.5.0 to 17.5.1.10 as known affected with no fix, and its workaround is to answer earlier, from a client-side event such as `HTTP_REQUEST`, or later, from a server-side event such as `HTTP_REQUEST_RELEASE`.

Four more habits keep per-stream rules predictable.

- **Variables.** The [HTTP2 command reference](https://clouddocs.f5.com/api/irules/HTTP2.html) notes that with an HTTP/2 profile in versions before 14.1, Tcl variables set before `HTTP_REQUEST` are not carried over to later events. A rule written in that era may still carry its workaround.
- **Scope.** In a full proxy, with HTTP/2 profiles on both sides, each stream has its own Tcl context and so its own local variables, by design, so that streams never access the same set concurrently ([K24532424](https://my.f5.com/manage/s/article/K24532424)). A value set while handling one stream is not there for the next; where a value must cross streams, the article points to session table variables, which persist across streams within the same TCP session.
- **Version checks.** [`HTTP::version`](https://clouddocs.f5.com/api/irules/HTTP__version.html) returns "2.0" for HTTP/2 from v16.0, though it cannot set it, and `HTTP2::active` tells a rule whether a request was generated by HTTP/2.
- **Priorities.** [Bug 1043985](https://cdn.f5.com/product/bugtracker/ID1043985.html) records that after an iRule is edited, the execution order of events with the same priority may change; the workaround is to give iRules that handle the same event explicit priorities. The [priority article](/learn/irule-priority-and-event-order) covers the command.

## Testing it, and reading it

curl negotiates HTTP/2 inside the TLS handshake for an HTTPS URL, which matches the profile's ALPN activation mode. Its manual adds that curl does not itself insist on TLS 1.2 or higher for HTTP/2 over HTTPS, although the specification requires it, and that `--tlsv1.2` adds the requirement ([curl manual](https://curl.se/docs/manpage.html)).

```
# Negotiate HTTP/2 through the TLS handshake and insist on TLS 1.2 or later, as the specification requires
curl --http2 --tlsv1.2 -sv https://www.example.com/ -o /dev/null
```

When you test an iRule or profile change, use a new connection. [K13253](https://my.f5.com/manage/s/article/K13253) states that changes to local traffic objects such as iRules, monitors and profiles apply only to connections established after the change, while existing connections keep the options they started with, so an HTTP/2 client that reuses one connection for many requests can go on showing the old behaviour. The article's command for clearing a test client's existing connections is `tmsh delete /sys connection cs-client-addr <client> cs-server-addr <virtual> cs-server-port <port>`.

In a capture, every HTTP/2 frame begins with a 9-octet frame header, and a stream identifier of zero is used for connection control messages rather than for a request ([RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html)). Frames on stream zero concern the connection as a whole; frames on any other stream belong to one exchange of request and response.

## The stream limit is a security setting

Concurrent Streams Per Connection defaults to 10, and F5's advisory for CVE-2023-44487, the HTTP/2 Rapid Reset attack, says that default was set because F5 had anticipated this type of flaw in the protocol ([K000137106](https://my.f5.com/manage/s/article/K000137106)). With an HTTP/2 profile on the virtual server, the default behaviour keeps exploit attempts from reaching the load-balanced application; a FastL4 virtual server, or one with only a TCP profile that passes HTTP/2 through to the pool, has no visibility into the HTTP/2 traffic and cannot protect the members. The advisory's mitigations follow from that: iRules are not an effective mitigation; where a configuration can use either protocol, F5 recommends HTTP with HTTP/2 disabled; and where HTTP/2 must stay, lowering the concurrent streams per connection lessens the impact, at a possible cost in performance. The indicator is in the HTTP/2 profile statistics: RST_STREAM frames received should be low next to DATA and SETTINGS frames, and a count that far exceeds them may mean an attack. The BIG-IP fixes are 17.1.1.3, 16.1.4.3 and 15.1.10.4; 14.x and 13.x will not be fixed.
