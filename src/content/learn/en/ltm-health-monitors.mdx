Load balancing is only as good as the BIG-IP's knowledge of which backends are alive. That knowledge comes from health monitors: small, repeating probes attached to pools, members, or nodes. A monitor's job is binary, to mark a target up or down, but the way it reaches that decision is worth understanding because it governs both false alarms and slow detection.

## What a probe checks

The simplest monitors check reachability. An `icmp` monitor pings the member's address; a `gateway-icmp` monitor is commonly used to watch a next hop. A `tcp` monitor confirms that a port accepts a connection. The most useful monitors go further into the application. An `http` or `https` monitor sends a request and inspects the reply: the `send` field holds the request string, such as a `GET` for a health-check URL, and the `recv` field holds the text the response must contain, such as a status line or a known string in the body. A member is healthy only when the received data matches; a server that accepts the connection but returns an error page will correctly be marked down by a well-written `recv` string.

Some services show they are healthy only over a short dialogue, a greeting, a command and a reply, and for those BIG-IP has the Scripted monitor. It plays a file of `send` and `expect` lines kept in /config/eav/ against the member, with an Interval of 10 seconds and a Timeout of 31 by default ([TMSH Reference v17, ltm monitor scripted](https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/ltm/ltm_monitor_scripted.html)). Its rules are strict: the file must use LF line endings, exactly one space separates each keyword from its text, and an expect matches only the start of a reply, never text further in ([BIG-IP 21.1.0 Monitors Settings Reference, Scripted monitor settings](https://techdocs.f5.com/en-us/bigip-21-1-0/big-ip-local-traffic-manager-monitors-reference/monitors-settings-reference.html#scripted-monitor-settings)). [BIG-IP LTM Scripted monitors](/learn/bigip-ltm-scripted-monitors) works through scripts for SMTP, POP3, IMAP and FTP from their RFCs, and the [Scripted monitor explainer](/tools/bigip-scripted-monitor-explainer) checks a file against F5's rules and plays it against a server transcript.

## Interval and timeout

Two timing fields decide how fast a failure is noticed. The `interval` is how often the probe runs, in seconds. The `timeout` is how long the BIG-IP waits, without a successful probe, before declaring the member down. The conventional relationship is `timeout = 3 * interval + 1`, so the default of interval 5 and timeout 16 gives a silent member four probes, at 0, 5, 10 and 15 seconds, before it is taken out of rotation at 16. Shortening these values detects failures faster but raises the risk of flapping on a member that is merely slow; lengthening them is more forgiving but leaves a failed member in service longer. There is no universally correct setting, only a trade-off to make deliberately.

F5's own documents pin the timing down. The Interval is how often the monitor checks a member that is down or whose status is unknown, an optional Up Interval sets how often it checks a member that is up, and F5 recommends that the greater of the two be a multiple of the lesser ([BIG-IP 21.1.0 Monitors Settings Reference](https://techdocs.f5.com/en-us/bigip-21-1-0/big-ip-local-traffic-manager-monitors-reference/monitors-settings-reference.html)). The Timeout runs from the first probe that goes unanswered: with the defaults, if the probes at 0, 5, 10 and 15 seconds all fail, the member is marked down at 16, and an answer to any of them inside that window keeps it up ([K350](https://my.f5.com/manage/s/article/K350)); once down, it stays down until a probe receives a correct reply ([K11359](https://my.f5.com/manage/s/article/K11359)). F5 recommends three times the interval plus one second because that keeps the monitor from marking a member down before the last check has gone out, and calls a member that is repeatedly marked down and back up "bouncing", which can interrupt connections to the virtual server ([K12531](https://my.f5.com/manage/s/article/K12531)). The system will not accept a timeout shorter than the interval; with an Up Interval longer than the timeout, one missed probe is enough to mark the member down, after which checks run at the Interval until it answers ([K000138395](https://my.f5.com/manage/s/article/K000138395)). On the way back, a member is marked up on its first correct response by default; a Time Until Up of N seconds marks it up N seconds after that first correct response, and only if every response in that period is correct, while Manual Resume keeps it down until an administrator re-enables it ([BIG-IP 21.1.0 Monitors Concepts](https://techdocs.f5.com/en-us/bigip-21-1-0/big-ip-local-traffic-manager-monitors-reference/monitors-concepts.html)). For tcp and http monitors, a member that answers a probe with a reset is marked down at once, without waiting for the timeout ([TMSH Reference v17, ltm monitor http](https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/ltm/ltm_monitor_http.html)).

## Where the monitor is attached

The same monitor behaves differently depending on where it sits. Attached to a pool, it probes each pool member at that member's address and port; the special destination `*:*` means exactly that, the member's own address and service. Attached to a node, it judges the whole backend host regardless of port, so one failed probe can pull every pool member on that host out of service at once. A pool can also require a minimum number of healthy members through `min-active-members`, below which the pool itself is considered down. And a pool with no monitor at all assumes every member is always up, which means a dead server will keep receiving connections until something else notices.

## Reading monitors in a config

When you review a configuration, a missing or mismatched monitor is one of the highest-value things to catch. A pool without a monitor, a single-member pool with no redundancy, or an HTTP monitor whose `recv` string no longer matches the application's response are all silent availability risks. The [tmsh config explainer](/tools/f5-tmsh-config-explainer) surfaces these directly, noting when a pool has no health monitor or only one member. To see how the pool and its monitor fit into the larger request path, read [how a virtual server works](/learn/how-a-virtual-server-works); for the configuration grammar itself, see [the anatomy of a bigip.conf file](/learn/anatomy-of-bigip-conf).

## Where the probe comes from, and what 21.1 changes

A probe also has a source, and it is not the client's. By default monitors use self IP addresses as their source, and BIG-IP 21.1 adds an alternative for the monitors that run inside TMM: per the [21.1 release notes](https://techdocs.f5.com/en-us/bigip-21-1-0/big-ip-release-notes/big-ip-new-features.html), the in-TMM GATEWAY ICMP, TCP, HTTP and HTTPS monitors can now take their source address from a SNAT pool, for pool members in networks that do not route back to private self IPs. In an HA pair only the active unit sends those probes and synchronises member status to the standby. The same release adds a Layer 2 check, MAC-address monitoring inside TMM using ARP, which proves a device answers on the segment and nothing about its application, and rebuilds BigD as a single multithreaded daemon supporting up to 15,000 control-plane monitors (the [BigD thread calculator](/tools/f5-bigd-thread-calculator) works through the sizing formulas). One older detail still catches people: an `https` monitor negotiates TLS through its own `ssl-profile`, and the per-monitor cipher, certificate and key fields have been deprecated since v13.1.0 in favour of it, per the [tmsh reference](https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/ltm/ltm_monitor_https.html).
