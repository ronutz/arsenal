Quase toda a criptografia que um engenheiro de redes ou de segurança escreve é pequena: um checksum para uma imagem de software, uma assinatura em um webhook, um token para uma API, uma chave para um laboratório, uma senha que precisa ser conferida depois sem que ela mesma fique guardada. A biblioteca padrão do Python tem um módulo para cada trabalho. O `hashlib` calcula digests, o `hmac` calcula digests com chave e os compara com segurança, e o `secrets` produz aleatoriedade que um atacante não consegue prever. Esta parte da [série de Python](/learn/python-explained) os percorre nessa ordem, a partir da referência da biblioteca lida em 27 de outubro de 2026, e roda cada exemplo no CPython 3.13.16, um release do branch 3.13, que o Developer's Guide lista na fase de segurança até outubro de 2029. Onde um resultado pode ser conferido em outro lugar, ele é conferido com a [ferramenta de hash](/tools/hash) e a [ferramenta de HMAC](/tools/hmac) do site.

## hashlib: uma interface para muitas funções de hash

A referência da biblioteca descreve o `hashlib` como "a common interface to many different hash algorithms": a família SHA-2 da FIPS 180-4, a família SHA-3 da FIPS 202 e os legados SHA-1 e MD5. Cada algoritmo tem um construtor que devolve um objeto de hash; você o alimenta com bytes por `update()` e lê o resultado com `digest()` ou `hexdigest()`. Os construtores de SHA-1, das funções SHA-2 e SHA-3, de SHAKE e de BLAKE2 "are always present"; o MD5 "is normally available as well, though it may be missing or blocked" em raros builds com conformidade FIPS, e o resto depende do OpenSSL com que o interpretador foi ligado e se alcança pelo nome, com `hashlib.new()`. Desde a 3.12, o CPython recorre a "a verified implementation from the HACL* project" para MD5, SHA-1, SHA-2 e SHA-3 quando o OpenSSL não os oferece.

```python
import hashlib  # as funções de hash da biblioteca padrão

# Uma chamada: o dado precisa ser bytes, então o texto é codificado antes.
print(hashlib.sha256("abc".encode("utf-8")).hexdigest())

# O mesmo digest alimentado em partes: chamadas de update() se concatenam.
h = hashlib.sha256()  # um objeto SHA-256 vazio
h.update(b"a")  # primeira parte
h.update(b"bc")  # segunda parte: o mesmo que update(b"abc")
print(h.hexdigest(), h.digest_size, "bytes")

# Pelo nome, para algoritmos escolhidos em tempo de execução (de um arquivo de configuração, por exemplo).
print(hashlib.new("sha3_256", b"abc").hexdigest()[:16], "...")

# O que todo CPython tem, e o que o OpenSSL deste build acrescenta.
print(len(hashlib.algorithms_guaranteed), "guaranteed:", sorted(hashlib.algorithms_guaranteed)[:6], "...")
print(len(hashlib.algorithms_available), "available here")

# MD5 para um trabalho que não é de segurança (chave de cache, detecção de duplicata): diga isso explicitamente.
print(hashlib.md5(b"show running-config", usedforsecurity=False).hexdigest())
```

O SHA-256 de `abc` é o valor que a [ferramenta de hash](/tools/hash) calcula e mantém entre os seus próprios vetores de teste, e o [artigo sobre hashing](/learn/hashing) explica o que a função garante. Dois detalhes pesam na prática. Uma função de hash trabalha sobre bytes, então fazer hash de texto exige escolher uma codificação antes, que é o assunto do [artigo sobre bytes e texto](/learn/python-bytes-text-and-encodings) desta série. E desde o Python 3.9 todo construtor aceita o argumento nomeado `usedforsecurity`: nas palavras da referência, um valor falso "allows the use of insecure and blocked hashing algorithms in restricted environments" e indica "that the hashing algorithm is not used in a security context, e.g. as a non-cryptographic one-way compression function". Ele documenta a intenção, e por isso um build restrito por FIPS deixa a última linha rodar e um scanner de código trata de outro jeito uma chamada de MD5 sem ele, como mostra o [artigo sobre código seguro](/learn/python-secure-coding). A referência também avisa que MD5 e SHA-1 têm "known hash collision weaknesses"; o [artigo sobre famílias de hash](/learn/hash-function-families) diz quais aposentar.

## Hash de um arquivo

O checksum de uma página de download é o hash mais comum na vida de um engenheiro. Desde o Python 3.11, o `hashlib.file_digest()` recebe um objeto de arquivo aberto em modo binário e devolve o objeto de hash atualizado, lendo o arquivo em blocos para que uma imagem de software grande nunca precise ficar inteira na memória. A referência acrescenta que o arquivo precisa estar em modo bloqueante, e a partir da 3.13.4 um arquivo não bloqueante levanta `BlockingIOError` em vez de produzir um digest errado.

```python
import hashlib  # file_digest() está no hashlib desde o Python 3.11
from pathlib import Path  # caminhos de arquivo

PUBLISHED = "19D6D9FAF9CE166ABEB8452FF274241877EB1C09580F7EF62FF77696A6BEE1FC"  # como a página de download o imprime

def sha256_of(path: Path) -> str:
    """SHA-256 em hexa de um arquivo, lido em blocos para que uma imagem grande nunca fique inteira na memória."""
    with path.open("rb") as f:  # modo binário: hashes trabalham sobre bytes
        return hashlib.file_digest(f, "sha256").hexdigest()  # o helper lê e alimenta os blocos

good = Path("lab-image.bin")  # um substituto para uma imagem de software baixada
good.write_bytes(bytes(range(256)) * 40_000)  # 10.240.000 bytes de dados de teste
bad = Path("lab-image-copy.bin")  # o mesmo arquivo com um bit alterado no caminho
data = bytearray(good.read_bytes())  # uma cópia mutável da imagem boa
data[5_000_000] ^= 0x01  # inverte um bit no meio
bad.write_bytes(data)  # grava a cópia danificada

for path in (good, bad):  # confere os dois arquivos contra o valor publicado
    digest = sha256_of(path)  # 64 dígitos hexa minúsculos
    print(f"{path.name:<19} {digest[:16]}...  match={digest == PUBLISHED.lower()}")  # hexa não diferencia caixa: normalize
```

```text
lab-image.bin       19d6d9faf9ce166a...  match=True
lab-image-copy.bin  27d8fb24e702ecd8...  match=False
```

Um bit invertido dá um digest sem relação nenhuma com o original, e é isso que torna a comparação útil. O que ela prova é mais estreito do que parece: o arquivo confere com o checksum que você recebeu. Se o checksum veio da mesma página que o arquivo, quem consegue alterar um consegue alterar o outro; uma assinatura feita com uma chave em que você já confia fecha essa brecha, e o [próximo artigo](/learn/python-cryptography-and-tls) assina e verifica um backup de configuração com Ed25519.

## Senha é outro trabalho

A própria referência traça a linha: "Naive algorithms such as sha1(password) are not resistant against brute-force attacks. A good password hashing function must be tunable, slow, and include a salt." A seção de BLAKE2 acrescenta que hash com salt usando BLAKE2 "or any other general-purpose cryptographic hash function, such as SHA-256, is not suitable for hashing passwords". O [guia de hash de senha](/learn/choosing-a-password-hash) do site dá a ordem de preferência: Argon2id, depois scrypt, depois bcrypt, e PBKDF2 onde a conformidade FIPS exigir. O Password Storage Cheat Sheet da OWASP dá os parâmetros de partida: para Argon2id, 19 MiB de memória, duas iterações e grau de paralelismo 1 (ou uma linha equivalente da tabela); para scrypt, N de 2^17, r de 8 e p de 1; para PBKDF2 com HMAC-SHA-256, 600.000 iterações.

A biblioteca padrão tem dois dos quatro. O `hashlib.scrypt()` implementa a RFC 7914, e o `hashlib.pbkdf2_hmac()` implementa o PBKDF2 do PKCS #5, que desde a 3.12 só existe quando o Python é compilado com OpenSSL. Para os dois, a referência pede um salt de "about 16 or more bytes from a proper source, e.g. os.urandom()" e sugere limitar a senha a um tamanho sensato (o exemplo dela é 1024).

```python
import base64  # guarda bytes como texto
import hashlib  # scrypt() e pbkdf2_hmac()
import hmac  # compare_digest()
import os  # urandom() para o salt
import time  # quanto tempo leva uma derivação

N, R, P = 2**17, 8, 1  # a primeira configuração de scrypt da OWASP: cerca de 128 MiB de memória por hash

salt = os.urandom(16)  # um salt aleatório novo para cada senha, 16 bytes ou mais
try:
    hashlib.scrypt(b"correct horse", salt=salt, n=N, r=R, p=P)  # maxmem deixado no padrão
except ValueError as exc:  # o teto de memória padrão do OpenSSL é 32 MiB
    print("default maxmem:", exc)

def hash_password(password: str) -> str:
    """Deriva com scrypt e guarda cada parâmetro junto do resultado, para que possam subir depois."""
    salt = os.urandom(16)  # único por senha
    key = hashlib.scrypt(password.encode("utf-8"), salt=salt, n=N, r=R, p=P,
                         maxmem=256 * 1024 * 1024, dklen=32)  # libera os 128 MiB de que esta configuração precisa
    b64 = lambda b: base64.b64encode(b).decode("ascii")  # bytes para texto imprimível
    return f"scrypt${N}${R}${P}${b64(salt)}${b64(key)}"  # nosso próprio formato de armazenamento

def verify_password(password: str, stored: str) -> bool:
    """Recalcula com os parâmetros guardados e compara em tempo constante."""
    _, n, r, p, salt, key = stored.split("$")  # os campos escritos por hash_password()
    again = hashlib.scrypt(password.encode("utf-8"), salt=base64.b64decode(salt), n=int(n), r=int(r),
                           p=int(p), maxmem=256 * 1024 * 1024, dklen=32)  # mesmas entradas, mesmos parâmetros
    return hmac.compare_digest(again, base64.b64decode(key))  # nunca ==

t0 = time.perf_counter()  # dispara o relógio
stored = hash_password("correct horse battery staple")  # o que o banco de dados guardaria
print(f"scrypt: {time.perf_counter() - t0:.2f} s ->", stored[:40] + "...")
print("right password:", verify_password("correct horse battery staple", stored))
print("wrong password:", verify_password("correct horse battery stapler", stored))

t0 = time.perf_counter()  # PBKDF2 onde se exigem primitivas validadas pelo FIPS
dk = hashlib.pbkdf2_hmac("sha256", b"correct horse battery staple", salt, 600_000)  # OWASP: 600.000 para HMAC-SHA-256
print(f"pbkdf2_hmac sha256 x 600,000: {time.perf_counter() - t0:.2f} s ->", dk.hex()[:16] + "...")
```

```text
default maxmem: [digital envelope routines] memory limit exceeded
scrypt: 0.47 s -> scrypt$131072$8$1$DrX7bbIm/jFfjb4xHTooKg...
right password: True
wrong password: False
pbkdf2_hmac sha256 x 600,000: 0.35 s -> e962d30f12e2ddf6...
```

A primeira linha é a armadilha: a referência anota que `maxmem` "limits memory (OpenSSL 1.1.0 defaults to 32 MiB)", então a configuração recomendada pela OWASP falha até você subir o teto. A string de armazenamento é um formato próprio deste exemplo; o que importa é que o salt e cada parâmetro de custo viajam junto do hash, para que os parâmetros possam subir para senhas novas enquanto as antigas continuam sendo verificadas, e que a verificação usa `compare_digest()`, explicado mais abaixo. Os tempos são os da execução registrada na máquina de build.

O Argon2id não está na biblioteca padrão. O pacote pyca/cryptography tem uma classe `Argon2id` desde o release 44.0.0, e desde o 45.0.0 ela lê e escreve o formato de string do Password Hashing Competition (PHC), que leva o algoritmo, os parâmetros, o salt e o hash em uma só string. A documentação do pacote diz que o Argon2id "should be used by most users, as recommended in RFC 9106":

```python
import os  # urandom() para o salt
from cryptography.exceptions import InvalidKey  # levantada quando a senha não confere
from cryptography.hazmat.primitives.kdf.argon2 import Argon2id  # cryptography 44.0 em diante

kdf = Argon2id(salt=os.urandom(16), length=32, iterations=2, lanes=1, memory_cost=19456)  # OWASP: 19 MiB, t=2, p=1
stored = kdf.derive_phc_encoded(b"correct horse battery staple")  # uma string: algoritmo, parâmetros, salt, hash
print(stored)

for attempt in (b"correct horse battery staple", b"correct horse battery stapler"):  # a certa, depois a errada
    try:
        Argon2id.verify_phc_encoded(attempt, stored)  # os parâmetros vêm da própria string
        print(attempt.decode(), "-> accepted")
    except InvalidKey:  # uma divergência é uma exceção, não False
        print(attempt.decode(), "-> rejected")
```

```text

correct horse battery staple -> accepted

```

A execução usou o cryptography 50.0.2, instalado com pip em um ambiente virtual descartável; o [próximo artigo](/learn/python-cryptography-and-tls) explica por que essa classe mora debaixo de um pacote chamado `hazmat`.

## Pwned Passwords: SHA-1 como chave de busca

Conferir uma senha nova contra vazamentos conhecidos é a outra metade do conselho do guia de senhas, e a API de faixas do Have I Been Pwned foi construída para que a senha nunca saia da máquina. A documentação descreve o modelo de k-anonymity: o cliente envia "the first 5 characters of either a SHA-1 or an NTLM hash", o serviço responde com "the suffix of every hash beginning with the specified prefix", cerca de 800 deles, e o cliente procura o próprio sufixo localmente; há 1.048.576 prefixos, e todos devolvem HTTP 200. O script abaixo calcula o que seria enviado e para por aí:

```python
import hashlib  # SHA-1, usado aqui como chave de busca e não para proteger nada

password = "P@ssw0rd"  # uma string de teste conhecida; nunca ponha uma senha real em um script
digest = hashlib.sha1(password.encode("utf-8"), usedforsecurity=False).hexdigest().upper()  # o formato da API de faixas
prefix, suffix = digest[:5], digest[5:]  # 5 caracteres saem da máquina, 35 ficam

print("SHA-1  :", digest)
print("sent   :", f"GET https://api.pwnedpasswords.com/range/{prefix}")  # impresso, não requisitado
print("kept   :", suffix, "(compared locally with the suffixes in the reply)")
print("ranges :", 16**5)  # todo prefixo de 00000 a FFFFF é uma faixa válida
```

```text
SHA-1  : 21BD12DC183F740EE76F27B78EB39C8AD972A757
sent   : GET https://api.pwnedpasswords.com/range/21BD1
kept   : 2DC183F740EE76F27B78EB39C8AD972A757 (compared locally with the suffixes in the reply)
ranges : 1048576
```

`21BD1` é também o prefixo cuja resposta de exemplo a documentação da API imprime. O SHA-1 serve aqui pelo motivo que o guia de senhas dá: nada é guardado nem protegido por ele, ele só divide o acervo em faixas, e `usedforsecurity=False` diz exatamente isso. A [verificação do Pwned Passwords](/dev/out/pwned-passwords) do site faz o mesmo no seu navegador, mostra os cinco caracteres antes de qualquer envio e só pergunta quando você aperta Perguntar ou Enter.

## hmac: um hash com chave

Um hash simples só diz que um dado não mudou se o próprio hash chegou a você em segurança. O HMAC, definido na RFC 2104, mistura uma chave secreta no hash, de modo que só quem tem a chave produz uma tag válida; o [artigo sobre HMAC](/learn/hmac) do site explica a construção, e o [por que HMAC](/learn/why-hmac) explica por que `hash(key + message)` não é um substituto seguro. Em Python, `hmac.new(key, msg, digestmod)` devolve um objeto HMAC, e a referência insiste que `digestmod` é obrigatório "despite its argument position" (desde a 3.8). O `hmac.digest()` é uma forma de uma chamada só que "uses an optimized C or inline implementation", e funções de saída extensível como o SHAKE "cannot be used with HMAC".

```python
import hashlib  # o hash sobre o qual o HMAC é construído
import hmac  # HMAC da RFC 2104
import json  # um corpo JSON no estilo de webhook

# RFC 4231, caso de teste 2: chave "Jefe", dado "what do ya want for nothing?".
print(hmac.new(b"Jefe", b"what do ya want for nothing?", hashlib.sha256).hexdigest())
print(hmac.digest(b"Jefe", b"what do ya want for nothing?", "sha256").hex()[:16], "...")  # forma de uma chamada só

SECRET = b"lab-shared-secret-0f7c"  # no uso real: de um cofre ou do ambiente, nunca no código

def sign(body: bytes) -> str:
    """O que o remetente põe em um header: HMAC-SHA256 em hexa dos bytes exatos do corpo."""
    return hmac.new(SECRET, body, hashlib.sha256).hexdigest()  # digestmod é obrigatório desde a 3.8

def verify(body: bytes, received: str) -> bool:
    """O que o destinatário faz: recalcula sobre os bytes como chegaram e compara em tempo constante."""
    return hmac.compare_digest(sign(body), received)  # nunca ==

body = b'{"event": "config-change", "device": "r1", "user": "netops"}'  # os bytes como chegaram
tag = sign(body)  # a assinatura do remetente
print("intact body      :", verify(body, tag))
print("one byte changed :", verify(body.replace(b"r1", b"r2"), tag))
# Reserializar o JSON lido muda os bytes (aqui, os espaços), e a tag deixa de conferir.
reserialised = json.dumps(json.loads(body), separators=(",", ":")).encode()  # mesmos dados, outros bytes
print("re-serialised    :", verify(reserialised, tag))
```

```text
5bdcc146bf60754e6a042426089575c75a003f089d2739839dec58b964ec3843
5bdcc146bf60754e ...
intact body      : True
one byte changed : False
re-serialised    : False
```

A primeira linha é o valor HMAC-SHA-256 publicado pela RFC 4231 para o segundo caso de teste, e a [ferramenta de HMAC](/tools/hmac) guarda o mesmo vetor. A última linha é o bug que manda gente para os fóruns: um destinatário que faz o parsing do JSON e o reserializa antes de conferir calcula a tag sobre outros bytes, mesmo com os dados iguais. Verifique sobre o corpo cru, como chegou, e só depois faça o parsing. Uma tag válida também não diz nada sobre ser recente; o [artigo sobre verificação](/learn/verifying-hmac) acrescenta timestamps e janelas contra replay, e o [artigo sobre assinatura de API](/learn/hmac-api-signing) mostra esquemas reais construídos sobre a mesma função.

## compare_digest, e por que == é a comparação errada

O aviso da referência em `digest()` e `hexdigest()` é curto: ao compará-los "to an externally supplied digest during a verification routine", use `compare_digest()` "instead of the == operator to reduce the vulnerability to timing attacks". A função devolve `a == b` "using an approach designed to prevent timing analysis by avoiding content-based short circuiting behaviour"; desde a 3.10 ela usa o `CRYPTO_memcmp()` do OpenSSL quando disponível. A nota dela marca o limite com honestidade: quando os tamanhos diferem ou ocorre um erro, um timing attack "could theoretically reveal information about the types and lengths" dos dois argumentos, mas não os valores. O módulo `secrets` exporta a mesma função.

```python
import hmac  # compare_digest()
import secrets  # a mesma função, com um segundo nome

tag = "5bdcc146bf60754e6a042426089575c75a003f089d2739839dec58b964ec3843"  # uma tag em hexa, como texto ASCII
print(secrets.compare_digest is hmac.compare_digest)  # uma função, dois nomes
print(hmac.compare_digest(tag, tag), hmac.compare_digest(bytes.fromhex(tag), bytes.fromhex(tag)))  # str/str, bytes/bytes

for x, y in ((tag, bytes.fromhex(tag)), ("café", "café")):  # tipos misturados, depois texto não ASCII
    try:
        hmac.compare_digest(x, y)  # os dois casos são recusados
    except TypeError as exc:  # a função levanta exceção em vez de adivinhar
        print("TypeError:", exc)
```

```text
True
True True
TypeError: a bytes-like object is required, not 'str'
TypeError: comparing strings with non-ASCII characters is not supported
```

Os dois argumentos precisam ser do mesmo tipo: objetos do tipo bytes ou strings "ASCII only, as e.g. returned by HMAC.hexdigest()". Comparar os digests crus como bytes elimina de vez a questão de maiúsculas e minúsculas no hexa. A mesma regra vale além do HMAC: um token de API, um cookie de sessão ou um hash de senha lido do armazenamento devem ser comparados assim.

## secrets: aleatoriedade que um atacante não prevê

O módulo `random` é a ferramenta errada para qualquer segredo, e a própria documentação dele diz isso: o gerador Mersenne Twister é "completely deterministic" e "completely unsuitable for cryptographic purposes". A PEP 506 acrescentou o `secrets` no Python 3.6 porque, nas palavras dela, a biblioteca padrão tornava "too easy for developers to inadvertently make serious security errors". O módulo dá "access to the most secure source of randomness that your operating system provides", com helpers para as formas que os segredos costumam ter:

```python
import random  # um gerador para simulação: nunca para segredos
import secrets  # a melhor aleatoriedade do sistema operacional
import string  # alfabetos para senhas

print(secrets.DEFAULT_ENTROPY, "bytes by default")  # o tamanho padrão das funções token_* hoje
print(secrets.token_hex(16))  # 16 bytes aleatórios como 32 dígitos hexa
print(secrets.token_urlsafe())  # 32 bytes, base64url, seguro em uma URL ou em um header
key = secrets.token_bytes(32)  # bytes crus, para uma chave de HMAC ou uma chave pré-compartilhada
print(len(key), "raw bytes")

alphabet = string.ascii_letters + string.digits  # 62 símbolos
print("".join(secrets.choice(alphabet) for _ in range(20)))  # uma senha de 20 caracteres, a receita da documentação

# Por que não random: a mesma semente dá a mesma sequência "aleatória", em qualquer máquina.
random.seed(2026)  # quem descobrir ou adivinhar a semente...
first = [random.randrange(256) for _ in range(4)]  # ...consegue reconstruir estes bytes
random.seed(2026)  # a mesma semente de novo
print(first, first == [random.randrange(256) for _ in range(4)])  # idênticos
```

```text
[60, 163, 52, 114] True
```

A documentação explica o padrão: "As of 2015, it is believed that 32 bytes (256 bits) of randomness is sufficient for the typical use-case", e avisa que o valor exato de `DEFAULT_ENTROPY` "is subject to change at any time, including during maintenance releases", então passe o tamanho explicitamente quando um protocolo o fixar. A seção de receitas gera senhas com `secrets.choice()` e lembra que aplicações "should not store passwords in a recoverable format". A documentação do pyca/cryptography dá o mesmo conselho para chaves e nonces: use `os.urandom()` ou `secrets`, nunca `random`.

## O que um scanner vê neste código

Um scanner de código lê essas escolhas como padrões. O Bandit, tratado no [artigo sobre código seguro](/learn/python-secure-coding) desta série, aponta chamadas de MD4, MD5 e SHA-1 no `hashlib` (teste B324, que também lê o `usedforsecurity`; a chamada de MD5 na execução daquele artigo saiu com severidade alta) e qualquer uso dos geradores do módulo `random` (B311, severidade baixa). Os dois são fáceis de corrigir em código novo: marque os digests que não são de segurança, e tire todo segredo do `secrets`.

## Um checklist curto

- Faça hash de bytes, não de texto: codifique explicitamente, e calcule o hash de arquivos com `hashlib.file_digest()`.
- Use SHA-256 ou mais novo para tudo o que precisa resistir a adulteração; marque os usos de MD5 e SHA-1 com `usedforsecurity=False` quando nada depende da força deles.
- Nunca guarde uma senha com um hash simples: Argon2id pelo pyca/cryptography, ou scrypt do `hashlib` com os parâmetros guardados junto do hash e `maxmem` ajustado para cabê-los.
- Assine com HMAC os bytes exatos enviados e recebidos, e verifique antes do parsing.
- Compare tags, tokens e hashes com `hmac.compare_digest()`, bytes com bytes ou texto ASCII com texto ASCII.
- Tire todo token, chave, salt e nonce do `secrets` ou do `os.urandom()`, nunca do `random`.
