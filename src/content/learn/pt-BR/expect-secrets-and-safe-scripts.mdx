O manual do [Expect](/glossary/expect) é direto sobre senhas em scripts. "It is often useful to store passwords (or other private information) in Expect scripts. This is not recommended since anything that is stored on a computer is susceptible to being accessed by anyone. Thus, interactively prompting for passwords from a script is a smarter idea than embedding them literally." A maioria dos scripts reais fica em algum ponto entre essas frases: roda por um agendador, não há ninguém para digitar, e o dispositivo do outro lado quer um login. Este artigo percorre os caminhos mais seguros em ordem de preferência e, para cada um, o lugar onde um segredo vaza mesmo assim. Cada comportamento foi executado no Expect 5.45.4 real sobre [Tcl](/glossary/tcl) 8.6.14, com dispositivos falsos num contêiner; os documentos citados foram lidos em 2026-10-27.

## Primeira escolha: nenhuma senha, uma chave e um agente

Quando o outro lado é um servidor SSH, a melhor senha num script é nenhuma. O cliente do OpenSSH lê uma identidade do arquivo indicado por `IdentityFile` no ssh_config(5), e o `ssh-agent` "is a program to hold private keys used for public key authentication": a chave é destravada uma vez, com a sua passphrase, pelo `ssh-add` (que "adds private key identities to the authentication agent"), e toda conexão depois disso se autentica sem prompt de senha para o script responder. `IdentitiesOnly yes` restringe o ssh às identidades configuradas "even if ssh-agent(1) ... offers more identities"; a página diz que a opção "is intended for situations where ssh-agent offers many different identities".

O arquivo da chave tem uma regra de permissão que o próprio ssh impõe: os arquivos de chave privada "contain sensitive data and should be readable by the user but not accessible by others (read/write/execute). ssh will simply ignore a private key file if it is accessible by others." Uma passphrase, definida quando a chave é gerada, cifra "the sensitive part of this file".

A outra opção para scripts é o `BatchMode`: "If set to yes, user interaction such as password prompts and host key confirmation requests will be disabled. This option is useful in scripts and other batch jobs where no user is present to interact with ssh(1)." Com `-o BatchMode=yes`, o ssh nunca para para pedir uma senha que ninguém vai digitar: quando a chave deixa de funcionar, a conexão falha, o programa termina e o script vê um fim de arquivo, que um ramo `eof` pode relatar com o seu próprio código de saída (o artigo sobre [timeouts e eof](/learn/expect-timeouts-eof-and-loops) trata desses ramos).

## Segunda escolha: pedida na hora, com o eco desligado

Quando uma pessoa inicia o script, o idioma do próprio manual mantém a senha fora de qualquer arquivo:

```tcl
stty -echo
send_user "Password: "
expect_user -re "(.*)\n"
set password $expect_out(1,string)
stty echo
send_user "\n"
```

O manual o apresenta como um jeito "to temporarily disable echoing. This could be used in otherwise-automatic scripts to avoid embedding passwords in them." Repare no `stty echo` logo depois da leitura: um script que deixa o eco desligado devolve um terminal que não mostra mais o que se digita, e o [explicador de scripts Expect](/tools/expect-script-explainer) aponta um `stty -echo` que nunca é desfeito (a verificação E15).

Na execução, um Expect externo fez o papel da pessoa diante de um terminal. Com `stty -echo` a senha digitada nunca apareceu na tela; sem ele, apareceu. Mas o mesmo script tinha também um `log_file` aberto, e lá a senha estava nos dois casos: o `log_file` "will record a transcript of the session", e o que o `expect_user` lê da pessoa faz parte da sessão. O eco controla a tela, não o log. Pare o log em volta da leitura e retome depois (`log_file` sem argumento "will stop recording", e por padrão ele "appends to old files rather than truncating them"); na execução, isso manteve a senha fora do arquivo:

```tcl
log_file
expect_user -re "(.*)\n"
log_file -a $logpath
```

## Terceira escolha: o ambiente, ou um arquivo que só o dono pode ler

Um script sem ninguém olhando precisa tirar o segredo de algum lugar. Dois lugares o mantêm fora do texto do script.

**O ambiente.** O Tcl guarda o ambiente no array `env`: "Reading an element will return the value of the corresponding environment variable", e "Changes to the env array will affect the environment passed to children by commands like exec". O `spawn` do Expect também o repassa: na execução, um shell iniciado depois de a variável ser definida a imprimiu. Então leia o valor para uma variável comum e o remova antes de iniciar qualquer coisa ("Unsetting an element of env will remove the corresponding environment variable"); depois de `unset env(DEVPASS)`, o shell seguinte não viu nada.

```tcl
set password $env(DEVPASS)
unset env(DEVPASS)
spawn ssh -o StrictHostKeyChecking=accept-new admin@$host
```

**Um arquivo.** Um arquivo com uma linha, legível só pela conta que roda o script, segue a mesma regra que o ssh aplica às chaves. O Tcl pode criá-lo com permissões restritas (quando o `open` cria um arquivo, "permissions (an integer) is used to set the permissions for the new file in conjunction with the process's file mode creation mask") e conferi-las antes de cada leitura com o `file attributes`, cuja opção `-permissions` "retrieves or sets a file's access permissions, using octal notation by default". O Tcl 9 mudou um detalhe que importa aqui: "0NNN format is no longer octal interpretation. Use 0oNNN". Então `0600` no Tcl 9 é o decimal seiscentos, e a cadeia octal que o `file attributes` devolve, como `00600`, tem de ser lida com `scan ... %o`, que lê "an octal integer", em vez de usada como número. Escrita assim, a verificação funciona igual no Tcl 8.6 e no Tcl 9:

```tcl
proc read_secret {path} {
    scan [file attributes $path -permissions] %o mode
    if {$mode & 0o077} {
        error "recusado: $path pode ser lido pelo grupo ou por outros"
    }
    set ch [open $path r]
    set secret [gets $ch]
    close $ch
    return $secret
}
```

Na execução, um arquivo criado com `open $f {WRONLY CREAT TRUNC} 0o600` informou `00600` e foi lido; depois de uma mudança para 0644, o procedimento o recusou. O artigo do site sobre [modos de arquivo](/learn/file-modes-octal-symbolic-and-the-special-bits) explica os dígitos octais.

Venha a senha de onde vier, envie-a com `send --`: a flag "forces the next argument to be interpreted as a string rather than a flag", o "reliable mechanism to specify variable strings without being tripped up by those that accidentally look like flags", e uma senha pode muito bem começar com hífen.

O caminho que o explicador existe para pegar é o último: uma senha literal num `send` depois de um prompt de senha, ou numa variável com nome de senha. A verificação E1 classifica isso como erro, e ele mascara o valor na própria saída.

## O que chega à tela, ao log e ao diagnóstico

Três saídas podem carregar um segredo, e cada uma segue regras próprias.

**A tela.** "By default, the send/expect dialogue is logged to stdout (and a logfile if open). The logging to stdout is disabled by the command "log_user 0" and reenabled by "log_user 1"." O que aparece é o que o programa devolve, então uma senha só chega à tela se o programa a ecoar. Na execução, um dispositivo que desligava o eco no prompt de senha, como fazem o ssh e os programas de login, não deixou nada para ver; um dispositivo descuidado que a ecoava pôs a senha na tela.

**O arquivo de log.** Ele guarda o mesmo diálogo da tela, mais o texto do `send_user` e o que o `expect_user` lê, como acima. Uma flag decide o que acontece sob `log_user 0`: "The -a flag forces output to be logged that was suppressed by the log_user command." Na execução, um log aberto sem `-a` não recebeu nada do diálogo enquanto o `log_user` estava em 0, e um aberto com `-a` recebeu tudo, inclusive a senha ecoada pelo dispositivo descuidado. Um script silencioso com registro completo usa, portanto, `log_user 0` com `log_file -a`, e para o log em volta de qualquer troca que possa ecoar um segredo. O explicador aponta um `log_user 0` que nunca volta a 1 (E12), para que um operador não fique sem saída nenhuma.

**O diagnóstico.** O `exp_internal 1` e o `expect -d` imprimem "every character received, and every attempt made to match the current output against the patterns", e na execução também imprimiram cada `send` por inteiro: `send: sending "S3cr3t-Run06\r" to { exp3 }`, mesmo com um dispositivo que nunca a ecoava. Um arquivo de diagnóstico aberto com `exp_internal -f` recebe a mesma linha. Desligue o diagnóstico em volta do send e religue depois; `exp_internal -info` devolve a configuração atual, para que ela volte exatamente como estava:

```tcl
set diag [exp_internal -info]
exp_internal 0
log_file
send -- "$password\r"
expect -re {[>#] $}
log_file -a $logpath
eval exp_internal $diag
```

## Chaves de host: accept-new, não no

A primeira conexão a um host novo é onde muitos scripts encontram uma pergunta inesperada. O ssh_config(5) define o `StrictHostKeyChecking`, e o padrão, `ask`, significa que "new host keys will be added to the user known host files only after the user has confirmed that is what they really want to do". O script que esperava um prompt de senha recebe uma pergunta `(yes/no)` no lugar.

A correção comum, `StrictHostKeyChecking=no`, responde a mais do que essa pergunta. Com `no` ou `off`, "ssh will automatically add new host keys to the user known hosts files and allow connections to hosts with changed hostkeys to proceed, subject to some restrictions". Uma chave de host alterada é o sinal de alerta de um ataque man-in-the-middle, justamente o ataque contra o qual, segundo a própria página, o `yes` dá "maximum protection". O `accept-new` fica só com a metade segura: "ssh will automatically add new host keys to the user's known_hosts file, but will not permit connections to hosts with changed host keys". É o valor para um script sem ninguém olhando que encontra dispositivos novos; o `yes`, com um arquivo `known_hosts` preparado antes, é ainda mais estrito, já que "forces the user to manually add all new hosts".

Com `accept-new`, um dispositivo cuja chave mudou faz o ssh recusar a conexão, e o script vê um fim de arquivo em vez de um prompt, que o ramo `eof` transforma numa falha clara. A verificação E10 do explicador aponta um ssh iniciado sem `no`, `off` ou `accept-new` e sem ramo para a pergunta `(yes/no)`, e conta o `accept-new` como resolvido.

## Uma lista curta

- Prefira uma chave num agente, com `BatchMode=yes`, a qualquer senha.
- Nunca escreva uma senha no script: o E1 do explicador está lá para pegá-la.
- Leia uma senha digitada com `stty -echo` e religue o eco logo em seguida; pare o `log_file` em volta do `expect_user`.
- Tire a senha do `env()` e faça o `unset` antes do `spawn`, ou de um arquivo conferido como 0600 com `scan %o`, escrito `0o600` para o Tcl 9.
- Envie-a com `send --`; mantenha o `exp_internal` e o log desligados em volta desse send.
- Use `StrictHostKeyChecking=accept-new`, nunca `no`, e dê a toda espera um ramo `eof`.

O [gerador de scripts Expect](/tools/expect-script-builder) escreve scripts que seguem esta lista: a senha vem do ambiente, com `unset` antes do `spawn`, ou é pedida com o eco desligado, e nunca vem do arquivo; o ssh usa `accept-new`; o arquivo de log só abre depois do login; e toda espera tem um ramo `eof`.
