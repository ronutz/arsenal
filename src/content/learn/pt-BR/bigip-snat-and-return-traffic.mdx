Quando o BIG-IP balanceia uma conexão, por padrão ele preserva o IP de origem do cliente em direção ao pool member. O member vê o endereço real do cliente, o que frequentemente é o que você quer, mas isso cria um requisito de roteamento fácil de deixar passar.

## A armadilha do roteamento assimétrico

Uma conexão TCP só funciona se ambas as direções fluírem pelo mesmo dispositivo que está rastreando seu estado. O BIG-IP está rastreando a conexão, então a resposta do member precisa voltar pelo BIG-IP. Se a rota padrão do próprio member aponta para o roteador da rede em vez de para o BIG-IP, o member enviará sua resposta *diretamente* em direção ao IP do cliente, contornando o BIG-IP por completo. O cliente então recebe um pacote de um endereço para o qual ele nunca abriu uma conexão, e o descarta. Isso é **roteamento assimétrico**: a requisição foi por um caminho, a resposta tentou ir por outro, e a conexão trava. É uma das causas mais comuns de "o virtual server está up mas nada funciona".

## O que o SNAT faz

O **SNAT** (source network address translation) resolve isso mudando o endereço de origem que o BIG-IP usa em direção ao member. Em vez do IP do cliente, o member vê um endereço pertencente ao BIG-IP, seja um self IP escolhido automaticamente (**SNAT automap**) ou um endereço de um **SNAT pool** definido. Agora a resposta do member é naturalmente endereçada de volta ao BIG-IP, que a encaminha ao cliente, e o caminho fica simétrico não importa como o roteamento do member esteja configurado.

## O custo e sua mitigação

O SNAT abre mão do IP real do cliente: como o member agora vê um endereço do BIG-IP como origem, ele não pode mais logar ou tomar decisões com base no endereço verdadeiro do cliente. Para HTTP isso normalmente é tratado inserindo um header `X-Forwarded-For` carregando o IP original do cliente, para que a aplicação ainda possa vê-lo. No `bigip.conf` isso aparece como um `snat-type automap` no virtual server ou um `snatpool` anexado. A regra prática é que o SNAT é o que você usa quando não pode garantir que os members roteiam o tráfego de retorno de volta pelo BIG-IP, o que na maioria das redes reais é exatamente a situação.


## O SNAT resolve o roteamento e compra um teto de portas

Ligar o SNAT corrige a assimetria, porque o membro passa a responder para o endereço do BIG-IP com quem falou. Também introduz um limite que só aparece sob carga.

Cada conexão de um endereço SNAT precisa de uma porta de origem que nenhuma outra conexão desse endereço para o mesmo destino esteja usando. A visão geral de SNAT da F5, o [K7820](https://my.f5.com/manage/s/article/K7820), diz isso diretamente: "Each SNAT address, like any IP address, has only 65535 ports available", e mesmo assim ele pode processar mais conexões simultâneas do que isso "as long as each socket pair is unique", sendo o par o endereço e a porta de origem com o endereço e a porta de destino; assim, a mesma porta de origem pode ser reaproveitada para outro endereço ou outra porta de destino (o [guia de estudo do 301a no clouddocs](https://clouddocs.f5.com/training/community/f5cert/html/class7/modules/module1.html) da F5 cita as mesmas linhas). Com um pool atrás do virtual server, o socket remoto é o membro escolhido do pool, então um endereço SNAT configurado em um único virtual server consegue tratar cerca de 65535 conexões simultâneas para cada membro do pool; para planejamento, o K7820 manda tratar 65535 como a capacidade de qualquer endereço SNAT e configurar mais endereços SNAT, por exemplo com um SNAT pool, quando mais conexões puderem precisar de tradução. Um virtual server movimentado à frente de poucos membros pode esgotar as portas para esses poucos destinos e, quando esgota, novas conexões falham enquanto todos os monitores continuam verdes. **Parece problema de backend e é problema de aritmética**: o orçamento é o número de endereços SNAT multiplicado pelo de destinos com que eles falam, então mais endereços SNAT sempre abrem espaço, e mais membros no pool só abrem espaço para o tráfego que se distribui entre eles.

As duas metades dessa aritmética se apoiam em regras documentadas. O capítulo da F5 sobre NATs e SNATs, que lista a 21.1.0 entre as versões a que se aplica, diz que um SNAT para conexões iniciadas pelo cliente faz o servidor mandar as respostas de volta pelo BIG-IP quando a rota padrão do servidor não faria isso; sem ele, o cliente rejeita uma resposta cuja origem não bate com o destino da sua requisição. O mesmo capítulo avisa que um SNAT assim pode esgotar as portas efêmeras, ficando sem conseguir processar novas conexões até que portas de origem voltem a ficar livres ([NATs and SNATs](https://techdocs.f5.com/en-us/bigip-14-1-0/big-ip-tmos-routing-administration-14-1-0/nats-and-snats.html)). O TCP define uma conexão pelo seu par de sockets, cada um sendo um endereço com uma porta ([RFC 9293, seções 3.4.1 e 4](https://www.rfc-editor.org/rfc/rfc9293.html)), então conexões que saem de um mesmo endereço de tradução precisam de portas de origem diferentes quando vão para o mesmo endereço e porta de membro. O outro custo é atribuição. **O membro deixa de ver o endereço do cliente**, então, a menos que o profile insira um cabeçalho `X-Forwarded-For` e a aplicação o registre, os logs de acesso guardam apenas o endereço SNAT. Descobrir isso durante um incidente é descobrir tarde demais.

## O header é uma alegação, não um endereço

O `X-Forwarded-For` devolve o endereço do cliente só na medida em que a aplicação confia em quem o escreveu. A opção `insert-xforwarded-for` do profile HTTP, desabilitada por padrão na [referência do tmsh](https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/ltm/ltm_profile_http.html), acrescenta o IP de cliente que o BIG-IP de fato viu, mas o cliente pode mandar o próprio header antes, e a RFC 7239, que padroniza o campo `Forwarded`, é direta sobre a família toda: ele "cannot be relied upon to be correct, as it may be modified, whether mistakenly or for malicious reasons, by every node on the way to the server, including the client making the request" ([RFC 7239, seção 8.1](https://www.rfc-editor.org/rfc/rfc7239.html)). Mesmo uma lista de proxies confiáveis só garante o trecho que ela cobre; os endereços registrados antes do primeiro proxy confiável continuam sendo a palavra do cliente. O mesmo profile tem a chave oposta, `accept-xff`, que faz o próprio BIG-IP confiar no IP de cliente de um header XFF recebido; ligue-a só onde o hop à frente do BIG-IP é um que você controla.

## Antes do teto: o aviso de port-find

A aritmética de portas acima tem um sinal de alerta antecipado. As configurações globais de traffic-control na [referência do tmsh](https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/ltm/ltm_global-settings_traffic-control.html) limitam o esforço do sistema para achar uma porta de origem livre, `port-find-linear` e `port-find-random`, 16 tentativas cada por padrão, e o `port-find-threshold-warning`, habilitado por padrão, gera um aviso quando a busca começa a sofrer. O gatilho dele, `port-find-threshold-trigger`, é "the value of random port attempts when attempting to find an unused outbound port", padrão 8, faixa de 1 a 12: uma contagem de tentativas, não um percentual de portas em uso. Leia esse aviso como a chegada do problema aritmético e acrescente endereços de tradução antes que novas conexões comecem a falhar.

Quando o esgotamento acontece, o K7820 mostra o que ele deixa em `/var/log/ltm`: mensagens no formato `01010201:2: Inet port exhaustion on <endereço de tradução> to <destino>:<porta> (proto 6)`, que o TMM registra para esgotamento de portas em qualquer objeto de gerenciamento de tráfego, não só num SNAT. O `tmsh show /ltm snat` mostra as conexões simultâneas que passam por um SNAT. O tempo de vida da porta importa tanto quanto a quantidade: o mesmo artigo recomenda manter o idle timeout de um SNAT tão curto quanto o tráfego permitir, sendo 60 segundos mais que suficientes para HTTP em geral, e observa que o idle timeout do SNAT automap não é configurável, então um configurável exige um SNAT pool ou um endereço de tradução definido.

Uma correção vale conhecer quando o SNAT pool parece ignorado. As [release notes do 21.1.0.3](https://techdocs.f5.com/kb/en-us/products/big-ip_ltm/releasenotes/related/relnote-supplement-bigip-21-1-0-3.html) registram o 2288617-1: um pool atribuído no `source-address-translation` de um virtual server não é aplicado a menos que o type esteja explicitamente em `snat`, embora a mudança pareça bem-sucedida, corrigido no 21.1.0.2 e no 17.5.1.9. Uma automação que define o pool mas não o type é o gatilho clássico.
