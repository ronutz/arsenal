Um virtual server, em termos de BIG-IP, é o objeto ao qual os clientes de fato se conectam. Ele é definido por um `destination` (um endereço IP e uma porta) e por um conjunto de recursos que decidem o que acontece com o tráfego que chega ali. Todo o resto de uma configuração de tráfego local existe para ser referenciado por um virtual server.

## O ouvinte

O campo `destination` define o endereço e a porta em que o virtual server responde, por exemplo `10.0.0.80:443`. A `mask` decide se este é um ouvinte de host único ou de uma rede inteira, e `ip-protocol` fixa o protocolo de camada 4, normalmente `tcp`. Juntos, eles determinam quais pacotes o virtual server reivindica. Um virtual que escuta na porta 443 é convencionalmente HTTPS, mas o número da porta sozinho não o torna assim; o que acontece com o TLS depende dos perfis, descritos a seguir.

## Quando vários virtuals disputam a mesma conexão

Uma conexão pode corresponder a mais de um virtual server, por exemplo um virtual de host na porta 80 e um virtual de rede que escuta em todas as portas. O [K14800](https://my.f5.com/manage/s/article/K14800) dá a regra da versão 11.3.0 em diante, a que passou a permitir que um virtual server aceite tráfego só de endereços de origem configurados: a precedência é decidida primeiro pelo endereço de destino, depois pelo endereço de origem e por último pela porta de serviço, e em cada nível um endereço de host vence um endereço de rede, que vence o curinga. A tabela do K14800 detalha isso em 18 linhas, de destino de host, origem de host e porta definida até o curinga nos três, e os exemplos dele escrevem um host como /32 e o curinga como 0.0.0.0/0. Nem a ordem numérica dos endereços nem a ordem dos virtuals na configuração entram na conta. A ordem é estrita, então uma origem mais específica supera uma porta mais específica: com o mesmo destino de host nos dois, um virtual que aceita só 192.168.2.0/25 em todas as portas vence um que aceita qualquer origem na porta 80, para um cliente dentro desse /25. A recomendação decorre da regra: quando um virtual tem endereço de origem, defina destino e origem da forma mais específica que a aplicação permitir.

A mesma rigidez produz o exemplo menos intuitivo do K14800. Um cliente em 192.168.2.1 se conecta a 192.168.1.200 na porta 80. Um virtual tem o destino curinga, a porta 80 e a própria 192.168.2.0/24 do cliente como origem; outro escuta em 192.168.1.0/24, em todas as portas, para qualquer origem. Quem fica com a conexão é o segundo: o destino de rede dele vence o destino curinga, e a porta e a origem nem chegam a ser comparadas.

Entre dois endereços de rede, quem decide é a máscara. Os exemplos do próprio K14800 escolhem a sub-rede mais próxima, uma origem /25 sobre uma /24 para o mesmo destino, e o [K9038](https://my.f5.com/manage/s/article/K9038) afirma que, entre virtual servers, o endereço de destino e a máscara mais específicos têm precedência, também para os listeners de origem e destino da versão 11.3.0 em diante. A tabela do K14800 trata todo endereço de rede como uma classe só, então uma rede estreita numa linha de baixo e uma larga numa linha de cima podem ficar numa ordem pelas linhas e na ordem oposta pelas máscaras; a F5 não publica exemplo resolvido desse caso, e o laboratório abaixo compara as máscaras e avisa quando as duas leituras divergem.

Antes da 11.3.0 a regra era outra: o [K6459](https://my.f5.com/manage/s/article/K6459) descreve a escolha só pelo destino, a sub-rede mais longa primeiro, depois a porta que bate, depois o curinga. O K14800 remete a um guia separado para address lists e port lists (14.1.x em diante) sem dizer como elas entram na precedência, e não menciona route domains. Precedência também não é disponibilidade: por padrão, diz o [K8009](https://my.f5.com/manage/s/article/K8009), quando o virtual server de maior precedência está desabilitado, o BIG-IP rejeita o pacote em vez de passá-lo a um de precedência menor, a menos que a variável de banco de dados `tm.continuematching` esteja em true.

## A pilha de perfis

O bloco `profiles` é o coração do comportamento de um virtual server. Os perfis são empilhados: um perfil TCP governa o transporte, um perfil HTTP acrescenta a análise de camada 7, e os perfis SSL terminam ou originam o TLS. Um perfil client-SSL significa que o TLS é descriptografado no BIG-IP; sem ele, um virtual com aparência de HTTPS simplesmente repassa os bytes criptografados direto ao backend. Se nenhum perfil estiver anexado, o virtual recai para o padrão FastL4 e se comporta como um encaminhador puro de camada 4, sem consciência de HTTP ou TLS. Ler a lista de perfis é, portanto, a forma mais rápida de saber se um virtual é um repasse L4 (Camada 4, transporte) ou um proxy L7 (Camada 7, aplicação) completo.

## Persistência e o pool

Depois que o tráfego é analisado, o virtual decide para onde enviá-lo. Um perfil `persist` mantém um determinado cliente fixado ao mesmo membro do pool entre conexões, o que importa para aplicações com estado. O campo `pool` nomeia o pool padrão de membros de backend. O modo de balanceamento e o monitor de saúde do próprio pool então escolhem um membro específico e saudável para receber a conexão; essa seleção é abordada em [o artigo sobre monitores de saúde](/learn/ltm-health-monitors). Um virtual server sem pool não está necessariamente quebrado: o tráfego pode ser direcionado inteiramente por uma iRule, por uma policy de tráfego local ou por uma configuração de encaminhamento.

## Tradução de endereço de origem

A última decisão é qual endereço de origem o backend enxerga. O bloco `source-address-translation` controla isso. Com `automap` ou um SNAT pool, o BIG-IP substitui o IP de origem do cliente por um dos seus próprios, de modo que o tráfego de retorno volta naturalmente por ele. Com `type none`, o membro do pool enxerga o IP real do cliente, o que às vezes é exigido para registro ou geolocalização, mas força a rota padrão do membro, ou uma rota específica, a apontar de volta para o BIG-IP. Errar nisso é uma causa clássica de roteamento assimétrico, em que as requisições chegam mas as respostas nunca retornam.

## O virtual server como um caminho

Em conjunto, um virtual server descreve um caminho: um cliente alcança o `destination`, a pilha de perfis analisa e possivelmente descriptografa a conexão, a persistência e o pool selecionam um membro, e a tradução de origem reescreve a origem de saída. O [explicador de configuração tmsh](/tools/f5-tmsh-config-explainer) dispõe esses campos e destaca os que têm mais chance de surpreender, como uma porta HTTPS sem perfil client-SSL ou uma configuração de SNAT igual a none. Para a gramática em que esses objetos são escritos, veja [a anatomia de um arquivo bigip.conf](/learn/anatomy-of-bigip-conf).
