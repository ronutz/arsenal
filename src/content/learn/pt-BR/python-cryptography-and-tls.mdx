O Python chega ao TLS e à criptografia por duas camadas. O módulo `ssl` da biblioteca padrão, que a documentação chama de "TLS/SSL wrapper for socket objects", é o que fornece o contexto a `urllib`, `http.client` e `smtplib`, e o que o Requests e o HTTPX chamaram por baixo no [artigo sobre APIs dos equipamentos](/learn/python-and-device-apis) desta série. O pacote pyca/cryptography, instalado com pip, acrescenta o que o `ssl` não faz: montar e ler certificados, assinar, cifrar dados guardados. Esta parte da [série de Python](/learn/python-explained) usa os dois sem sair da interface de loopback: uma CA de teste montada com o cryptography, um servidor TLS em 127.0.0.1 e clientes que mostram o que o Python verifica e o que ele recusa. Todo exemplo rodou no CPython 3.13.16, com o cryptography 50.0.2 em um ambiente virtual descartável; a documentação foi lida em 27 de outubro de 2026.

## Dois OpenSSL no mesmo processo

```python
import ssl  # o TLS da biblioteca padrão, ligado ao OpenSSL com que o CPython foi compilado
import sys  # a versão do interpretador

import cryptography  # pyca/cryptography, instalado com pip em um ambiente virtual
from cryptography.hazmat.backends.openssl import backend  # o OpenSSL dentro do wheel do cryptography

print("Python      :", sys.version.split()[0])
print("ssl module  :", ssl.OPENSSL_VERSION)  # a biblioteca que o módulo ssl está usando
print("cryptography:", cryptography.__version__, "with", backend.openssl_version_text())  # um segundo OpenSSL, separado
```

```text
Python      : 3.13.16
ssl module  : OpenSSL 3.0.13 30 Jan 2024
cryptography: 50.0.2 with OpenSSL 4.0.3 29 Sep 2026
```

As duas linhas nomeiam bibliotecas diferentes, e cada uma tem o seu caminho de atualização. O módulo `ssl` usa o OpenSSL ao qual quem compilou o interpretador o ligou; no ambiente de build, é o pacote OpenSSL 3.0.13 da distribuição Linux. A estratégia de releases do projeto OpenSSL lista o 3.0 entre as versões que "are no longer supported" (suporte estendido para correções de segurança é oferecido à parte), o 3.5 como o release de suporte longo, com suporte até 8 de abril de 2030, e o 4.0 com suporte até 14 de maio de 2027. O changelog do próprio CPython para a 3.13.16 registra que os instaladores do python.org para macOS e Windows passaram ao OpenSSL 3.5.9, "jumping from the 3.0 series to 3.5 after 3.0's end of public support in September 2026". No Linux, quem decide é a distribuição, e uma distribuição que faz backport de correções mantém o número de versão antigo, ponto que o [artigo sobre as vulnerabilidades do PHP](/learn/php-october-2026-vulnerabilities) faz com todas as letras: número de versão não é veredito, e é no changelog do pacote que as correções aparecem.

O cryptography segue o outro caminho. O guia de instalação diz que ele "ships statically-linked wheels for macOS, Windows, and Linux" para que ambientes compatíveis "use the most recent OpenSSL, regardless of what is shipped by default on those platforms", e a entrada do changelog da 50.0.2, lançada em 30 de setembro de 2026, diz "Updated Windows, macOS, and Linux wheels to be compiled with OpenSSL 4.0.3". Então `pip install --upgrade cryptography` corrige uma camada, e as atualizações do sistema operacional corrigem a outra.

## Um contexto de cliente que verifica

A documentação do `ssl` abre com um aviso para não usar o módulo "without reading the Security considerations", porque "the default settings of the ssl module are not necessarily appropriate for your application". As considerações então recomendam uma função para uso em cliente: o `create_default_context()` "will load the system's trusted CA certificates, enable certificate validation and hostname checking, and try to choose reasonably secure protocol and cipher settings".

```python
import ssl  # contextos TLS

ctx = ssl.create_default_context()  # o ponto de partida documentado para um cliente
print("protocol      :", ctx.protocol.name)
print("verify_mode   :", ctx.verify_mode.name)  # o outro lado precisa apresentar uma cadeia válida
print("check_hostname:", ctx.check_hostname)  # ...para o nome que pedimos
print("minimum       :", ctx.minimum_version.name)  # TLS 1.2 desde o Python 3.10
print("verify_flags  :", [f.name for f in ssl.VerifyFlags if f and f in ctx.verify_flags])  # a 3.13 acrescenta STRICT e PARTIAL_CHAIN
print("CA certs      :", ctx.cert_store_stats()["x509_ca"], "loaded from the system store")

server_side = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)  # um contexto montado à mão, do lado do servidor
print("hand-made server context asks clients for certificates:", server_side.verify_mode.name)  # CERT_NONE até ser configurado

try:
    ctx.wrap_bio(ssl.MemoryBIO(), ssl.MemoryBIO())  # um objeto TLS de cliente sem server_hostname
except ValueError as exc:  # a 3.13.16 em diante recusa: não haveria nome para verificar
    print("wrap_bio without a name:", exc)
```

```text
protocol      : PROTOCOL_TLS_CLIENT
verify_mode   : CERT_REQUIRED
check_hostname: True
minimum       : TLSv1_2
verify_flags  : ['VERIFY_X509_STRICT', 'VERIFY_X509_TRUSTED_FIRST', 'VERIFY_X509_PARTIAL_CHAIN']
CA certs      : 122 loaded from the system store
hand-made server context asks clients for certificates: CERT_NONE
wrap_bio without a name: check_hostname requires server_hostname
```

Cada linha tem uma versão por trás na documentação. O `PROTOCOL_TLS_CLIENT` "enables CERT_REQUIRED and check_hostname by default"; desde a 3.10 os protocolos de cliente e de servidor "use TLS 1.2 as minimum TLS version"; desde a 3.13 o contexto padrão acrescenta `VERIFY_X509_PARTIAL_CHAIN` e `VERIFY_X509_STRICT`. Um contexto montado à mão é outra história: o do lado do servidor, acima, não pede certificado aos clientes até ser configurado para isso, o que está certo para a maioria dos servidores e errado para [TLS mútuo](/learn/mutual-tls). A última linha é uma correção da 3.13.16: o `wrap_bio()`, a variante em buffers de memória do `wrap_socket()` sobre a qual frameworks assíncronos se apoiam, aceitava um contexto com verificação de nome sem nenhum nome e, nas palavras da documentação, "verified the certificate chain but never the peer's identity". A documentação também avisa que as configurações do contexto padrão "may change to more restrictive values anytime without prior deprecation".

Compare com o `openssl s_client`, que o [artigo sobre o s_client](/learn/reading-openssl-s-client-output) lê linha a linha: o s_client verifica a cadeia mas segue com o handshake seja qual for o resultado, e não confere nome nenhum a menos que alguém peça. O contexto padrão do Python faz as duas verificações, e quando o nome não confere o handshake "is aborted early and a TLS alert message is sent to the peer". O [explicador do openssl s_client](/tools/openssl-s-client-explainer) decodifica qualquer um dos dois tipos de saída.

## Um laboratório: uma CA de teste, um servidor TLS, SNI e ALPN

A CA de teste e os certificados foram montados com o construtor X.509 do cryptography, do jeito que o tutorial do próprio pacote monta uma hierarquia de CA, mas sem a intermediária: uma raiz autoassinada e depois um certificado de servidor para `device.lab.test` e `127.0.0.1`, válido por sete dias. A função que emite o certificado do servidor pode deixar uma extensão de fora, e a próxima seção precisa disso:

```python
def issue_server(name: str, with_aki: bool) -> None:
    """Emite um certificado de servidor para device.lab.test e 127.0.0.1, com ou sem a extensão AKI."""
    key = ec.generate_private_key(ec.SECP256R1())  # o par de chaves do servidor
    b = (x509.CertificateBuilder()  # os campos, uma chamada cada
         .subject_name(x509.Name([x509.NameAttribute(NameOID.COMMON_NAME, "device.lab.test")]))  # para pessoas
         .issuer_name(ca.subject).public_key(key.public_key())  # emitido pela CA do laboratório
         .serial_number(x509.random_serial_number()).not_valid_before(NOW).not_valid_after(NOW + WEEK)  # serial, 7 dias
         .add_extension(x509.SubjectAlternativeName([x509.DNSName("device.lab.test"),  # os nomes que os clientes verificam
                                                     x509.IPAddress(ipaddress.ip_address("127.0.0.1"))]), critical=False)
         .add_extension(x509.BasicConstraints(ca=False, path_length=None), critical=True)  # não é uma CA
         .add_extension(x509.ExtendedKeyUsage([ExtendedKeyUsageOID.SERVER_AUTH]), critical=False)  # servidor TLS
         .add_extension(x509.SubjectKeyIdentifier.from_public_key(key.public_key()), critical=False))  # o ID da própria chave
    if with_aki:  # RFC 5280 4.2.1.1: MUST ser incluído por CAs conformes
        b = b.add_extension(x509.AuthorityKeyIdentifier.from_issuer_subject_key_identifier(
            ca.extensions.get_extension_for_class(x509.SubjectKeyIdentifier).value), critical=False)  # aponta para a chave da CA
    save(name, b.sign(ca_key, hashes.SHA256()), key)  # assinado pela CA

issue_server("server", with_aki=True)  # o certificado conforme
issue_server("server-noaki", with_aki=False)  # o mesmo certificado sem o AKI, para o caso de falha
```

O servidor abaixo escuta em 127.0.0.1, apresenta o certificado conforme, oferece dois protocolos ALPN e registra o nome de servidor que cada cliente pede. O cliente confia só na CA do laboratório e se conecta quatro vezes, chamando o servidor por um nome diferente a cada vez:

```python
import socket  # TCP debaixo do TLS
import ssl  # contextos e sockets TLS
import threading  # o servidor de teste roda ao lado do cliente

# ---- O servidor de teste: só 127.0.0.1, o certificado do laboratório, ALPN e um registro do SNI recebido.
seen = []  # nomes de servidor que o servidor recebeu, em ordem

def remember_sni(sslobj, server_name, context):  # chamada depois que o ClientHello chega
    seen.append(server_name)  # None quando o cliente não mandou a extensão server_name

srv_ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)  # lado do servidor, TLS 1.2 no mínimo
srv_ctx.load_cert_chain("pki/server.pem", "pki/server.key")  # o certificado conforme do laboratório
srv_ctx.set_alpn_protocols(["h2", "http/1.1"])  # o que o servidor fala, o preferido primeiro
srv_ctx.sni_callback = remember_sni  # olha o SNI; um servidor real poderia trocar de certificado aqui

listener = socket.create_server(("127.0.0.1", 0))  # porta 0: o kernel escolhe uma porta livre
PORT = listener.getsockname()[1]  # a porta escolhida

def serve() -> None:
    """Aceita conexões para sempre; completa cada handshake ou anota por que falhou."""
    while True:  # a thread termina junto com o processo
        conn, _ = listener.accept()  # uma conexão TCP
        try:
            with srv_ctx.wrap_socket(conn, server_side=True) as tls:  # o handshake acontece aqui
                tls.sendall(b"hello from the lab server\n")  # uma linha de dados de aplicação
        except (ssl.SSLError, OSError):  # um cliente que nos recusou, por exemplo
            pass  # o lado cliente imprime o motivo

threading.Thread(target=serve, daemon=True).start()  # inicia o servidor

# ---- O cliente: um contexto que verifica, confiando só na CA do laboratório.
cli_ctx = ssl.create_default_context(cafile="pki/ca.pem")  # verifica contra a CA do laboratório, não o store do sistema
cli_ctx.set_alpn_protocols(["h2", "http/1.1"])  # oferecidos no ClientHello

def connect(server_hostname: str, alpn=None) -> None:
    """Conecta ao servidor do laboratório chamando-o de server_hostname; imprime o que foi negociado."""
    if alpn:  # uma oferta de ALPN diferente, opcional
        cli_ctx.set_alpn_protocols(alpn)
    try:
        with socket.create_connection(("127.0.0.1", PORT), timeout=5) as raw:  # sempre o mesmo endereço
            with cli_ctx.wrap_socket(raw, server_hostname=server_hostname) as tls:  # o SNI e o nome a verificar
                cert = tls.getpeercert()  # um dict, porque a cadeia foi verificada
                print(f"{server_hostname:<16} {tls.version()} {tls.cipher()[0]} alpn={tls.selected_alpn_protocol()}"
                      f" sni_seen={seen[-1]!r}")
                print(" " * 17, "SAN:", cert["subjectAltName"], "| notAfter:", cert["notAfter"])
    except ssl.SSLCertVerificationError as exc:  # a verificação falhou: nenhum dado foi trocado
        print(f"{server_hostname:<16} refused: {exc.verify_message}")

connect("device.lab.test")  # o nome DNS que está no certificado
connect("127.0.0.1")  # o endereço IP que está no certificado
connect("router.lab.test")  # um nome que o certificado não traz
connect("device.lab.test", alpn=["imap"])  # um protocolo que o servidor não oferece
```

```text
device.lab.test  TLSv1.3 TLS_AES_256_GCM_SHA384 alpn=h2 sni_seen='device.lab.test'
                  SAN: (('DNS', 'device.lab.test'), ('IP Address', '127.0.0.1')) | notAfter: Nov  3 10:11:58 2026 GMT
127.0.0.1        TLSv1.3 TLS_AES_256_GCM_SHA384 alpn=h2 sni_seen=None
                  SAN: (('DNS', 'device.lab.test'), ('IP Address', '127.0.0.1')) | notAfter: Nov  3 10:11:58 2026 GMT
router.lab.test  refused: Hostname mismatch, certificate is not valid for 'router.lab.test'.
device.lab.test  TLSv1.3 TLS_AES_256_GCM_SHA384 alpn=None sni_seen='device.lab.test'
                  SAN: (('DNS', 'device.lab.test'), ('IP Address', '127.0.0.1')) | notAfter: Nov  3 10:11:58 2026 GMT
```

O `server_hostname` faz dois trabalhos ao mesmo tempo: vai como Server Name Indication, que a RFC 6066 define para que um mesmo endereço hospede vários certificados, e é o nome que o certificado precisa conter. O `sni_callback` do servidor, que a documentação descreve como chamado "after the TLS Client Hello handshake message has been received", viu `device.lab.test` na primeira conexão. Na segunda o cliente usou um endereço IP, e o servidor não viu nome nenhum: a RFC 6066 diz que "Literal IPv4 and IPv6 addresses are not permitted" nesse campo, e o certificado conferiu mesmo assim pela entrada de endereço IP. A terceira conexão falhou durante o handshake, antes de qualquer dado trafegar, porque o certificado não traz `router.lab.test`. A quarta mostra o ALPN (RFC 7301): o cliente ofereceu só `imap`, o servidor não suporta nada disso, e `selected_alpn_protocol()` devolveu `None`, um dos resultados que a documentação lista. A RFC 7301 diz que um servidor nessa situação "SHALL respond with a fatal" alerta `no_application_protocol`; este servidor Python deixou a conexão seguir, então um cliente que precisa de um protocolo tem de conferir o resultado em vez de supô-lo. O handshake em si foi TLS 1.3, cujas diferenças em relação ao 1.2 o [artigo sobre a família de handshakes](/learn/tls12-tls13-dtls-quic) percorre.

## Quando a verificação falha: o Authority Key Identifier

O [artigo sobre APIs dos equipamentos](/learn/python-and-device-apis) desta série deu de cara com essa falha na primeira execução: três clientes diferentes, a biblioteca padrão, o Requests e o HTTPX, recusaram os certificados de uma CA de laboratório com `Missing Authority Key Identifier`. A causa é uma das duas flags novas do padrão do Python 3.13. A documentação diz que elas fazem o OpenSSL "behave more like a conforming implementation of RFC 5280, in exchange for a small amount of incompatibility with older X.509 certificates", e anota que o `VERIFY_X509_STRICT` "may reject pre-RFC 5280 or malformed certificates that the underlying OpenSSL implementation otherwise would accept". A RFC 5280 é explícita sobre essa extensão: o identificador de chave dela "MUST be included in all certificates generated by conforming CAs to facilitate certification path construction", com uma exceção, o certificado autoassinado da própria CA. Um certificado vindo de uma CA que a omite, um equipamento que emite o próprio certificado por exemplo, falha do mesmo jeito. O mesmo cliente, contra um servidor que apresenta o certificado sem a extensão, nos dois interpretadores do ambiente de build:

```python
ctx = ssl.create_default_context(cafile="pki/ca.pem")  # confia só na CA do laboratório; flags padrão
with socket.create_connection(listener.getsockname(), timeout=5) as raw:  # conecta ao servidor de teste
    try:
        with ctx.wrap_socket(raw, server_hostname="device.lab.test") as tls:  # verifica a cadeia e o nome
            print(platform.python_version(), "handshake completed:", tls.version())
    except ssl.SSLCertVerificationError as exc:  # a cadeia foi recusada
        print(platform.python_version(), "refused:", exc.verify_message)
```

```text
3.13.16 refused: Missing Authority Key Identifier
```

```text
3.12.3 handshake completed: TLSv1.3
```

O segundo resultado é o pacote Python 3.12 da distribuição Linux, cujo contexto padrão não tem a flag estrita; um upgrade da 3.12 para a 3.13 basta, portanto, para transformar um script de equipamento que funcionava em um que falha. A documentação mostra como remover a flag, `ctx.verify_flags &= ~ssl.VERIFY_X509_STRICT`, e diz com todas as letras que desligá-la "is not recommended". A correção melhor é o certificado. Para ver o problema pelo lado do certificado, o cryptography lê os dois certificados e depois valida cada um com o próprio construtor de caminhos, uma API que o changelog dele declarou estável na 50.0.0:

```python
from pathlib import Path  # os arquivos PEM da PKI do laboratório

from cryptography import x509  # parsing e validação de caminho
from cryptography.hazmat.primitives import hashes  # fingerprints
from cryptography.x509.verification import PolicyBuilder, Store, VerificationError  # API estável desde a 50.0

ca = x509.load_pem_x509_certificate(Path("pki/ca.pem").read_bytes())  # a âncora de confiança do laboratório

def describe(path: str) -> x509.Certificate:
    """Imprime o que um engenheiro confere primeiro em um certificado, e o devolve."""
    cert = x509.load_pem_x509_certificate(Path(path).read_bytes())  # de PEM para um objeto
    san = cert.extensions.get_extension_for_class(x509.SubjectAlternativeName).value  # os nomes que um cliente compara
    print(path)
    print("  subject :", cert.subject.rfc4514_string(), "| issuer:", cert.issuer.rfc4514_string())
    print("  valid   :", cert.not_valid_before_utc, "to", cert.not_valid_after_utc)  # UTC com fuso explícito
    print("  SAN     :", san.get_values_for_type(x509.DNSName), [str(i) for i in san.get_values_for_type(x509.IPAddress)])
    print("  key/sig :", cert.public_key().curve.name, "/", cert.signature_hash_algorithm.name)  # P-256 / SHA-256
    print("  SHA-256 :", cert.fingerprint(hashes.SHA256()).hex(":")[:47], "...")  # como as ferramentas de certificado mostram
    print("  exts    :", [type(e.value).__name__ for e in cert.extensions])  # quais extensões estão presentes
    try:
        aki = cert.extensions.get_extension_for_class(x509.AuthorityKeyIdentifier).value  # RFC 5280 4.2.1.1
        print("  AKI     :", aki.key_identifier.hex(), "| CA's SKI:",
              ca.extensions.get_extension_for_class(x509.SubjectKeyIdentifier).value.digest.hex())
    except x509.ExtensionNotFound:  # o caso que a verificação estrita do Python 3.13 recusa
        print("  AKI     : missing")
    return cert

verifier = PolicyBuilder().store(Store([ca])).build_server_verifier(x509.DNSName("device.lab.test"))  # nome + âncora
for path in ("pki/server.pem", "pki/server-noaki.pem"):  # o certificado conforme, depois o outro
    cert = describe(path)  # imprime os campos
    try:
        chain = verifier.verify(cert, [])  # validação de caminho no cryptography, independente do módulo ssl
        print("  cryptography verifier: OK,", len(chain), "certificates in the path")
    except VerificationError as exc:  # nenhum caminho válido
        print("  cryptography verifier: refused:", exc)
```

O Authority Key Identifier do certificado conforme é igual ao Subject Key Identifier da CA, que é como um validador encontra a chave do emissor; o outro certificado simplesmente não o tem, e 2.5.29.35 é o identificador de objeto dessa extensão. Dois validadores independentes, o OpenSSL pelo `ssl` e a validação de caminho do próprio cryptography, chegam ao mesmo veredito; as políticas padrão do cryptography são, nas palavras da documentação, "based on CA/B Forum guidelines". Os mesmos campos podem ser lidos sem código no [decodificador X.509](/tools/x509), e o [montador de cadeias](/tools/cert-chain-builder) ordena e confere uma cadeia colada de um equipamento. O [artigo sobre validação de certificados](/learn/certificate-validation) explica cada verificação, a [anatomia do X.509](/learn/x509-anatomy) as extensões e o [artigo sobre cadeias](/learn/certificate-chains-order-anchors-and-what-breaks-them) como um emissor é encontrado. Em uma conexão real, `getpeercert()` só devolve o dicionário para um par validado (a documentação diz que o dict vem vazio caso contrário), e desde a 3.13 `get_verified_chain()` devolve a cadeia como uma lista de certificados DER que `x509.load_der_x509_certificate()` lê.

## Receitas e hazmat

A documentação do cryptography descreve a organização em dois níveis. Um guarda "safe cryptographic recipes that require little to no configuration choices". O outro guarda "low-level cryptographic primitives", que "are often dangerous and can be used incorrectly" e "require making decisions and having an in-depth knowledge of the cryptographic concepts at work"; por causa desse perigo ele "is referred to as the hazardous materials or hazmat layer", mora em `cryptography.hazmat`, e toda página dele abre com um aviso de que o módulo é "full of land mines, dragons, and dinosaurs with laser guns". O conselho é usar as receitas "whenever possible". A receita mais conhecida é o Fernet, que "guarantees that a message encrypted using it cannot be manipulated or read without the key":

```python
import datetime as dt  # para ler o timestamp do token
from cryptography.fernet import Fernet, InvalidToken  # a camada de receitas

key = Fernet.generate_key()  # 32 bytes aleatórios em base64 seguro para URL: guarde como se guarda uma senha
f = Fernet(key)  # cifra e decifra com um só objeto

backup = b"hostname r1\nsnmp-server community lab-only-ro RO\n"  # um trecho de configuração que vale proteger
token = f.encrypt(backup)  # AES-128-CBC mais HMAC-SHA256, conforme a especificação do Fernet
print(token[:32], b"...", len(token), "bytes")
print(f.decrypt(token, ttl=3600) == backup)  # ttl: recusa tokens com mais de uma hora
print("created at", dt.datetime.fromtimestamp(f.extract_timestamp(token), dt.timezone.utc))  # guardado em claro dentro do token

i = 80  # um caractere no meio do token
tampered = token[:i] + (b"B" if token[i:i + 1] == b"A" else b"A") + token[i + 1:]  # troca por outra letra de base64
try:
    f.decrypt(tampered)  # autenticado: a alteração é detectada antes de qualquer decifragem
except InvalidToken:
    print("tampered token: InvalidToken")
try:
    Fernet(Fernet.generate_key()).decrypt(token)  # o token certo, a chave errada
except InvalidToken:
    print("wrong key: InvalidToken")
```

```text
b'gAAAAABq4HjvBHZvysxh5r3CYFSg2lXp' b'...' 164 bytes
True
created at 2026-10-27 10:11:59+00:00
tampered token: InvalidToken
wrong key: InvalidToken
```

A documentação lista do que o Fernet é feito, AES em modo CBC com chave de 128 bits e padding PKCS7, HMAC com SHA-256 para a autenticação e vetores de inicialização vindos de `os.urandom()`, e o que ele não esconde: o token "contains the current time when it was generated in plaintext". Ele serve para dados que "easily fits in memory"; o release 50.0.0 acrescentou uma receita de streaming, o Cobblestone, para mensagens grandes. O `MultiFernet` cuida da rotação de chaves.

A camada hazmat é onde protocolos são construídos, e toda escolha é de quem chama. Duas primitivas que um engenheiro de redes pode usar bem, AES-GCM para cifrar com contexto autenticado e Ed25519 para assinar um backup de configuração:

```python
import os  # urandom() para nonces
from cryptography.exceptions import InvalidSignature, InvalidTag  # como a camada hazmat diz "não"
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey  # assinaturas
from cryptography.hazmat.primitives.ciphers.aead import AESGCM  # criptografia autenticada

# AES-GCM: toda escolha é sua, inclusive o nonce, que nunca pode se repetir com a mesma chave.
key = AESGCM.generate_key(bit_length=256)  # uma chave aleatória de 256 bits
aead = AESGCM(key)  # a primitiva
nonce = os.urandom(12)  # 96 bits, o tamanho que o NIST recomenda; guarde ou envie junto do texto cifrado
ct = aead.encrypt(nonce, b"enable secret lab-only", b"device=r1")  # o último argumento é autenticado, não cifrado
print(len(ct), "bytes: plaintext + 16-byte tag")
print(aead.decrypt(nonce, ct, b"device=r1"))  # mesmo nonce, mesmos dados associados
try:
    aead.decrypt(nonce, ct, b"device=r2")  # o texto cifrado foi parar no registro de outro equipamento
except InvalidTag:
    print("wrong associated data: InvalidTag")

# Ed25519: assina um backup de configuração para que um leitor futuro prove que ele não mudou.
signing_key = Ed25519PrivateKey.generate()  # fica com quem faz os backups
public_key = signing_key.public_key()  # vai para quem os confere
config = b"hostname r1\ninterface Gi0/1\n description uplink\n"  # o backup
signature = signing_key.sign(config)  # 64 bytes
public_key.verify(signature, config)  # devolve None quando a assinatura é válida
print("signature verified,", len(signature), "bytes")
try:
    public_key.verify(signature, config.replace(b"uplink", b"uplink-2"))  # uma edição
except InvalidSignature:
    print("edited backup: InvalidSignature")
```

```text
38 bytes: plaintext + 16-byte tag
b'enable secret lab-only'
wrong associated data: InvalidTag
signature verified, 64 bytes
edited backup: InvalidSignature
```

A página do AES-GCM traz o aviso em maiúsculas, "NEVER REUSE A NONCE with a key", e explica que a reutilização "compromises the security of any message with that nonce and key pair"; o Fernet existe para que a maior parte do código nunca precise cuidar disso. Os dados associados prendem o texto cifrado ao seu registro, então um segredo copiado para a entrada de outro equipamento não decifra. Para o Ed25519 a documentação é direta como poucas vezes: "If you do not have legacy interoperability concerns then you should strongly consider using this signature algorithm." Uma assinatura é o que faltava ao checksum do [artigo anterior](/learn/python-hashing-hmac-and-secrets): quem verifica precisa só da chave pública, e ninguém sem a chave privada consegue produzir uma assinatura válida para um arquivo editado.

A política de estabilidade de API do pacote explica o que um upgrade pode mudar: as versões são X.0.Z, um recurso fica depreciado por dois releases maiores antes de ser removido, e "One exception to our API stability policy is for security". O release 50.0.0, por exemplo, depreciou o Diffie-Hellman sobre corpos finitos.

## O nível de patch faz parte da configuração

O mesmo branch do interpretador se comporta de forma diferente de um release de patch para o outro. A 3.13.16 mudou o `wrap_bio()`, como mostrado acima. A 3.13.18, lançada em 25 de outubro de 2026, dois releases de segurança depois daquele que estas execuções usaram, faz o módulo `ssl` recusar cadeias que contenham qualquer uma de um conjunto de chaves de CAs intermediárias da eMudhra que o changelog e a página do release descrevem como comprometidas (CVE-2026-115557). O changelog chama isso de "an extraordinary measure and a last line of defense": remover a confiança "is primarily the job of the platform root store", e a lista embutida compara o SHA-256 do SubjectPublicKeyInfo de cada certificado, de modo que também cobre certificados com assinatura cruzada que reutilizam uma chave desconfiada. O CPython 3.13.16 não tem essa lista, mais um motivo para o [artigo de abertura da série](/learn/python-explained) tratar o nível de patch como parte da configuração. O cryptography anda no próprio relógio: a 50.0.1 e a 50.0.2 fizeram pouco mais do que recompilar os wheels contra releases mais novos do OpenSSL.

## Um checklist curto

- Comece todo cliente com `ssl.create_default_context()`; passe `cafile` para uma CA privada em vez de desligar a verificação.
- Passe sempre o `server_hostname`, o nome que o certificado precisa conter; é também o que o SNI envia.
- Quando a 3.13 recusar um certificado, leia o motivo: um Authority Key Identifier ausente se corrige reemitindo o certificado, não limpando o `VERIFY_X509_STRICT`.
- Confira `selected_alpn_protocol()` quando o protocolo importa; `None` é uma resposta possível.
- Use Fernet para dados guardados, a menos que um protocolo exija outra coisa; na camada hazmat, nunca reutilize um nonce de AES-GCM.
- Assine com Ed25519 o que precisa ser provado como inalterado (backups, configurações exportadas).
- Mantenha as duas camadas com patch: o sistema operacional ou o build do Python para o `ssl`, o pip para o cryptography.
