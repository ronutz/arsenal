## O problema que o VOSS resolve

Numa rede Ethernet tradicional, levar uma VLAN para outra parte do campus significa passar aquele VLAN ID em trunk, hop a hop (cada switch do caminho), e depender do spanning tree para manter a topologia sem loops. Funciona, mas escala mal: todo switch do caminho precisa carregar a VLAN, o spanning tree bloqueia links pelos quais você pagou, e uma mudança no meio da rede se propaga para o resto dela. O VOSS, o Fabric Connect da Extreme, construído sobre o Shortest Path Bridging MAC (SPBM, IEEE 802.1aq), segue outro caminho: você provisiona o serviço só na borda, e a fabric se encarrega de transportá-lo automaticamente.

## O I-SID é o serviço

A unidade desse serviço é o **I-SID** (Service Instance Identifier), um número de 24 bits que vai no header (cabeçalho) MAC-in-MAC do SPBM. Em vez de estender uma VLAN pelo core, você mapeia a VLAN para um I-SID no switch de borda, o Backbone Edge Bridge, ou BEB. Qualquer outro BEB com o mesmo I-SID configurado entra no mesmo serviço; os switches de core que ficam no meio, os Backbone Core Bridges (BCBs), nem precisam saber que ele existe. O VLAN ID continua local em cada borda: só o I-SID é global.

## Três tipos de serviço, um só mecanismo

O mesmo mecanismo de I-SID transporta três tipos de serviço, dependendo do que você mapeia para ele:

- **Layer 2 VSN**: uma VLAN de cliente é mapeada para um I-SID (`vlan i-sid <vlan> <isid>`). É um serviço de camada 2 any-to-any: a VLAN aparece em todos os BEBs que compartilham o I-SID, como se estivessem todos no mesmo switch.
- **Layer 3 VSN**: uma VRF (Virtual Routing and Forwarding instance) é mapeada para um I-SID. É um serviço roteado, em full mesh: uma tabela de roteamento virtualizada, transportada pela fabric.
- **IP Shortcuts**: a tabela de roteamento global (VRF 0) é encaminhada via IS-IS, sem nenhum I-SID; o encaminhamento segue a alcançabilidade dos backbone MACs pelo caminho mais curto.

Então o número do I-SID, sozinho, não diz se o serviço é de camada 2 ou de camada 3: isso depende do que você associou a ele. É exatamente por isso que a ferramenta complementar valida o número e explica as opções, em vez de tentar adivinhar o tipo.

## Como um frame atravessa a fabric

Quando um BEB recebe um frame (quadro) numa VLAN mapeada para o I-SID 100, ele consulta o I-SID, descobre qual backbone MAC remoto é dono daquele serviço e encapsula o frame original num novo header de backbone MAC, com o seu próprio B-MAC nodal como origem e o B-MAC do nó de destino como destino; depois, encaminha o frame encapsulado para o core. Os BCBs fazem o switching só pelo backbone MAC e nunca olham o frame do cliente. O BEB de destino tira o header de backbone e entrega o frame original. Isso é o MAC-in-MAC: o mundo do cliente e o mundo do backbone ficam bem separados.

## Onde entra o control plane

Nada disso usa spanning tree. A fabric roda **IS-IS** como o seu único control plane (plano de controle) link-state: os nós formam adjacências, aprendem a topologia, calculam os caminhos mais curtos e distribuem por flooding a informação de quais I-SIDs cada nó tem, à medida que os serviços são provisionados. Duas Backbone VLANs (normalmente a 4051 e a 4052) transportam o tráfego, mas não fazem flooding de frames desconhecidos, de broadcast ou de multicast: elas só encaminham com base nas tabelas de backbone MAC que o IS-IS monta. Essa é a promessa do SPBM: montar a rede uma vez, provisionar na borda e não mexer mais no core.
