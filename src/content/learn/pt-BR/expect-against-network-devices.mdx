[Scripts Expect, lidos devagar](/learn/expect-scripts-explained) passou as frases do manual expect(1) uma a uma contra um programa comum. Um equipamento de rede acrescenta cinco coisas que o manual não tem como saber: um prompt que traz o nome do host e muda com o modo, um pager que para a saída longa até alguém apertar uma tecla, um passo de privilégio, perguntas que querem uma tecla só, e uma tecla de retorno definida pela própria linha de comando do equipamento. Este artigo trata delas nessa ordem para as cinco linhas de comando que o site ensina: Cisco IOS como referência comum, o tmsh do F5 BIG-IP, o Fortinet FortiOS, e o Switch Engine (EXOS) e o Fabric Engine (VOSS) da Extreme Networks. Todo comando vem da documentação do próprio fabricante, lida em 27 de outubro de 2026, e todo comportamento do Expect afirmado aqui também foi executado com o expect 5.45.4 real contra um pequeno equipamento falso escrito para isso.

Para o Fabric Engine, a 9.4, cuja 9.4.1.0 é a Maintenance Release recomendada pela Extreme desde 15 de julho de 2026. ## Prompts: ancorados no fim do que chegou

Todo prompt da tabela termina em `>` ou `#`, e é por isso que um padrão de um caractere falha: contra o equipamento falso, cujo banner diz "Authorised access only #", `expect "#"` casou com essa linha do banner antes de existir qualquer prompt. O manual dá o remédio. Os padrões não são ancorados, `$` marca o fim, e como "expect is not line oriented, these characters match the beginning and end of the data (as opposed to lines) currently in the expect matching buffer". O prompt do equipamento é a única linha que não é seguida de quebra de linha, porque o equipamento está esperando entrada; uma linha de banner, com quantos `#` tiver, termina em CR LF. Então um padrão para uma linha que termina no caractere do prompt bem no fim dos dados espera o prompt de verdade:

```tcl
expect {
    -re {(?:^|[\r\n])[^\r\n#>]+[>#] ?$} { }
    timeout { send_user "sem prompt\n"; exit 1 }
}
```

Leia da direita para a esquerda: um espaço opcional, depois `>` ou `#`, no fim do buffer; antes deles, um nome de host sem quebra de linha, `#` ou `>`; antes disso, uma quebra de linha ou o começo do buffer. O começo importa. Quando o casamento anterior já consumiu a quebra de linha, o prompt abre o buffer, e um padrão que exige `[\r\n]` antes dele nunca casa; uma das execuções caiu exatamente nisso. As chaves mantêm o Tcl longe dos colchetes e do `$`. Em outra execução o equipamento falso parou um segundo inteiro logo depois da linha de banner com "#", e esse padrão continuou esperando o prompt.

Os prompts dos fabricantes cabem nesse formato, com variações. Cisco e Fabric Engine põem o modo entre parênteses antes do `#`, como em `Router(config-if)#` e `Switch:1(config)#`. O FortiOS mostra do mesmo jeito o escopo do comando config atual: `(admin)#` depois de `config system admin`, `(27) #` depois de `edit 27`. O prompt do Switch Engine é o sysname SNMP, um ponto e o número do comando na sessão, como em `5420F-48P-4XE.1 #`, com um asterisco na frente enquanto há mudanças não salvas; o número muda a cada comando, então um script não pode esperar o texto literal que viu da última vez. O tmsh termina com o módulo atual entre parênteses, `(tmos)#` na raiz e `(tmos.ltm.node)#` mais adentro, precedido por padrão pelo usuário, pelo host e por itens de status. A preferência de prompt `multi-line` põe o `#` sozinho na linha seguinte, e o padrão passa a ser `(?:^|[\r\n])# ?$`.

## Pagers: desligue, ou responda cada página

Um pager para a saída no fim de uma tela e espera uma tecla. A Cisco documenta o prompt `--More--` (Return mostra mais uma linha, a barra de espaço a próxima tela) e o `terminal length 0`, que define o número de linhas "for the current session" no valor que desliga as pausas. O FortiOS também pagina com `--More--` (Space continua, q interrompe), mas o seu ajuste é configuração: `config system console`, `set output standard`, `end`. As dicas técnicas da Fortinet o chamam de ajuste global que outros administradores vão ver, então um script que desliga a paginação deve devolver o `set output more` antes de sair. O `disable cli paging` do Switch Engine aceita `session`, o padrão, ou `permanent`. O `terminal more disable` do Fabric Engine é um comando do User EXEC cuja referência declara o escopo de sessão para o `terminal length`, mas não diz nada sobre o escopo do `more`. O tmsh manda a saída de `list` e `show` para o `less` enquanto a opção `pager` do `cli preference` está habilitada, e acima do `display-threshold` pergunta "Display all [number] items? (y/n)"; `modify /cli preference pager disabled display-threshold 0` remove as duas coisas.

Deixado de lado, um pager vira timeout: na execução em que a paginação ficou ligada e o script esperou só o prompt, a saída parou no primeiro `--More--` e o ramo de timeout disparou depois dos três segundos inteiros. O `expect_out(buffer)` naquele momento ainda guardava o casamento anterior: o manual grava o buffer quando um padrão casa, quando chega o fim de arquivo ou quando o buffer enche, e o timeout o deixou intocado.

Onde a paginação não pode ser desligada, responda dentro do mesmo `expect` e continue:

```tcl
expect {
    -ex "--More--" { append out $expect_out(buffer); send " "; exp_continue }
    -re {(?:^|[\r\n])[^\r\n#>]+[>#] ?$} { append out $expect_out(buffer) }
    timeout { send_user "a saída parou\n"; exit 1 }
}
```

Dois detalhes vêm do manual. Cada casamento esvazia o buffer, então o texto é acumulado página a página, e chega com o prompt de paginação e os caracteres que o equipamento usa para apagá-lo ainda dentro; texto coletado assim precisa de limpeza, que é o argumento mais forte para desligar a paginação. E o `exp_continue` "resets the timeout timer", a menos que receba `-continue_timer`: contra um equipamento que levava dois segundos por página, um timeout de três segundos sobreviveu a uma listagem de seis segundos com o `exp_continue` simples, e desistiu depois de três segundos com `-continue_timer`. O Switch Engine acrescenta um primo do pager: alguns comandos `show` atualizam a tela sozinhos, e `disable cli refresh` interrompe isso. A palavra-chave tem `permanent` como padrão, então um script escreve `disable cli refresh session`.

## Privilégio: enable, contas, perfis e papéis

Só dois dos cinco têm o passo `enable`. A Cisco descreve o user EXEC (`Router>`) e o privileged EXEC (`Router#`), em que se entra com `enable`, normalmente com senha, e o prompt muda de `>` para `#`. O Fabric Engine tem os mesmos modos e diz que o `enable` pode pedir nome de usuário e senha, dependendo da configuração; os documentos lidos não imprimem essas perguntas, então nenhum padrão para elas é oferecido aqui. O Switch Engine não tem passo: uma conta com capacidades de administrador recebe o prompt `#`, e uma com capacidades de usuário, o `>`. O FortiOS também não: perfis de administrador dão acesso de leitura, de escrita ou nenhum a cada área, e uma conta com o perfil `super_admin` alcança todos os comandos. O BIG-IP dá a cada usuário um papel por partição e um shell, `tmsh`, `bash` (só o papel Administrator) ou `none`. Um script para Cisco ou Fabric Engine espera o `>`, envia `enable`, responde à pergunta de senha a partir do ambiente (veja [segredos e scripts seguros](/learn/expect-secrets-and-safe-scripts)) e espera o `#`.

## Perguntas que querem uma tecla

Aqui a resposta documentada importa mais do que o texto:

| Plataforma | Comando | Pergunta como documentada | Resposta documentada |
| --- | --- | --- | --- |
| Cisco IOS | `reload` | `Proceed with reload? [confirm]` | Enter confirma, n cancela |
| FortiOS | `execute restore image tftp ...` | `Do you want to continue? (y/n)` | digite y |
| Switch Engine | `save configuration` | `Do you want to save configuration to primary.cfg and overwrite it? (y/N)` | y salva, n cancela |
| Switch Engine | `reboot` | `(y - save and reboot, n - reboot without save, <cr> - cancel command)` | um retorno sozinho cancela |
| Fabric Engine | `reset -in 45` | `Are you sure you want to perform a delayed reset? (y/n) ?` | y |
| tmsh do BIG-IP | `list` acima do limite | `Display all [number] items? (y/n)` | y |

Os colchetes de `[confirm]` são uma substituição de comando do Tcl e uma classe de caracteres do glob, então o padrão é `-ex {[confirm]}` ou uma expressão regular entre chaves e escapada. Uma pergunta de uma tecla leva uma tecla: nas execuções, `y\r` enviado a uma pergunta `(y/n)` deixou o retorno para trás como uma linha de comando vazia, e o equipamento a respondeu com um segundo prompt. Quando os dois prompts chegaram separados, o `expect` seguinte encontrou o extra primeiro; quando chegaram juntos, dividiram uma linha, `lab-sw1#lab-sw1#`, que o padrão ancorado, por não admitir `#` no meio da linha, nunca casou. E o mesmo retorno significa coisas opostas: num `[confirm]` da Cisco ele concorda, num reboot do Switch Engine ele cancela. Várias plataformas deixam o script evitar a pergunta: o `reset -y` do Fabric Engine, o `display-threshold 0` do tmsh e, a partir do shell do sistema, o `tmsh -q`, que "prevents tmsh from responding to user actions with questions". O `disable cli prompting` do Switch Engine faz todo prompt da sessão "automatically continue with the default answer", que é o padrão da própria pergunta e não necessariamente sim.

## A tecla de retorno, o terminal e o eco

O manual representa o caractere de retorno como `\r`, e os fabricantes dizem o mesmo com as próprias palavras: a Cisco manda apertar a tecla Return ou Enter, a Fortinet manda apertar Enter depois do nome da conta e da senha, e as duas linhas de comando da Extreme mostram `<cr>` na ajuda de comandos, que o guia da Extreme explica como "Carriage Return/Enter Key". `\r` é essa tecla.

Se `\n` também funcionaria depende de quem lê o terminal. O `spawn` dá ao programa um pseudoterminal "initialized the same way as the user's tty" e depois deixado "sane"; nas execuções isso significou `icrnl` e `onlcr` ligados. O POSIX diz que, com ICRNL ligado, "a received CR character shall be translated into an NL character", então um programa que lê linhas recebe um newline de qualquer forma, e na execução tanto `show version\r` quanto `show version\n` chegaram ao equipamento falso como LF e os dois rodaram. Linhas de comando que respondem a um `?` ou a um Tab assim que ele é digitado, como o FortiOS e o tmsh documentam, estão lendo teclas, não linhas. Uma linha de comando falsa em modo raw recebeu exatamente o byte enviado, 0x0D para `\r` e 0x0A para `\n`; se um dado equipamento trata um LF sozinho como Enter é algo que nenhum destes documentos promete. Envie `\r`.

O mesmo terminal molda o que volta. Com ONLCR ligado, "the NL character shall be transmitted as the CR-NL character pair", então toda linha de saída termina em `\r\n`, e o comando que o equipamento ecoa faz parte do buffer: depois de `show version`, o `expect_out(buffer)` começava com `show version\r\n`, depois trazia a resposta, depois o próximo prompt. Padrões para fim de linha nomeiam `[\r\n]`, e um script que guarda a saída descarta a primeira linha, o eco, e a última, o prompt.

## Consoles lentos e respostas longas

A Fortinet documenta o seu console a 9600 bits por segundo, 8 bits de dados, sem paridade, um bit de parada; o console do Fabric Engine roda a 115200. A 9600 uma listagem longa leva segundos, e o timeout conta a partir do início do `expect`, não do último byte recebido. Numa execução com o equipamento falso limitado a 9600 bits por segundo, um único `expect` pelo prompt final deu timeout enquanto o texto ainda chegava, e um `expect` que casava cada linha e chamava `exp_continue` leu as cem linhas em cerca de 4,5 segundos sob um timeout de dois segundos. Dimensione o timeout pela resposta mais lenta, ou deixe um casamento por linha ou por página manter o timer vivo ([timeouts, eof e loops](/learn/expect-timeouts-eof-and-loops) tem o resto).

Mais dois ajustes pertencem às respostas longas. O `match_max` limita o buffer: o manual diz que mais de 2000 bytes "can force earlier bytes to be forgotten", e em cinco execuções de 400 linhas o buffer no prompt final tinha perdido as primeiras 250 linhas ou mais com o padrão, e começava na linha 1 depois de `match_max 100000` (veja [padrões e o buffer](/learn/expect-patterns-and-the-buffer)). E um console pode perder caracteres digitados mais rápido do que ele lê. O `send -s` envia "slowly", para "avoid the common situation where a computer outtypes an input buffer that was designed for a human", no ritmo da variável `send_slow`; com `set send_slow {1 .05}` o equipamento falso recebeu um comando de doze caracteres e o seu retorno ao longo de 600 milissegundos, em vez de uma fração de um.

## Um script, do começo ao fim

Montado para a referência comum, Cisco IOS por SSH com a senha vinda do ambiente:

```tcl
#!/usr/bin/expect -f
set timeout 20
match_max 100000
set host [lindex $argv 0]
spawn ssh -o StrictHostKeyChecking=accept-new $env(DEVICE_USER)@$host
expect {
    -nocase "password:" { send -- "$env(DEVICE_PASS)\r" }
    timeout { send_user "sem prompt de senha de $host\n"; exit 1 }
    eof { send_user "conexão com $host fechada\n"; exit 1 }
}
expect {
    -re {(?:^|[\r\n])[^\r\n#>]+[>#] ?$} { }
    timeout { send_user "sem prompt de $host\n"; exit 1 }
    eof { send_user "$host fechou a sessão\n"; exit 1 }
}
send "terminal length 0\r"
expect {
    -re {(?:^|[\r\n])[^\r\n#>]+[>#] ?$} { }
    timeout { send_user "sem prompt depois do terminal length\n"; exit 1 }
    eof { send_user "$host fechou a sessão\n"; exit 1 }
}
set config ""
send "show running-config\r"
expect {
    -ex "--More--" { append config $expect_out(buffer); send " "; exp_continue }
    -re {(?:^|[\r\n])[^\r\n#>]+[>#] ?$} { append config $expect_out(buffer) }
    timeout { send_user "a saída de $host parou\n"; exit 1 }
    eof { send_user "$host fechou a sessão\n"; exit 1 }
}
send "exit\r"
expect {
    eof { }
    timeout { send_user "$host não fechou a sessão\n"; exit 1 }
}
puts $config
```

O [explicador de scripts Expect](/tools/expect-script-explainer) o lê sem nenhum erro e sem nenhum aviso; a sua única nota é o `send " "` sem retorno, que é justamente o objetivo de apertar uma tecla. Executado contra o equipamento falso por meio de um substituto do `ssh` que nunca sai da máquina, imprimiu as sessenta linhas de configuração com a paginação desligada; contra um equipamento que ignorava o `terminal length 0`, o ramo do `--More--` coletou todas as páginas, com os prompts de paginação junto. O [gerador de scripts Expect](/tools/expect-script-builder) o adapta às outras plataformas a partir de perfis construídos sobre os mesmos documentos. O próximo artigo da série, [monitores scripted do BIG-IP LTM](/learn/bigip-ltm-scripted-monitors), trata do monitor de envio e espera que o BIG-IP roda sozinho, e [o Expect e as suas alternativas](/learn/expect-and-its-alternatives) pergunta quando a API do equipamento é a ferramenta melhor.
