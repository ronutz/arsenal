## De quem é o bug, e o que ele faz

É tentador chamar isso de "o bug da AMI que deixa pacotes ICMP sobrescreverem a BIOS": a primeira correção pública veio de um engenheiro da AMI, e "BIOS" ainda é como a maioria das pessoas chama o firmware de servidor. Depois de ler os documentos primários, das palavras dessa frase eu só manteria "ICMP" e "bug".

O código não é da AMI. Ele está no EDK II, a implementação open source da Unified Extensible Firmware Interface (UEFI) mantida pelo projeto TianoCore, que também é a CVE Numbering Authority (CNA, a autoridade que numera CVEs, Common Vulnerabilities and Exposures) que publicou a CVE-2026-97631 em 22 de outubro de 2026. A AMI entrega firmware construído sobre esse código, como, segundo a imprensa, a maioria das empresas que fazem firmware para servidores, e as distribuições Linux também, quando empacotam esse código para máquinas virtuais. O papel da AMI nessa história é outro e, acho, mais interessante: a primeira correção pública veio de um engenheiro cujo perfil no GitHub cita a AMI e cujo commit tem sign-off com um endereço da AMI, meses antes da divulgação coordenada que, segundo a imprensa, os descobridores tinham planejado.

E nada do que o TianoCore publicou diz que a falha regrava a BIOS, a Basic Input/Output System, termo que o National Institute of Standards and Technology (NIST) usa na sua orientação para firmware convencional e UEFI. O que o projeto diz é pior num sentido e mais estreito em outro: código roda dentro do firmware antes de o sistema operacional carregar, antes de o Secure Boot ou o measured boot verificarem qualquer coisa, e só enquanto a máquina está dando boot pela rede. Se esse ponto de apoio vira algo que sobrevive a um reboot depende da plataforma, e eu volto a isso mais abaixo com os documentos que tratam do assunto.

O boletim do projeto é um security advisory do GitHub, o GHSA-99cj-7hg9-mp4m, no repositório do EDK II; o conteúdo dele também está reproduzido na lista oss-security, e o registro da CVE traz a descrição, a nota e os créditos do próprio TianoCore. Vale conhecer dois campos da página do boletim antes de tudo. Ele lista como afetado "EDK II master as of 2026-09-14" e, em patched versions, ainda dizia "Not patched currently" em 2 de novembro, embora a correção esteja no branch master desde 15 de outubro: nenhuma release com tag a traz ainda. Tudo o que vem a seguir sai desses documentos, do histórico de código e dos pull requests do projeto e das páginas dos próprios fabricantes e distribuições, e das especificações, pesquisas e reportagens listadas em Fontes, cada um lido em 2 de novembro de 2026.

## A falha, no nível do boletim

O resumo do boletim é uma frase só, e vale ler inteira, nas palavras do projeto: "While a machine is PXE-booting over IPv4 or IPv6, an unauthenticated network attacker who can deliver ICMP error messages to it can corrupt DXE-phase memory and execute arbitrary code before the operating system loads, before Secure Boot or measured boot has verified or measured any OS component."

O mecanismo, nos termos do boletim e com os nomes que ele usa: durante o boot pela rede, o driver PXE Base Code (Preboot Execution Environment), NetworkPkg/UefiPxeBcDxe, mantém um pedido de recepção aberto para mensagens de erro do Internet Control Message Protocol (ICMP) e copia cada uma que recebe para `Mode.IcmpError`, o campo fixo de 504 bytes da sua estrutura de contexto privada. O tratamento dos limites dessa cópia está errado tanto no handler de IPv4 quanto no de IPv6, `PxeBcIcmpErrorDpcHandle` e `PxeBcIcmp6ErrorDpcHandle`: para uma mensagem com mais de 504 bytes, o loop continua copiando bytes para o campo e avança o ponteiro de destino pelo total acumulado até ali, e não pelo tamanho do fragmento que acabou de copiar. Por isso uma mensagem grande demais escreve bytes controlados pelo atacante além do fim do campo. E, segundo o boletim, nada antes disso no caminho de recepção limita o tamanho da mensagem.

O boletim descreve dois desfechos. O primeiro é determinístico: os dados do próprio driver são corrompidos e o boot trava no erro ICMP seguinte, o que nega o provisionamento ou a recuperação da máquina. O segundo exige mais: um atacante que conhece o build de firmware do alvo consegue fazer bytes dele serem executados na fase Driver Execution Environment (DXE), em ring 0, "before any OS security control exists". Basta ao atacante entregar uma mensagem de erro ICMP unicast endereçada ao IP do cliente, "from any network distance", e a janela dura o tempo do boot PXE.

O registro da CVE classifica a falha de três formas na Common Weakness Enumeration (CWE-120, a cópia de buffer clássica sem checar tamanho; CWE-131, cálculo errado do tamanho do buffer; CWE-787, escrita fora dos limites) e dá a nota 9.5, Critical, no Common Vulnerability Scoring System (CVSS) versão 4.0, com o vetor `AV:N/AC:L/AT:P/PR:N/UI:N/VC:H/VI:H/VA:H/SC:H/SI:H/SA:H`. O `AT:P` é a parte honesta desse vetor: existe um requisito de ataque, que aqui é a máquina estar no meio de um boot PXE quando a mensagem chega.

A correção que entrou no EDK II são três commits. O principal, chamado "Fix ICMP buffer overflow in IPv4/IPv6 handlers (CVE-2026-97631)", acrescenta a checagem de limite que faltava e acerta o cálculo do offset no buffer, de modo que mensagens de erro ICMP grandes demais passam a ser truncadas com segurança quando o buffer enche. Um segundo commit zera o buffer antes de cada cópia, e um terceiro acrescenta testes unitários da cópia. É todo o conserto. Não há chave para revogar nem binário assinado para deixar de confiar, um ponto a que eu volto quando comparo este caso com eventos de firmware anteriores.

O diff mostra o conserto com os mesmos nomes. Nos dois handlers, em NetworkPkg/UefiPxeBcDxe/PxeBcSupport.c, o loop antigo somava o tamanho de cada fragmento a um total corrente e, quando o total passava do tamanho do campo, ainda copiava a quantidade excedente, e depois avançava o ponteiro de destino pelo total corrente. O loop novo copia, para cada fragmento, o menor valor entre o tamanho do fragmento e o espaço que sobra em `EFI_PXE_BASE_CODE_ICMP_ERROR`, a estrutura de 504 bytes por trás de `Mode.IcmpError`, avança pelo que copiou e para quando o campo enche. O segundo commit põe um `ZeroMem` do campo inteiro antes do loop, "so short packets do not leave stale bytes from a previous error", e os testes cobrem o empacotamento dos fragmentos e o truncamento em IPv4 e IPv6.

## Onde isso fica no boot

A descrição do próprio TianoCore para o fluxo de boot das especificações Platform Initialization (PI) tem cinco fases antes do sistema operacional. A fase Security (SEC) trata os eventos de reinício, cria uma memória temporária e serve "as the root of trust in the system". A Pre-EFI Initialization (PEI) ativa a memória permanente e passa o controle adiante. A DXE é onde acontece a maior parte da inicialização do sistema. A Boot Device Selection (BDS) aplica a política de boot e tenta as opções de boot, e a Transient System Load (TSL) é o estágio em que o loader do sistema operacional é uma aplicação EFI.

A rede mora na DXE. Quando a Quarkslab publicou as falhas PixieFail no mesmo pacote, em janeiro de 2024, ela disse isso sem rodeios: "UEFI implements a full IP stack at the DXE phase, opening the door to attacks from the local network during this early stage of the boot process." A página do TianoCore sobre o NetworkPkg lista os drivers: os drivers de interface da placa de rede (o Simple Network Protocol, SNP, e a Universal Network Driver Interface, UNDI) e a camada do Managed Network Protocol (MNP) são compartilhados pelas pilhas IPv4 e IPv6, e o driver PXE é um driver combinado que dá boot sobre as duas. A especificação UEFI descreve o boot pela rede como os protocolos que o PXE escolheu, UDP, DHCP (Dynamic Host Configuration Protocol) e TFTP (Trivial File Transfer Protocol), acessados pelo protocolo PXE Base Code, e o boot manager dá boot num dispositivo de rede pelo seu protocolo Load File, em que a imagem é materializada sem precisar de um sistema de arquivos.

## Por que o firmware escuta erros ICMP

A primeira reação que eu ouço a essa falha é a que eu mesmo teria numa turma de firewall: por que o firmware está escutando ICMP? A resposta é que ele foi feito para isso.

O ICMP é o jeito de o IP avisar que uma entrega falhou. Desde o RFC 792, de 1981, ele leva Destination Unreachable, Time Exceeded e os outros tipos de erro, e o RFC 1122, dos requisitos de host, diz que toda mensagem de erro ICMP "includes the Internet header and at least the first 8 data octets of the datagram that triggered the error", e que, quando é o caso, o erro sobe para o protocolo de transporte que mandou o pacote original. Um cliente que nunca escutasse só veria um timeout onde a rede tinha dito exatamente o que deu errado.

A especificação UEFI leva isso para o boot. O protocolo PXE Base Code guarda o último erro ICMP nos seus dados de modo, no campo `IcmpError`, ao lado de uma flag, `IcmpErrorReceived`, que "Indicates whether the IcmpError field has been updated", e as funções de DHCP, de discovery, de transferência de arquivo e de UDP devolvem um status de erro ICMP quando um pacote de erro ICMP é recebido, avisando que o pacote ficou em cache. A especificação pede que o firmware guarde o último erro ICMP para que quem está conduzindo o boot saiba por que uma transferência falhou. Escutar era a funcionalidade. A cópia para esse cache era o bug.

É essa parte que eu levaria para a sala de aula. Toda turma de firewall tem a conversa do ICMP, bloqueia e quebra o path MTU discovery (maximum transmission unit), libera e aceita o risco, e quase ninguém na sala pensou no firmware como um ponto que recebe ICMP. Ele é, durante cada boot pela rede, e num data center que reprovisiona máquinas o dia inteiro essas janelas se somam.

## Por que importa: antes de toda verificação em que a gente confia

O Secure Boot cuida do que é carregado. O capítulo de assinatura de drivers da especificação UEFI trata de executáveis que "may be delivered via a un-secured transport layer (such as a network)" e permite que a plataforma autentique a origem ou a integridade deles antes de rodarem. Na descrição que a Quarkslab faz de um boot PXE, o programa de bootstrap baixado pela rede é "downloaded, verified (in the case of Secure Boot), and executed". Este estouro acontece antes do "verified": durante o download, dentro dos drivers do próprio firmware, que o Secure Boot não tem motivo para checar porque eles são o firmware.

O measured boot tem o mesmo ponto cego, pelo mesmo motivo. HD Moore, citado pela Ars Technica, pôs a consequência em termos operacionais: um atacante poderia "hijack program flow at a point where the boot process still has access to sensitive components, like the endpoint's TPM", o Trusted Platform Module, o que "could be used to break disk encryption for cases where an attacker has short-term network access". Essa é a avaliação dele, não do TianoCore, e para mim é a frase mais útil escrita sobre essa falha até agora, porque ela nomeia o ativo em risco em vez da nota.

Agora a BIOS. Nenhum documento primário que eu li diz que a falha escreve na flash, e a cobertura que foi mais longe nesse ponto, a da Ars Technica, diz que os payloads não têm persistência sozinhos, mas abrem caminho para o atacante instalar outros payloads que têm. A página de fluxo de boot do TianoCore observa que o núcleo da DXE é código de boot services, então "no code from the Dxe Core itself is allowed to persist into the OS runtime environment", embora os serviços dos drivers de runtime persistam. Sobreviver a um reboot exige escrever no armazenamento do firmware, que é justamente o que as proteções de flash da plataforma existem para impedir. A análise do BlackLotus que a ESET publicou em 2023 descreve as defesas que um implante desses precisa vencer, "the multilevel SPI flash defenses" (SPI é a Serial Peripheral Interface) e as proteções "provided by hardware (like Intel Boot Guard)", e a SP 800-147 do NIST explica por que isso importa: uma modificação maliciosa da BIOS pode significar uma negação de serviço permanente ou uma presença persistente de malware. Então a minha avaliação, marcada como tal: "sobrescrever partes da BIOS" é um segundo estágio possível numa plataforma com proteções de flash fracas ou mal configuradas, não algo que o boletim afirme.

Há mais dois lugares em que a janela se abre além de "uma máquina que por acaso dá boot pela rede". O primeiro é o gerenciamento remoto. O Redfish, a interface de gerenciamento padronizada pela Distributed Management Task Force (DMTF), descreve um servidor no schema ComputerSystem, e esse schema lista `Pxe`, "Boot from the Pre-boot eXecution Environment (PXE)", entre as origens de boot que um cliente de gerenciamento pode escolher. Minha avaliação: quem controla o gerenciamento out-of-band de um servidor, em geral a baseboard management controller (BMC), consegue abrir a janela do PXE quando quiser, então o acesso à BMC entra no modelo de ameaça desta falha. O segundo são as máquinas virtuais. O Open Virtual Machine Firmware (OVMF), o build do EDK II para máquinas virtuais como as do QEMU, "provides a UEFI network stack by default", e o posicionamento da Red Hat para esta CVE diz que, nos produtos dela, o EDK2 fornece o firmware UEFI de guests virtualizados e que guests que dão boot só a partir do armazenamento local não ficam expostos.

## Quem é afetado e como descobrir

O registro da CVE lista o TianoCore EDK2, pacote NetworkPkg, como afetado em todas as versões até a `edk2-stable202608`, inclusive, que é a tag estável mais recente. Quais produtos carregam esse código é uma pergunta de cadeia de suprimentos, e as respostas até agora vêm de várias direções.

A página de produto da própria AMI diz que o firmware Aptio V "Integrates the latest UEFI, EDKII, ACPI and PI specifications" e que o Aptio Community Edition é "Based on EDK II". A Ars Technica relata que praticamente todos os fabricantes independentes de BIOS, citando AMI, Insyde e Phoenix, usam o código de referência extensamente, e que o fork Project Mu, da Microsoft, também carregava o componente vulnerável; os branches de release do próprio Project Mu confirmam esse último ponto, porque receberam a correção em 22 e 23 de outubro (UTC). A Intel disse à Ars que nenhum dos seus "commercial products currently under security support" é sabidamente afetado e que ela "does not include the affected EDK2 functionality in its reference code, though it may be integrated by an OEM board vendor or system manufacturer". A Arm disse à Ars que a CVE "is not directly applicable to Arm's product portfolio". A Ars observa que o código de firmware que as duas empresas disponibilizam se apoia fortemente no EDK II. A Thomas-Krenn, uma montadora alemã de servidores, escreve que, pelo conhecimento atual, todo sistema de todo fabricante comum é afetado, mas que sistemas que dão boot por disco, ou com o boot PXE desligado, não são, e que o atacante precisa conhecer ou adivinhar vários endereços para cada versão e configuração.

Então a pergunta para cada máquina tem três partes: o firmware dela deriva do EDK II com esse driver, o boot PXE está ligado ou alcançável pela ordem de boot ou pela BMC, e um atacante consegue fazer um erro ICMP chegar até ela durante o boot. Responder isso exige um inventário que a maioria das organizações não tem num lugar só: fabricante e versão do firmware por modelo, a configuração de PXE por máquina, quais hosts dão boot pela rede por padrão e quais máquinas virtuais usam firmware EDK II com uma placa de rede virtual em primeiro lugar na ordem de boot.

A última linha é a entrada que a Cybersecurity and Infrastructure Security Agency (CISA) acrescentou ao registro da CVE dentro da sua Stakeholder-Specific Vulnerability Categorization (SSVC). A divergência sobre o attack vector é a interessante. O boletim do TianoCore diz que a mensagem pode vir "from any network distance"; Red Hat e SUSE pontuaram como ataque de rede adjacente. As duas leituras se defendem: um atacante roteado precisa do endereço do cliente enquanto ele dá boot pela rede, o que é muito mais fácil no segmento de provisionamento do que de fora. As classificações mais baixas de SUSE, Ubuntu e Debian fazem sentido para o que eles entregam, sobretudo firmware de máquina virtual; a Red Hat, que manteve Critical, diz que a exposição se limita ao boot pela rede. Para um parque de servidores físicos que reprovisiona por PXE, eu leria o número do TianoCore.

O registro da CVE credita dois descobridores, Alex Matrosov, listado na Anthropic, e Dan Holmes-Mitra, listado no Google, e o boletim agradece aos dois "for finding this issue and providing the recommended fix".

A Ars Technica relata que os descobridores tinham combinado manter a falha em sigilo até uma divulgação coordenada marcada para janeiro, e que um pull request publicado pela AMI no mês passado "detailed the vulnerability and included a code fix"; a Thomas-Krenn escreve que a falha foi publicada sem querer e que só deveria vir a público no começo de 2027. O repositório confirma isso. O pull request 13200 foi aberto em público em 28 de setembro, às 14:14 UTC, quatro dias depois de o TianoCore reservar o número, por um engenheiro cujo perfil no GitHub cita a AMI; o título traz a CVE-2026-97631 e o commit tem sign-off com um endereço da AMI. Um revisor achou a mudança correta e pediu testes unitários, um steward do TianoCore (um dos maintainers de todo o projeto que o Maintainers.txt lista) ofereceu uma refatoração com os testes, e um terceiro revisor pediu alterações. Como não veio resposta, esse steward abriu o pull request 13302 em 14 de outubro com uma versão revisada e os testes, mantendo o autor e o sign-off originais, fechou o 13200 como duplicado, e o 13302 entrou no dia seguinte.

O TianoCore disse, numa linha, como isso aconteceu. Respondendo a uma pergunta no pull request que entrou, a conta que publicou o boletim em nome do TianoCore escreveu que nesse caso o "embargo was violated due to a mistake", e que foi por isso que o pull request foi criado em aberto. De quem foi o erro, e se o engenheiro achou a falha por conta própria, ele não diz. A leitura do Matrosov, conforme a ISMG relatou os posts dele no X, aponta para a segunda hipótese e vai além: "AI-assisted research is killing embargoes. When everyone's using the same tools and the same intelligence to find vulnerabilities, you're not the only one finding that bug." Sobre os ciclos de correção de firmware que levavam mais de um ano, ele disse que essa mentalidade é "a leftover from outdated processes and slow testing and bring-up environments", e acrescentou que "Product security and PSIRT need a serious rethink", PSIRT sendo o product security incident response team. São opiniões dele, e eu as coloco ao lado de dois documentos.

O primeiro é a página de processo do próprio TianoCore. Ela pede que os membros do grupo de segurança "only share details of unmitigated issues within the draft GHSA", avisa que compartilhar "on un-encrypted email or open source prior to embargo expiry may lead to removal" do grupo e, na mesma página, pede que quem reporta "Use the capabilities of AI models to generate proof-of-concept code and suggested patches". O projeto agora pede correções geradas por máquina nos reports e depende da discrição humana para mantê-las privadas. O segundo é a carta do chief information security officer da AMI na página de boletins da empresa, que pede às empresas de pesquisa de segurança que sigam as boas práticas de PSIRT porque "Coordinating findings with supply chain vendors before public announcements is crucial". Concordo com ela. O commit de setembro lembra que a mesma disciplina tem de chegar a todo engenheiro que consegue abrir um pull request num repositório público, porque hoje esse é o canal de divulgação mais rápido que existe.

A mesma conversa no pull request traz uma lição mais dura. A pergunta que gerou a resposta do TianoCore veio de um pesquisador que tinha aberto vários reports pelo processo privado de boletins, alguns com patch, e disse que estavam sem resposta havia meses, alguns já perto de um ano, enquanto problemas levantados em pull requests públicos, como este, eram revisados e corrigidos rápido. O TianoCore respondeu que os boletins privados continuam sendo o caminho para reportar, que está "currently facing a backlog of reports" e que vai priorizar os reports que chegam com uma correção pronta para revisão. É uma resposta honesta, e ela descreve um problema de incentivo, não de disciplina: quando o canal privado é lento e o público é rápido, manter uma correção privada até o boletim sair pede a quem reporta, e aos engenheiros dos fabricantes, que ajam contra o próprio interesse em ver o bug corrigido. Embargo se sustenta quando o canal privado funciona.

O contraste com 2023 é a lição mais clara. A linha do tempo que a Quarkslab publicou para as PixieFail mostra os fabricantes pedindo mais prazo: um embargo de 90 dias estendido para 120 a pedido da Insyde, Microsoft e Dell pedindo maio de 2024 e um paper do UEFI Forum citado a favor de um embargo de 300 dias. A divulgação saiu em 16 de janeiro de 2024, cerca de cinco meses e meio depois do report. Em 2026, a janela planejada ia, segundo a imprensa, até janeiro, e um patch ficou público quatro dias depois da reserva do número, duas semanas depois do snapshot do master que o boletim lista como afetado. Minha leitura: seja qual for a opinião sobre a duração de embargos, um embargo longo agora é uma aposta de que ninguém mais, com ferramentas parecidas, está olhando o mesmo código.

Quanto aos "dezesseis anos": esse é o número da imprensa, e o histórico de código bate com ele. O NetworkPkg entrou no repositório do EDK II em 1º de novembro de 2010. A Ars Technica acrescenta que as campanhas de fuzzing iniciadas depois das PixieFail parecem não ter achado esta falha.

## O que fazer enquanto o firmware novo não chega

Se eu tivesse servidores rodando em algum lugar, a lista seria esta, nesta ordem:

1. **Achar as máquinas que dão boot pela rede, e as que podem ser levadas a isso.** Configuração do firmware, ordem de boot, ferramentas de provisionamento e as BMCs que conseguem marcar um boot PXE avulso. Somar as máquinas virtuais com firmware EDK II e placa de rede como primeiro dispositivo de boot.
2. **Desligar o PXE onde ele não é usado.** Foi o primeiro workaround que o CERT Coordination Center (CERT/CC) deu para as PixieFail em 2024 ("Disable PXE boot if it is not used or supported"), e ele vale aqui sem mudança. Onde o setup do firmware oferece uma chave para a pilha de rede UEFI inteira, desligar também essa chave tira a pilha do boot.
3. **Isolar a rede de provisionamento.** O segundo workaround do CERT/CC era o isolamento de rede, para que o ambiente de pré-boot só seja alcançável a partir de uma rede protegida. Uma VLAN (rede local virtual) dedicada a builds, com os servidores de boot nela e mais nada, encolhe o "any network distance" para quem já está lá dentro.
4. **Avaliar filtrar mensagens de erro ICMP na borda desse segmento, de propósito.** Avaliação minha, não de fabricante: num segmento de provisionamento cujos servidores de boot ficam no mesmo link, há pouco motivo para deixar erros ICMP vindos de além do roteador chegarem às máquinas em boot. Faça isso como exceção delimitada e documentada, porque o RFC 4890 põe erros ICMPv6 como o Packet Too Big entre o tráfego que "must not be dropped" na comunicação normal, e uma regra genérica em outros lugares vai quebrar coisas.
5. **Tratar o HTTPS Boot como direção, não como correção.** O CERT/CC disse à cadeia de suprimentos que considerasse "modern network boot environments that employ secure protocols such as UEFI HTTPS Boot". No EDK II ele é um driver diferente (HttpBootDxe) do driver PXE citado neste boletim, o que tira o código vulnerável desse caminho de boot. Mas a própria página do TianoCore diz que o HTTPS boot dele só suporta "server authentication with an unauthenticated client", e ele continua rodando sobre a mesma pilha de rede do firmware, que recebeu outras correções nas últimas semanas.
6. **Perguntar ao fabricante por escrito, com o número da CVE e os modelos.** Para servidores, pedir ao fabricante da placa ou do sistema a versão de BIOS corrigida e a data; para máquinas virtuais, acompanhar os pacotes edk2 e ovmf nos trackers acima e desligar os guests e ligá-los de novo depois de atualizar, porque a imagem do firmware é carregada quando a máquina virtual sobe, e um reboot de dentro do guest mantém a imagem com que ela subiu. Não espere o scanner apontar: o NVD lista o registro como "Deferred", sem prioridade para enriquecimento, então ferramentas que dependem dos dados de produto do NVD podem nunca sinalizá-lo, e os dados para trabalhar são a faixa afetada do TianoCore e os boletins dos fabricantes.
7. **Manter o Secure Boot e o measured boot ligados, sem contar com eles para isto.** Eles continuam protegendo os estágios posteriores do boot. Depois da atualização, conferir a integridade do firmware do jeito que a NIST SP 800-193 enquadra o assunto, proteção, detecção e recuperação, em vez de presumir.
8. **Decidir sobre as máquinas que ninguém vai corrigir.** Hardware fora do suporte do fabricante não vai ganhar essa BIOS. HD Moore disse à Ars que espera um bug "forever" nos sistemas sem suporte. Para eles, PXE desligado e isolamento não são paliativo, são o plano, e a data de troca tem de entrar num orçamento.

## Um pacote, os servidores de todo mundo

A parte estratégica dessa história está num arquivo de texto. O Maintainers.txt do EDK II define o package maintainer como a pessoa "Responsible for reviewing and pushing package changes to source control", e o reviewer como alguém que ajuda, mas não tem acesso de push. No dia em que esta falha foi corrigida, e até 30 de outubro, o arquivo não listava nenhum maintainer para o NetworkPkg, só dois reviewers. Um maintainer foi acrescentado naquele dia. O mesmo arquivo ainda lista o NetworkPkg, junto com o SecurityPkg, em "Maintainers Wanted". Essa é a pilha de rede que, pelos relatos de fabricantes e da imprensa acima, está no firmware da maioria dos servidores, e as pessoas que cuidam dela cabem num parágrafo curto de um arquivo de texto.

A segunda parte é como as obrigações descem pela cadeia. A página de processo do TianoCore diz que, desde que o projeto virou CNA, emitir CVE é um "Must" para conteúdo do TianoCore e um "May" para derivados, abertos ou fechados. O upstream open source agora é obrigado a divulgar; o firmware que de fato vai nos servidores só se obriga pela prática de cada fabricante. A carta do CISO da AMI faz a mesma observação pelo outro lado: se os fornecedores de código open source seguirem protocolos mínimos como as CVEs, "the risk of a 'Forever Vulnerability' significantly diminishes". O TianoCore emitiu a CVE, o que deixa o resto da frase para quem está mais abaixo na cadeia.

A terceira é atenção, e ela é uma faca de dois gumes. Na quinzena seguinte à correção, o histórico do EDK II mostra uma série de outras correções de limite e de validação entrando no mesmo pacote, a maioria escrita entre junho e agosto: no código de neighbor discovery do IPv6, nos registros de configuração IPv4 e IPv6 guardados e no driver de resolução de endereços. É assim que um código fica quando uma fila de correções começa a andar, e também é assim que ele fica para qualquer outra pessoa que esteja lendo.

Escrevi semana passada sobre [o PHP2Shell e a camada que ninguém acha que é sua](/blog/php2shell-and-the-layer-nobody-owns). O firmware é o caso extremo dessa camada. O time de servidores cuida do sistema operacional, o time de facilities cuida do rack, e o firmware pertence à agenda de releases de um fabricante, à imagem testada de um integrador e a uma atualização de BIOS que precisa de janela de manutenção. Uma cultura de patch construída em torno de sistemas operacionais não chega até ele, a menos que alguém decida que deve chegar.

## Como se compara com eventos anteriores de pré-boot

| Evento | Onde | O que exigia | O que a correção exigiu |
| --- | --- | --- | --- |
| BlackLotus, analisado pela ESET em 1º de março de 2023 | Um bootkit que abusa da CVE-2022-21894 em componentes de boot do Windows | Direitos de administrador no sistema em execução para instalar; visto em ataques reais | Revogação, porque os binários assinados vulneráveis não podiam simplesmente deixar de ser confiáveis de uma vez; a ESET ainda não os encontrou na lista de revogação na época |
| LogoFAIL, CERT/CC VU#811862, 6 de dezembro de 2023 | Parsers de imagem que exibem o logotipo de boot, no firmware de vários fabricantes | "local privileged access", ou uma atualização de firmware manipulada | Atualizações de firmware de cada fabricante; os grandes fabricantes de BIOS obtiveram CVEs próprias |
| PixieFail, CERT/CC VU#132380, 16 de janeiro de 2024 | Nove falhas no NetworkPkg do EDK II, a maioria no caminho IPv6 | Um atacante na rede local, em alguns casos remoto, durante o boot PXE | Atualizações de firmware descendo a cadeia, depois de um embargo de cinco meses e meio |
| CVE-2026-97631, 22 de outubro de 2026 | Uma cópia no driver PXE do EDK II, IPv4 e IPv6 | Mensagens de erro ICMP de qualquer distância de rede, durante o boot PXE | Uma atualização de firmware; nenhuma revogação |

As PixieFail são o antepassado direto: mesmo pacote, mesma fase, mesma condição de um boot PXE. O LogoFAIL lembra que os parsers dentro do firmware são onde esses bugs moram, e que a cadeia de suprimentos responde em uma dúzia de vozes. O BlackLotus é o contraste que faz este caso parecer administrável: Jesse Michael, da Eclypsium, disse à Ars que, ao contrário dos bypasses de Secure Boot em boot loaders, esta falha "can be fixed with a basic code fix", sem revogações nem atualização de bancos de chaves. Isso é verdade, e também é a pegadinha. Uma correção de código em firmware só chega a uma máquina por uma atualização de BIOS que alguém precisa gerar, testar, distribuir, agendar e aplicar, um modelo de cada vez.

## O que eu tiro disso

Três coisas, e nenhuma delas é sobre ICMP.

A primeira é o nome. Chamar isso de "o bug da AMI" mandaria o leitor para o fornecedor errado e para a correção errada. O código é do TianoCore, está, pelos relatos acima, na maior parte do firmware de servidores, e a pergunta a fazer não é "a gente usa AMI?", e sim "quais das nossas máquinas dão boot pela rede, e de quem é o firmware que elas rodam?".

A segunda é o tempo. A discussão de 2023 era sobre quanto tempo um embargo deveria durar. A lição de 2026 é que essa duração já não é definida por quem a combinou: é definida pela próxima pessoa, com o próximo conjunto de ferramentas, que acha o mesmo bug e pode não saber que existe um relógio correndo, ou não estar preso a ele.

A terceira é a camada. Uma correção entrou no upstream em outubro; a maioria dos servidores físicos vai recebê-la quando os fabricantes entregarem uma BIOS e os donos agendarem o reboot, e alguns nunca vão receber. As máquinas que decidem a exposição de uma organização são as que ninguém olha desde a instalação. Para elas, os controles que funcionam hoje são os antigos, os mesmos que trinta anos de redes continuam me ensinando: desligar o que não se usa, manter a rede que monta máquinas longe de todo o resto e saber o que se tem.
