## What happened

On 10 November 2026, Fortinet's Product Security Incident Response Team (PSIRT) published four advisories rated Critical on its FortiGuard site. Each one describes a flaw that, in Fortinet's words, can be used by an attacker who has not logged in, and each one lives in the same two products: FortiManager, the central management platform for FortiGate firewalls, and FortiAnalyzer, the log collection and analysis platform that sits next to it. One of them also reaches FortiManager Cloud, FortiAnalyzer Cloud, FortiAnalyzer-BigData and FortiSASE-Sovereign, Fortinet's sovereign edition of its secure access service edge offering.

All four advisories carry the same discovery note: the flaws were found internally by Fortinet's Product Security team "with the use of Frontier AI model: Claude Mythos", and one of them, FG-IR-26-276, also thanks an external researcher from the XOR team at JP Morgan Chase who reported it under responsible disclosure. All four mark the "Known Exploited" field as "No". None publishes indicators of compromise. Only one, FG-IR-26-219, offers a workaround.

The Brazilian outlet CISO Advisor covered the advisories on 11 November 2026 under the headline "Fortinet: falhas críticas permitem execução de código sem login", critical flaws that allow code execution without login, and that summary is the reason they deserve attention: the products affected are the ones that hold the keys to everything else ([CISO Advisor, 11 November 2026](https://www.cisoadvisor.com.br/fortinet-falhas-criticas-permitem-execucao-sem-login/)).

Everything below comes from the four FortiGuard advisory pages and the machine-readable Common Security Advisory Framework (CSAF) files Fortinet attaches to them, from the Common Vulnerabilities and Exposures (CVE) records Fortinet published as CVE Numbering Authority (CNA), from the National Vulnerability Database (NVD), from the Known Exploited Vulnerabilities (KEV) catalogue of the Cybersecurity and Infrastructure Security Agency (CISA), and from Fortinet's own product documentation, each read on 12 November 2026 at the São Paulo time given in the status table and the Sources, and read again on 15 November 2026.

Update, 15 November 2026: two things change the picture, and one does not. First, the fixes were not new on 10 November. In a post of 21 October 2026, updated on 10 November, Fortinet's chief information security officer (CISO), Carl Windsor, wrote that fixes from the company's "frontier AI-assisted security testing program" were available for FortiMail and FortiAuthenticator on 21 October and scheduled for FortiOS, FortiManager and FortiAnalyzer on 22 October, with the public advisories to follow on the November Patch Tuesday; the fixed versions he listed for FortiManager and FortiAnalyzer are 8.0.2, 7.6.8, 7.4.12 and 7.2.13 ([Fortinet, 21 October 2026, updated 10 November](https://www.fortinet.com/blog/ciso-collective/fortinet-releases-security-hardening-release-for-multiple-products)). Set beside the advisory tables, that means a FortiManager or FortiAnalyzer upgraded to those October builds on the 7.6, 7.4 or 7.2 branch was already on the target versions of every advisory here that applies to it, and on 8.0 it still waits for 8.0.3 for FG-IR-26-219; CISO Advisor's report makes the same point, that an October build does not settle every November finding on every branch ([CISO Advisor, 11 November 2026](https://www.cisoadvisor.com.br/fortinet-falhas-criticas-permitem-execucao-sem-login/)). It also means the fixes were public for 19 to 20 days before the advisories said what they fixed. Second, the same batch of 10 November carried more than these four: three critical FortiOS advisories, for high availability, the Border Gateway Protocol (BGP) and Open Shortest Path First (OSPF), covered in [a companion post](/blog/fortios-november-advisories-ha-bgp-ospf), and a fifth critical advisory for FortiManager and FortiAnalyzer, FG-IR-26-244, which needs an administrator login (see the upgrade paths below). What has not changed: re-read on 15 November, the four advisories are still at their first version with "Known Exploited" set to "No", 8.0.3 and FortiAnalyzer-BigData 7.6.3 are still "upcoming", CVE-2026-126260 still has no record, NVD has analysed none of the four, and none is in the KEV catalogue; CISA has added its entries to two more of the CVE records.

The Common Vulnerability Scoring System (CVSS) scores are the ones FortiGuard displays; the Common Weakness Enumeration (CWE) identifiers are Fortinet's own. Two protocol names recur. FGFM is the FortiGate to FortiManager protocol, the channel a FortiGate uses to register with its manager and receive configuration, which Fortinet's port documentation lists on TCP/541. OFTP is the protocol FortiGate units and other Fortinet devices use to send logs, which the same documentation lists on TCP/514 for both FortiManager and FortiAnalyzer.

## The four flaws, one at a time

### FG-IR-26-219: JSON injection in the JSON-RPC API

Fortinet's summary: an improper encoding or escaping of output vulnerability "in FortiSASE-Sovereign, FortiAnalyzer, FortiManager, FortiAnalyzer Cloud, FortiManager Cloud and FortiAnalyzer Big-Data GUI may allow an unauthenticated attacker to execute unauthorized code or commands via a specially crafted HTTP request". The CSAF file titles it "Unauthenticated RCE in multiple products", remote code execution (RCE) being the outcome. The advisory's "Impact" field, oddly, reads "Denial of service", and the CVE record carries the same phrase next to CWE-116; the summary and the CSAF title describe code execution, and those are the words to plan by.

The condition that matters most is in the workaround: "The vulnerability exists only when the JSON API is enabled (Disabled by default)". The JSON API is the JSON remote procedure call (JSON-RPC) interface that automation tools and integrations use; FortiManager's port documentation lists it on TCP/443 and TCP/80. It is switched on per administrator profile, and Fortinet gives the way to switch it off:

```
config system admin profile
    edit <profile name>
        set rpc-permit none
end
```

### FG-IR-26-274: server-side request forgery through OFTP

Fortinet's summary: an SSRF vulnerability "in FortiAnalyzer, FortiManager with FortiAnalyzer features, may allow an attacker that can reach the oftp port to execute requests server side via crafted OFTP packets". An SSRF makes the server send requests on the attacker's behalf, which matters most when the server can reach places the attacker cannot, such as its own local services or an internal network. The advisory's Impact field reads "Execute unauthorized code or commands".

## Why "no login needed" matters on these two products

An unauthenticated flaw on any internet-facing service is serious. On these two it is worse, for reasons that come from what the products are for.

FortiManager holds the configuration of every FortiGate it manages: policies, objects, VPN (virtual private network) settings, administrator accounts, and the credentials and pre-shared keys that make all of that work. It also pushes configuration down. A compromise of the manager is, in operational terms, a compromise of the estate it manages, which is exactly what Fortinet's 2024 description of the FGFM exploitation records: files with "the IPs, credentials and configurations of the managed devices" taken by script.

FortiAnalyzer holds the logs. That makes it the place an incident responder looks first, and therefore a place an intruder has every reason to reach: logs reveal the network, and logs can be altered.

Both listen where they must. FGFM on TCP/541 has to be reachable by every FortiGate the manager controls, and for branch offices and remote sites that often means reachable across the internet. OFTP on TCP/514 has to be reachable by every device that sends logs. The authentication these products enforce sits on the administrative interfaces; the device channels authenticate devices, through registration, serial numbers and certificates. Three of the four flaws are on those device channels, before the device has proved anything. The fourth is on the JSON API, before the administrator has.

Assessment, labelled as such: a management or logging platform is an edge device whenever its device-facing ports are reachable from outside, even if no human ever logs in to it from there. The inventory question is not "is the administrative interface exposed" but "which of the device ports are".

The advisories give target versions, not the intermediate steps between a running build and the target.

## How to check exposure

Fortinet's advisories do not publish a check, so the steps below use the commands and ports Fortinet documents elsewhere, each with its source.

**1. Which version is running.** Record the firmware version of every unit, physical, virtual and high-availability peer alike, and compare it with the tables above.

**2. Is FortiManager running FortiAnalyzer features.** Two of the advisories, 274 and 276, apply to FortiManager only "with FortiAnalyzer features". Fortinet's administration guide shows the switch:

```
config system global
    set faz-status {enable | disable}
end
```

The same page warns that "When FortiAnalyzer is added to FortiManager, FortiAnalyzer features are automatically enabled to support the managed FortiAnalyzer unit, and cannot be disabled", and that changing the setting reboots the FortiManager. A FortiManager that manages a FortiAnalyzer should be treated as having the features on.

**3. Is the JSON API enabled on any administrator profile.** FG-IR-26-219 applies only when it is. Fortinet's workaround names the setting, `rpc-permit`, under `config system admin profile`; every profile that does not show `rpc-permit none` deserves a look, and any automation that relies on the API needs to be known before the setting is changed, because the change will stop it.

**4. Who can reach TCP/541, TCP/514 and TCP/443 on these boxes.** Fortinet's port documentation lists FGFM management on TCP/541 (IPv6 FGFM from FortiManager 7.4.1), OFTP on TCP/514, and the JSON API on TCP/443 and TCP/80 for FortiManager, and OFTP on TCP/514 for FortiAnalyzer. An external scan of the organization's own address ranges, and a review of the firewall rules and network address translation in front of the management segment, answer the question for the internet; the same review for internal segments answers it for an intruder already inside.

**5. Whether a source restriction is already in place.** For the 2024 FGFM flaw, Fortinet documented local-in policies that accept TCP/541 only from listed FortiGate addresses:

```
config system local-in-policy
    edit 1
        set action accept
        set dport 541
        set src <allowed FortiGate addresses>
    next
    edit 2
        set dport 541
    next
end
```

That example comes from FG-IR-24-423, written for CVE-2024-47575; Fortinet has not said that it mitigates any of the four November flaws. Assessment: limiting who can reach a pre-authentication port reduces the number of people who can try a pre-authentication flaw on it, whatever the flaw, and the same idea applies to TCP/514 for OFTP. It is not a substitute for the upgrade.

## Detection and indicators of compromise

None of the four advisories publishes indicators of compromise, log signatures or file paths, and none has a FortiGuard virtual patch: each advisory's "Virtual Patch" field reads "No".

The nearest published material is from the 2024 FGFM case. FG-IR-24-423 listed event log entries of type `event`, subtype `dvm`, with messages such as "Unregistered device localhost add succeeded", together with files under `/tmp/.tm` and `/var/tmp/.tm`. Those are indicators for CVE-2024-47575, not for the November flaws, and Fortinet itself warned at the time that the log entries "may keep being logged even on an up-to-date, patched system", in which case they indicate a failed attempt rather than a compromise. Assessment: the device manager event logs on FortiManager, where registrations and device additions are recorded, are where an unexpected registration attempt would show, and reviewing them since the products were last upgraded is a reasonable first step. Treat anything found there as a lead, not as proof.

## Exploitation status, as Fortinet and CISA state it

- **Fortinet:** each of the four advisories sets "Known Exploited" to "No", read at 21:29 on 12 November 2026 and again at 16:21 on 15 November 2026.
- **Fortinet's own exploit maturity:** the CVSS vectors Fortinet published carry `E:P` (proof-of-concept code exists) for FG-IR-26-219 and FG-IR-26-276, and `E:U` (unproven) for FG-IR-26-274 and FG-IR-26-275. Proof-of-concept code held by the vendor is not public exploitation, but it does mean the path from flaw to working code has been walked once.
- **CISA KEV:** none of the four CVEs is in the catalogue, version 2026.11.10, released 10 November 2026 at 19:03 UTC and read at 21:30 São Paulo time on 12 November, nor in version 2026.11.13, released 13 November at 20:24 UTC and read on 15 November. The catalogue lists 32 Fortinet entries, among them CVE-2024-47575 in FortiManager.
- **CISA's entries in the CVE records:** on 12 November only CVE-2026-126262 (FG-IR-26-276) had one. CISA's Stakeholder-Specific Vulnerability Categorization (SSVC) entry, timestamped 12 November 2026 at 14:16 UTC, records "Exploitation: none", "Automatable: yes" and "Technical Impact: total". By 15 November, CISA had added the same three values to CVE-2026-126170 (FG-IR-26-219) and CVE-2026-126261 (FG-IR-26-275), with SSVC timestamps of 13 November; CVE-2026-126260 has no record to add them to. Assessment: an "automatable" yes next to a "total" technical impact is the combination that lets one flaw become a campaign run by script.

## Where the records and the scores disagree

Four discrepancies were visible on 12 November, and each one affects how scanners and patch tools will see these flaws.

**The scores do not match their own vectors.** For FG-IR-26-274, 275 and 276, the vector strings Fortinet published in the CSAF files and the CVE records begin `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`: network attack vector, low complexity, no privileges, no user interaction, unchanged scope, high impact on confidentiality, integrity and availability. Under the CVSS 3.1 formula that vector is a base score of 9.8. FortiGuard shows 9.0, 9.0 and 9.3. NVD, which displays Fortinet's metric as computed from the vector, shows 9.8 for all three it lists. All of them are Critical either way; what differs is the ranking of these flaws against others in a dashboard that sorts by score.

**One CVE record did not exist.** CVE-2026-126260, the identifier FortiGuard gives for FG-IR-26-274, returned "CVE_RECORD_DNE", "The cve record for the cve id does not exist", from the CVE Services API at 21:29 on 12 November, two days after the advisory, and NVD had no entry for it; on 15 November at 16:21, five days after the advisory, the answer was the same. Tools that build their inventory from the CVE list or from NVD will not know about the OFTP SSRF until that record is published.

**NVD has not analysed any of them.** The three records NVD holds are marked "Awaiting Analysis", with no NVD product configurations; scanners that match on NVD's product data may not flag them yet.

**The product lists differ by document.** The CSAF summary for FG-IR-26-274 names FortiAnalyzer-BigData; its table does not. The CSAF summary for FG-IR-26-276 says "in FortiManager" while its table lists FortiAnalyzer and FortiManager. The advisory tables are the more complete documents; the summaries are what some feeds show.

## What to do now

In this order, for anyone who runs FortiManager, FortiAnalyzer or their cloud editions:

1. **Inventory the boxes and their versions**, including FortiManager units with FortiAnalyzer features on (step 2 above) and virtual machines nobody has logged in to recently.
2. **Upgrade to the branch minimums** in the upgrade-path table: 7.6.8, 7.4.12 or 7.2.13, or 8.0.2 on the 8.0 branch for both products (FG-IR-26-244 asks the same of FortiManager there); 7.0 has to move to a supported branch. Plan the intermediate steps from the running build before the maintenance window.
3. **On 8.0, on FortiAnalyzer-BigData 7.6 and anywhere the upgrade waits, apply the FG-IR-26-219 workaround**: `set rpc-permit none` on every administrator profile that does not need the JSON API, after identifying the integrations that use it. Where an integration needs it, restrict which addresses can reach TCP/443 on the box.
4. **Take TCP/541 and TCP/514 off the internet where they do not need to be there**, and restrict them to known device addresses where they do. Assessment: for FGFM, a site-to-site tunnel from branches to the management segment removes the need for an internet-facing FGFM port at all.
5. **Review FortiManager's device manager event logs** for unexpected device registrations or additions since the last upgrade, as a lead for further investigation, keeping in mind that the only published indicators are for the 2024 flaw.
6. **Check the cloud editions with Fortinet.** FortiManager Cloud and FortiAnalyzer Cloud are listed for FG-IR-26-219; who upgrades them, and when, is a question for the account team.
7. **Watch four values daily**: the "Known Exploited" field on each advisory, the KEV catalogue, the CISA entries in the CVE records, and the publication of CVE-2026-126260. A change in any of them is the signal to move faster.
8. **Do not wait for a scanner to raise these.** With one CVE record missing and the other three unanalysed by NVD, tools that rely on those feeds may not flag the flaws; the advisory tables are the data to work from.

## The pattern behind the four

Three things stand out, and none of them is new to anyone who has followed Fortinet's advisories, which is part of the point.

The first is where the flaws are. All four are on interfaces meant for machines, not people: a device registration channel, a log transport and an automation API. Those interfaces are built to accept input from many sources at scale, and they are the ones least likely to be behind the controls that protect a human login page.

The second is how they were found. Fortinet credits a frontier AI model in all four, and says so in the advisory text. That is a vendor using the same class of tool that others can use against the same code. The [earlier post on the SATAN argument and Mythos](/blog/satan-to-mythos-the-argument-that-comes-back) traced how that debate has gone before; what this batch adds is a vendor publishing the result as fixed, internally found and unexploited, which is the best version of the story, provided the fixes reach the boxes before anyone else's model reaches the same flaws.

The third is the gap between a published advisory and the data most organizations use to act on it. Two days after publication, one of the four CVEs had no record, none had NVD analysis, and three scores did not match their own vectors. Organizations that wait for those feeds to settle are waiting on a process that has nothing to do with their exposure.

<ReaderQuestions>

- Fortinet rates exploit code maturity "proof-of-concept" for two of the four flaws; should a vendor that holds working proof-of-concept code for an unauthenticated flaw publish fixed versions only, or also the details defenders need to detect attempts?
- FGFM on TCP/541 has now had two pre-authentication flaws in two years; should FortiManager deployments treat an internet-facing FGFM port as an exception that needs a written justification?
- Three of the four flaws are reached on device channels (FGFM and OFTP) rather than on the administrative login; how many organizations include device-facing ports in their external attack surface reviews?
- On the 8.0 branch the JSON API flaw has a workaround and no released fix; how should a team weigh disabling the API against breaking the automation that depends on it?
- When the CVE record for an advisory does not exist two days after publication, who should a scanner vendor treat as authoritative: the vendor's advisory or the CVE list?
- Fortinet found all four with an AI model; if attackers use similar models on the same code, how long should anyone assume an internally found flaw stays undiscovered elsewhere?
