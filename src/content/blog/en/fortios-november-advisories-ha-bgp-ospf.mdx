## What happened

On 10 November 2026, the same day it published four critical advisories for FortiManager and FortiAnalyzer, covered in [the earlier post on those four](/blog/fortimanager-fortianalyzer-pre-auth-flaws), Fortinet's Product Security Incident Response Team (PSIRT) published three critical advisories for FortiOS, the operating system of FortiGate firewalls. None of the three is in a feature a person logs in to. One is in high-availability (HA) synchronization between FortiGates, one in the daemon that runs the Border Gateway Protocol (BGP), and one in the daemon that runs Open Shortest Path First (OSPF) ([FG-IR-26-273](https://fortiguard.fortinet.com/psirt/FG-IR-26-273); [FG-IR-26-268](https://fortiguard.fortinet.com/psirt/FG-IR-26-268); [FG-IR-26-267](https://fortiguard.fortinet.com/psirt/FG-IR-26-267)).

All three were found inside Fortinet: each advisory credits a member of Fortinet's Product Security team and says the work used the frontier AI model Claude Mythos, the same note carried by the FortiManager and FortiAnalyzer advisories of that day ([FG-IR-26-273](https://fortiguard.fortinet.com/psirt/FG-IR-26-273); [FG-IR-26-268](https://fortiguard.fortinet.com/psirt/FG-IR-26-268); [FG-IR-26-267](https://fortiguard.fortinet.com/psirt/FG-IR-26-267)). Two of them also reach FortiSASE, Fortinet's secure access service edge (SASE) service, which runs on FortiOS.

The fixed versions were not new on 10 November. In a post of 21 October 2026, updated on 10 November, Fortinet's chief information security officer (CISO), Carl Windsor, announced a hardening release from the company's "frontier AI-assisted security testing program", with fixes for FortiOS scheduled for 22 October in 8.0.2, 7.6.8, 7.4.13 and 7.2.14, the versions that clear all three advisories on each branch, and the advisories themselves promised for the November Patch Tuesday ([Fortinet, 21 October 2026, updated 10 November](https://www.fortinet.com/blog/ciso-collective/fortinet-releases-security-hardening-release-for-multiple-products)). The fixes were therefore available for 19 days before the advisories said what they fixed, which is also how the Brazilian outlet CISO Advisor reported the batch ([CISO Advisor, 11 November 2026](https://www.cisoadvisor.com.br/fortinet-falhas-criticas-permitem-execucao-sem-login/)).

Everything below comes from the three FortiGuard advisory pages, the Common Vulnerabilities and Exposures (CVE) records Fortinet published for them, the National Vulnerability Database (NVD), and the Known Exploited Vulnerabilities (KEV) catalogue of the US Cybersecurity and Infrastructure Security Agency (CISA), all read on 15 November 2026 between 16:20 and 16:50 São Paulo time, and from Fortinet's own documentation where a configuration is described. Where this post goes beyond what those documents say, it says so with the word "Assessment".

## FG-IR-26-273: commands through high-availability synchronization

Fortinet's summary says the flaw, in FortiOS, "may allow an unauthenticated attacker with HA FGSP + standalone-config-sync, or autoscale to execute command as super admin via crafted HA packets" ([CVE-2026-126259](https://cveawg.mitre.org/api/cve/CVE-2026-126259)). Super admin is the highest administrative profile on a FortiGate.

Two configurations are named, and both exist to copy state between FortiGates:

- **FGSP with standalone configuration sync.** FGSP is Fortinet's way of making standalone FortiGates share sessions, as opposed to the FortiGate Clustering Protocol (FGCP) cluster described in [the Learn article on FGCP clustering](/learn/fortigate-fgcp-ha-clustering). Fortinet's FGSP setup page builds the peer relationship under `config system standalone-cluster`, with each unit naming the other's address in `set peerip`, and says sessions are synchronized by default over layer 3 on the interface that reaches the peer ([Fortinet, FGSP basic peer setup, FortiOS 7.6.7](https://docs.fortinet.com/document/fortigate/7.6.7/administration-guide/869218)). Standalone configuration sync is a further switch, `set standalone-config-sync enable` under `config system ha`, that copies "firewall policies, firewall addresses, and UTM profiles" from a primary to the secondaries over "one or more layer 2 heartbeat connections" ([Fortinet cookbook, Using standalone configuration synchronization, FortiOS 6.2.6](https://docs.fortinet.com/document/fortigate/6.2.6/cookbook/84777)).
- **Autoscale.** `config system auto-scale` turns on configuration synchronization between a primary and secondary units, with the settings `status`, `role`, `sync-interface`, `primary-ip` and `psksecret` ([Fortinet, config system auto-scale, FortiOS 7.6.7 CLI reference](https://docs.fortinet.com/document/fortigate/7.6.7/cli-reference/336417547)).

Assessment: in both cases the flaw sits on the channel whose job is to accept configuration from a peer, which is why a missing authentication check there ends in commands run as super admin rather than in a smaller problem.

Two details on the page do not agree. The title says "adjacent", while the published vector begins `AV:N`, a network attack vector, which in CVSS means an attacker anywhere that can route packets to the target. And the score shown is 9.0, while that vector, `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`, computes to 9.8 under the CVSS 3.1 formula; with an adjacent vector instead, it would compute to 8.8 ([FG-IR-26-273](https://fortiguard.fortinet.com/psirt/FG-IR-26-273); [FIRST, CVSS v3.1 specification](https://www.first.org/cvss/v3-1/specification-document)). Assessment: the configuration pages above describe heartbeat links at layer 2 and session sync on the interface facing the peer, which fits "adjacent"; the practical question for each deployment is who, besides the peers, can put a packet on those links.

## FG-IR-26-268: a numeric truncation in the BGP daemon

Fortinet's summary says a numeric truncation error in the FortiOS and FortiSASE BGP daemon "may allow a configured ibgp neighbor to send malicious/malformed attributes to all connected routers via a specially crafted request" ([FG-IR-26-268](https://fortiguard.fortinet.com/psirt/FG-IR-26-268)). MITRE defines the weakness as what happens "when a primitive is cast to a primitive of a smaller size and data is lost in the conversion" ([MITRE, CWE-197](https://cwe.mitre.org/data/definitions/197.html)).

This is the only one of the three that requires a relationship already in place: the attack type is listed as authenticated, with low privileges, and the attacker must be a configured iBGP neighbour, that is, a BGP peer inside the same autonomous system (the [BGP primer](/learn/bgp-primer) explains the difference between internal and external peers). The vector, `AV:N/AC:L/PR:L/UI:N/S:C/C:N/I:H/A:H`, marks the scope as changed: the damage reaches beyond the FortiGate to the routers it talks to, which matches the summary's "all connected routers". Fortinet's impact field reads "Denial of service" ([FG-IR-26-268](https://fortiguard.fortinet.com/psirt/FG-IR-26-268)).

Fortinet's own exploit maturity for this flaw is the highest among the eight critical advisories of 10 November: the vector ends `E:F`, functional exploit code, where the other seven carry `E:P` (proof of concept) or `E:U` (unproven) ([FG-IR-26-268](https://fortiguard.fortinet.com/psirt/FG-IR-26-268); [FIRST, CVSS v3.1 specification](https://www.first.org/cvss/v3-1/specification-document)). The advisory was revised on 13 November to add intrusion prevention system (IPS) package information, and it lists a virtual patch, FG-VD-62507.0day, in database update 26.118.

Assessment: an iBGP neighbour is normally another router of the same organization, so the realistic paths to this flaw are a router that has already been compromised, a peering configured more widely than intended, and providers or partners that share an autonomous system. The [Learn article on BGP as a chokepoint](/learn/bgp-and-the-routing-chokepoint) covers why a malformed attribute that one router passes on can become everyone's problem.

## FG-IR-26-267: an authentication bypass in the OSPF daemon

Fortinet's summary names "An Authentication Bypass by Primary Weakness vulnerability [cwe-305] in FortiOS and FortiSASE ospf daemon" ([FG-IR-26-267](https://fortiguard.fortinet.com/psirt/FG-IR-26-267)), which "may allow an unauthenticated attacker to broadcast LSA via specially crafted request" ([CVE-2026-126253](https://cveawg.mitre.org/api/cve/CVE-2026-126253)). A link-state advertisement (LSA) is the unit in which OSPF routers describe the network to each other, as the [OSPF primer](/learn/ospf-primer) explains; a router that accepts a forged one can be led to compute different routes.

MITRE's definition of the weakness is precise: "The authentication algorithm is sound, but the implemented mechanism can be bypassed as the result of a separate weakness that is primary to the authentication error" ([MITRE, CWE-305](https://cwe.mitre.org/data/definitions/305.html)). The vector, `AV:A/AC:L/PR:N/UI:N/S:C/C:N/I:H/A:H`, sets the attack vector to adjacent: the attacker has to be on a network segment where OSPF runs. Fortinet's impact field reads "Improper access control"; there is no virtual patch and no workaround ([FG-IR-26-267](https://fortiguard.fortinet.com/psirt/FG-IR-26-267)).

Assessment: the CWE chosen describes exactly the case where authentication is configured and sound and is still bypassed, so a segment with OSPF authentication turned on should not be treated as safe on that basis until Fortinet says otherwise.

## How to check exposure

1. **Versions.** Record the FortiOS version of every FortiGate, cluster members and virtual machines included, and compare it with the table above.
2. **FG-IR-26-273: is either named configuration in use?** Look for `set standalone-config-sync enable` under `config system ha` together with a `config system standalone-cluster` block, and for `config system auto-scale` with `set status enable` ([Fortinet cookbook, 6.2.6](https://docs.fortinet.com/document/fortigate/6.2.6/cookbook/84777); [Fortinet, FGSP basic peer setup, 7.6.7](https://docs.fortinet.com/document/fortigate/7.6.7/administration-guide/869218); [Fortinet, config system auto-scale, 7.6.7](https://docs.fortinet.com/document/fortigate/7.6.7/cli-reference/336417547)). Where either is on, list which interfaces carry heartbeat, session sync and the autoscale `sync-interface`, and who else can reach them.
3. **FG-IR-26-268: which iBGP neighbours exist?** List the BGP neighbours whose remote autonomous system equals the local one, and ask of each whether it could be, or has been, controlled by someone else.
4. **FG-IR-26-267: where does OSPF run?** List the interfaces with OSPF enabled and every device that shares those segments. Assessment: OSPF on a segment that also carries user or guest devices is the case to fix first.
5. **Virtual patches.** For FG-IR-26-273 and FG-IR-26-268, Fortinet lists virtual patches; whether they cover a given deployment is a question for its FortiGuard subscription and its IPS configuration. Assessment: they are a bridge to the upgrade, not a replacement for it.

## Exploitation status, as Fortinet and CISA state it

- **Fortinet:** all three advisories set "Known Exploited" to "No", read on 15 November 2026 ([FG-IR-26-273](https://fortiguard.fortinet.com/psirt/FG-IR-26-273); [FG-IR-26-268](https://fortiguard.fortinet.com/psirt/FG-IR-26-268); [FG-IR-26-267](https://fortiguard.fortinet.com/psirt/FG-IR-26-267)).
- **Fortinet's exploit maturity:** `E:F` (functional) for FG-IR-26-268, `E:P` (proof of concept) for FG-IR-26-267, `E:U` (unproven) for FG-IR-26-273. Code held by the vendor is not exploitation in the wild, but a functional exploit for the BGP flaw means the path from flaw to working code has been completed once.
- **CISA KEV:** none of the three CVEs is in the catalogue, version 2026.11.13, released 13 November 2026 at 20:24 UTC, which lists 1,781 entries and 32 Fortinet ones ([CISA KEV feed](https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json)).
- **CISA's entries in the CVE records**, under its Stakeholder-Specific Vulnerability Categorization (SSVC): CVE-2026-126259, exploitation none, automatable yes, technical impact total (13 November); CVE-2026-126254, exploitation none, automatable no, technical impact partial (12 November); CVE-2026-126253, exploitation none, automatable yes, technical impact partial (12 November) ([CVE-2026-126259](https://cveawg.mitre.org/api/cve/CVE-2026-126259); [CVE-2026-126254](https://cveawg.mitre.org/api/cve/CVE-2026-126254); [CVE-2026-126253](https://cveawg.mitre.org/api/cve/CVE-2026-126253)).

## The rest of the batch

The same day carried one more critical advisory for the management side, FG-IR-26-244, "Authorization bypass through user-controlled key in dmserver" (CVE-2026-126229, 9.1). It needs an administrator login, and Fortinet says it "may allow an authenticated administrator to access to other VDOMs via specially crafted HTTP requests" in FortiManager, FortiAnalyzer and their Cloud editions, fixed in 8.0.2, 7.6.8, 7.4.12 and 7.2.13, with 7.0 told to migrate ([FG-IR-26-244](https://fortiguard.fortinet.com/psirt/FG-IR-26-244); [CVE-2026-126229](https://cveawg.mitre.org/api/cve/CVE-2026-126229)). The four unauthenticated FortiManager and FortiAnalyzer flaws of the day are in [the earlier post](/blog/fortimanager-fortianalyzer-pre-auth-flaws).

## Where the records and the scores disagree

- **FG-IR-26-273:** the title says "adjacent" and the vector says network; the vector computes to 9.8 and the page shows 9.0. The same gap between a 9.8 vector and a displayed 9.0 appears in two of the FortiManager advisories of the day.
- **FG-IR-26-267:** the vector carries `RL:U`, remediation level "unavailable", on an advisory that lists fixed versions for every supported branch.
- **FG-IR-26-268 and FG-IR-26-267:** both scores, 9.6 and 9.3, do match their vectors under the CVSS 3.1 formula ([FIRST, CVSS v3.1 specification](https://www.first.org/cvss/v3-1/specification-document)).

Assessment: scanners and patch tools that read the vector rather than the displayed score will rank FG-IR-26-273 higher than FortiGuard's page does; teams that sort by score alone should sort these three by exposure instead.

## What the three have in common

All three are in code that exists to trust another device: a cluster peer, a BGP neighbour, an OSPF router. These protocols were designed for networks where the devices on the other end belong to the same administrator, and the defences around them are usually placement (dedicated links, internal peerings, routing on infrastructure segments) rather than strong authentication on every packet. When the code that parses a peer's packets has a flaw, the placement is the whole defence.

And, as with the four management-side advisories of the same day, Fortinet found them with an AI model and published them as fixed and unexploited, with functional or proof-of-concept code held for two of the three.
