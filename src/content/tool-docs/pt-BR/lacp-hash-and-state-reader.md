## O que faz

Um link aggregation group (LAG) junta links paralelos num só, e o Link Aggregation Control Protocol (LACP) faz as duas pontas concordarem sobre quais links fazem parte dele. Duas perguntas aparecem sempre que um bundle se comporta mal: em qual membro está este flow, e o que as duas pontas estão dizendo uma à outra? A página responde às duas, em dois modos:

- **Qual link.** Para um bond do Linux, o membro que leva um flow, calculado com o próprio transmit hash do driver: cada valor intermediário, o membro que o flow usa quando cada um dos outros membros cai e, se você pedir, como uma sequência de flows se distribui pelos membros. Para a mesma quantidade de membros, mostra a divisão que a Cisco documenta para o hash do Catalyst 6500/6000, que é o motivo de 2, 4 e 8 membros dividirem o tráfego por igual e 3, 5, 6 e 7 não.
- **Flags de estado.** Os octetos de estado do actor e do partner de um LACPDU (a unidade de dados do LACP), ou as flags que um comando show imprime, lidos bit a bit de LACP_Activity a Expired, com os timers que decorrem deles e um veredito para o par. O PortState da Huawei pode ser digitado como o `display eth-trunk` mostra, ou a saída inteira pode ser colada, e então cada linha de membro é lida.

Tudo é calculado no seu navegador.

## Por que só o hash do Linux é calculado

O jeito como um bundle distribui os frames fica a cargo de cada implementação. O próprio módulo de gerência do IEEE 802.1AX diz que a descrição do algoritmo de distribuição "could include information about the distribution algorithm in use" e que "The contents are vendor specific", ou seja, o conteúdo é específico de cada fabricante ([IEEE8023-LAG-MIB](https://www.ieee802.org/1/files/public/MIBs/IEEE8021-AX-MIB-202005290000Z.mib), dot3adAggDescription). Só dá para calcular um membro onde uma implementação publica o hash por inteiro, e uma publica: o driver de bonding do Linux, cujo [HOWTO](https://docs.kernel.org/networking/bonding.html) dá cada policy como fórmula e cujo código, [bond_main.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/net/bonding/bond_main.c), fixa cada detalhe. O bonding do RouterOS da MikroTik descreve as mesmas policies em palavras e remete à documentação do Linux ([MikroTik, Bonding](https://manual.mikrotik.com/docs/7.24/high-availability-solutions/bonding/)).

Os fabricantes de switch documentam quais campos entram no hash, não a função, então a página os nomeia e não calcula nada para eles:

- **Cisco.** No Catalyst 6500/6000, "The Cisco-proprietary hash algorithm computes a value in the range 0 to 7", o hash proprietário dá um valor de 0 a 7, e o documento diz quantos desses valores cada porta aceita, não o hash ([Cisco, documento 12023](https://www.cisco.com/c/en/us/support/docs/lan-switching/etherchannel/12023-4.html)). O guia do Catalyst 9300 lista os métodos de load-balance, com "The default is src-mac", e diz que o switch reduz "part of the binary pattern that is formed from the addresses in the frame to a numerical value", parte do padrão binário dos endereços do frame a um número ([Cisco, Configuring EtherChannels, IOS XE 17.18](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-18/configuration_guide/lyr2/b_1718_lyr2_9300_cg/configuring_etherchannels.html)).
- **Juniper.** O hash usa campos do pacote "as well as on some internal values like source port ID and source device ID", além de valores internos como o ID da porta e do dispositivo de origem ([Juniper, Hashing Algorithms for LAG and ECMP](https://www.juniper.net/documentation/us/en/software/junos/interfaces-ethernet-switches/topics/topic-map/hashing-algoriths-lag-bundle-ecmp.html)), que ninguém que lê o pacote tem como saber.
- **Arista.** "Hashing algorithm inputs varies by switch platform", as entradas variam conforme a plataforma ([Arista EOS, Port Channels and LACP](https://www.arista.com/en/um-eos/eos-port-channels-and-lacp)).
- **HPE Aruba.** O AOS-CX oferece l2-src-dst, l3-src-dst e l4-src-dst sem descrever a função ([AOS-CX 10.16, LACP configuration settings](https://arubanetworking.hpe.com/techdocs/AOS-CX/10.16/HTML/link_aggregation/Content/Chp_LAG/lac-cnf-set-10.htm)).
- **Extreme.** O Switch Engine nomeia xor, crc-16 e crc-32 como algoritmos de hash, mas não como os campos entram neles ([Switch Engine 33.7.1 Command References](https://documentation.extremenetworks.com/Switch%20Engine%20v33.7.1%20Command%20References/downloads/Switch_Engine_33_7_1_Command_References.pdf), configure sharing address-based custom).
- **Huawei.** A command reference do S5700 e do S6700 lista os modos de `load-balance` `dst-ip`, `dst-mac`, `src-ip`, `src-mac`, `src-dst-ip`, `src-dst-mac` e `enhanced profile`, diz que "The default load balancing mode is src-dst-ip", o default é src-dst-ip, e que "Load balancing is valid only for outgoing traffic; therefore, the load balancing modes for the interfaces at both ends of the link can be different": o balanceamento só vale para o tráfego de saída, então as duas pontas de um link podem usar modos diferentes. Depois de configurado um modo, "the hash factors used to calculate the outbound interface vary according to the packet type and device model", os fatores do hash variam com o tipo de pacote e o modelo: pacotes de camada 2 caem nos endereços MAC de origem e de destino; o S5736-S usa src-dst-ip com as portas TCP ou UDP de origem e de destino "regardless of whether you configure this parameter", seja qual for a configuração, e aceita um só modo para o switch inteiro; e no S5731-H, S5731-S, S5731S-S, S5731S-H, S5732-H, S6730-H, S6730S-H, S6730-S e S6730S-S, seja qual for o modo básico configurado entre os seis, "packets are load balanced based on physical-layer source port numbers in the packets", o balanceamento segue os números de porta de origem da camada física. A função em si não é dada, então nada é calculado para a Huawei; "You can run the display eth-trunk load-balance command to check the hash factors used when the outbound interface is calculated", o `display eth-trunk load-balance` mostra os fatores de hash usados ([Huawei, Link Aggregation Commands, V200R025C00](https://support.huawei.com/enterprise/en/doc/EDOC1100514211/54c5f31b/link-aggregation-commands), lida num navegador: o site recusa leituras automáticas).
- **Chips de switch da MikroTik.** Um bond com offload para o chip do switch faz o hash lá, e o manual não dá fórmula para isso.

Para perguntar ao próprio switch, o documento 12023 da Cisco mostra o comando `test etherchannel load-balance interface port-channel` do Catalyst 6500, que responde com a porta que um par de endereços usaria.

## Qual link: as entradas

- **Transmit hash policy**: os valores de `xmit_hash_policy` do HOWTO, `layer2` (o default), `layer2+3`, `layer3+4` e `vlan+srcmac`. O formulário mostra só os campos que a policy lê.
- **Byte order do processador**: little-endian (o default) ou big-endian, para `layer2+3` e `layer3+4`. Um valor de 32 bits ocupa quatro bytes: um processador big-endian guarda o byte mais significativo no endereço mais baixo, um little-endian guarda ali o menos significativo. Das arquiteturas de Linux que o Debian lista, amd64, arm64, ppc64el, riscv64 e loong64 são little-endian, e s390x, ppc64, mips e sparc64 são big-endian ([Debian Wiki, ArchitectureSpecificsMemo](https://wiki.debian.org/ArchitectureSpecificsMemo), lida num navegador: o site recusa leituras automáticas). O artigo [Big-endian e little-endian](/learn/big-endian-and-little-endian) explica o byte order com calma; como ele muda este hash está nas regras abaixo.
- **Membros que podem transmitir**: de 2 a 8, numerados a partir de 0.
- **MAC de origem e de destino** (`layer2`, `layer2+3`; o `vlan+srcmac` lê só o de origem), em notação com dois-pontos, hífen ou ponto da Cisco.
- **Endereço IP de origem e de destino**, IPv4 ou IPv6, da mesma família (em toda policy menos `vlan+srcmac`; no `layer2` eles só definem o EtherType).
- **Protocolo, porta de origem e porta de destino** (`layer3+4`): TCP ou UDP, portas de 0 a 65535.
- **VLAN ID e prioridade** (`vlan+srcmac`): um VLAN ID de 1 a 4094, ou em branco para um frame sem tag, e uma prioridade de 0 a 7; os MIBs do IEEE 802.1 não permitem 0 e 4095 como identificadores de VLAN e dão as prioridades de 0 a 7 ([IEEE8021-TC-MIB](https://www.ieee802.org/1/files/public/MIBs/IEEE8021-TC-MIB.mib), IEEE8021VlanIndex e IEEE8021PriorityValue).
- **Distribuição** (opcional): um campo que a policy lê, variando a partir do valor digitado, subindo, ao longo de 1 a 4096 flows.

## Qual link: as regras

As fórmulas do HOWTO, com os detalhes que o código fixa:

```text
layer2:    hash = source MAC[5] XOR destination MAC[5] XOR packet type ID
layer2+3:  hash = source MAC[5] XOR destination MAC[5] XOR packet type ID
           hash = hash XOR source IP XOR destination IP
           hash = hash XOR (hash RSHIFT 16)
           hash = hash XOR (hash RSHIFT 8)
layer3+4:  hash = source port, destination port (as in the header)
           hash = hash XOR source IP XOR destination IP
           hash = hash XOR (hash RSHIFT 16)
           hash = hash XOR (hash RSHIFT 8)
           hash = hash RSHIFT 1
vlan+srcmac: hash = (vlan ID) XOR (source MAC vendor) XOR (source MAC dev)
```

e em todos os casos o hash "is reduced modulo slave count", é reduzido ao módulo da quantidade de membros ([HOWTO de bonding do Linux](https://docs.kernel.org/networking/bonding.html), xmit_hash_policy).

- **O packet type ID** é o EtherType do frame como número: o driver faz XOR com `be16_to_cpu(ep->h_proto)` (bond_eth_hash), então 0x0800 para IPv4 e 0x86DD para IPv6 ([IANA, IEEE 802 Numbers](https://www.iana.org/assignments/ieee-802-numbers/ieee-802-numbers.txt)).
- **Endereços IPv6** são "first hashed using ipv6_addr_hash" (HOWTO), o XOR das quatro palavras de 32 bits do endereço ([include/net/ipv6.h](https://raw.githubusercontent.com/torvalds/linux/master/include/net/ipv6.h)).
- **O byte order do processador.** O driver faz o XOR dos endereços como `flow_get_u32_dst` e `flow_get_u32_src` os devolvem, os 32 bits crus guardados no pacote, e copia as portas com `memcpy` de uma estrutura que guarda primeiro a porta de origem ([include/net/flow_dissector.h](https://raw.githubusercontent.com/torvalds/linux/master/include/net/flow_dissector.h)). Um processador big-endian lê esses bytes com o mais significativo primeiro, que é a fórmula do HOWTO como está escrita; um processador little-endian lê na ordem inversa e chega a outro hash. Os campos que contam, os dois folds, o shift e o módulo são os mesmos. O `layer2` e o `vlan+srcmac` leem bytes isolados, ou montam os números byte a byte, então o byte order não muda o resultado deles. A página mostra as duas palavras como o processador escolhido as lê. O byte order só muda o membro quando a quantidade de membros não é uma potência de dois. Os dois folds do `bond_ip_hash` (`hash ^= (hash >> 16); hash ^= (hash >> 8);`) deixam no byte mais baixo o XOR dos quatro bytes da palavra, que inverter os bytes não muda, e um módulo por 2, 4 ou 8 só lê bits desse byte, também depois do shift do `layer3+4`. Rodando este engine em 2026-11-08 com 4.000 flows aleatórios (endereços IPv4, endereços MAC e portas aleatórios) em `layer2+3` e `layer3+4`, com cada quantidade de membros de 2 a 8, as duas ordens escolheram o mesmo membro em todos os 24.000 casos com 2, 4 ou 8 membros, e um membro diferente em 23.031 dos 32.000 casos com 3, 5, 6 ou 7. O flow do Exemplo mostra os dois casos: com 2 ou 4 membros ele usa o membro 0 ou 2 em qualquer processador; com 5 membros, o membro 2 num processador little-endian e o membro 4 num big-endian. Os golden vectors fixam os dois casos.
- **O bit mais baixo.** O `layer3+4` descarta esse bit no fim, segundo o comentário do código, "to deal with the common even ports pattern", por causa do padrão comum de portas pares (bond_ip_hash), então duas portas que diferem só no último bit costumam cair no mesmo membro.
- **A VLAN.** O `vlan+srcmac` faz XOR com `skb_vlan_tag_get(skb)`, que é toda a tag control information da tag, `vlan_tci` ([include/linux/if_vlan.h](https://raw.githubusercontent.com/torvalds/linux/master/include/linux/if_vlan.h)), então os bits de prioridade contam junto com o VLAN ID; um frame sem tag conta como 0. A página toma o drop eligible indicator como 0.
- **Qual membro.** Os membros que podem transmitir (no modo 802.3ad, os do aggregator ativo) ficam listados na ordem em que entraram no bond (bond_update_slave_arr), e o driver pega `slaves->arr[hash % count]` (bond_xmit_3ad_xor_slave_get). Quando um membro cai, a lista é refeita sem ele e o módulo passa a usar um membro a menos, então a página mostra, para cada membro, para onde o flow vai se aquele cair: muitas vezes um flow muda de lugar mesmo com o membro dele de pé.
- **Portas.** O `layer3+4` lê as portas de TCP e UDP sem fragmentação; "For fragmented TCP or UDP packets and all other IPv4 and IPv6 protocol traffic, the source and destination port information is omitted", em pacotes fragmentados e em outros protocolos as portas ficam de fora (HOWTO). A página lê só TCP e UDP.

**A divisão da Cisco.** Para a quantidade de membros escolhida, a página também mostra a tabela que o documento 12023 dá para o Catalyst 6500/6000, "the ratios of the values that each port accepts", a proporção dos valores que cada porta aceita: 4:4 para duas portas, 3:3:2 para três, 2:2:2:2 para quatro, 2:2:2:1:1 para cinco, 2:2:1:1:1:1 para seis, 2:1:1:1:1:1:1 para sete e um valor para cada uma com oito. Daí "you can only achieve perfect load balancing, even with random addresses, if you have two, four, or eight ports": balanceamento perfeito só com duas, quatro ou oito portas, mesmo com endereços aleatórios. A página mostra a parte de cada porta nos 8 valores como porcentagem; é a tabela documentada, não um cálculo do hash da Cisco.

**A distribuição.** Com a distribuição ligada, a página calcula o membro de cada flow da sequência e conta quantos caem em cada membro. Ela chama a distribuição de igual quando nenhum membro leva mais de um flow a mais que outro, e lista os membros dos 16 primeiros flows, o que mostra padrões como os pares que o `layer3+4` forma com portas de origem consecutivas.

**Cada ponta faz o hash só do que envia.** "Slave selection for outgoing traffic is done according to the transmit hash policy", a escolha do membro vale para o tráfego de saída (HOWTO): o switch escolhe o membro do tráfego de volta com o hash próprio, que a página não calcula.

## Flags de estado: as entradas

- **Como os valores estão escritos**:
  - **Octeto**: como o LACPDU leva, em hexadecimal com `0x` (`0x3D`, a forma da coluna State do `show lacp neighbor` da Cisco, que dá 0x3D como valor esperado, [documento 220367](https://www.cisco.com/c/fr_ca/support/docs/switches/catalyst-9300-series-switches/220367-troubleshoot-etherchannels-on-catalyst-9.html)), em decimal (`61`, como o Linux mostra o `port state` em /proc/net/bonding, [bond_procfs.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/net/bonding/bond_procfs.c)) ou em binário com `0b`. Um `3D` sem prefixo é recusado, para nunca ser lido como decimal.
  - **SNMP BITS**: `dot3adAggPortActorOperState` ou `dot3adAggPortPartnerOperState` como o SNMP devolve, um octeto em hexadecimal (com ou sem `0x`) ou oito dígitos binários com `0b`.
  - **Flags da Extreme**: as oito posições do Switch Engine na ordem da legenda dele, "A-Activity, T-Timeout, G-Aggregation, S-Synchronization C-Collecting, D-Distributing, F-Defaulted, E-Expired", com hífen para bit desligado, como na amostra `A-GSCD--` (Switch Engine 33.7.1 Command References, show lacp member-port).
  - **Letras da Arista**: a legenda do EOS, "A = Active, P = Passive; S=ShortTimeout, L=LongTimeout; G = Aggregable, I = Individual; s+=InSync, s-=OutOfSync; C = Collecting, X = state machine expired, D = Distributing, d = default neighbor state", como na amostra `ALGs+CD` ([Arista EOS](https://www.arista.com/en/um-eos/eos-port-channels-and-lacp)). Uma letra de cada par é obrigatória, C, X, D e d são opcionais, cada letra uma vez só, em qualquer ordem.
  - **PortState da Huawei**: a coluna PortState do `display eth-trunk`, "eight bits, such as 10111100", oito bits, impressos do Bit 1 ao Bit 8 ([Huawei, Link Aggregation Commands, V200R025C00](https://support.huawei.com/enterprise/en/doc/EDOC1100514211/54c5f31b/link-aggregation-commands), lida num navegador: o site recusa leituras automáticas). Digite o PortState do actor e o do partner, ou cole a saída inteira: a página lê cada linha de membro da tabela Local (porta, Status, PortType, PortPri, PortNo, PortKey, PortState, Weight) e da tabela Partner (porta, prioridade do sistema, system ID, PortPri, PortNo, PortKey, PortState, sob uma linha de header que também começa com ActorPortName), pareia as duas pelo nome da porta, mostra como impressas as linhas de header que reconhece (LAG ID, WorkingMode, Hash arithmetic, System Priority, System ID) e lê em detalhe o membro que você escolher, o primeiro por default. As linhas são reconhecidas pelo formato, então as palavras do header podem variar. O `display eth-trunk` sem número lista todos os trunks, cada um aberto por uma linha como `Eth-Trunk10's state information is:`; a página lê o primeiro trunk com linhas de membro, mostra o nome dele e avisa que os outros não foram lidos.
- **Actor**: o estado da ponta cuja saída você está lendo.
- **Partner** (opcional): o estado do partner como essa ponta informa, que é o que ela recebeu por último, ou os defaults dela quando Defaulted está ligado.

O `show lacp interfaces` da Juniper imprime as flags como palavras (Activity, Timeout, Aggr, Syn, Col, Dist, Def, Exp); leia as palavras e digite o octeto, ou compare com a lista de bits da página.

## Flags de estado: as regras

**Os bits.** O próprio IEEE 802.1AX é oferecido pelo IEEE GET Program, atrás de uma conta IEEE ([IEEE SA, 802.1AX-2020](https://standards.ieee.org/ieee/802.1AX/6768/)), e não foi lido. O módulo MIB publicado dele dá a ordem: "The first bit corresponds to bit 0 of the Actor_State (LACP_Activity), the second bit corresponds to bit 1 (Short_Timeout), the third bit corresponds to bit 2 (Aggregation)", e assim por diante até "bit 7 (Expired)" ([IEEE8023-LAG-MIB](https://www.ieee802.org/1/files/public/MIBs/IEEE8021-AX-MIB-202005290000Z.mib), dot3adAggPortActorAdminState). O driver do Linux dá a esses mesmos bits o lugar deles no octeto, de `LACP_STATE_LACP_ACTIVITY 0x1` a `LACP_STATE_EXPIRED 0x80` ([include/uapi/linux/if_bonding.h](https://raw.githubusercontent.com/torvalds/linux/master/include/uapi/linux/if_bonding.h)), então o bit 0 é o bit menos significativo do octeto: 0x3D é Activity, Aggregation, Synchronization, Collecting e Distributing.

**A forma SNMP.** O MIB declara o estado como BITS, e o SNMP envia um valor BITS com "all the named bits ... commencing with the first bit and proceeding to the last bit, ... placed in bits 8 (high order bit) to 1 (low order bit) of the first octet", o primeiro bit nomeado no bit mais significativo do primeiro octeto ([RFC 3417](https://www.rfc-editor.org/rfc/rfc3417.txt), seção 8). LACP_Activity é o primeiro bit nomeado, então o SNMP mostra o octeto com os bits invertidos: 0x3D no fio aparece como 0xBC pelo SNMP. A página mostra cada estado nas duas formas.

**O PortState da Huawei.** A Huawei numera os oito caracteres do Bit 1 ao Bit 8 a partir da esquerda. A tabela dela descreve o Bit 1 como "Whether the member interface is an Actor. This bit has a fixed value 1", se a interface membro é um Actor, com valor fixo 1; o Bit 2 como o timeout (1 curto, 0 longo; "By default, an Eth-Trunk member interface uses the long timeout interval (90s)", o longo, de 90 segundos, é o default); o Bit 3 como a permissão para a interface membro ser agregada; o Bit 4 como ela estar "added to the link aggregation group (LAG)", incluída no LAG; os Bits 5 e 6 como poder receber e enviar LACPDUs; o Bit 7 como LACPDUs com valores de parâmetro default; e o Bit 8 como a receive state machine do actor estar no estado Expired. São os bits 0 (LACP_Activity) a 7 (Expired) do MIB, escritos a partir do mais baixo, o inverso do octeto em binário: `10111100` como impresso é 0b00111101, 0x3D, o valor esperado pela Cisco, e os mesmos oito dígitos do valor SNMP BITS 0xBC escrito em binário. A página rotula cada bit com os dois números (Bit 1 · bit 0) e mostra também cada estado na forma da Huawei. A Huawei descreve os Bits 5 e 6 em termos de LACPDUs onde o MIB fala em Collecting e Distributing; a página mantém os nomes do MIB e os significados da Juniper abaixo. A coluna Status tem as palavras da própria Huawei: "Selected: A member interface in Selected state is active", Selected é ativa, Unselect é inativa, e ForceFwd é uma que "can forward Layer 2 traffic", pode encaminhar tráfego de camada 2. No exemplo da Huawei, o Eth-Trunk10 tem três membros: o GigabitEthernet0/0/2 e o 0/0/3 estão Selected com 10111100 nas duas pontas (0x3D, no bundle), e o GigabitEthernet0/0/4 está Unselect com 10100000 aqui e 10110000 vindo do partner (0x05 e 0x0D: esta ponta fora de sync, o partner em sync mas sem collecting nem distributing).

**O que cada bit quer dizer**, pelo `show lacp interfaces` da Juniper ([Juniper](https://www.juniper.net/documentation/us/en/software/junos/cli-reference/topics/ref/command/show-lacp-interfaces.html)):

| Bit | Nome | Ligado | Desligado |
|---|---|---|---|
| 0 | LACP_Activity | Ativo: participa "regardless of the partner's control value", seja qual for a configuração do partner | Passivo: "not transmitting LAC PDUs unless its partner's control value is Active", só envia se o partner for ativo |
| 1 | LACP_Timeout | Timeout curto (rápido) | Timeout longo (lento) |
| 2 | Aggregation | Pode agregar | "operate only as an individual link", só opera como link individual |
| 3 | Synchronization | "allocated to the correct link aggregation group", com um aggregator compatível e uma identidade "consistent with the system ID and operational key information transmitted" | "not in the right aggregation", fora da agregação certa |
| 4 | Collecting | Recepção de frames habilitada | Não habilitada |
| 5 | Distributing | Distribuição de frames de saída habilitada | "currently disabled", desabilitada |
| 6 | Defaulted | Usando "the default operational partner information, administratively configured for the partner", as informações default do partner | Informações do partner "received in an LACP PDU", recebidas num LACPDU |
| 7 | Expired | A receive machine está no estado Expired | Sem expired |

**Os timers.** "In a fast timeout, PDUs are sent every second and in a slow timeout, PDUs are sent every 30 seconds. LACP timeout occurs when 3 consecutive PDUs are missed": no rápido, um PDU por segundo, no lento, a cada 30 segundos, e o timeout vem com 3 PDUs perdidos seguidos, 3 ou 90 segundos (Juniper, como acima); o `lacp rate` da Cisco dá "the fast rate, once every 1 second" e a taxa normal "every 30 seconds" ([Cisco, Command Reference, IOS XE 17.18](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-18/command_reference/b_1718_9300_cr/layer_2_3_commands.html)); o timeout de LACP da Extreme é "either 90 seconds, long, or 3 seconds, short", longo por default (configure sharing lacp timeout). O bit de Timeout é um pedido ao partner: o `lacp_rate` do Linux é o "rate in which we'll ask our link partner to transmit LACPDU packets", a taxa que se pede ao partner, lenta (30 segundos) por default (HOWTO). No driver, uma ponta envia rápido enquanto o bit de Timeout do partner estiver ligado e devagar no caso contrário, e desiste do partner pelo próprio bit; quando nenhuma ponta está ativa, não há transmissão periódica nenhuma (ad_periodic_machine e ad_rx_machine, [bond_3ad.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/net/bonding/bond_3ad.c), cujas constantes são `AD_FAST_PERIODIC_TIME 1`, `AD_SLOW_PERIODIC_TIME 30` e três vezes cada uma para os timeouts). O `lacp timeout` da Huawei: com `fast`, o intervalo em que um Eth-Trunk precisa receber LACPDUs é de 3 segundos e "If fast is specified, the remote device sends an LACPDU every 1 second", a outra ponta envia um LACPDU por segundo; `slow`, o default, é de 90 segundos, com um envio a cada 30 segundos; um valor `user-defined` vai de 3 a 90 segundos; a configuração "takes effect on all its member interfaces", vale para todas as interfaces membro, e "The timeout interval on the two ends can be different. To facilitate maintenance, you are advised to set the same timeout interval at both ends": os timeouts das duas pontas podem ser diferentes, mas a Huawei recomenda o mesmo valor nas duas (Huawei, como acima). A página mostra com que frequência cada ponta envia e depois de quanto tempo cada uma desiste da outra.

**O veredito.** O par está no bundle quando as duas pontas estão agregáveis, em sync, em collecting e distributing, nenhuma está Defaulted nem Expired, e pelo menos uma está ativa. Só com o estado do actor, o veredito é sobre essa ponta. Os achados, na ordem:

- **Os dois passivos**: "If both links are in passive mode, they won't exchange LACP packets, and the aggregated link won't be established", com os dois passivos não há troca de pacotes LACP e a agregação não sobe ([Juniper, Aggregated Ethernet LACP](https://www.juniper.net/documentation/us/en/software/junos/interfaces-ethernet-switches/topics/topic-map/aggregated-ethernet-lacp-switches.html)); Cisco: uma porta passiva "cannot form an EtherChannel with another port that is also in the passive mode".
- **Expired** (nesta ponta, ou informado pelo partner): nenhum LACPDU chegou antes de o timer do estado Current estourar uma vez; "If no LACP PDU is received before the timer for the Current state expires a second time, the state machine enters the Defaulted state", na segunda vez a máquina entra em Defaulted (Juniper). Enquanto está Expired, o driver do Linux liga o Timeout curto do partner, então envia a cada segundo.
- **Defaulted** (nesta ponta, ou informado pelo partner): nenhum LACPDU recebido a tempo; os valores do partner ao lado são defaults, não o que a outra ponta disse.
- **Individual**: Aggregation desligado em alguma das pontas.
- **Fora de sync**: o link não está na agregação certa. As portas formam uma agregação quando têm "the same actor system ID, actor key, partner system ID, and partner key", o mesmo system ID e a mesma key de actor e de partner ([HPE Aruba, ArubaOS 8.11, LACP](https://arubanetworking.hpe.com/techdocs/Archived/AOS-8/ArubaOS_8.11.2_Web_Help/Content/arubaos-solutions/lacp/lacp-over.htm)), então um membro cabeado em outro switch, ou numa porta de outro grupo lá, mostra um system ID ou uma key de partner diferente dos outros membros: compare nas colunas de partner do comando show.
- **Em sync, mas sem collecting e distributing**: ainda sendo anexado ao aggregator, ou esperando o partner (os mux states da Juniper dizem qual).
- **Timeouts diferentes**: cada ponta envia na taxa que a outra pede, então uma falha silenciosa é percebida depois de um tempo diferente em cada sentido.

## O que recusa, e por quê

- **Qual link**: uma policy fora das quatro (encap2+3 e encap3+4 podem ler os headers internos de um túnel, o que a página não recebe); um byte order que não seja little ou big; menos de 2 ou mais de 8 membros; um campo que a policy lê e que está faltando; um MAC malformado (seis octetos, um separador só do começo ao fim, ou a notação com ponto da Cisco); um endereço IP com octeto acima de 255, zero à esquerda, tamanho de prefixo ou zona; endereços de famílias diferentes; um protocolo que não seja TCP ou UDP; uma porta fora de 0 a 65535; um VLAN ID 0 ou 4095 ou fora de 1 a 4094; uma prioridade fora de 0 a 7, ou uma prioridade num frame sem tag; uma distribuição sobre um campo que a policy não lê (não mudaria nada), com mais de 4096 flows, ou que passe do último valor do campo. Os campos que a policy não lê nem são lidos, então um valor antigo ali não trava a página.
- **Flags de estado**: um valor que não caiba num octeto (acima de 255, mais de dois dígitos hexadecimais ou oito binários); hexadecimal sem `0x`; oito caracteres 0 e 1 na forma de octeto, que são ou um PortState da Huawei digitado no formato errado ou binário sem o `0b` (a mensagem cita os dois); um valor SNMP de mais de um octeto; uma string da Extreme que não tenha oito posições com a letra certa ou um hífen; letras da Arista com um par faltando, uma letra repetida ou um caractere que a Arista não imprime; um PortState da Huawei que não seja oito caracteres 0 e 1; uma saída colada junto com valores digitados; uma saída colada sem nenhuma linha de membro, com uma linha que começa como uma linha Local ou Partner mas não se lê como tal, com duas linhas para a mesma porta na mesma tabela, ou com uma linha Partner de uma porta que a tabela Local não lista; uma porta escolhida que a tabela Local não lista.
- Todo campo tem no máximo 64 caracteres, menos a saída colada: no máximo 8192 caracteres e 96 linhas que não estejam em branco, e uma linha com mais de 200 caracteres não é linha de membro e não é lida. A saída colada só é lida no formato da Huawei.

## Exemplos práticos

O curso [LAN Switch Operations and Maintenance](/materials/lan-switch-operations-and-maintenance), capítulo 2.2, agrega dois cabos, as portas 47 e 48, e os slides de fabricante configuram a taxa rápida do LACP; o curso não dá flows nem endereços para o bundle. Então os Exemplos são:

- **Qual link**: um bond de dois membros, como o lab do curso agrega dois cabos, levando o primeiro flow do lab do [artigo do Learn](/learn/link-aggregation-and-lacp), um stream de backup de 192.0.2.10, porta TCP 50001, para 198.51.100.20, porta TCP 873, com `layer3+4` num processador little-endian. As portas são lidas como 0x690351c3, os dois endereços como 0x0a0200c0 e 0x146433c6; depois do XOR e dos folds o hash é 0x3b89385a, par, então o membro 0 leva o flow. Nas 64 portas de origem seguintes, os dois membros ficam com 32 flows cada, em pares (0, 1, 1, 0, 0, 1, 1, 0 ...), porque o último shift descarta o bit mais baixo.
- **A leitura do lab do Learn**: o mesmo flow em quatro membros e num processador big-endian dá 0x62d3e15a e o membro 2, o valor que o lab calcula à mão.
- **layer2 para um roteador**: com todo flow endereçado ao MAC do roteador, o `layer2` dá 0x0000080b (0x01 XOR 0x0a XOR 0x0800) e o membro 3 de 4 para todos eles; variando o MAC de destino em 256 valores, eles se distribuem 64 por membro.
- **IPv6 em três membros**: 2001:db8::10, porta TCP 443, para 2001:db8:1::20; as 300 portas de destino seguintes a partir de 51000 caem 118, 91 e 91 nos três membros, e não um terço exato para cada. A divisão documentada pela Cisco para três portas também é desigual: 3:3:2 dos 8 valores dela, 37,5 %, 37,5 % e 25 %.
- **Flags de estado**: 0x3F nas duas pontas: ativo, timeout curto, agregável, em sync, em collecting e distributing; no bundle, com cada ponta enviando a cada segundo e desistindo depois de 3 segundos. 0x3D nas duas é o mesmo com a taxa lenta, o valor esperado pela Cisco. 68 e 0, como o /proc/net/bonding os mostra, são um bond Linux passivo que não ouviu nada, diante de um estado de partner 0, o default do driver: os dois passivos, Defaulted, fora de sync. `A-GSCD--` (Extreme), `ALGs+CD` (Arista), 0xBC (SNMP) e `10111100` (Huawei) são todos 0x3D.
- **display eth-trunk da Huawei**: a amostra cola o exemplo da command reference da Huawei, literalmente. O GigabitEthernet0/0/2, Selected (como o 0/0/3), lê 10111100 nas duas pontas: 0x3D, no bundle, cada ponta enviando a cada 30 segundos. Escolhendo o GigabitEthernet0/0/4, Unselect, lê 10100000 e 10110000: 0x05 e 0x0D, fora do bundle, com esta ponta fora de sync e o partner ainda sem collecting e distributing.

## O que não faz

Não conversa com nenhum switch nem servidor: os valores são seus. Não calcula o hash de nenhum fabricante além do driver do Linux, nem a escolha do switch para o tráfego de volta, nem as policies encap, fragmentos ou protocolos além de TCP e UDP no `layer3+4`. Não decodifica um LACPDU inteiro, só os dois octetos de estado (os system IDs, keys e números de porta de uma saída colada da Huawei aparecem como impressos, sem verificação), e não simula as máquinas de estado do LACP. Para ver os flows mudarem de membro quando você derruba um, use o lab de hashing do artigo [Link aggregation e LACP](/learn/link-aggregation-and-lacp).

## Compartilhar resultado

Abaixo do veredito, **Compartilhar resultado** monta um link para esta página, só quando você clica, que leva o modo e os campos dele como digitados, depois do `#`: `mode` (`link` ou `state`) sempre; no modo de link, `policy`, `order` (`little` ou `big`) e `members`, e então só os campos que a policy lê, quando digitados (`srcmac`, `dstmac`, `srcip`, `dstip`, `protocol`, `srcport`, `dstport`, `vlan`, `priority`), e `spread` e `count` quando a distribuição está ligada; no modo de estado, `format`, `actor` e `partner` quando digitado, ou, no formato da Huawei com uma saída colada, `display` (a saída, com as linhas dela) e `port` quando um membro é escolhido, no lugar de `actor` e `partner`. Os campos que a policy não lê, e os do outro modo, não vão no link. No modo de link, o popover acrescenta um aviso: endereços MAC e IP e portas podem descrever hosts de uma rede privada, então confira antes de enviar o link. Com uma saída colada, acrescenta um aviso próprio: a saída mostra os system IDs dos switches (endereços MAC) e as interfaces.

A [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986.txt) (seção 3.5, lida em 2026-11-08) define o fragmento como "separated from the rest of the URI prior to a dereference", separado do resto da URI antes do acesso, então esses valores não vão para o servidor quando o link é aberto; ficam na barra de endereço e no histórico de quem abre, e qualquer um que tenha o link consegue lê-los.

- **Tamanho.** Um link leva no máximo 16.384 caracteres, o limite que o site usa para todo valor depois do `#`; uma saída colada de até 8192 caracteres cabe, e os outros campos são bem mais curtos.
- **Ao abrir um link.** O modo e os campos dele são preenchidos como se tivessem sido digitados (no modo de link, um campo que a policy não lê mantém o valor que tinha, e a falta de `spread` desliga a distribuição), e a página calcula. Um link com modo, policy, order, protocolo, formato ou campo de distribuição desconhecidos, um campo do outro modo ou que a policy não lê, um campo obrigatório faltando, um `count` sem `spread` ou o contrário, um `display` ou `port` fora do formato da Huawei, um `display` junto com `actor` ou `partner`, um `port` sem `display`, ou um valor em duas linhas (menos o `display`) é ignorado. Aceitos ou não, os valores saem do endereço da página na hora, sem requisição, então recarregar, salvar nos favoritos ou usar o próprio botão de compartilhar da página não leva nada que você não tenha escolhido compartilhar.

## Proveniência

O engine é aritmética de bits fixa, sem relógio, sem rede e sem aleatoriedade. Os golden vectors (conjunto `lacp-hash-and-state-reader-golden-2026-11-08b`) fixam cada policy nos dois byte orders para 2 a 8 membros, os seis flows do lab do Learn, IPv6 (inclusive com final IPv4 com pontos), as três notações de MAC, portas e endereços nos limites, a policy de VLAN com e sem prioridade, nove distribuições (até 4096 flows), cada um dos 256 octetos de estado como actor, 24 pares de actor e partner, as formas SNMP, Extreme e Arista, os Exemplos e as amostras, as frases que carregam as regras e as recusas. Todo valor esperado foi obtido por uma implementação separada em Python, e não rodando este engine: o hash a partir do código do driver, com os endereços e as portas lidos por `struct.unpack` no byte order do processador, e os estados pela ordem de bits do MIB e pela regra da RFC 3417. Os resultados big-endian dela batem com os vetores do próprio lab do Learn, inclusive o hash que ele calcula à mão. O segundo conjunto acrescenta o PortState da Huawei: cada octeto de novo como PortState, o exemplo da command reference da Huawei com cada membro escolhido, saídas com fim de linha do Windows, linhas em branco e tabs, linhas sem header, uma linha ForceFwd e uma porta 10GE, cada recusa de uma saída colada e os limites dela; os valores esperados vêm de um segundo modelo em Python, que lê um PortState como a string invertida e separa as linhas pelos espaços. Os resultados little-endian do lab do Learn, que a chave de byte order dele agora oferece, batem com este engine flow a flow.

## API

O mesmo engine responde em `/api/v1/lacp-hash-and-state-reader` na API HTTP do site; o contrato está na [página da API](/api), que também diz se este site serve a API.

- **Requisição.** Um objeto JSON. Qual link: `{"mode": "link", "policy": "layer3+4", "byteOrder": "little", "members": 2, "srcIp": "192.0.2.10", "dstIp": "198.51.100.20", "protocol": "tcp", "srcPort": 50001, "dstPort": 873, "spread": {"field": "srcPort", "count": 64}}`; `policy` (`layer2` por default), `byteOrder` (`little` por default), `protocol` (`tcp` por default), `vlan`, `priority` e `spread` são opcionais, e `srcMac` e `dstMac` são exigidos por `layer2` e `layer2+3` (só `srcMac` pelo `vlan+srcmac`). Flags de estado: `{"mode": "state", "format": "octet", "actor": "0x3F", "partner": "0x3F"}`; `format` (`octet` por default) e `partner` são opcionais. No formato da Huawei, `display` pode levar a saída inteira do `display eth-trunk` no lugar de `actor` e `partner`, com `port` indicando o membro lido em detalhe.
- **Resposta, qual link.** `mode`, `policy`, `policyDefault`, `byteOrder`, `byteOrderMatters`, `members`, `family`, `etherType`, `used`, `formula`, `steps` (cada um com `id` e `value`), `hash`, `hashDecimal`, `member`, `ifDown` (para cada membro que cai, o membro que o flow passa a usar), `ciscoValues`, `ciscoEven`, `spread` (`field`, `count`, `from`, `to`, `counts`, `min`, `max`, `even`, `first`, ou null) e `notes`.
- **Resposta, flags de estado.** `mode`, `format`, `formatDefault`, `actor` e `partner` (cada um com `octet`, `hex`, `decimal`, `binary`, `snmp`, `extreme`, `huawei` e `bits`, oito itens com `bit`, `name`, `mask`, `set` e `text`; `partner` null quando não informado), `huawei` (null a menos que uma saída tenha sido colada; senão `lagId`, `workingMode`, `hashArithmetic`, `systemPriority`, `systemId`, cada um null quando não impresso, `members`, cada um com `port`, `status`, `statusText`, `portType`, `portPri`, `portNo`, `portKey`, `weight`, `portState`, `hex`, `partner` e `verdict`, e então `port` e `portDefault`), `timers` (`actorTimeout`, `partnerTimeout`, `actorSends`, `partnerSends`, `periodic`), `status` (`bundled`, `bundled-this-end` ou `not-bundled`), `verdictText`, `findings` (cada um com `id`, `level` e `text`) e `notes`.
- **Erros.** HTTP 400, `invalid_input`, com a mensagem do engine, por exemplo `"3D" looks hexadecimal: write it with 0x in front (0x3D), so it is not read as decimal.`.
