## O que faz

Cole uma linha de comando `openssl s_client`, o texto que ela imprimiu, ou os dois, e a ferramenta explica tudo. Cada opção é lida segundo as páginas de manual do OpenSSL 3.5, a versão de suporte de longo prazo (com suporte até 8 de abril de 2030), os padrões que valem porque falta uma opção são ditos por extenso, cada bloco da saída é reconhecido e explicado, e os achados que pedem ação aparecem primeiro, os mais sérios no topo. O comando pode ir na caixa dele, ou na primeira linha da caixa de saída exatamente como o terminal mostra; a ferramenta separa os dois. Ela só lê texto: nada é conectado, resolvido, enviado ou executado.

## A linha de comando

Cada opção aparece no seu grupo (destino, nome do servidor, verificação, trust store, versões do protocolo, cipher suites e groups, o que o s_client imprime, sessões, certificado de cliente, STARTTLS e ALPN, OCSP stapling, entrada, DANE, PSK, providers) com o que ela faz. As opções são lidas como o próprio parser de opções do OpenSSL lê: `-nome` e `--nome` são a mesma opção, `--nome=valor` funciona, `--` encerra as opções, e uma palavra de destino pode vir depois delas. Uma opção que não está na página do 3.5, uma opção sem o valor dela e um flag com valor são apontados, porque o s_client para com erro de uso em cada caso. As opções `-ocsp_check_leaf` e `-ocsp_check_all` chegaram no OpenSSL 3.6: a ferramenta as explica, marca como "Não existe no OpenSSL 3.5" e avisa que um openssl 3.5 para nelas.

Os padrões são onde mora a maior parte das surpresas, então a ferramenta diz quais estão valendo:

- **Onde conecta.** Sem `-connect` e sem palavra de destino, o s_client conecta no host local, porta 4433. Um `-connect` sem porta mantém esse 4433: `openssl s_client -connect example.com` não fala com a porta 443. O BIO_parse_hostserv(3) diz que um host sozinho deixa o serviço intocado, e o s_client parte de 4433.
- **O nome enviado como SNI.** Desde o OpenSSL 1.1.1, sem `-servername` o host do `-connect` vai como Server Name Indication quando tem forma de nome DNS, nada vai quando é um endereço IP (a RFC 6066 não permite IP literal ali), e "localhost" vai quando não há `-connect` nenhum. O `-servername` envia o que receber; o `-noservername` não envia nada.
- **A verificação nunca para o handshake.** O certificado do servidor é sempre conferido e o resultado impresso, mas sem `-verify_return_error` o handshake segue qualquer que seja o resultado: a página avisa que o s_client aceita qualquer cadeia e que uma aplicação de verdade que fizesse isso estaria exposta a man-in-the-middle. O `-verify` liga a verificação com limite de profundidade, e ainda assim não aborta.
- **Nenhum hostname é conferido.** O `-servername` só escolhe o SNI. O s_client compara o certificado com um nome só quando `-verify_hostname`, `-verify_ip`, `-verify_email` ou o DANE pedem; sem um deles, "Verify return code: 0 (ok)" não diz nada sobre o certificado pertencer ao site.
- **O trust store.** Sem `-CAfile`, `-CApath` ou `-CAstore`, quem decide é o store padrão daquela compilação do openssl. O OpenSSL não traz âncoras de confiança próprias; distribuições Linux costumam apontá-lo para o store do sistema, e é por isso que o mesmo comando pode verificar numa máquina e falhar em outra.
- **Versões do protocolo.** Por padrão o cliente oferece todas as versões que suporta. O `-tls1_2` e seus irmãos permitem uma versão só e não se combinam com as opções `-no_*`, que o SSL_CONF_cmd(3) marca como depreciadas em favor de `-min_protocol` e `-max_protocol`. TLS 1.0 e 1.1 estão depreciados (RFC 8996) e são recusados a partir do nível de segurança 1, então forçá-los também exige uma cipher string com `@SECLEVEL=0`, que permite tudo.
- **Cipher suites e groups.** O `-cipher` define só a lista do TLS 1.2 para baixo; as suites do TLS 1.3 se definem com `-ciphersuites`. A ferramenta aponta cada uma quando as opções de versão a tornam inútil. Sem `-groups`, o OpenSSL 3.5 usa a lista DEFAULT embutida, que começa pelo híbrido pós-quântico X25519MLKEM768 e manda dois key shares no ClientHello do TLS 1.3, X25519MLKEM768 e X25519 (SSL_CTX_set1_groups_list(3), e a lista em si em `ssl/t1_lib.c`).

O shell em volta do comando também é lido: `echo |` ou `</dev/null` antes do s_client encerram a entrada dele na hora, e a página observa que uma execução sem terminal pode então fechar cedo demais, sobretudo com TLS 1.3; um pipe para `openssl x509` é identificado. Segredos na linha de comando são apontados: `-keylogfile` (um key log com que o Wireshark decifra o tráfego), uma senha `pass:` visível no `ps`, e `-proxy_user` (autenticação Basic em claro até o proxy).

## A saída, bloco a bloco

A saída é lida linha a linha, e cada linha ou bloco aparece com os números de linha e o que significa. O que o s_client imprime não está descrito nas páginas de manual, então o formato foi lido no próprio código-fonte do OpenSSL, na tag `openssl-3.5.9`. As linhas que só o OpenSSL 3.0 ou o 3.6 imprimem também são lidas, a partir do código nas tags `openssl-3.0.13` e `openssl-3.6.5`, então a saída dessas versões é explicada também:

- `Connecting to 127.0.0.1`: o OpenSSL 3.5 imprime na saída de erro o endereço em que conectou assim que a conexão TCP abre (o 3.0 não imprimia nada ali);
- as linhas `depth=N` / `verify error:num=N:texto` / `verify return:1` do callback de verificação (profundidade 0 é o certificado do servidor; o OpenSSL percorre da raiz para baixo; `verify return:1` é o s_client escolhendo seguir). O OpenSSL 3.5 escreve os nomes como `C=BR, O=Example Lab, CN=www.example.test`; o 3.0 escrevia `C = BR, O = Example Lab, ...`;
- `CONNECTED(00000003)`, que só diz que a conexão TCP está aberta (o número é o descritor do socket);
- `Certificate chain`, os certificados como o servidor enviou, com `s:` subject, `i:` issuer, `a:` chave e algoritmo de assinatura e `v:` validade; a página diz que não é uma cadeia verificada. No 3.5 a chave aparece como `a:PKEY: RSA, 2048 (bit); sigalg: sha256WithRSAEncryption`, ou `EC, (prime256v1)` para uma chave de curva elíptica; o 3.0 imprimia `rsaEncryption` e `RSA-SHA256`;
- `Server certificate` com o PEM (o PEM de todos os certificados com `-showcerts`) e as linhas `subject=` e `issuer=`;
- o pedido de certificado de cliente, se houver, `Peer signing digest` e `Peer signature type`, que o OpenSSL 3.5 dá pelo nome IANA do signature scheme, como `rsa_pss_rsae_sha256` (o 3.0 imprimia `RSA-PSS`); depois a chave efêmera do servidor: `Peer Temp Key` no 3.5, ou `Negotiated TLS1.3 group` quando o TLS 1.3 não tem objeto de chave temporária para mostrar, como com o grupo híbrido pós-quântico X25519MLKEM768 que dois peers OpenSSL 3.5 negociam por padrão (o 3.0 imprimia `Server Temp Key`);
- `SSL handshake has read N bytes and written M bytes` (ler 0 bytes quer dizer que o servidor não devolveu nada);
- `Verification: OK` ou `Verification error: texto`, e `Verified peername` quando um hostname foi conferido;
- `New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384` (ou `Reused` numa sessão retomada). A versão nesta linha é a versão que definiu o cipher pela primeira vez (SSL_CIPHER_get_version), não necessariamente a negociada: uma conexão TLS 1.1 imprime `New, TLSv1.0, Cipher is ECDHE-RSA-AES256-SHA`. A versão negociada está na linha `Protocol:` que o OpenSSL 3.5 imprime em seguida, e no bloco SSL-Session;
- `Server public key is N bit`, a linha de renegociação (`Secure Renegotiation IS supported` até o TLS 1.2; no TLS 1.3, que não tem renegociação, o 3.5 imprime "This TLS version forbids renegotiation." onde o 3.0 imprimia `IS NOT supported`), compressão, ALPN, early data;
- `Verify return code: N (texto)`, o resultado final da verificação, com o significado;
- o bloco `SSL-Session`, campo a campo. No TLS 1.2 ele vem uma vez, depois do handshake; no TLS 1.3 vem uma vez a cada `Post-Handshake New Session Ticket arrived:`, porque o servidor envia os tickets depois do handshake (RFC 9846, seção 4.7.1). `Master-Key` (TLS 1.2) e `Resumption PSK` (TLS 1.3) são segredos da sessão;
- com `-status`, a linha de OCSP: `OCSP response: no response sent` (OpenSSL 3.5 e 3.0; o 3.6 mudou para `no OCSP response received`, ou `OCSP responses: no responses sent` no TLS 1.3), ou a resposta recebida via stapling, impressa entre duas linhas de sinais `=`, da qual se leem o status da resposta, o Cert Status e a janela This Update / Next Update;
- o resumo do `-brief`, os passos do `-state` (`SSL_connect:...` e alertas), as mensagens do `-msg` com os bytes em hex, as leituras e escritas do `-debug`, as extensões do `-tlsextdebug`, as linhas de raw public key da RFC 7250, e as linhas da fila de erros do OpenSSL, lidas no formato que o ERR_print_errors(3) documenta (código, biblioteca, função, motivo, arquivo e linha).

Qualquer outra coisa, como uma resposta HTTP que o servidor enviou depois do handshake, aparece como dados e nunca é descartada.

## Verify return codes

O número em `verify error:num=N` e em `Verify return code: N` é um código X509_V_ERR. O openssl-verify(1) remete ao X509_STORE_CTX_get_error(3) para a lista e ao header `<openssl/x509_vfy.h>` para os números. A ferramenta traz os 96 códigos do OpenSSL 3.5.9 (0 a 95) com a constante, o texto exato impresso e uma leitura em linguagem simples, e também os seis códigos que o OpenSSL 3.6 acrescentou (96 a 101, cinco deles sobre OCSP), marcados como só do 3.6. O texto entre parênteses vem de `crypto/x509/x509_txt.c`: para os códigos 0 a 94 ele é o mesmo no 3.0.13 e no 3.5.9, o código 95 (uma raw public key sem nada configurado para confiar nela) não existe no 3.0.13, e o 3.6 estende o código 9 para "certificate is not yet valid or the system clock is incorrect". Os mais vistos: 0 ok, 10 expirado, 18 certificado do servidor auto-assinado, 19 uma raiz auto-assinada em que o cliente não confia no topo da cadeia, 20 um emissor que não está nem no que o servidor enviou nem no trust store, 21 um certificado único que não dá para verificar, e 62 hostname mismatch.

## Achados

Os achados juntam a leitura. Os mais frequentes: a verificação falhou (com o significado do código) e o handshake seguiu mesmo assim; uma intermediária ausente, deduzida do erro 20 ou 21 e da cadeia que o servidor enviou (o último certificado enviado cita um emissor que nunca foi enviado); uma raiz não confiável, um certificado auto-assinado, expirado ou ainda não válido, um nome que não confere; uma verificação que passou sem checagem de hostname nenhuma; um handshake que falhou ou não leu nada; TLS 1.0 ou 1.1 negociado; a armadilha da versão na linha do cipher; suites NULL, RC4, export, DES, 3DES ou anônimas, transporte de chave RSA, DHE de corpo finito e suites CBC no TLS 1.2 (RFC 9325); assinatura SHA-1 ou MD5 no TLS 1.2 (RFC 9155); falta de renegociação segura ou de extended master secret no TLS 1.2 (RFC 9325, seção 3.5); uma cadeia fora de ordem ou levando a própria raiz (RFC 9846, seção 4.5.1); OCSP sem stapling, good, revoked ou unknown (RFC 6960); uma opção que o OpenSSL 3.5 não tem; e valores de Master-Key ou Resumption PSK para apagar antes de compartilhar a saída.

## Versões do OpenSSL

A ferramenta se baseia no OpenSSL 3.5 porque ele é a versão de suporte de longo prazo: a estratégia de versões do OpenSSL, lida em 27 de outubro de 2026, dá suporte ao 3.5 até 2030-04-08, ao 3.6 até 2026-11-01 e ao 4.0 até 2027-05-14, e lista o 3.0 como sem suporte; a página Downloads dá o 3.5.9, lançado em 29 de setembro de 2026, como a versão 3.5 atual. Onde o 3.0 ou o 3.6 imprimem uma linha diferente, a ferramenta lê essa linha também e diz qual versão a imprime. O OpenSSL 4.1.0 saiu em 23 de outubro de 2026; a página do 4.1 tira o `-engine` (removido no 4.0), não lista mais o `-ssl3` e faz o `-quiet` implicar `-verify_quiet`. A ferramenta avisa sobre os dois primeiros quando aparecem num comando.

## Exemplos

O botão Exemplo carrega uma captura no formato do OpenSSL 3.5: um servidor que envia o certificado sem a intermediária, com o cliente confiando na raiz via `-CAfile`. O s_client imprime o erro 20 e depois o 21 na profundidade 0, termina o handshake mesmo assim e fecha com "Verify return code: 21 (unable to verify the first certificate)".

Os golden vectors são dezenove capturas contra instâncias locais de `openssl s_server` e uma CA de teste descartável: TLS 1.3 com cadeia completa, TLS 1.2 forçado com ALPN h2, TLS 1.1 no nível de segurança 0, uma CA desconhecida cujo servidor também envia a raiz, um certificado auto-assinado, `-verify_return_error` abortando o handshake, `-showcerts`, `-brief`, `-status` com e sem resposta via stapling, um hostname que não confere e um que confere, um certificado expirado (via `-attime`), `-state`, `-msg`, e `-reconnect` nos dois formatos. Cada uma é uma execução real feita em 27 de outubro de 2026 com o OpenSSL 3.5.9, compilado a partir do release oficial do código-fonte depois de conferir o SHA-256 e a assinatura, nas duas pontas da conexão. Dois peers 3.5.9 negociam o grupo híbrido X25519MLKEM768 no TLS 1.3, então essas capturas imprimem `Negotiated TLS1.3 group: X25519MLKEM768` onde as de TLS 1.2 imprimem `Peer Temp Key: X25519, 253 bits`, e a captura com `-msg` mostra o ClientHello levando o key share desse grupo. Vetores curtos de formato de linha cobrem as linhas que nenhuma captura tem, como a forma EC do `a:PKEY`, o formato do 3.0 e as linhas de OCSP que só o 3.6 imprime, e vinte e seis linhas de comando escritas para os testes fixam as regras da leitura do comando. Nove vetores de compartilhamento fixam, byte a byte, a cópia que um link de Compartilhar resultado leva: os dois valores de Resumption PSK do Exemplo, um Master-Key de TLS 1.2, os seis de uma execução com `-reconnect`, os quatro segredos de linha de comando, as origens que ficam, as formas `--opt=valor` e com continuação de linha, um comando no topo da caixa da saída e a senha de outro comando; em cada um, a página que recebe lê os mesmos achados, menos só o dos segredos impressos.

## Ferramentas e leituras relacionadas

- **Os certificados.** Cole os blocos PEM que o `-showcerts` imprime no [montador de cadeia de certificados](/tools/cert-chain-builder), que os põe em ordem e aponta o intermediário que falta, ou um único certificado no [decodificador de certificados X.509](/tools/x509) para ler os campos e as extensões dele. A página traz os dois links ao lado da cadeia que mostra.
- **A suíte de cifra.** O [decodificador de suítes de cifra](/tools/cipher) separa a suíte da linha `Cipher is` em troca de chaves, autenticação, cifra e MAC, com o nome IANA e o status de recomendação.
- **Um BIG-IP do outro lado.** Quando o servidor é um virtual server do BIG-IP, o perfil client-ssl dele define as versões de protocolo e as suítes de cifra que o s_client encontra: o [explicador de perfil SSL do F5](/tools/f5-ssl-profile-explainer) lê o perfil, e o [explicador de cipher string do F5](/tools/f5-cipher-string-expander), a cipher string.
- **Compartilhar uma captura.** Apague os segredos da sessão antes de uma captura ir para um slide ou um chamado. A verificação de segredos do [Código em imagem](/tools/code-to-image) não tem regra para eles: deixa uma linha `Resumption PSK:` do TLS 1.3 como foi impressa, e só mascara uma linha `Master-Key:` do TLS 1.2 porque a linha tem a forma de uma chave YAML com um nome de segredo.
- **Leitura.** [Como ler o openssl s_client](/learn/reading-openssl-s-client-output) mostra o que o comando confere e o que a saída prova, e [Cadeias de certificados](/learn/certificate-chains-order-anchors-and-what-breaks-them) explica a cadeia por trás dos erros 20 e 21.

## Compartilhar resultado

Abaixo dos achados, o botão **Compartilhar resultado** cria um link para esta página, só quando você clica, que leva as duas caixas depois do `#` com cada valor secreto trocado por `[redacted]`, nunca como foram coladas: cada `Master-Key` e `Resumption PSK` dos blocos de sessão, uma senha passada como `pass:` a `-pass` ou `-proxy_pass` (ou nessa forma em qualquer outro ponto do texto), a chave do `-psk` e a senha do `-srppass`. O popover dele diz primeiro o que o link leva e quantos valores foram trocados, e então oferece Copiar link e, onde o navegador tiver, a tela de compartilhamento do sistema; o endereço da página não muda.

Uma saída completa do s_client quase sempre traz um dos dois segredos de sessão, e por isso o link leva uma cópia em vez do que foi colado. Todo o resto fica: nomes de host, a cadeia, as origens `env:`, `file:`, `fd:` e `stdin` de uma senha (a [openssl-passphrase-options(1)](https://docs.openssl.org/3.5/man1/openssl-passphrase-options/), lida em 2026-10-27, só trata a forma `pass:` como a própria senha) e os bytes do ticket, que não retomam uma sessão sem o segredo dela ([RFC 9846](https://www.rfc-editor.org/rfc/rfc9846), seções 4.7.1 e 4.3.11.2, lida em 2026-10-27). A [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (seção 3.5, lida em 2026-10-27) diz que o fragmento é "separated from the rest of the URI prior to a dereference" (separado do resto do URI antes de o recurso ser buscado), então a cópia não é enviada ao servidor quando o link é aberto; ela fica na barra de endereço e no histórico de quem abre, e qualquer pessoa com o link consegue lê-la.

- **Tamanho.** No máximo 16.384 caracteres no total, o limite que o site usa para todo valor depois do `#`; um compartilhamento maior não ganha link, e o popover diz o tamanho.
- **Ao abrir um link.** As duas caixas são preenchidas como numa colagem (uma ausente fica vazia) e a página as explica; nada é conectado, como sempre. Os vetores de compartilhamento conferem que a página que recebe lê o mesmo handshake: os mesmos achados, menos só o dos segredos impressos. Os valores então saem do endereço da página na hora, sem nenhuma requisição, então recarregar a página ou usar o botão Compartilhar da própria página não leva nada.
- **Links do console serial.** Um relatório passado como `#input=` continua preenchendo a caixa da saída exatamente como antes; Compartilhar resultado usa nomes próprios (`command`, `output`), então os dois nunca se misturam.

## API

O mesmo engine responde à operação `/api/v1/openssl-s-client-explainer` da API HTTP do site, descrita no contrato OpenAPI na [página da API](/api), que também diz se este site serve a API. Apague os valores de Master-Key e Resumption PSK antes de mandar a saída para qualquer lugar, esta API inclusive.

- **Requisição.** Texto: a linha de comando, a saída, ou a linha de comando seguida da saída.
- **Resposta.** `command` (null quando não se achou comando): `found`, `program`, `options` (cada uma com `typed`, `name`, `value`, `known`, `group`, `text`, `dflt`, `since`, `deprecated`, `notIn35`, `problem`), `target` (`raw`, `from`, `host`, `port`, `portDefaulted`, `hostIsIp`), `sni` (`mode`, `value`, `text`), `stdinClosed`, `inputFrom`, `outputTo`, `absent` e `findings`. `output` (null quando não houve saída): `recognised`, `layout` (`full`, `brief` ou `unknown`), `lines`, `truncated`, `items` (cada um com `kind`, `start`, `end`, `text`, `fields`, `connection`, `explain` e `detail`), `connections` (um por handshake: protocolo, cipher, verificação, cadeia, chaves, ALPN, OCSP, tickets, segredos impressos, motivos de erro) e `findings`. Depois, `findings` (as duas listas juntas, as mais sérias primeiro) e `splitFromOutput`. Toda explicação vem como `{"en": ..., "pt": ...}`; todo achado tem um `id` estável, uma `severity` (`high`, `warn` ou `info`) e a `source` em que se apoia.
- **Erros.** Texto que não é nem comando nem saída do s_client não é erro HTTP: os achados dizem `noCommandFound` ou `notSClientOutput`.
