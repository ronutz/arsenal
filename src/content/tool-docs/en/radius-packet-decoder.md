## What it does

RADIUS (Remote Authentication Dial-In User Service) carries almost everything it says in clear octets: who is logging in, from which switch port, which VLAN the server hands back, which accounting session just started. This decoder reads those octets, in your browser, from the hex of one packet as a capture shows it:

- **The header**: the Code, named from IANA's RADIUS Packet Type Codes registry; the Identifier; the Length, checked against the octets you gave; and the 16-octet Authenticator, with what it is for this Code.
- **Every attribute** as type, length and value, named from IANA's RADIUS Attribute Types registry, with the value read in the data type IANA gives it (RFC 8044): text, string, integer, enum with IANA's value names, time, IPv4 and IPv6 addresses and prefixes, interface identifiers, 64-bit integers and TLVs.
- **Vendor-Specific** (type 26) split into the vendor's Private Enterprise Number and its sub-attributes, named where the vendor's own documentation defines them; **extended attributes** (RFC 6929) reassembled from their fragments.
- **The EAP packet** carried in EAP-Message attributes, and **VLAN assignment** when the tunnel attributes describe one.
- **Warnings** where the packet breaks a rule of the RFCs, and **notes** on what each part means.

It is the packet half of the [RADIUS end to end](/learn/radius-end-to-end) article and of chapter 4.6 (AAA: RADIUS and TACACS+) of the open course LAN Switch Operations and Maintenance, where the administrator netadmin logs in to SW-CORE-01 through a RADIUS server. Below every reading, a short panel sets RADIUS beside TACACS+, the protocol of the [TACACS+ for device administration](/learn/tacacs-plus-device-administration) article.

No shared secret is ever asked for. Hidden attributes and authenticators are explained, never decrypted or verified, and a Share results link carries a copy with them replaced by zeros.

## The packet

A RADIUS packet is a Code (one octet), an Identifier (one octet), a Length (two octets), a 16-octet Authenticator and the attributes. RFC 2865 sets the Length between 20 and 4096, says that "Octets outside the range of the Length field MUST be treated as padding and ignored on reception", and that a packet shorter than its Length "MUST be silently discarded" ([RFC 2865](https://www.rfc-editor.org/rfc/rfc2865.txt), section 3). The decoder does the same: extra octets are shown as padding with a warning, and a short packet is refused. RFC 2866 gives accounting packets a maximum of 4095 ([RFC 2866](https://www.rfc-editor.org/rfc/rfc2866.txt), section 3), and a 4096-octet accounting packet gets a warning.

The Authenticator differs by Code, and the page says which applies:

- **Access-Request**: the Request Authenticator, a random number that "SHOULD be unpredictable and unique over the lifetime of a secret" and that hides User-Password (RFC 2865, section 3). Status-Server makes it the same way ([RFC 5997](https://www.rfc-editor.org/rfc/rfc5997.txt), section 3).
- **Access-Accept, Access-Reject, Access-Challenge**: the Response Authenticator, MD5 over the reply, the request's Request Authenticator and the shared secret (RFC 2865, section 3).
- **Accounting-Request**: MD5 over the packet with 16 zero octets in the Authenticator's place, followed by the shared secret (RFC 2866, section 3); Disconnect-Request and CoA-Request use the same method and go to UDP port 3799 ([RFC 5176](https://www.rfc-editor.org/rfc/rfc5176.txt), section 2.3).

A Code IANA does not assign gets a warning, because "When a packet is received with an invalid Code field, it is silently discarded" (RFC 2865, section 3).

## Attributes and their data types

An attribute is Type, Length and Value, and its Length counts the Type and Length octets themselves (RFC 2865, section 5). IANA's registry, as read on 8 November 2026 (last updated 2026-10-09), gives each attribute its name and its RFC 8044 data type, and the decoder reads the value by that type ([RFC 8044](https://www.rfc-editor.org/rfc/rfc8044.txt), section 3): integer and enum as four octets, "most significant octet first" (RFC 2865, section 5), the network byte order that [Big-endian and little-endian](/learn/big-endian-and-little-endian) explains, time as seconds since 1970 printed in UTC (unsigned, so past 2038; a date before 2017 gets RFC 8044's note that it is "likely to indicate configuration errors"), ipv4addr and ipv6addr as addresses, IPv6 printed in RFC 5952's canonical text ([RFC 5952](https://www.rfc-editor.org/rfc/rfc5952.txt), section 4), ipv6prefix and ipv4prefix with their Prefix-Length, ifid as eight octets, integer64 as a 64-bit number, text as UTF-8 ([RFC 3629](https://www.rfc-editor.org/rfc/rfc3629.txt)) and string as octets, with a text reading when every octet is printable.

Enumerated values are named from IANA's value sub-registries: Service-Type 6 is Administrative, NAS-Port-Type 15 is Ethernet and 5 is Virtual, Acct-Status-Type 1 is Start, Tunnel-Type 13 is Virtual LANs (VLAN). Names are shown as IANA publishes them, in English on every page.

The tunnel attributes of [RFC 2868](https://www.rfc-editor.org/rfc/rfc2868.txt) carry a Tag that groups the attributes of one tunnel: Tunnel-Type, Tunnel-Medium-Type and Tunnel-Preference always have one, and in the string tunnel attributes the first octet is a Tag only when it is 0x00 to 0x1F; above that it is "the first byte of the following String field" (sections 3.1 to 3.10).

## Vendor-Specific attributes

A Vendor-Specific attribute is a four-octet Vendor-Id, "the SMI Network Management Private Enterprise Code of the Vendor", followed by a String that "SHOULD be encoded as a sequence of vendor type / vendor length / value fields" (RFC 2865, section 5.26). When the String divides that way the decoder lists the sub-attributes; when it does not, it shows the octets, as RFC 2865 asks a robust implementation to support them.

The vendor's name comes from IANA's Private Enterprise Numbers registry (last updated 2026-11-06) for the vendors this tool names, and the sub-attributes are named only where the vendor's own documentation defines them, as read on 8 November 2026:

- **Cisco (9)**: cisco-avpair (1), a string "protocol : attribute sep value", where "sep is = for mandatory attributes and is * for optional attributes", as in shell:priv-lvl=15 (Cisco Catalyst 9300 IOS XE 17.18 Security Configuration Guide, Configuring RADIUS). The decoder splits the parts.
- **Juniper (2636)**: Juniper-Local-User-Name (1) to Juniper-Deny-Configuration-Regexps (14), from Table 1 of the Junos User Access and Authentication guide.
- **Arista (30065)**: Arista-AVPair (1, string, with shell:priv-lvl and shell:roles) and Arista-Config-Vlan (22), from the EOS 4.36.2F manual.
- **HPE Aruba (14823)**: Aruba-User-Role (1) and nine more from the AOS-CX 10.16 Security Guide.
- **Extreme (1916)**: Extreme-CLI-Authorization (201) to Extreme-URL-Redirect (234), from Tables 143 and 146 of the Switch Engine v33.7.1 User Guide.
- **MikroTik (14988)**: MIKROTIK_RECV_LIMIT (1) to Mikrotik-Switching-Filter (30), names as the RouterOS 7.24 manual's table writes them; that table gives no data types, so the values are shown as octets.
- **Microsoft (311)**: the MS- sub-attributes of [RFC 2548](https://www.rfc-editor.org/rfc/rfc2548.txt), which every MS-CHAP and PEAP exchange carries.
- **Huawei (2011)**: the 68 sub-attributes of Table 1-11, "Huawei proprietary RADIUS attributes", in the S5700 and S6700 V200R025C00 configuration guide, from HW-Input-Peak-Information-Rate (1) to HW-Product-ID (255), read in the type the table gives: integer as four octets, string with a text reading when printable, ipaddr as an IPv4 address (four octets) or an IPv6 address (sixteen: HW-Framed-IPv6-Address is the "IPv6 address to be configured for the user", an address, not a prefix), hex as octets. HW-DHCP-Option (26-158), the table's one hex attribute, is a "DHCP Option, encapsulated in Type-Length-Value (TLV) format", and "Only Option 82 can be delivered": the decoder lists its options by code and length, reads Option 82, the Relay Agent Information option, as [RFC 3046](https://www.rfc-editor.org/rfc/rfc3046.txt) defines it (sub-options of code, length and value, at least one, so a minimum length of two; 1 is the Agent Circuit ID and 2 the Agent Remote ID, section 2.0), says so when the octets do not divide that way, and quotes the table for any other option. HW-Exec-Privilege (26-29) is the "Privilege level of an administrator (such as a Telnet user)": the table gives "0 to 15" and says "The priority that is greater than or equal to 16 is ineffective", and the decoder says which applies. A vendor type that is not in the table is shown as octets, saying so. The site refuses automated reads, so the table, and the descriptions of rows 26-158 and 26-253, were read in a browser on 8 November 2026.

The Enterasys guide of the course's C3 lab is no longer online, so its sub-attributes are shown by number. Any other Private Enterprise Number is shown as a number, with IANA's registry as the place to look it up.

## Extended attributes

RFC 6929 keeps types 241 to 246 for the extended space: an Extended-Type octet after the Length (241 to 244), and for 245 and 246 a flags octet whose More bit says the value continues in the next attribute, which "MUST have both the same Type and Extended-Type", and whose Length must be 255 while More is set ([RFC 6929](https://www.rfc-editor.org/rfc/rfc6929.txt), section 2.2; RFC 8044, section 3.16). The decoder reassembles the fragments, names the result from IANA's registry by its dotted identifier (241.1 is Frag-Status, 245.1 SAML-Assertion), and reads Extended-Vendor-Specific attributes (241.26 to 246.26) as Vendor-Id, Vendor-Type and data, identified as 245.26.1.6 and so on (section 2.7). A tlv value is listed TLV by TLV (RFC 8044, section 3.13).

## Hidden attributes and what is never shown

- **User-Password** is the password padded to a multiple of 16 octets and XORed, 16 octets at a time, with MD5 of the shared secret and the Request Authenticator (RFC 2865, section 5.2). The decoder says how long the password can be and nothing more.
- **CHAP-Password** is a CHAP Ident and a 16-octet response to the challenge in CHAP-Challenge or the Request Authenticator (RFC 2865, section 5.3).
- **Tunnel-Password** is a Tag, a Salt whose top bit "MUST be set" and the encrypted password (RFC 2868, section 3.5); **MS-MPPE-Send-Key** and **MS-MPPE-Recv-Key** are salted the same way (RFC 2548, sections 2.4.2 and 2.4.3).
- **Message-Authenticator** is an HMAC-MD5 of the whole packet keyed with the shared secret ([RFC 3579](https://www.rfc-editor.org/rfc/rfc3579.txt), section 3.2).

All of these need the shared secret, so the decoder explains them and stops there. Everything else in the packet is readable as it is, which is exactly what the decoder shows.

## EAP and VLAN assignment

An 802.1X login travels as EAP inside EAP-Message attributes, which "MUST be in order and they MUST be consecutive" and are joined into one EAP packet (RFC 3579, section 3.1). The decoder joins them and reads the EAP header ([RFC 3748](https://www.rfc-editor.org/rfc/rfc3748.txt), section 4): Code, Identifier, Length and, for a Request or Response, the Type named from IANA's EAP registry (last updated 2026-08-31), with the identity of an EAP-Response/Identity. A packet with EAP-Message and no Message-Authenticator gets RFC 3579's warning.

VLAN assignment is RFC 3580's Tunnel-Type VLAN (13), Tunnel-Medium-Type 802 (6) and Tunnel-Private-Group-ID carrying "a value between 1 and 4094" as a string ([RFC 3580](https://www.rfc-editor.org/rfc/rfc3580.txt), section 3.31). When the three share a Tag, the page names the VLAN.

## Which attributes a packet may carry

The RFCs print tables of which attributes may appear in which packet type, and how often. The decoder applies the tables of RFC 2865 (section 5.44), RFC 2866 (section 5.13), RFC 2868 (section 4), RFC 3162 (section 3), RFC 3579 (section 3.3, for packets with EAP-Message) and RFC 5997 (section 5, Status-Server), and Message-Authenticator's limit of one from RFC 2869 (section 5.19), and warns when an attribute "MUST NOT be present", appears more often than allowed, or is missing where exactly one is required. It also checks the rules in the text: an Access-Request needs a NAS-IP-Address, NAS-Identifier or NAS-IPv6-Address and a User-Password, CHAP-Password, State or EAP-Message, and must not combine two of those credentials; an Accounting-Request needs NAS-IP-Address or NAS-Identifier; a Status-Server needs a Message-Authenticator.

An Access-Request without Message-Authenticator gets one more warning, and it says where the requirement comes from. RFC 2865 as published does not ask for the attribute, and RFC 3579 makes it optional in an Access-Request without EAP-Message ("It MAY be used in any Access-Request", section 3.2). The requirement comes from CVE-2024-3596 and from [draft-ietf-radext-deprecating-radius](https://datatracker.ietf.org/doc/draft-ietf-radext-deprecating-radius/), an Internet-Draft of the IETF's RADIUS Extensions (radext) working group (revision 10 of 3 July 2026; the datatracker shows no RFC number on 8 November 2026). [RFC 2865 erratum 9034](https://www.rfc-editor.org/errata/eid9034), reported on 22 July 2026, records it for readers, "Access-Request packets MUST contain a Message-Authenticator attribute", with the status Held for Document Update since 26 August 2026, not Verified; its notes say "We do not expect to rev 2865".

## Malformed packets and invalid attributes

RFC 6929 separates the two (section 2.8). A **malformed** packet is one whose lengths cannot be followed, and the decoder refuses it with the octet and the rule: fewer than 20 octets, a Length below 20 or above 4096, a Length larger than the octets given, an attribute Length below 2, an attribute that runs past the end, one octet left over. An **invalid attribute** is one whose length can be followed but whose value does not fit its data type (an integer of three octets, text that is not UTF-8, an enum value IANA does not list, a prefix length over 128, a VSA whose Vendor-Id has a non-zero high octet); RFC 6929 says it "MUST NOT result in the implementation discarding the entire packet", so the decoder shows it as octets, marks it with the reason, and reads the rest.

## Reading a capture

The box takes plain hex (one run of digits, as a capture tool's hex stream), bytes separated by spaces, colons, hyphens, dots or commas, with or without 0x, in either case, and hex dumps with offsets in the format Wireshark copies and text2pcap reads: each line "must begin with an offset", of 3 to 8 hex digits with an optional 0x and colon, and "Any text on a line after the bytes is ignored, e.g. an ASCII character dump" (Wireshark text2pcap 4.6.9 manual page); lines that begin with # are comments. Offsets must count the bytes, and a line never holds more bytes than the next offset leaves room for, so an ASCII column that happens to look like hex is not read as bytes. On the last line nothing bounds it, and any such octets beyond the packet's Length are reported as padding.

Copy the RADIUS layer, not the frame. If the octets begin with an Ethernet header (EtherType 0x0800 or 0x86DD, [RFC 894](https://www.rfc-editor.org/rfc/rfc894.txt) and [RFC 2464](https://www.rfc-editor.org/rfc/rfc2464.txt)) or an IPv4 or IPv6 header carrying UDP ([RFC 791](https://www.rfc-editor.org/rfc/rfc791.txt), [RFC 8200](https://www.rfc-editor.org/rfc/rfc8200.txt), [RFC 768](https://www.rfc-editor.org/rfc/rfc768.txt)), the decoder refuses them and says at which octet the RADIUS packet starts. If they read as a TACACS+ header ([RFC 8907](https://www.rfc-editor.org/rfc/rfc8907.txt), section 4.1), it names the header's fields and stops: a TACACS+ body is obfuscated with the shared secret (section 4.5).

**Attributes only** reads attribute octets without the 20-octet header, as RFC 6929's examples print them; the checks that need a Code are then skipped.

## RADIUS and TACACS+

The panel under every reading compares the two protocols from their own documents, with Cisco's tech note 13838, "Compare TACACS + and RADIUS" (updated 30 June 2025, read in a browser on 8 November 2026 because the site refuses automated reads), where it says the same: "RADIUS uses UDP while TACACS+ uses TCP", RADIUS hides only the password and "The remainder of the packet is unencrypted", TACACS+ "leaves a standard TACACS+ header", and "RADIUS combines authentication and authorization" where TACACS+ separates them. Where Cisco writes that TACACS+ encrypts the body, the panel follows RFC 8907, which calls it obfuscation. From the RFCs: UDP 1812, 1813 and 3799 against TCP 49 (RFC 2865, RFC 2866, RFC 5176; RFC 8907, section 3.4); the hidden attributes of RADIUS against the obfuscated TACACS+ body, which RFC 8907 says provides "no meaningful integrity, privacy, or replay protection" (section 10.1); authentication and authorisation in one RADIUS exchange against TACACS+'s three separate ones, "useful for the Device Administration use case, specifically, for authorization and accounting of individual commands in a session" (section 1); network access against device administration; RADIUS over TLS on TCP 2083 ([RFC 6614](https://www.rfc-editor.org/rfc/rfc6614.txt), Experimental) and RADIUS/1.1 ([RFC 9765](https://www.rfc-editor.org/rfc/rfc9765.txt), Experimental) against TACACS+ over TLS 1.3 on TCP 300 ([RFC 9887](https://www.rfc-editor.org/rfc/rfc9887.txt), Proposed Standard). The ports are those of IANA's Service Name and Transport Protocol Port Number Registry, and the statuses those of the RFC Editor's index, both read on 8 November 2026.

If a packet came over RADIUS/1.1, its octets 2 and 5 to 20 are reserved fields and a Token rather than the Identifier and Authenticator, and User-Password is not hidden (RFC 9765, section 4.1); the octets alone do not say which applies, so the decoder reads them as RADIUS.

## Worked examples

- **The Example** is RFC 2865 section 7.1's Access-Request, verbatim: user nemo, a hidden User-Password, NAS-IP-Address 192.168.1.16, NAS-Port 3, computed by the RFC with the shared secret "xyzzy5461". Its Access-Accept answers Service-Type Login (1), Login-Service Telnet (0) and Login-IP-Host 192.168.1.3.
- **RFC 2865 section 7.2** is a CHAP login (CHAP Ident 22) and an Access-Accept for PPP. The Accept's octets carry Framed-Routing 2, Listen for routing packets, where the RFC's text says None; verified erratum 1469 records the difference, and the decoder reads the octets.
- **RFC 2865 section 7.3** is a challenge: an Access-Challenge with Reply-Message "Challenge 32769430.  Enter response at prompt." and State "32769430". The second Access-Request, as printed, has State Length 0x10 where 10 octets follow; the decoder refuses it, and verified erratum 6486's corrected octets decode.
- **The course lab**: an 802.1X Access-Accept placing the port in VLAN 10 with an EAP-Success, an accounting Start for netadmin on SW-CORE-01, the SSH login request (its Share results link zeroes the User-Password and the Message-Authenticator), a Cisco Access-Accept with shell:priv-lvl=15, and a Huawei Access-Accept with HW-Exec-Privilege 15. Their authenticators and hidden octets are placeholders: no secret stands behind them.
- **RFC 5997 section 6** (Status-Server and its replies), **RFC 5176 section 7** (three Disconnect-Requests, the RADIUS octets of its traces) and **RFC 6929 section 9** (18 attribute examples, under Attributes only). RFC 6929 says its examples "show format, rather than consistent meaning", and read against today's registry some are invalid attributes. RFC 5997's section 6.2 reply begins with 02, Access-Accept, though its text calls it an Accounting-Response (5). Its Response Authenticator, 0f 6f 92 14 ..., is the MD5 the RFC describes taken over Code 5 with the RFC's shared secret "xyzzy5461" (computed on 8 November 2026 from the RFC's own octets; over Code 2 it would be 8a 11 b1 d0 ...), so the 02 is the misprint. No erratum on it was listed on 8 November 2026. The listings of all three replies (sections 6.1 to 6.3) also label the 16 octets after the Length "Request Authenticator", where section 3 of the same RFC calls them the Response Authenticator; the decoder uses the name of section 3.

## What it does not do

It does not verify an Authenticator or a Message-Authenticator and does not decrypt any hidden attribute: those need the shared secret, which it never asks for. It does not see the conversation, so it cannot match a reply to its request or check a State against a challenge. It decodes RADIUS on its own: TACACS+ bodies, Diameter and RADIUS/1.1's TLS records are outside it. Vendor sub-attributes are named only for the vendors above, and their values are read in the types their documentation gives, or as octets where it gives none. IANA's names are those of the registries as read on 8 November 2026, and the registries change.

## Share results

Under the headline, **Share results** builds a link to this page, only when you press it and only while the page shows a reading. The link never carries a hidden credential: it carries a copy of the packet in which the octets below are replaced by zero octets of the same length, so every Length still adds up and the receiving page decodes the same structure, with each zeroed field marked **redacted in this link**. There is no switch to include the originals.

What the copy zeroes, and why:

- **User-Password** (RFC 2865, section 5.2), whose hiding RFC 2865 says "might not provide sufficient confidentiality protection" (section 8); **Tunnel-Password**'s String (RFC 2868, section 3.5) and the **MS-MPPE-Send-Key** and **MS-MPPE-Recv-Key** keys (RFC 2548, sections 2.4.2 and 2.4.3), hidden the same way, which RFC 3579 counts as compromised once their key stream is known (section 4.3.4). The Tag and the Salt stay.
- **CHAP-Password**'s response (RFC 2865, section 5.3): RFC 3579 warns that a captured "CHAP challenge and response" allows a dictionary attack offline (section 3.2). The CHAP Ident stays.
- **Message-Authenticator** and the **Response Authenticator** of every reply: "The RADIUS shared secret is vulnerable to offline dictionary attack, based on capture of the Response Authenticator or Message-Authenticator attribute" (RFC 3579, section 4.3.3). The **Request Authenticator** of an Accounting-Request, a Disconnect-Request or a CoA-Request goes too: it is an MD5 over the packet and the shared secret (RFC 2866, section 3; RFC 5176, section 2.3), so the packet alone would let a reader test guesses of the secret. The Request Authenticator of an Access-Request or a Status-Server stays: it is a random number (RFC 2865, section 3; RFC 5997, section 3), and every value computed from it with the secret is zeroed in the copy. The Authenticator of a Code this tool does not know is zeroed.
- **ARAP-Password**, **ARAP-Challenge-Response** and **ARAP-Security-Data** ([RFC 2869](https://www.rfc-editor.org/rfc/rfc2869.txt), sections 5.4, 5.15 and 5.8): the dial-in user's challenge and response, the server's response computed "with the authenticating user's password as the key", and a security module's "challenge or response".
- **Digest-Response**, **Digest-Response-Auth** and **Digest-HA1** ([RFC 5090](https://www.rfc-editor.org/rfc/rfc5090.txt), sections 3.1, 3.4 and 3.19): the first two let each side "prove possession of the password", and H(A1) "makes offline dictionary attacks easier" (section 8.2).
- **PKM-AUTH-Key**'s key, which "MUST be encrypted under the public key from the Subscriber Station certificate" ([RFC 5904](https://www.rfc-editor.org/rfc/rfc5904.txt), section 3.7). The Lifetime and the Sequence stay.
- In **EAP-Message**, the type-data of every EAP Request or Response other than Identity, Notification and Nak: RFC 3748 rates MD5-Challenge, One-Time Password and Generic Token Card "Dictionary attack prot.: No" (sections 5.4 to 5.6), and a GTC Response holds "the Token Card information necessary for authentication"; other methods are defined outside the RFCs this tool reads, so it cannot tell what their data holds. The EAP header and the Type stay; after the header of any other EAP packet the octets are zeroed too.
- **Microsoft**'s challenge responses, password changes, encrypted passwords and keys (RFC 2548: MS-CHAP-Response, MS-CHAP-CPW-1 and -2, MS-CHAP-LM-Enc-PW, MS-CHAP-NT-Enc-PW, MS-CHAP-MPPE-Keys, MS-Old-ARAP-Password and MS-New-ARAP-Password, which are "DES-encrypted", MS-CHAP2-Response and MS-CHAP2-CPW), and **MS-CHAP2-Success**, whose 42-octet authenticator response [RFC 2759](https://www.rfc-editor.org/rfc/rfc2759.txt) computes from the password (section 8.7).
- **MikroTik**'s Mikrotik-Wireless-Enc-Key, "WEP encryption key for the client", and MIKROTIK_WIRELESS_PSK and MIKROTIK_WIRELESS_MPKEY, which the RouterOS 7.24 table names without describing them: a link is better without a value that may be a key.
- In Huawei's **HW-DHCP-Option**, the values of Option 82's sub-options: the Agent Circuit ID names the port ("Switching Hub port number" is one of its uses) and the Agent Remote ID the subscriber (it "MUST be globally unique", and may be "a 'caller ID' telephone number" or "a 'user name'"; RFC 3046, sections 3.1 and 3.2). The codes and lengths stay; an Option 82 whose sub-options do not divide, or a value that does not divide into options, is zeroed whole. Other DHCP options stay.
- Any octets after the **Length**: the tool does not read them (RFC 2865, section 3), and a capture can run into the next packet.

The copy is written as plain hex, 16 octets a line, so the ASCII column and the comment lines of a pasted dump do not travel. The box goes as typed only when nothing in it needs zeroing, or when it is one of the RFCs' published examples, whose octets and shared secret the RFC prints. The popover says which, or how many fields are zeroed, and a caution line says what a copy still shows: user names, NAS and client addresses, MAC addresses and session identifiers of a private network. The link carries the text as `input`, `mode=attributes` when Attributes only is on, and `redacted=1` when it is a copy.

[RFC 3986](https://www.rfc-editor.org/rfc/rfc3986.txt) (section 3.5, read 2026-11-08) has the fragment "separated from the rest of the URI prior to a dereference", so the value is not sent to the server when the link is opened; it stays in the address bar and the history of whoever opens it, and anyone who has the link can read it.

- **How long.** A link carries at most 16,384 characters, the bound the site uses for every value after the `#`; the box holds at most 24,000, so a long dump may get no link.
- **Opening a link.** The box and the mode are filled as a paste would fill them, and the page decodes; with `redacted=1`, every zeroed field is marked while the box still holds that copy (any edit, Example, chip or Clear ends it). A blank value, one over the bound, an unknown mode or a `redacted` other than 1 is ignored. Accepted or not, the values then leave the page's own address at once, without a request.

## Provenance

The engine is fixed parsing over the rules above, two packed tables generated from IANA's RADIUS Types and EAP registries (XML), and a vendor table written from the vendors' documents, with no clock, no network and no randomness. It ships 228 golden vectors (set `radius-packet-decoder-golden-2026-11-08b`): every example packet of RFC 2865 section 7 (with erratum 6486's correction), RFC 5997 section 6 and RFC 5176 section 7 and the 18 attribute examples of RFC 6929 section 9, all agreeing with the RFCs' own listings; the five lab packets; one constructed packet per rule (text formats, refusals, pasted frames, the tables of attributes, EAP, every data type and its invalid forms, tags, hidden attributes, vendors with Huawei's types, HW-Exec-Privilege and HW-DHCP-Option with its Option 82, extended formats, the API); 34 shared copies, one per zeroing rule and per case that goes as typed; and 11 arrivals of those copies, marked or not. Huawei's sub-attributes come from Table 1-11 as read in a browser, saved line by line and checked by SHA-256 against the page, and both the vendor table and the oracle read that file. Every expected value was derived by a separate Python implementation with its own reading of the IANA files and its own tables, not by running this engine, and a mutation test (six deliberate faults, each caught) checked that the vectors bite.

## API

The same engine answers `/api/v1/radius-packet-decoder` on the site's HTTP API; the contract is on the [API page](/api), which also says whether this site serves the API.

- **Request.** The hex itself, as typed in the box (`?input=` on GET, or the POST body), read as a packet; or a JSON object `{"input": "<hex>", "mode": "attributes"}`.
- **Response.** For a packet: `mode`, `format` (`hex` or `dump`), `octets`, `header` (`code`, `codeName`, `codeRow`, `identifier`, `length`, `authenticator`, `authenticatorKind`, `authenticatorRedacted`), `padding`, `paddingRedacted`, `attributes`, `eap`, `vlan`, `example`, `holdsSecret`, `warnings` and `notes`. Each attribute has `index`, `offset`, `type`, `id`, `name`, `length`, `dataType`, `hex`, `value`, `valueName`, `number`, `tag`, `invalid`, `notes`, `vendor` (`id`, `name`, `format`, `subs`), `extended` (`container`, `extType`, `more`, `truncation`, `fragments`, `vendorType`), `tlvs`, `fragmentOf` and `redacted`. `authenticatorRedacted`, `paddingRedacted` and `redacted` mark the fields a Share results copy zeroed and are always false from the API, which reads only `input` and `mode`. Attributes only drops `header`, `padding` and `paddingRedacted`. For the Example the API answers `header.codeName` `Access-Request` and the first attribute's `value` `nemo`.
- **Errors.** HTTP 400, `invalid_input`, with the engine's message, for example `The Length field says 40 octets, but only 26 were given: ...`.
