## What it does

OSPF (Open Shortest Path First) chooses paths by the sum of interface costs, and two routers exchange routes only after they become neighbours. Both go wrong in ways a class meets every week: links of different speeds that end up with the same cost, and neighbours that never come up because one parameter differs. This checker works out both, in two modes:

- **Cost from bandwidth.** For a vendor, a reference bandwidth (or the vendor's default) and one to eight interface speeds: the cost each interface gets by that vendor's own documented rule, which speeds collapse to the same cost, and the smallest reference bandwidth that gives each speed a cost of its own, with the commands that change it.
- **Adjacency mismatch.** For the two interfaces at the ends of one link, side by side: every parameter that does not match, in the order a router checks a received packet, which router drops which packet and under which rule of [RFC 2328](https://www.rfc-editor.org/rfc/rfc2328.txt) (OSPF version 2) or [RFC 5340](https://www.rfc-editor.org/rfc/rfc5340.txt) (OSPF for IPv6), and how far each side gets with the other: no neighbour at all, Init, 2-Way, ExStart, Exchange or Full.

Everything is computed in your browser. No key is ever asked for: the adjacency mode asks only whether the two sides hold the same one.

## Cost: what the standard says, and what it does not

RFC 2328 does not tie cost to bandwidth. The interface output cost is a configured number, "expressed in the link state metric", and "The interface output cost must always be greater than 0" ([RFC 2328](https://www.rfc-editor.org/rfc/rfc2328.txt), appendix C.3); the router-LSA (link state advertisement) carries it in a 16-bit metric field (appendix A.4.2), so it runs from 1 to 65535. Deriving a cost from the interface speed is each vendor's own convention, and the vendors do not agree, so the page applies each vendor's rule as that vendor's own pages state it, read on 8 November 2026, and computes nothing a vendor's pages do not let it compute.

Cisco's, Huawei's, Arista's and Aruba's sites answer HTTP 403 or 406 to the build's plain download. The Huawei pages, Cisco's command reference, Arista's OSPFv2 chapter and both AOS-CX pages were read in a browser on 8 November 2026; Cisco's configuration guide and its `ip ospf mtu-ignore` entry through a second reader. The References list marks each. The browser read corrected the first build: Arista documents `auto-cost reference-bandwidth`, which the second reader had reported absent.

**Collapse.** Two speeds collapse when they get the same documented cost: OSPF then sees the links as equal and cannot prefer the faster one. At the 100 Mbit/s default every speed from 100 Mbit/s up costs 1 on Cisco, Junos, FRRouting and Huawei, so cost becomes hop count. On Arista, until `auto-cost reference-bandwidth` is configured, every Ethernet interface costs 10 whatever its speed. AOS-CX's 100 Gbit/s default keeps campus speeds apart and leaves anything faster than 100 Gbit/s uncomputed. Where a cost is a range, the page says two speeds *may* share a cost when their ranges overlap.

**The smallest reference that tells them apart.** For every vendor with a reference bandwidth (Cisco, Junos, FRRouting, Huawei, Arista and AOS-CX), the page searches the vendor's own configuration grid (whole Mbit/s, except whole bits per second for Junos) for the smallest reference at which every speed you entered gets a documented cost of its own, and prints it with the command (`auto-cost reference-bandwidth 2000`, `set protocols ospf reference-bandwidth 2g`, `bandwidth-reference 2000`). On Arista without the command, that is the value to configure. On AOS-CX, where neither rounding nor a minimum is documented, it is a reference at which every quotient is a whole number of at least 1. Costs change only where the reference crosses a whole multiple of a speed, so those multiples are the only places it looks. It is the smallest, not a recommendation: a larger reference can merge two costs again, the slowest interface's cost must stay at or below 65,535, and Juniper's user guide suggests "Configuring a reference bandwidth value that is based on a multiple of the highest speed interface in your network".

**The same reference everywhere.** Each router advertises its own interface costs and every router adds them up as one scale. FRRouting's documentation states the rule outright: "This configuration setting MUST be consistent across all routers within the OSPF domain." The other vendors' pages read do not say it; the page notes both.

A cost set by hand on the interface (`ip ospf cost`, `ospf cost`, `metric`, `configure ospf vlan <name> cost`) overrides every rule above; the page shows each vendor's command.

## Cost: the inputs

- **Vendor**: one of the nine above.
- **Reference bandwidth**: blank for the vendor's default, or typed as the vendor's CLI takes it: a bare number is whole Mbit/s for Cisco, FRRouting, Huawei, Arista and AOS-CX and bits per second for Junos; a unit works anywhere (`10G`, `100000M`). On Arista a blank reference means `auto-cost reference-bandwidth` is not configured, and a typed one that it is configured with that rate. Only vendors with a reference bandwidth take one (not Switch Engine, Fabric Engine or RouterOS).
- **Interface speeds**: one to eight, each with a unit, separated by commas: `100M, 1G, 2.5G, 10G, 1544k`. Three chips fill common sets.

## Adjacency: the inputs

Both routers side by side, one field per row; a row whose two values differ is marked.

- **OSPF version**: OSPFv2 (RFC 2328) or OSPFv3 (RFC 5340).
- **Label** (optional) and **Router ID** (optional, dotted decimal).
- **Area ID** (dotted decimal or a decimal number) and **area type**: normal, stub or NSSA (not-so-stubby area). Area 0 can be neither: "The backbone cannot be configured as a stub area" (RFC 2328, section 6) and "The backbone is always a Type-5 capable area" ([RFC 3101](https://www.rfc-editor.org/rfc/rfc3101.txt), section 1.3).
- **Network type**: point-to-point, broadcast, NBMA (non-broadcast multi-access) or point-to-multipoint.
- **Address/prefix** (OSPFv2 only), such as `10.0.12.1/30`.
- **HelloInterval** and **RouterDeadInterval** in seconds, and the **interface MTU** (maximum transmission unit) in bytes.
- **Authentication**: in OSPFv2 none, simple password, Keyed-MD5 or HMAC-SHA-1, -256, -384 or -512 ([RFC 5709](https://www.rfc-editor.org/rfc/rfc5709.txt)), with a **Key ID** for the cryptographic ones; in OSPFv3 none, an Authentication Trailer algorithm ([RFC 7166](https://www.rfc-editor.org/rfc/rfc7166.txt)) with an **SA ID**, or IPsec ([RFC 4552](https://www.rfc-editor.org/rfc/rfc4552.txt)). **Same key on both sides** is a yes or no: the key itself is never entered.
- **Router Priority** (optional, 0 to 255) and **Instance ID** (0 by default).

## Adjacency: the rules, in the order a router applies them

1. **The packet header, for every packet.** "The fields specified in the header must match those configured for the receiving interface. If they do not, the packet should be discarded" ([RFC 2328](https://www.rfc-editor.org/rfc/rfc2328.txt), section 8.2):
   - the **Area ID** must match; then, except on point-to-point links, the source must be on the receiving interface's **subnet**, "after masking both addresses with the interface mask";
   - "Locally originated packets should not be passed on to OSPF", so two interfaces with the **same address** each discard the other's packets;
   - the **AuType** must match the receiving interface's (as verified erratum 3734 corrects section 8.2 from "area" to "interface"), and the packet must authenticate: a **simple password** must equal the configured one (appendix D.5.2); for cryptographic authentication the receiver needs a key with the packet's **Key ID** (appendix D.5.3, step 1), and the **algorithm** "is indicated implicitly by the KeyID" ([RFC 5709](https://www.rfc-editor.org/rfc/rfc5709.txt), section 3.4), so a different algorithm or a different **key** produces a different digest and the packet is discarded;
   - an **Instance ID** other than the receiving interface's "MUST be discarded" ([RFC 6549](https://www.rfc-editor.org/rfc/rfc6549.txt), section 3.1, for OSPFv2; [RFC 5340](https://www.rfc-editor.org/rfc/rfc5340.txt), section 4.2.2, checks it with the Area ID).
2. **The Hello's own fields.** "the values of the Network Mask, HelloInterval, and RouterDeadInterval fields in the received Hello packet must be checked against the values configured for the receiving interface. Any mismatch causes processing to stop and the packet to be dropped", except that "on point-to-point networks and on virtual links, the Network Mask in the received Hello Packet should be ignored" (RFC 2328, section 10.5). The **E-bit** must match the area (clear in a stub, set otherwise; section 10.5), and in an NSSA "both the N-bit and the E-bit" must match ([RFC 3101](https://www.rfc-editor.org/rfc/rfc3101.txt), section 2.1).
3. **Who becomes adjacent.** Point-to-point and point-to-multipoint neighbours "always become adjacent"; on broadcast and NBMA networks routers become adjacent only with the Designated Router and the Backup Designated Router, otherwise "the state of the neighbor communication stops at 2-Way" (section 10.4). With both priorities at 0 neither can be elected (appendix C.3).
4. **The Database Description exchange.** "If the Interface MTU field in the Database Description packet indicates an IP datagram size that is larger than the router can accept on the receiving interface without fragmentation, the Database Description packet is rejected" (section 10.6). Hellos carry no MTU, so the two reach 2-Way first. ExStart ends only when one side finds the neighbour's Router ID larger or smaller than its own (section 10.6), which also means two routers with the **same Router ID** never leave ExStart.
5. **After Full.** No Hello field carries the **network type**. A point-to-point side describes the link as a Type 1 link to the neighbour's Router ID (section 12.4.1.1); a broadcast or NBMA side as a link to the Designated Router's transit network (section 12.4.1.2); and the shortest-path calculation skips a link whose far end "does not have a link back" (section 16.1, step 2b). So point-to-point against broadcast can reach Full and still carry no route. Point-to-point against point-to-multipoint describes the link the same way at both ends and works; broadcast against NBMA depends on the NBMA side having the neighbour configured (section 9.5.1).

**What each side sees.** The checks run in each direction. When both routers drop each other's Hellos, neither lists the other at all. When only one drops them, the other hears Hellos that never list it and stays in **Init**. With an MTU mismatch, the side with the smaller MTU rejects the other's Database Description packets and stays in **ExStart**; the side with the larger MTU stays in ExStart if its Router ID is the higher (it insists on being Leader, the term [RFC 9454](https://www.rfc-editor.org/rfc/rfc9454.txt) gives the old master) or moves to **Exchange** as Follower if it is the lower. Without both Router IDs the page says it depends.

**Every mismatch, not only the first.** The first failure decides what the routers do, but the page lists every mismatch, marking those the routers do not reach yet, because fixing one reveals the next.

**Vendor-specific behaviour, labelled.** MTU mismatch detection can be turned off on some platforms: Cisco IOS XE has `ip ospf mtu-ignore` ("OSPF MTU mismatch detection is enabled" by default; the check "is performed when neighbors exchange DBD packets"), and Extreme Fabric Engine 9.4 has `ip ospf mtu-ignore enable`, whose page also says incoming DBD packets are dropped "if their MTU is greater than 1500 bytes". Huawei VRP works the other way round: "By default, an interface adds the MTU 0 (not the actual MTU) in DD packets to be sent and does not check the MTUs in received DD packets", so a Huawei side left at its default neither rejects the other's Database Description (DD) packets nor sends a size the other could reject; `ospf mtu-enable` sends the actual MTU and checks "whether the MTU in a received DD packet is greater than the local MTU", after which "If the interface MTU settings of the local and remote ends are different, an OSPF neighbor relationship cannot enter the Full state", and configuring it restarts the OSPF process. The Juniper, Switch Engine, RouterOS, FRRouting and Arista EOS pages read document no setting to ignore the check (Arista's OSPFv2 chapter mentions the MTU only in command output and for the path MTU discovery of tunnels).

**Huawei's timers, beside a Hello or dead mismatch.** `ospf timer hello` defaults to 10 s on point-to-point and broadcast interfaces and 30 s on NBMA and point-to-multipoint ones, and `ospf timer dead` to 40 s and 120 s; when only the Hello is set, "the dead interval of an OSPF neighbor is four times the value of hello interval", so changing the Hello on a Huawei side changes its dead interval too. A dead interval below 20 s does not take effect as set: "the actual dead interval of an OSPF neighbor is not shorter than 20s" (and the same for a Hello below 5 s), unless `ospf timer hello` is given its `conservative` keyword. The page adds that note for any side with a dead interval below 20 s.

**OSPFv3 differences.** Neighbours are identified by Router ID on every link type, "There is no longer a Network Mask field in the Hello packet", and the source need not be on the link's subnet, because "IPv6 OSPF runs per-link instead of per-IP-subnet" (RFC 5340, sections 4.2.2 and 4.2.2.1); the Hello and dead intervals, the E-bit and N-bit and the MTU are checked as in OSPFv2. "In OSPF for IPv6, authentication has been removed from the OSPF protocol" (section 2.6): with the Authentication Trailer, a router drops Hellos "with the AT-bit clear" (RFC 7166, section 4.6); with IPsec, "OSPFv3 packets that are not protected with AH or ESP MUST be silently discarded" (RFC 4552, section 3).

**Warnings about one side.** A RouterDeadInterval not longer than the HelloInterval (it "should be some multiple of the HelloInterval (say 4)", appendix C.3), a simple password ("Anyone with physical access to the network can learn the password", appendix D.2), and Keyed-MD5 where RFC 5709 makes HMAC-SHA-256 the algorithm implementations MUST support.

## What it refuses, and why

- An interface speed without a unit, outside 1 kbit/s to 10 Tbit/s (the tool's own bounds), not a whole number of bits per second, or entered twice; fewer than one or more than eight speeds.
- A reference bandwidth for a vendor that documents none (Extreme Switch Engine, Extreme Fabric Engine, MikroTik RouterOS), off the vendor's grid (whole Mbit/s everywhere except Junos), or outside the vendor's documented range (Huawei 1 to 2147483648 Mbit/s, Arista 1 to 4294967, AOS-CX 1 to 4000000 Mbps).
- A Router ID or Area ID that is not a 32-bit value; area 0 as a stub or NSSA; an unknown network type or area type.
- An OSPFv2 interface without address and prefix length, and an OSPFv3 interface with one.
- A HelloInterval outside 1 to 65535 (a 16-bit field), a RouterDeadInterval outside 1 to 4294967295 in OSPFv2 (32 bits) or 1 to 65535 in OSPFv3 (16 bits), an MTU outside 1 to 65535, a Key ID outside 0 to 255 (8 bits) or an SA ID outside 0 to 65535 (16 bits), a priority or Instance ID outside 0 to 255.
- Simple password or MD5 in OSPFv3, IPsec in OSPFv2, a Key ID where no cryptographic authentication applies, and two routers with the same label.

## Worked examples

The adjacency Example and chips are the OSPF lab of chapter 4.1 of the open course [LAN Switch Operations and Maintenance](/materials/lan-switch-operations-and-maintenance): SW-CORE-01 with Router ID 10.255.0.1 and its uplink 10.0.12.1/30, the uplink router at 10.0.12.2 on 10.0.12.0/30, area 0, the uplink as a point-to-point network, HMAC-SHA with the same key on both sides. The course gives no timers, no Key ID and no Router ID for the uplink router; the page uses 10 and 40 seconds, HMAC-SHA-256 with Key ID 1, and leaves that Router ID blank.

- **The Example (the lab's step 8, "a different Hello")**: the uplink router at 5 and 20 seconds. Each side drops the other's Hellos (RFC 2328, section 10.5): no neighbour on either side, as the lab's verification expects.
- **A different key** (step 8's first breakage): every packet fails authentication in both directions; no neighbour.
- **MTU 1500 and 9000**: both reach 2-Way; SW-CORE-01 rejects the uplink router's Database Description packets and stays in ExStart; the uplink router stays in ExStart or moves to Exchange depending on the Router ID the course leaves blank.
- **Area 1 by mistake**: every packet is discarded at the Area ID check.
- **Point-to-point against broadcast**: both reach Full, and the link carries no route.
- **The cost Example**: Junos at its 100 Mbit/s default with 100 Mbit/s, 1 Gbit/s and 10 Gbit/s: all three cost 1; the smallest reference that tells them apart is 2 Gbit/s (`set protocols ospf reference-bandwidth 2g`), where they cost 20, 2 and 1.
- **Cisco's own examples**: at the default reference, 64 kbit/s costs 1562 and 1544 kbit/s costs 64; at `auto-cost reference-bandwidth 1000`, 100 Mbit/s (the FDDI link) costs 10 and 1 Gbit/s costs 1; with `auto-cost reference-bandwidth 100000`, 1, 10, 40 and 100 Gbit/s cost 100, 10, 2 and 1.
- **Huawei**: at the default 100 Mbit/s, 1 Gbit/s and 10 Gbit/s cost 1 ("smaller than 1, the cost is 1"); at `bandwidth-reference 1000`, 300 Mbit/s costs 3 (the integer of 3.33).
- **Arista's own examples**: with `auto-cost reference-bandwidth` at 100 a 10 Gbit/s interface costs 1, at 59000 it costs 5 (5.9 rounded down); without the command, 10.
- **AOS-CX**: at the 100000 Mbps default, 1, 10, 25 and 100 Gbit/s cost 100, 10, 4 and 1; 40 Gbit/s (2.5) is shown as 2 or 3, and 400 Gbit/s is not computed.

## What it does not do

It talks to no router. It does not model virtual links, NBMA neighbour lists, more than one key per interface, several areas or instances on one link, the Designated Router election beyond "is anyone eligible", Bidirectional Forwarding Detection, or timers such as RxmtInterval; and it computes no shortest-path tree. Vendor defaults other than the cost rules above and the Huawei MTU and timer notes are not included: read each vendor's documentation and the course's vendor slides.

## Share results

Under the verdict, **Share results** builds a link to this page, only when you press it, that carries the mode and its fields as typed, after the `#`: `mode` (`cost` or `adjacency`); in cost mode `vendor`, `links` and `reference` when typed; in adjacency mode `version` (`2` or `3`), `samekey` (`1` or `0`), and `a` and `b`, each side as thirteen words in a fixed order (label, Router ID, Area ID, area type, network type, address, HelloInterval, RouterDeadInterval, MTU, authentication, Key ID, priority, Instance ID), with `*` for a field left blank. The other mode's fields are not carried, and no key can be, because the page never asks for one. In adjacency mode the popover adds a caution: Router IDs, addresses and labels describe a private network.

[RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (section 3.5, read 2026-11-08) has the fragment "separated from the rest of the URI prior to a dereference", so these values are not sent to the server when the link is opened; they stay in the address bar and the history of whoever opens it, and anyone who has the link can read them.

- **How long.** A link carries at most 16,384 characters, the bound the site uses for every value after the `#`; these fields are far shorter.
- **Opening a link.** The mode and its fields are set as typing would set them, the other mode keeps its values, and the page computes. A link with an unknown mode, vendor, version, switch value, area type, network type or authentication, a field of the other mode, a missing required field, a value on two lines, or a side that is not thirteen words is ignored. Accepted or not, the values then leave the page's own address at once, without a request.

## Provenance

The engine is exact arithmetic (bandwidths as whole bits per second, quotients as exact fractions) and fixed receive checks, with no clock, no network and no randomness. It ships 220 golden vectors (set `ospf-cost-and-adjacency-checker-golden-2026-11-08b`): 99 computed readings (every vendor with three sets of speeds, Cisco's, Juniper's and Arista's documented examples, Huawei's integer rule, AOS-CX's reference, fractions, ranges and the 65,535 ceiling, and every adjacency check in both versions, including the course lab and its breakages) and 121 written out (the sentences that carry the rules, including Huawei's MTU and timer notes and the vendors that document no MTU-ignore setting, the refusals and the API's text). The set was renewed the same evening, when the Huawei, Cisco, Arista and AOS-CX pages were read in a browser: Huawei is computed, Cisco costs an interface faster than the reference at 1, Arista's blank reference became "not configured" and AOS-CX's default became its reference bandwidth. Every expected value of the computed readings was derived by a separate Python implementation, not by running this engine: costs from each vendor's rule in exact fractions, the smallest reference by brute force over the vendor's whole grid rather than the engine's search, and the adjacencies from a per-direction table of the RFC receive checks. A cross-check of every field found no difference.

## API

The same engine answers `/api/v1/ospf-cost-and-adjacency-checker` on the site's HTTP API; the contract is on the [API page](/api), which also says whether this site serves the API.

- **Request, cost.** `{"mode": "cost", "vendor": "juniper-junos", "reference": "", "links": "100M, 1G, 10G"}`; `reference` is optional (blank or absent for the default) and `links` may be a list.
- **Request, adjacency.** `{"mode": "adjacency", "version": 2, "sameKey": true, "a": {...}, "b": {...}}`, each side with `area`, `network`, `hello`, `dead`, `mtu`, `address` (OSPFv2), and optionally `name`, `routerId`, `areaType`, `auth`, `keyId`, `priority` and `instance`.
- **Response, cost.** `mode`, `vendor`, `vendorLabel`, `kind` (`reference`, `table` or `unknown`), `reference` (`bps`, `label`, `isDefault`, `command`) or null (a table or unknown vendor, and Arista while `auto-cost reference-bandwidth` is not configured), `links` (each: `index`, `text`, `bps`, `label`, `quotient`, `cost`, `range`, `basis`), `groups`, `possible`, `allDistinct` (true, false or null), `smallest` (`bps`, `label`, `command`, `costs`) or null, `costCommand`, `verdictText`, `warnings` and `notes`.
- **Response, adjacency.** `mode`, `version`, `a` and `b` (the sides as read), `findings` (each: `check`, `stage`, `reached`, `dropsAtA`, `dropsAtB`, `text`, `vendor`), `viewA` and `viewB` (`none`, `Init`, `2-Way`, `ExStart`, `Exchange`, `ExStart or Exchange`, `Full`), `outcome` (`full`, `full-unused`, `stalled` or `none`), `verdictText`, `warnings` and `notes`.
- **Errors.** HTTP 400, `invalid_input`, with the engine's message, for example `Area 0 cannot be a stub area: "The backbone cannot be configured as a stub area" (RFC 2328 section 6).`
