## What it does

Paste an `openssl s_client` command line, the text it printed, or both, and the tool explains them. Every option is read against the manual pages of OpenSSL 3.5, the long-term-support release (supported until 8 April 2030), the defaults that apply because an option is missing are spelled out, every block of the output is recognised and explained, and the findings worth acting on are listed first, most serious at the top. The command can go in its own box, or on the first line of the output box exactly as a terminal shows it; the tool separates the two. It reads text only: nothing is connected to, resolved, sent or run.

## The command line

Each option is shown in its group (target, server name, verification, trust store, protocol versions, cipher suites and groups, what s_client prints, sessions, client certificate, STARTTLS and ALPN, OCSP stapling, input handling, DANE, PSK, providers) with what it does. Options are read the way OpenSSL's own option parser reads them: `-name` and `--name` are the same option, `--name=value` works, `--` ends the options, and one target word may follow them. An option that is not on the 3.5 page, an option missing its value, and a flag given a value are flagged, since s_client stops with a usage error on each. `-ocsp_check_leaf` and `-ocsp_check_all` arrived in OpenSSL 3.6: the tool explains them, marks them "Not in OpenSSL 3.5", and warns that a 3.5 openssl stops on them.

The defaults are where most surprises live, so the tool states the ones in force:

- **Where it connects.** With no `-connect` and no target word, s_client connects to the local host on port 4433. A `-connect` value with no port keeps that 4433: `openssl s_client -connect example.com` does not talk to port 443. BIO_parse_hostserv(3) says a host given alone leaves the service untouched, and s_client starts from 4433.
- **The name sent as SNI.** Since OpenSSL 1.1.1, without `-servername` the `-connect` host is sent as Server Name Indication when it has the form of a DNS name, nothing is sent when it is an IP address (RFC 6066 does not allow IP literals there), and "localhost" is sent when there is no `-connect` at all. `-servername` sends whatever it is given; `-noservername` sends nothing.
- **Verification never stops the handshake.** The server certificate is always checked and the result printed, but unless `-verify_return_error` is given the handshake carries on whatever the result: the page warns that s_client accepts any chain and that a real application doing this would be open to a man-in-the-middle. `-verify` turns verification on with a depth limit, and still does not abort.
- **No host name is checked.** `-servername` only chooses the SNI. s_client compares the certificate with a name only when `-verify_hostname`, `-verify_ip`, `-verify_email` or DANE asks for it; without one of them, "Verify return code: 0 (ok)" says nothing about whether the certificate belongs to the site.
- **The trust store.** Without `-CAfile`, `-CApath` or `-CAstore`, the default store of that openssl build decides. OpenSSL ships no trust anchors of its own; Linux distributions usually point it at the system store, which is why the same command can verify on one machine and fail on another.
- **Protocol versions.** By default the client offers every version it supports. `-tls1_2` and its siblings allow one version only and cannot be combined with the `-no_*` options, which SSL_CONF_cmd(3) marks deprecated in favour of `-min_protocol` and `-max_protocol`. TLS 1.0 and 1.1 are deprecated (RFC 8996) and refused from security level 1 up, so forcing them also takes a cipher string with `@SECLEVEL=0`, which permits everything.
- **Cipher suites and groups.** `-cipher` sets the TLS 1.2-and-below list only; TLS 1.3 suites are set with `-ciphersuites`. The tool flags each when the version options make it useless. Without `-groups`, OpenSSL 3.5 uses its built-in DEFAULT list, which starts with the hybrid post-quantum X25519MLKEM768 and sends two key shares in the TLS 1.3 ClientHello, X25519MLKEM768 and X25519 (SSL_CTX_set1_groups_list(3), and the list itself in `ssl/t1_lib.c`).

The shell around the command is read too: `echo |` or `</dev/null` in front of s_client end its input at once, and the page notes that a non-interactive run may then close too early, especially with TLS 1.3; a pipe into `openssl x509` is named. Secrets on the command line are flagged: `-keylogfile` (a key log Wireshark can decrypt with), a `pass:` password visible to `ps`, and `-proxy_user` (Basic authentication in the clear to the proxy).

## The output, block by block

The output is read line by line, and every line or block is shown with its line numbers and what it means. What s_client prints is not described in the manual pages, so the layout was read from OpenSSL's own source at the tag `openssl-3.5.9`. Lines that only OpenSSL 3.0 or 3.6 print are read too, from the source at `openssl-3.0.13` and `openssl-3.6.5`, so output from those releases is explained as well:

- `Connecting to 127.0.0.1`: OpenSSL 3.5 prints the address it connected to on standard error as soon as the TCP connection is open (3.0 printed nothing there);
- the `depth=N` / `verify error:num=N:text` / `verify return:1` lines of the verification callback (depth 0 is the server's certificate; OpenSSL walks from the root down; `verify return:1` is s_client choosing to go on). OpenSSL 3.5 writes names as `C=BR, O=Example Lab, CN=www.example.test`; 3.0 wrote `C = BR, O = Example Lab, ...`;
- `CONNECTED(00000003)`, which only says the TCP connection is open (the number is the socket's file descriptor);
- `Certificate chain`, the certificates as the server sent them with `s:` subject, `i:` issuer, `a:` key and signature algorithm and `v:` validity; the page says it is not a verified chain. In 3.5 the key reads `a:PKEY: RSA, 2048 (bit); sigalg: sha256WithRSAEncryption`, or `EC, (prime256v1)` for an elliptic-curve key; 3.0 printed `rsaEncryption` and `RSA-SHA256`;
- `Server certificate` with its PEM (every certificate's PEM with `-showcerts`) and the `subject=` and `issuer=` lines;
- the client certificate request, if any, `Peer signing digest` and `Peer signature type`, which OpenSSL 3.5 gives as the IANA signature scheme name, such as `rsa_pss_rsae_sha256` (3.0 printed `RSA-PSS`); then the server's ephemeral key: `Peer Temp Key` in 3.5, or `Negotiated TLS1.3 group` when TLS 1.3 has no temporary key object to show, as with the hybrid post-quantum group X25519MLKEM768 that two OpenSSL 3.5 peers negotiate by default (3.0 printed `Server Temp Key`);
- `SSL handshake has read N bytes and written M bytes` (0 bytes read means the server sent nothing back);
- `Verification: OK` or `Verification error: text`, and `Verified peername` when a host name was checked;
- `New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384` (or `Reused` for a resumed session). The version on this line is the version that first defined the cipher (SSL_CIPHER_get_version), not necessarily the version negotiated: a TLS 1.1 connection prints `New, TLSv1.0, Cipher is ECDHE-RSA-AES256-SHA`. The negotiated version is on the `Protocol:` line OpenSSL 3.5 prints next, and in the SSL-Session block;
- `Server public key is N bit`, the renegotiation line (`Secure Renegotiation IS supported` up to TLS 1.2; under TLS 1.3, which has no renegotiation, 3.5 prints "This TLS version forbids renegotiation." where 3.0 printed `IS NOT supported`), compression, ALPN, early data;
- `Verify return code: N (text)`, the final verification result, with its meaning;
- the `SSL-Session` block, field by field. In TLS 1.2 it comes once, after the handshake; in TLS 1.3 it comes once per `Post-Handshake New Session Ticket arrived:`, because the server sends its tickets after the handshake (RFC 9846, section 4.7.1). `Master-Key` (TLS 1.2) and `Resumption PSK` (TLS 1.3) are secrets of the session;
- with `-status`, the OCSP line: `OCSP response: no response sent` (OpenSSL 3.5 and 3.0; 3.6 changed it to `no OCSP response received`, or `OCSP responses: no responses sent` under TLS 1.3), or the stapled response printed between two lines of `=` signs, from which the response status, Cert Status and the This Update / Next Update window are read;
- the `-brief` summary, the `-state` steps (`SSL_connect:...` and alerts), the `-msg` messages with their hex bytes, `-debug` reads and writes, `-tlsextdebug` extensions, the raw public key lines of RFC 7250, and OpenSSL error-queue lines, read in the format ERR_print_errors(3) documents (code, library, function, reason, file and line).

Anything else, such as an HTTP response the server sent after the handshake, is shown as data and never dropped.

## Verify return codes

The number in `verify error:num=N` and `Verify return code: N` is an X509_V_ERR code. openssl-verify(1) points to X509_STORE_CTX_get_error(3) for the list and to the header `<openssl/x509_vfy.h>` for the numbers. The tool carries the 96 codes of OpenSSL 3.5.9 (0 to 95) with their constant, the exact text printed and a plain reading, and also the six codes OpenSSL 3.6 added (96 to 101, five of them about OCSP), marked as 3.6 only. The text in the parentheses comes from `crypto/x509/x509_txt.c`: for codes 0 to 94 it is the same in 3.0.13 and 3.5.9, code 95 (a raw public key with nothing configured to trust it) does not exist in 3.0.13, and 3.6 extends code 9 to "certificate is not yet valid or the system clock is incorrect". The ones seen most often: 0 ok, 10 expired, 18 a self-signed server certificate, 19 a self-signed root the client does not trust at the top of the chain, 20 an issuer found neither in what the server sent nor in the trust store, 21 a single certificate that cannot be verified, and 62 hostname mismatch.

## Findings

The findings put the reading together. The most frequent: verification failed (with the code's meaning) and the handshake went on anyway; a missing intermediate, worked out from error 20 or 21 and the chain the server sent (the last certificate sent names an issuer that was never sent); an untrusted root, a self-signed certificate, an expired or not yet valid one, a name mismatch; verification that passed without any host name check; a handshake that failed or read nothing; TLS 1.0 or 1.1 negotiated; the cipher-line version trap; NULL, RC4, export, DES, 3DES or anonymous suites, RSA key transport, finite-field DHE and CBC suites in TLS 1.2 (RFC 9325); a SHA-1 or MD5 signature in TLS 1.2 (RFC 9155); no secure renegotiation or no extended master secret in TLS 1.2 (RFC 9325, section 3.5); a chain out of order or carrying its own root (RFC 9846, section 4.5.1); OCSP not stapled, good, revoked or unknown (RFC 6960); an option OpenSSL 3.5 does not have; and Master-Key or Resumption PSK values to blank out before the output is shared.

## OpenSSL versions

The tool is based on OpenSSL 3.5 because it is the long-term-support release: OpenSSL's release strategy, read on 27 October 2026, gives 3.5 support until 2030-04-08, 3.6 until 2026-11-01 and 4.0 until 2027-05-14, and lists 3.0 as no longer supported; the Downloads page gives 3.5.9, released on 29 September 2026, as the current 3.5 release. Where 3.0 or 3.6 prints a line differently, the tool reads it too and says which release prints it. OpenSSL 4.1.0 was released on 23 October 2026; the 4.1 page removes `-engine` (removed in 4.0), no longer lists `-ssl3`, and makes `-quiet` imply `-verify_quiet`. The tool notes the first two when they appear in a command.

## Examples

The Example button loads a capture in the OpenSSL 3.5 layout: a server that sends its certificate without the intermediate, with the client trusting the root through `-CAfile`. s_client prints error 20 then 21 at depth 0, finishes the handshake anyway, and ends with "Verify return code: 21 (unable to verify the first certificate)".

The golden vectors are nineteen captures against local `openssl s_server` instances and a throwaway test CA: TLS 1.3 with a full chain, TLS 1.2 forced with ALPN h2, TLS 1.1 at security level 0, an unknown CA whose server also sends its root, a self-signed certificate, `-verify_return_error` aborting the handshake, `-showcerts`, `-brief`, `-status` with and without a stapled response, a host name mismatch and a match, an expired certificate (through `-attime`), `-state`, `-msg`, and `-reconnect` in both layouts. Each is a real run made on 27 October 2026 with OpenSSL 3.5.9, built from the official source release after checking its SHA-256 and signature, on both ends of the connection. Two 3.5.9 peers negotiate the hybrid group X25519MLKEM768 under TLS 1.3, so those captures print `Negotiated TLS1.3 group: X25519MLKEM768` where the TLS 1.2 ones print `Peer Temp Key: X25519, 253 bits`, and the `-msg` capture shows the ClientHello carrying that group's key share. Short line-format vectors cover the lines no capture holds, such as the EC `a:PKEY` form, the 3.0 layout and the OCSP lines only 3.6 prints, and twenty-six command lines written for the tests pin the rules of the command reader. Nine share vectors pin the copy a Share results link carries, byte for byte: the Example's two Resumption PSK values, a TLS 1.2 Master-Key, the six of a `-reconnect` run, the four command-line secrets, the sources that stay, the `--opt=value` and continued forms, a command at the top of the output box, and another command's pass phrase; for each, the receiving page reads the same findings, less only the one about printed secrets.

## Related tools and reading

- **The certificates.** Paste the PEM blocks that `-showcerts` prints into the [certificate chain builder](/tools/cert-chain-builder), which puts them in order and names a missing intermediate, or one certificate into the [X.509 certificate decoder](/tools/x509) to read its fields and extensions. The page links both beside the chain it shows.
- **The cipher suite.** The [cipher suite decoder](/tools/cipher) splits the suite on the `Cipher is` line into its key exchange, authentication, cipher and MAC, with its IANA name and recommendation status.
- **A BIG-IP on the other end.** When the server is a BIG-IP virtual server, its client-ssl profile sets the protocol versions and cipher suites s_client meets: the [F5 SSL profile explainer](/tools/f5-ssl-profile-explainer) reads the profile and the [F5 cipher-string explainer](/tools/f5-cipher-string-expander) its cipher string.
- **Sharing a capture.** Blank out the session secrets before a capture goes on a slide or in a ticket. The secrets check of [code to image](/tools/code-to-image) has no rule for them: it leaves a TLS 1.3 `Resumption PSK:` line as printed, and masks a TLS 1.2 `Master-Key:` line only because the line has the shape of a YAML key with a secret-looking name.
- **Reading.** [Reading openssl s_client](/learn/reading-openssl-s-client-output) walks through what the command checks and what the output proves, and [Certificate chains](/learn/certificate-chains-order-anchors-and-what-breaks-them) explains the chain behind errors 20 and 21.

## Share results

Under the findings, **Share results** builds a link to this page, only when you press it, that carries both boxes after the `#` with every secret value replaced by `[redacted]`, never as pasted: each `Master-Key` and `Resumption PSK` of the session blocks, a pass phrase given as `pass:` to `-pass` or `-proxy_pass` (or in that form anywhere else in the text), the key of `-psk` and the password of `-srppass`. Its popover says first what the link carries and how many values were replaced, then offers Copy link and, where the browser has one, its share sheet; the page's address is not changed.

A full s_client output nearly always holds one of the two session secrets, which is why the link carries a copy rather than the paste. Everything else stays: host names, the chain, the `env:`, `file:`, `fd:` and `stdin` sources of a pass phrase ([openssl-passphrase-options(1)](https://docs.openssl.org/3.5/man1/openssl-passphrase-options/), read 2026-10-27, names only the `pass:` form as the password itself), and the ticket bytes, which cannot resume a session without its secret ([RFC 9846](https://www.rfc-editor.org/rfc/rfc9846), sections 4.7.1 and 4.3.11.2, read 2026-10-27). [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (section 3.5, read 2026-10-27) has the fragment "separated from the rest of the URI prior to a dereference", so the copy is not sent to the server when the link is opened; it stays in the address bar and the history of whoever opens it, and anyone who has the link can read it.

- **How long.** At most 16,384 characters in all, the bound the site uses for every value after the `#`; a longer share gets no link, and the popover says how long it is.
- **Opening a link.** Both boxes fill as a paste would (an absent one is emptied) and the page explains them; nothing is connected to, as always. The share vectors check that the receiving page reads the same handshake: the same findings, less only the one about printed secrets. The values then leave the page's address at once, without a request, so a reload or the page's own Share button carries nothing.
- **Links from the serial console.** A report handed over as `#input=` still fills the output box exactly as before; Share results uses names of its own (`command`, `output`), so the two never mix.

## API

The same engine answers the `/api/v1/openssl-s-client-explainer` operation of the site's HTTP API, written out in the OpenAPI contract on the [API page](/api), which also says whether this site serves the API. Blank out Master-Key and Resumption PSK values before sending output anywhere, this API included.

- **Request.** Text: the command line, the output, or the command line followed by the output.
- **Response.** `command` (null when none was found): `found`, `program`, `options` (each with `typed`, `name`, `value`, `known`, `group`, `text`, `dflt`, `since`, `deprecated`, `notIn35`, `problem`), `target` (`raw`, `from`, `host`, `port`, `portDefaulted`, `hostIsIp`), `sni` (`mode`, `value`, `text`), `stdinClosed`, `inputFrom`, `outputTo`, `absent` and `findings`. `output` (null when there was none): `recognised`, `layout` (`full`, `brief` or `unknown`), `lines`, `truncated`, `items` (each with `kind`, `start`, `end`, `text`, `fields`, `connection`, `explain` and `detail`), `connections` (one per handshake: protocol, cipher, verification, chain, keys, ALPN, OCSP, tickets, secrets printed, error reasons) and `findings`. Then `findings` (both lists together, most serious first) and `splitFromOutput`. Every explanation is given as `{"en": ..., "pt": ...}`; every finding has a stable `id`, a `severity` (`high`, `warn` or `info`) and the `source` it rests on.
- **Errors.** Text that is neither a command nor s_client output is not an HTTP error: the findings say `noCommandFound` or `notSClientOutput`.
