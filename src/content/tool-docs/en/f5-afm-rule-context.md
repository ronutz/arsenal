# AFM rule-context & match explainer

BIG-IP AFM - Advanced Firewall Manager's Network Firewall is a hierarchy, and the manual states its order plainly: policies process from the global context, to the route domain, and then to the virtual server or self IP, with management port rules processed separately and unable to take a policy at all. The sentence that decides real outcomes sits right next to that order: when traffic matches a rule within a context, that action is applied and the traffic is processed again at the next context. Accept, in other words, is a ticket to the next checkpoint, not through the whole building. Only accept-decisively ends the walk with a yes, the DevCentral overview's own wording: the packet is permitted and no further context processing is performed. Drop is silent; reject answers with a TCP RST or an ICMP unreachable.

Paste context declarations, the policies they enforce, and a packet line, and the walk runs in that documented order regardless of paste order. Each context renders as a step: the first matching rule, its action, and what the action means right there. Staged policies behave as the manual says staging behaves, the match is reported and connectivity is unaffected. Rule-lists expand in place, matching the recommendation to build policies from them.

Two sourced behaviours are enforced mechanically rather than mentioned in passing. The ICMP restriction, verbatim from the manual: rules for ICMP or ICMPv6 cannot be created on a self IP or virtual server context, and if a rule list smuggles one in, such a rule will be ignored; the walk skips those rules at edge contexts and says so. And the tool never invents a default: if no context terminates the packet and no `default-action` was declared, the walk says the disposition falls to the box's Default Firewall Action rather than guessing which mode you run.

A lone policy gets the audit using the system's own definitions: a rule whose criteria are fully covered by an earlier rule with the same action is redundant, with a different action conflicting, and the manual's special case is honored, accept versus accept-decisively count as conflicting even though both accept. Geolocation, FQDNs, and schedules are recognised and reported, not evaluated: a rule using them stops the walk with an honest indeterminate rather than a guess.

Everything runs locally; nothing you paste leaves the page, and nothing here touches any device.

## Share results

At the top of the reading, **Share results** builds a link to this page, only when you press it, that carries the box as typed after the `#`, and nothing else. Its popover says first what the link carries, then a caution of its own: a firewall policy names your addresses, contexts and virtual servers, so read it before you send the link. Then it offers Copy link and, where the browser has one, its share sheet; the page's address is not changed.

This page skips every stanza it does not explain, so a whole configuration file still gets a reading, and a link of it would carry everything in it. So while the paste holds a secret setting there is no link, and the popover names the setting: a tmsh attribute called `password`, `passphrase` or `secret`, or one whose name ends in them (`encrypted-password`, `proxy-ca-passphrase`, `shared-secret`), `bind-pw` or `community-name`, followed by a value other than `none`; or an `Authorization` header anywhere, as in a monitor's `send` string. F5's [tmsh reference for gtm monitor http](https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/gtm/gtm_monitor_http.html) (read 2026-10-27) lists `password` beside `send`, and [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110) (section 11.6.2, read 2026-10-27) defines the Authorization value as credentials. Remove that line and press again: this page never shows those values, so the rest reads the same.

[RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (section 3.5, read 2026-10-27) has the fragment "separated from the rest of the URI prior to a dereference", so the text is not sent to the server when the link is opened; it stays in the address bar and the history of whoever opens it, and anyone who has the link can read it.

- **How long.** At most 16,384 characters in all, the bound the site uses for every value after the `#`; a longer share gets no link, and the popover says how long it is.
- **Opening a link.** The text fills the box as a paste would and the page reads it; nothing is sent anywhere. The value then leaves the page's address at once, without a request, so a reload or the page's own Share button carries nothing.
