## What it does

This tool decodes the routes block of an F5 Distributed Cloud (XC) HTTP load balancer. Paste the full `http_loadbalancer` object from the Console's JSON view, just its `routes` array, or a create/get API envelope, and the tool walks each route in order and explains it: the route type (simple, redirect, direct-response, or custom), the match conditions (HTTP method, path as prefix / exact / regex, and any header or query-parameter conditions), the action (which origin pool with what weight, or the redirect target, or the direct-response code), any path rewrite and request/response header mutations, the host-rewrite override, and the per-route WAF attachment. It also simulates first-match evaluation - give it a method and a path, and it tells you which route would win. Everything runs in your browser.

## Why order matters

XC evaluates routes in the order they appear, and the first route that matches wins - the same first-match model Envoy uses under the hood. F5's own guidance makes this concrete: when you want a route to take priority, you drag it to the top of the list. That is why the tool numbers routes in order, states the first-match rule up front, and warns you when a catch-all route (prefix `/` or regex `.*` with no header conditions) sits above more specific routes, because those later routes can never be reached.

## The per-route WAF

A load balancer has one WAF policy at its base, but any simple route can override it. In Advanced Options a route can attach its own App Firewall, or disable WAF entirely, or leave it to inherit the load balancer's policy - which is the default. The tool shows each route's WAF mode explicitly and flags routes that disable WAF, because an unprotected route is easy to create by accident and hard to spot in raw JSON.

## The four route types

A simple route forwards matching traffic to an origin pool. A redirect route returns a 3xx to a new protocol, host, and path. A direct-response route returns a fixed status code and body without touching an origin - F5's own examples use this to serve small pages or scripts. A custom route object references a separately defined route, so its match and action live in that referenced object; the tool shows the reference and notes that the details are external, and the first-match simulator flags that such a route could match ahead of the one it picked.

## Share results

Under the request simulator, **Share results** builds a link to this page, only when you press it, that carries a copy of the object after the `#`, never the object as pasted, and the simulator's method and path when a path is typed. A load balancer object can hold secrets this page never reads. F5 Distributed Cloud's schema marks them: SecretType, "used in an object to indicate a sensitive/confidential field", holds the secret either in clear (`clear_secret_info.url`: "For string:/// scheme, Secret needs to be encoded Base64 format") or encrypted by Blindfold (`blindfold_secret_info.location`); the load balancer schema uses it for a certificate's private key, for the `secret_value` of a header or cookie the load balancer adds, and for API testing credentials ([XC API reference for the HTTP load balancer](https://docs.cloud.f5.com/docs-v2/api/views-http-loadbalancer), read 2026-11-01). The plain `value` of a header or cookie the load balancer adds (`request_headers_to_add` and its siblings, "Exclusive with [secret_value]") is a common place for an origin's shared secret too. The page reads each route's match, action, pools, rewrites and WAF, and names the headers a route adds without their values. So the copy replaces every SecretType secret and every added header or cookie value with `[redacted]`, and keeps every other byte as pasted. Before the link is offered, the page reads the copy again and must give the same reading, or there is no link; then the copy and the simulator's path are searched for a credential that is still there (a private key outside SecretType, an `Authorization` header matcher's value, a JWT, a password in a URL, read as in the site's other tools): one means no link, and the popover names its line; a value whose name only looks like a secret is named in the popover instead.

Its popover says first what the link carries, then offers Copy link and, where the browser has one, its share sheet; the page's address is not changed. It also says how many values were replaced, and that the object names your load balancer, pools, hosts and paths, and may name its tenant and namespace. When the copy replaced only header or cookie values (none of them an `Authorization` value or one whose name looks secret, and nothing else in the object a credential), a switch under its first line, **Include the replaced header and cookie values in the link**, lets you send them after all: it is off every time the popover opens; ticked, the link carries the object as pasted, and the popover warns that header and cookie values can hold tokens or an origin's shared secret. The switch is never offered beside a SecretType secret, nor when a credential has stopped the link.

[RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (section 3.5, read 2026-11-01) has the fragment "separated from the rest of the URI prior to a dereference", so what follows the `#` is not sent to the server when the link is opened; it stays in the address bar and the history of whoever opens it, and anyone who has the link can read it.

- **How long.** At most 16,384 characters in all, the bound the site uses for every value after the `#`; a longer share gets no link, and the popover says how long it is.
- **Opening a link.** The copy (or, with the switch, the object) fills the box as a paste would, the simulator's method and path fill, and the page reads it. The values then leave the page's address at once, without a request, so a reload or the page's own Share button carries nothing.
