## What it does

Paste the timing statistics from `tmsh show ltm rule <name> field-fmt`, give your platform's clock speed and core count, and this tool reproduces the four tables of DevCentral's long-standing iRules Runtime Calculator spreadsheet, entirely in the browser. For every event, and for the rule as a whole, it shows a best, typical, and worst case (the minimum, average, and maximum cycles) across four views: raw CPU cycles, runtime in microseconds, the CPU percentage a single request costs, and the maximum requests per second the rule can sustain. Nothing is sent anywhere.

## The measurement it reads

The `timing` command records, per event, the total executions and the cycles consumed as a minimum, average, and maximum. With `field-fmt`, that appears as blocks carrying `avg-cycles`, `min-cycles`, `max-cycles`, and `total-executions` (often abbreviated, like `43.0K`, which the tool expands). The classic one-line form, `HTTP_REQUEST 729 total 0 fail 0 abort | Cycles (min, avg, max) = (3693, 3959, 53936)`, is also accepted. Since version 11.5.0 timing is on by default. **Average is the column to trust.** Maximum is inflated because the first run of a freshly edited rule includes one-time compile-time optimisation, and operating-system scheduling adds overhead at least once per tick; timing itself carries a margin of error of roughly 70 to 100 cycles. Push a large, representative load (ten thousand requests or more) and clear the statistics once after the first hit.

## How the numbers are derived

Everything flows from one figure the spreadsheet calls Cycles per second, which it computes as cores times clock in MHz times one million, straight from `/proc/cpuinfo`; that is the default here, and an optional override accepts a platform-specific number. From it: runtime in microseconds is cycles times one million divided by Cycles per second; the CPU percentage per request is cycles divided by Cycles per second; and the maximum requests per second is Cycles per second divided by cycles. The Total row sums the per-event cycles and derives its microseconds, percentage, and requests from that sum. One caveat the tool restates: these figures assume the work spreads across all cores under CMP, so if a rule modifies a global variable and is demoted to a single core, recompute with a core count of one.

## Share results

Under the Cycles/Sec line, **Share results** builds a link to this page, only when you press it, that carries the four fields as typed: the timing output as `#input=`, then `&clock=`, `&cores=` and `&override=` when they are set. The timing output names the iRule and its events (`myrule:HTTP_REQUEST`); cycle counts and clock speeds are not sensitive. Everything the link carries goes after the `#`, which [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (section 3.5, read 2026-10-27) has "separated from the rest of the URI prior to a dereference": a browser does not send it to the server when the link is opened, but it stays in the address bar and history of whoever opens it, and anyone who has the link can read it.

- **How long.** A link carries at most 16,384 characters, the bound the site uses for every value after the `#`; a longer timing output gets no link, and the popover says how long it is.
- **Opening a link.** The four fields fill as typing would (a field the link does not carry is empty) and the tables are computed. The timing output is accepted as pasted (the page says when it finds no events); a number field longer than 32 characters makes the whole link ignored. Accepted or not, the values then leave the page's own address at once, without a request, so a reload, a bookmark or the page's own Share button carries nothing you did not choose to share.
