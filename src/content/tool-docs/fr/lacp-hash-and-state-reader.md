## Ce que fait l’outil

Un groupe d’agrégation de liens (LAG, link aggregation group) regroupe des liens parallèles en un seul, et le protocole LACP (Link Aggregation Control Protocol) permet aux deux extrémités de s’accorder sur les liens qui en font partie. Deux questions se posent chaque fois qu’un agrégat se comporte mal : sur quel membre passe ce flux, et que se disent les deux extrémités ? La page répond aux deux, avec deux modes :

- **Quel lien.** Pour un bond Linux, le membre qui transporte un flux, calculé avec le hachage d’émission du pilote lui-même : chaque valeur intermédiaire, le membre qu’emprunte le flux quand chacun des autres membres tombe et, si vous le demandez, la répartition d’une série de flux sur les membres. Pour le même nombre de membres, la page affiche le partage que Cisco documente pour le hachage de ses Catalyst 6500/6000, ce qui explique pourquoi 2, 4 et 8 membres se partagent équitablement le trafic, et pas 3, 5, 6 ni 7.
- **Indicateurs d’état.** Les octets d’état de l’acteur et du partenaire d’une LACPDU (LACP data unit, l’unité de données de LACP), ou les indicateurs qu’affiche une commande show, lus bit par bit de LACP_Activity à Expired, avec les temporisateurs qui en découlent et un verdict pour la paire. Le PortState de Huawei peut être saisi tel que l’affiche `display eth-trunk`, ou la sortie entière collée : chaque ligne de membre est alors lue.

Tout est calculé dans votre navigateur.

## Pourquoi seul le hachage Linux est calculé

La façon dont un agrégat répartit les trames est laissée à chaque implémentation. Le module de gestion d’IEEE 802.1AX lui-même indique que la description de l’algorithme de distribution pourrait contenir des informations sur l’algorithme utilisé (« could include information about the distribution algorithm in use ») et que ce contenu est propre à chaque constructeur (« The contents are vendor specific ») ([IEEE8023-LAG-MIB](https://www.ieee802.org/1/files/public/MIBs/IEEE8021-AX-MIB-202005290000Z.mib), dot3adAggDescription). Un membre ne peut être calculé que là où une implémentation publie entièrement son hachage, et l’une le fait : le pilote de bonding Linux, dont le [HOWTO](https://docs.kernel.org/networking/bonding.html) donne chaque politique sous forme de formule et dont le code source, [bond_main.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/net/bonding/bond_main.c), fixe chaque détail. Le bonding de RouterOS, chez MikroTik, décrit les mêmes noms de politiques en toutes lettres et renvoie à la documentation Linux ([MikroTik, Bonding](https://manual.mikrotik.com/docs/7.24/high-availability-solutions/bonding/)).

Les constructeurs de commutateurs documentent les champs qui entrent dans le hachage, pas la fonction : la page les nomme donc et ne calcule rien pour eux :

- **Cisco.** Sur le Catalyst 6500/6000, l’algorithme de hachage propriétaire calcule une valeur dans un intervalle fixe (« The Cisco-proprietary hash algorithm computes a value in the range 0 to 7 »), et le document indique combien de ces valeurs chaque port accepte, pas le hachage ([Cisco, document 12023](https://www.cisco.com/c/en/us/support/docs/lan-switching/etherchannel/12023-4.html)). Le guide du Catalyst 9300 liste les méthodes load-balance, avec src-mac par défaut (« The default is src-mac »), et précise que le commutateur réduit à une valeur numérique une partie du motif binaire formé par les adresses de la trame (« part of the binary pattern that is formed from the addresses in the frame to a numerical value ») ([Cisco, Configuring EtherChannels, IOS XE 17.18](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-18/configuration_guide/lyr2/b_1718_lyr2_9300_cg/configuring_etherchannels.html)).
- **Juniper.** Le hachage utilise des champs du paquet ainsi que certaines valeurs internes, comme les identifiants du port source et de l’équipement source (« as well as on some internal values like source port ID and source device ID ») ([Juniper, Hashing Algorithms for LAG and ECMP](https://www.juniper.net/documentation/us/en/software/junos/interfaces-ethernet-switches/topics/topic-map/hashing-algoriths-lag-bundle-ecmp.html)), qu’aucune lecture d’un paquet ne permet de connaître.
- **Arista.** Les entrées de l’algorithme de hachage varient selon la plateforme (« Hashing algorithm inputs varies by switch platform ») ([Arista EOS, Port Channels and LACP](https://www.arista.com/en/um-eos/eos-port-channels-and-lacp)).
- **HPE Aruba.** AOS-CX propose l2-src-dst, l3-src-dst et l4-src-dst sans décrire la fonction ([AOS-CX 10.16, LACP configuration settings](https://arubanetworking.hpe.com/techdocs/AOS-CX/10.16/HTML/link_aggregation/Content/Chp_LAG/lac-cnf-set-10.htm)).
- **Extreme.** Switch Engine nomme xor, crc-16 et crc-32 comme algorithmes de hachage, sans dire comment les champs leur sont présentés ([Switch Engine 33.7.1 Command References](https://documentation.extremenetworks.com/Switch%20Engine%20v33.7.1%20Command%20References/downloads/Switch_Engine_33_7_1_Command_References.pdf), configure sharing address-based custom).
- **Huawei.** La référence des commandes des S5700 et S6700 liste les modes `load-balance` `dst-ip`, `dst-mac`, `src-ip`, `src-mac`, `src-dst-ip`, `src-dst-mac` et `enhanced profile`, indique le mode par défaut (« The default load balancing mode is src-dst-ip ») et précise que l’équilibrage ne vaut que pour le trafic sortant, si bien que les deux extrémités peuvent avoir des modes différents (« Load balancing is valid only for outgoing traffic; therefore, the load balancing modes for the interfaces at both ends of the link can be different »). Une fois un mode défini, les facteurs de hachage varient selon le type de paquet et le modèle d’équipement (« the hash factors used to calculate the outbound interface vary according to the packet type and device model ») : les paquets de couche 2 se rabattent sur les adresses MAC source et destination ; le S5736-S utilise src-dst-ip avec les ports source et destination TCP ou UDP, que ce paramètre soit configuré ou non (« regardless of whether you configure this parameter »), et ne prend en charge qu’un seul mode d’équilibrage pour tout le commutateur ; et sur les S5731-H, S5731-S, S5731S-S, S5731S-H, S5732-H, S6730-H, S6730S-H, S6730-S et S6730S-S, quel que soit celui des six modes de base qui est configuré, la répartition se fait selon le numéro de port source physique (« packets are load balanced based on physical-layer source port numbers in the packets »). La fonction elle-même n’est pas donnée : rien n’est donc calculé pour Huawei, et c’est une commande qui permet de vérifier les facteurs de hachage (« You can run the display eth-trunk load-balance command to check the hash factors used when the outbound interface is calculated ») ([Huawei, Link Aggregation Commands, V200R025C00](https://support.huawei.com/enterprise/en/doc/EDOC1100514211/54c5f31b/link-aggregation-commands), consulté dans un navigateur, car le site refuse les lectures automatisées).
- **Puces de commutation MikroTik.** Un bond déchargé sur la puce de commutation y est haché, et le manuel ne donne aucune formule pour ce cas.

Pour interroger le commutateur lui-même, le document 12023 de Cisco montre la commande `test etherchannel load-balance interface port-channel` du Catalyst 6500, qui répond avec le port qu’utiliserait une paire d’adresses donnée.

## Quel lien : les entrées

- **Politique de hachage en émission** : les valeurs `xmit_hash_policy` du HOWTO, `layer2` (par défaut), `layer2+3`, `layer3+4` et `vlan+srcmac`. Le formulaire n’affiche que les champs que lit la politique.
- **Ordre des octets du processeur** : little-endian (par défaut) ou big-endian, pour `layer2+3` et `layer3+4`. Une valeur de 32 bits occupe quatre octets : un processeur big-endian stocke son octet de poids fort à l’adresse la plus basse, un processeur little-endian son octet de poids faible. Parmi les architectures Linux que liste Debian, amd64, arm64, ppc64el, riscv64 et loong64 sont little-endian, et s390x, ppc64, mips et sparc64 sont big-endian ([Debian Wiki, ArchitectureSpecificsMemo](https://wiki.debian.org/ArchitectureSpecificsMemo), consulté dans un navigateur, car le site refuse les lectures automatisées). L’article [Big-endian et little-endian](/learn/big-endian-and-little-endian) explique l’ordre des octets en détail ; son effet sur ce hachage est décrit dans les règles ci-dessous.
- **Membres pouvant émettre** : de 2 à 8, numérotés à partir de 0.
- **MAC source et destination** (`layer2`, `layer2+3` ; `vlan+srcmac` ne lit que la source), en notation à deux-points, à tirets ou pointée de Cisco.
- **Adresses IP source et destination**, IPv4 ou IPv6, de la même famille (toutes les politiques sauf `vlan+srcmac` ; pour `layer2`, elles ne fixent que l’EtherType).
- **Protocole, port source et port destination** (`layer3+4`) : TCP ou UDP, ports de 0 à 65535.
- **ID de VLAN et priorité** (`vlan+srcmac`) : un ID de VLAN de 1 à 4094, ou un champ vide pour une trame non étiquetée, et une priorité de 0 à 7 ; les MIB IEEE 802.1 n’admettent pas 0 ni 4095 comme identifiants de VLAN et donnent les priorités de 0 à 7 ([IEEE8021-TC-MIB](https://www.ieee802.org/1/files/public/MIBs/IEEE8021-TC-MIB.mib), IEEE8021VlanIndex et IEEE8021PriorityValue).
- **Répartition** (facultative) : un champ lu par la politique, que la page fait croître à partir de la valeur saisie, sur 1 à 4096 flux.

## Quel lien : les règles

Les formules du HOWTO, avec les détails que fixe son code source :

```text
layer2:    hash = source MAC[5] XOR destination MAC[5] XOR packet type ID
layer2+3:  hash = source MAC[5] XOR destination MAC[5] XOR packet type ID
           hash = hash XOR source IP XOR destination IP
           hash = hash XOR (hash RSHIFT 16)
           hash = hash XOR (hash RSHIFT 8)
layer3+4:  hash = source port, destination port (as in the header)
           hash = hash XOR source IP XOR destination IP
           hash = hash XOR (hash RSHIFT 16)
           hash = hash XOR (hash RSHIFT 8)
           hash = hash RSHIFT 1
vlan+srcmac: hash = (vlan ID) XOR (source MAC vendor) XOR (source MAC dev)
```

et, dans tous les cas, le hachage est réduit modulo le nombre de membres (« is reduced modulo slave count ») ([Linux bonding HOWTO](https://docs.kernel.org/networking/bonding.html), xmit_hash_policy).

- **L’identifiant de type de paquet** est l’EtherType de la trame sous forme de nombre : le pilote applique un XOR à `be16_to_cpu(ep->h_proto)` (bond_eth_hash), donc 0x0800 pour IPv4 et 0x86DD pour IPv6 ([IANA, IEEE 802 Numbers](https://www.iana.org/assignments/ieee-802-numbers/ieee-802-numbers.txt)).
- **Les adresses IPv6** sont d’abord hachées par une fonction dédiée (« first hashed using ipv6_addr_hash », HOWTO), le XOR des quatre mots de 32 bits de l’adresse ([include/net/ipv6.h](https://raw.githubusercontent.com/torvalds/linux/master/include/net/ipv6.h)).
- **L’ordre des octets du processeur.** Le pilote combine par XOR les adresses telles que les renvoient `flow_get_u32_dst` et `flow_get_u32_src`, c’est-à-dire les 32 bits bruts stockés dans le paquet, et copie les ports avec `memcpy` depuis une structure qui contient d’abord le port source ([include/net/flow_dissector.h](https://raw.githubusercontent.com/torvalds/linux/master/include/net/flow_dissector.h)). Un processeur big-endian lit ces octets poids fort en premier, ce qui correspond à la formule du HOWTO telle qu’écrite ; un processeur little-endian les lit dans l’autre sens et obtient un hachage différent. Les champs pris en compte, les deux repliements, le décalage et le modulo restent les mêmes. `layer2` et `vlan+srcmac` lisent des octets isolés, ou construisent leurs nombres octet par octet : l’ordre des octets ne les change donc pas. La page affiche les deux mots tels que les lit le processeur choisi. L’ordre des octets ne change le membre que si le nombre de membres n’est pas une puissance de deux. Les deux repliements de `bond_ip_hash` (`hash ^= (hash >> 16); hash ^= (hash >> 8);`) laissent dans l’octet de poids faible le XOR des quatre octets du mot, que leur inversion ne change pas, et un modulo par 2, 4 ou 8 ne lit que des bits de cet octet, y compris après le décalage de `layer3+4`. Sur ce moteur, le 8 novembre 2026, pour 4000 flux aléatoires (adresses IPv4, adresses MAC et ports aléatoires) avec `layer2+3` et `layer3+4` et chaque nombre de membres de 2 à 8, les deux ordres ont choisi le même membre dans la totalité des 24 000 cas à 2, 4 ou 8 membres, et un membre différent dans 23 031 des 32 000 cas à 3, 5, 6 ou 7 membres. Le flux de l’exemple montre les deux : avec 2 ou 4 membres, il utilise le membre 0 ou 2 sur l’un comme sur l’autre processeur ; avec 5 membres, le membre 2 sur un processeur little-endian et le membre 4 sur un processeur big-endian. Les vecteurs de référence (golden vectors) fixent les deux cas.
- **Le bit de poids faible.** `layer3+4` le supprime à la fin ; selon le commentaire du code source, c’est pour traiter le motif courant des ports pairs (« to deal with the common even ports pattern », bond_ip_hash) : deux ports qui ne diffèrent que par leur dernier bit atterrissent donc généralement sur le même membre.
- **Le VLAN.** `vlan+srcmac` applique un XOR à `skb_vlan_tag_get(skb)`, c’est-à-dire à l’ensemble des informations de contrôle de l’étiquette (tag control information), `vlan_tci` ([include/linux/if_vlan.h](https://raw.githubusercontent.com/torvalds/linux/master/include/linux/if_vlan.h)) : les bits de priorité comptent donc autant que l’ID de VLAN ; une trame non étiquetée compte pour 0. La page prend l’indicateur drop eligible à 0.
- **Quel membre.** Les membres pouvant émettre (en mode 802.3ad, ceux de l’agrégateur actif) sont listés dans l’ordre où ils ont rejoint le bond (bond_update_slave_arr), et le pilote prend `slaves->arr[hash % count]` (bond_xmit_3ad_xor_slave_get). Quand un membre tombe, la liste est reconstruite sans lui et le modulo porte sur un membre de moins : la page montre donc, pour chaque membre tour à tour, où va le flux si celui-ci tombe en panne. Souvent, un flux se déplace alors que son propre membre est resté actif.
- **Les ports.** `layer3+4` lit les ports TCP et UDP des paquets non fragmentés ; pour les paquets fragmentés et tout autre trafic, l’information de port est omise (« For fragmented TCP or UDP packets and all other IPv4 and IPv6 protocol traffic, the source and destination port information is omitted », HOWTO). La page ne lit que TCP et UDP.

**Le partage de Cisco.** Pour le nombre de membres choisi, la page affiche aussi la table que donne le document 12023 pour le Catalyst 6500/6000, les proportions des valeurs qu’accepte chaque port (« the ratios of the values that each port accepts ») : 4:4 pour deux ports, 3:3:2 pour trois, 2:2:2:2 pour quatre, 2:2:2:1:1 pour cinq, 2:2:1:1:1:1 pour six, 2:1:1:1:1:1:1 pour sept et une valeur chacun pour huit. D’où la conclusion du document : un équilibrage parfait, même avec des adresses aléatoires, n’est possible qu’avec deux, quatre ou huit ports (« you can only achieve perfect load balancing, even with random addresses, if you have two, four, or eight ports »). La page affiche chaque part des 8 valeurs en pourcentage ; c’est la table documentée, pas un calcul du hachage de Cisco.

**La répartition.** Avec une répartition, la page calcule le membre de chaque flux de la série et les compte par membre. Elle qualifie la répartition d’équilibrée quand aucun membre ne transporte plus d’un flux de plus qu’un autre, et elle liste les membres des 16 premiers flux, ce qui fait apparaître des motifs comme les paires que forme `layer3+4` avec des ports source consécutifs.

**Chaque extrémité ne hache que ce qu’elle envoie.** Le choix du membre pour le trafic sortant suit la politique de hachage en émission (« Slave selection for outgoing traffic is done according to the transmit hash policy », HOWTO) : le commutateur choisit le membre du trafic retour avec son propre hachage, que la page ne calcule pas.

## Indicateurs d’état : les entrées

- **Écriture des valeurs** :
  - **Octet** : tel que le transporte la LACPDU, en hexadécimal avec `0x` (`0x3D`, la forme de la colonne State de `show lacp neighbor` chez Cisco, qui donne 0x3D comme valeur attendue, [document 220367](https://www.cisco.com/c/fr_ca/support/docs/switches/catalyst-9300-series-switches/220367-troubleshoot-etherchannels-on-catalyst-9.html)), en décimal (`61`, comme Linux affiche `port state` dans /proc/net/bonding, [bond_procfs.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/net/bonding/bond_procfs.c)) ou en binaire avec `0b`. Un `3D` seul est refusé, pour ne jamais être lu comme un nombre décimal.
  - **SNMP BITS** : `dot3adAggPortActorOperState` ou `dot3adAggPortPartnerOperState` tels que SNMP les renvoie, un octet en hexadécimal (avec ou sans `0x`) ou huit chiffres binaires avec `0b`.
  - **Indicateurs Extreme** : les huit positions de Switch Engine dans l’ordre de sa légende (« A-Activity, T-Timeout, G-Aggregation, S-Synchronization C-Collecting, D-Distributing, F-Defaulted, E-Expired »), avec un tiret pour un bit à 0, comme dans son exemple `A-GSCD--` (Switch Engine 33.7.1 Command References, show lacp member-port).
  - **Lettres Arista** : la légende d’EOS (« A = Active, P = Passive; S=ShortTimeout, L=LongTimeout; G = Aggregable, I = Individual; s+=InSync, s-=OutOfSync; C = Collecting, X = state machine expired, D = Distributing, d = default neighbor state »), comme dans son exemple `ALGs+CD` ([Arista EOS](https://www.arista.com/en/um-eos/eos-port-channels-and-lacp)). Une lettre de chaque paire est obligatoire, C, X, D et d sont facultatives, et chaque lettre figure une seule fois, dans n’importe quel ordre.
  - **PortState Huawei** : la colonne PortState de `display eth-trunk` (« eight bits, such as 10111100 »), affichée de Bit 1 à Bit 8 ([Huawei, Link Aggregation Commands, V200R025C00](https://support.huawei.com/enterprise/en/doc/EDOC1100514211/54c5f31b/link-aggregation-commands), consulté dans un navigateur, car le site refuse les lectures automatisées). Saisissez le PortState de l’acteur et celui du partenaire, ou collez la sortie entière : la page lit chaque ligne de membre de sa table Local (port, Status, PortType, PortPri, PortNo, PortKey, PortState, Weight) et de sa table Partner (port, priorité système, ID système, PortPri, PortNo, PortKey, PortState, sous une ligne d’en-tête qui commence aussi par ActorPortName), les apparie par nom de port, affiche telles qu’imprimées les lignes d’en-tête qu’elle reconnaît (LAG ID, WorkingMode, Hash arithmetic, System Priority, System ID), et lit en détail le membre que vous choisissez, le premier par défaut. Les lignes sont reconnues à leur forme : les mots d’en-tête peuvent donc varier. `display eth-trunk` sans numéro liste tous les trunks, chacun introduit par une ligne comme `Eth-Trunk10's state information is:` ; la page lit le premier trunk qui a des lignes de membres, affiche son nom et signale que les autres n’ont pas été lus.
- **Acteur** : l’état de l’extrémité dont vous lisez la sortie.
- **Partenaire** (facultatif) : l’état du partenaire tel que cette extrémité le rapporte, c’est-à-dire ce qu’elle a reçu en dernier, ou ses valeurs par défaut quand Defaulted est à 1.

La commande `show lacp interfaces` de Juniper affiche les indicateurs en toutes lettres (Activity, Timeout, Aggr, Syn, Col, Dist, Def, Exp) : relevez-les et saisissez l’octet, ou comparez-les à la liste des bits de la page.

## Indicateurs d’état : les règles

**Les bits.** La norme IEEE 802.1AX elle-même est proposée via l’IEEE GET Program, derrière un compte IEEE ([IEEE SA, 802.1AX-2020](https://standards.ieee.org/ieee/802.1AX/6768/)), et n’a pas été lue. Son module MIB publié donne l’ordre, du premier bit (« The first bit corresponds to bit 0 of the Actor_State (LACP_Activity), the second bit corresponds to bit 1 (Short_Timeout), the third bit corresponds to bit 2 (Aggregation) ») jusqu’au dernier (« bit 7 (Expired) ») ([IEEE8023-LAG-MIB](https://www.ieee802.org/1/files/public/MIBs/IEEE8021-AX-MIB-202005290000Z.mib), dot3adAggPortActorAdminState). Le pilote Linux donne aux mêmes bits leur place dans l’octet, de `LACP_STATE_LACP_ACTIVITY 0x1` à `LACP_STATE_EXPIRED 0x80` ([include/uapi/linux/if_bonding.h](https://raw.githubusercontent.com/torvalds/linux/master/include/uapi/linux/if_bonding.h)) : le bit 0 est donc le bit de poids faible de l’octet, et 0x3D signifie Activity, Aggregation, Synchronization, Collecting et Distributing.

**La forme SNMP.** La MIB déclare l’état comme un type BITS, et SNMP envoie une valeur BITS en plaçant les bits nommés, du premier au dernier, du bit de poids fort au bit de poids faible du premier octet (« all the named bits ... commencing with the first bit and proceeding to the last bit, ... placed in bits 8 (high order bit) to 1 (low order bit) of the first octet ») ([RFC 3417](https://www.rfc-editor.org/rfc/rfc3417.txt), section 8). LACP_Activity est le premier bit nommé : SNMP montre donc l’octet avec ses bits inversés, et 0x3D sur le fil se lit 0xBC via SNMP. La page affiche chaque état sous les deux formes.

**Le PortState de Huawei.** Huawei numérote les huit caractères de Bit 1 à Bit 8 en partant de la gauche. Sa table décrit Bit 1 comme indiquant si l’interface membre est un acteur, avec une valeur fixe (« Whether the member interface is an Actor. This bit has a fixed value 1 »), Bit 2 comme le délai d’expiration (1 court, 0 long ; « By default, an Eth-Trunk member interface uses the long timeout interval (90s) »), Bit 3 comme l’autorisation d’agréger l’interface membre, Bit 4 comme son ajout au groupe d’agrégation (« added to the link aggregation group (LAG) »), Bits 5 et 6 comme la capacité à recevoir et à envoyer des LACPDU, Bit 7 comme des LACPDU qui portent des valeurs de paramètres par défaut, et Bit 8 comme la machine d’état de réception de l’acteur à l’état Expired. Ce sont les bits 0 (LACP_Activity) à 7 (Expired) de la MIB, écrits poids faible en premier, soit l’inverse de l’octet en binaire : `10111100` tel qu’affiché correspond à 0b00111101, soit 0x3D, la valeur attendue par Cisco, et aux mêmes huit chiffres que la valeur SNMP BITS 0xBC écrite en binaire. La page étiquette chaque bit avec ses deux numéros (Bit 1 · bit 0) et donne aussi chaque état sous la forme Huawei. Huawei formule les Bits 5 et 6 en termes de LACPDU, là où la MIB nomme Collecting et Distributing ; la page garde les noms de la MIB et les significations de Juniper ci-dessous. La colonne Status reprend les termes de Huawei : Selected pour une interface membre active (« Selected: A member interface in Selected state is active »), Unselect pour une interface inactive, et ForceFwd pour une interface qui peut transmettre du trafic (« can forward Layer 2 traffic »). Dans l’exemple de Huawei, Eth-Trunk10 a trois membres : GigabitEthernet0/0/2 et 0/0/3 sont Selected avec 10111100 aux deux extrémités (0x3D, agrégés), et GigabitEthernet0/0/4 est Unselect avec 10100000 de ce côté et 10110000 du côté du partenaire (0x05 et 0x0D : cette extrémité n’est pas synchronisée, le partenaire l’est mais ne collecte ni ne distribue).

**Signification de chaque bit**, d’après `show lacp interfaces` de Juniper ([Juniper](https://www.juniper.net/documentation/us/en/software/junos/cli-reference/topics/ref/command/show-lacp-interfaces.html)) :

| Bit | Nom | À 1 | À 0 |
|---|---|---|---|
| 0 | LACP_Activity | Actif : participe quelle que soit la valeur de contrôle du partenaire (« regardless of the partner's control value ») | Passif : n’émet pas de LACPDU, sauf si la valeur de contrôle du partenaire est Active (« not transmitting LAC PDUs unless its partner's control value is Active ») |
| 1 | LACP_Timeout | Délai d’expiration court (fast) | Délai d’expiration long (slow) |
| 2 | Aggregation | Peut être agrégé | Fonctionne uniquement comme lien individuel (« operate only as an individual link ») |
| 3 | Synchronization | Affecté au bon groupe d’agrégation (« allocated to the correct link aggregation group »), avec un agrégateur compatible et une identité cohérente avec l’ID système et la clé opérationnelle transmis (« consistent with the system ID and operational key information transmitted ») | Pas dans la bonne agrégation (« not in the right aggregation ») |
| 4 | Collecting | Collecte des trames entrantes activée | Non activée |
| 5 | Distributing | Distribution des trames sortantes activée | Actuellement désactivée (« currently disabled ») |
| 6 | Defaulted | Utilise les informations opérationnelles par défaut du partenaire, configurées administrativement (« the default operational partner information, administratively configured for the partner ») | Informations du partenaire reçues dans une LACPDU (« received in an LACP PDU ») |
| 7 | Expired | La machine de réception est à l’état Expired | Non expiré |

**Les temporisateurs.** Juniper décrit les deux cadences ainsi : « In a fast timeout, PDUs are sent every second and in a slow timeout, PDUs are sent every 30 seconds. LACP timeout occurs when 3 consecutive PDUs are missed », soit 3 secondes ou 90 secondes (Juniper, voir plus haut) ; la commande `lacp rate` de Cisco donne la cadence rapide (« the fast rate, once every 1 second ») et la cadence normale (« every 30 seconds ») ([Cisco, Command Reference, IOS XE 17.18](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-18/command_reference/b_1718_9300_cr/layer_2_3_commands.html)) ; chez Extreme, le délai d’expiration LACP vaut « either 90 seconds, long, or 3 seconds, short », long par défaut (configure sharing lacp timeout). Le bit Timeout est une demande adressée au partenaire : le `lacp_rate` de Linux est la cadence à laquelle l’extrémité demande à son partenaire d’émettre des LACPDU (« rate in which we'll ask our link partner to transmit LACPDU packets »), lente (30 secondes) par défaut (HOWTO). Dans le pilote, une extrémité émet rapidement tant que le bit Timeout de son partenaire est à 1, lentement sinon, et applique à son partenaire le délai d’expiration que fixe son propre bit ; quand aucune extrémité n’est active, il n’y a aucune émission périodique (ad_periodic_machine et ad_rx_machine, [bond_3ad.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/net/bonding/bond_3ad.c), dont les constantes sont `AD_FAST_PERIODIC_TIME 1`, `AD_SLOW_PERIODIC_TIME 30` et le triple de chacune pour les délais d’expiration). Pour la commande `lacp timeout` de Huawei : avec `fast`, l’intervalle dans lequel un Eth-Trunk doit recevoir des LACPDU est de 3 secondes, et l’équipement distant envoie alors une LACPDU à cadence rapide (« If fast is specified, the remote device sends an LACPDU every 1 second ») ; `slow`, la valeur par défaut, correspond à 90 secondes et à un envoi toutes les 30 secondes ; une valeur `user-defined` va de 3 à 90 secondes ; le réglage s’applique à toutes les interfaces membres (« takes effect on all its member interfaces »), et les deux extrémités peuvent avoir des délais différents, même s’il est conseillé de les aligner (« The timeout interval on the two ends can be different. To facilitate maintenance, you are advised to set the same timeout interval at both ends ») (Huawei, voir plus haut). La page indique à quelle fréquence chaque extrémité émet, et au bout de combien de temps chacune renonce à l’autre.

**Le verdict.** La paire est agrégée quand les deux extrémités sont agrégeables, synchronisées, en collecte et en distribution, qu’aucune n’est Defaulted ni Expired, et qu’au moins une est active. Avec le seul état de l’acteur, le verdict porte sur cette extrémité. Les constats, dans l’ordre :

- **Les deux passives** : si les deux liens sont en mode passif, ils n’échangent pas de paquets LACP et le lien agrégé ne s’établit pas (« If both links are in passive mode, they won't exchange LACP packets, and the aggregated link won't be established ») ([Juniper, Aggregated Ethernet LACP](https://www.juniper.net/documentation/us/en/software/junos/interfaces-ethernet-switches/topics/topic-map/aggregated-ethernet-lacp-switches.html)) ; Cisco précise qu’un port passif ne peut pas former d’EtherChannel avec un autre port lui aussi passif (« cannot form an EtherChannel with another port that is also in the passive mode »).
- **Expired** (cette extrémité, ou signalé par le partenaire) : aucune LACPDU n’est arrivée avant une première expiration du temporisateur de l’état Current ; si aucune n’arrive avant la seconde, la machine d’état passe à Defaulted (« If no LACP PDU is received before the timer for the Current state expires a second time, the state machine enters the Defaulted state », Juniper). Tant qu’il est Expired, le pilote Linux règle le Timeout de son partenaire sur court : il émet donc chaque seconde.
- **Defaulted** (cette extrémité, ou signalé par le partenaire) : aucune LACPDU n’a été reçue à temps ; les valeurs du partenaire affichées à côté sont des valeurs par défaut, et non ce qu’a dit l’autre extrémité.
- **Individuel** : Aggregation à 0 sur l’une ou l’autre extrémité.
- **Non synchronisé** : le lien n’est pas dans la bonne agrégation. Des ports forment une même agrégation quand ils ont les mêmes ID système et clés, côté acteur comme côté partenaire (« the same actor system ID, actor key, partner system ID, and partner key ») ([HPE Aruba, ArubaOS 8.11, LACP](https://arubanetworking.hpe.com/techdocs/Archived/AOS-8/ArubaOS_8.11.2_Web_Help/Content/arubaos-solutions/lacp/lacp-over.htm)) : un membre câblé vers un autre commutateur, ou vers un port d’un autre groupe sur celui-ci, montre un ID système ou une clé de partenaire différents de ceux des autres membres ; comparez-les dans les colonnes partenaire de la commande show.
- **Synchronisé, mais sans collecte ni distribution** : rattachement à l’agrégateur encore en cours, ou attente du partenaire (les états mux de Juniper le précisent).
- **Délais d’expiration différents** : chaque extrémité émet à la cadence que l’autre demande, si bien qu’une panne silencieuse est détectée au bout d’un temps différent dans chaque sens.

## Ce que l’outil refuse, et pourquoi

- **Quel lien** : une politique autre que les quatre (encap2+3 et encap3+4 peuvent lire les en-têtes internes d’un tunnel, ce que la page ne prend pas en charge) ; un ordre des octets autre que little ou big ; moins de 2 ou plus de 8 membres ; un champ manquant que la politique lit ; une adresse MAC mal formée (six octets, un même séparateur partout, ou la notation pointée de Cisco) ; une adresse IP avec un octet supérieur à 255, un zéro de tête, une longueur de préfixe ou une zone ; des adresses de deux familles ; un protocole autre que TCP ou UDP ; un port hors de l’intervalle de 0 à 65535 ; un ID de VLAN de 0 ou 4095, ou hors de l’intervalle de 1 à 4094 ; une priorité hors de l’intervalle de 0 à 7, ou une priorité sur une trame non étiquetée ; une répartition sur un champ que la politique ne lit pas (elle ne déplacerait rien), sur plus de 4096 flux, ou qui dépasse la dernière valeur du champ. Les champs que la politique ne lit pas ne sont pas lus du tout : une valeur périmée dans l’un d’eux ne bloque donc pas la page.
- **Indicateurs d’état** : une valeur qui ne tient pas sur un octet (supérieure à 255, plus de deux chiffres hexadécimaux ou de huit chiffres binaires) ; de l’hexadécimal seul, sans `0x` ; huit caractères 0 et 1 sous la forme Octet, qui sont soit un PortState Huawei saisi sous le mauvais format, soit du binaire sans son `0b` (le message nomme les deux) ; une valeur SNMP de plus d’un octet ; une chaîne Extreme qui ne compte pas huit positions de la bonne lettre ou d’un tiret ; des lettres Arista auxquelles il manque une paire, avec une lettre en double ou un caractère qu’Arista n’affiche pas ; un PortState Huawei qui ne compte pas huit caractères 0 et 1 ; une sortie collée à côté de valeurs saisies ; une sortie collée sans ligne de membre, avec une ligne qui commence comme une ligne Local ou Partner mais ne se lit pas comme telle, avec deux lignes pour un même port dans la même table, ou avec une ligne Partner dont la table Local ne liste pas le port ; un port choisi que la table Local ne liste pas.
- Chaque champ compte au plus 64 caractères, sauf une sortie collée : au plus 8192 caractères et 96 lignes non vides, une ligne de plus de 200 caractères n’étant pas une ligne de membre et n’étant pas lue. Une sortie collée n’est lue qu’au format Huawei.

## Exemples commentés

Le cours [LAN Switch Operations and Maintenance](/materials/lan-switch-operations-and-maintenance), au chapitre 2.2, agrège deux câbles, les ports 47 et 48, et ses diapositives constructeur configurent la cadence LACP rapide ; il ne donne ni flux ni adresses pour l’agrégat. Les exemples sont donc les suivants :

- **Quel lien** : un bond à deux membres, comme le lab du cours agrège deux câbles, qui transporte le premier flux du lab de l’[article Apprendre](/learn/link-aggregation-and-lacp), un flux de sauvegarde de 192.0.2.10, port TCP 50001, vers 198.51.100.20, port TCP 873, avec `layer3+4` sur un processeur little-endian. Les ports se lisent 0x690351c3, les deux adresses 0x0a0200c0 et 0x146433c6 ; après le XOR et les repliements, le hachage vaut 0x3b89385a, un nombre pair : c’est donc le membre 0 qui transporte le flux. Sur les 64 ports source suivants, les deux membres prennent 32 flux chacun, par paires (0, 1, 1, 0, 0, 1, 1, 0…), car le dernier décalage supprime le bit de poids faible.
- **La lecture du lab de l’article** : le même flux sur quatre membres et un processeur big-endian donne 0x62d3e15a et le membre 2, la valeur que le lab calcule à la main.
- **layer2 vers un seul routeur** : avec chaque flux adressé à la MAC du routeur, `layer2` donne 0x0000080b (0x01 XOR 0x0a XOR 0x0800) et le membre 3 sur 4 pour tous ; faire plutôt varier la MAC de destination sur 256 valeurs les répartit à raison de 64 par membre.
- **IPv6 sur trois membres** : 2001:db8::10, port TCP 443, vers 2001:db8:1::20 ; les 300 ports de destination suivants à partir de 51000 se répartissent en 118, 91 et 91 sur les trois membres, et non en un tiers chacun. Le partage documenté par Cisco pour trois ports est lui aussi inégal : 3:3:2 de ses 8 valeurs, soit 37,5 %, 37,5 % et 25 %.
- **Indicateurs d’état** : 0x3F aux deux extrémités, soit actif, délai court, agrégeable, synchronisé, en collecte et en distribution ; agrégé, chaque extrémité émettant chaque seconde et renonçant au bout de 3 secondes. 0x3D aux deux extrémités donne la même chose avec la cadence lente, la valeur attendue par Cisco. 68 et 0, tels que /proc/net/bonding les affiche, correspondent à un bond Linux passif qui n’a rien reçu, face à un état de partenaire à 0, la valeur par défaut du pilote : les deux passives, Defaulted, non synchronisé. `A-GSCD--` (Extreme), `ALGs+CD` (Arista), 0xBC (SNMP) et `10111100` (Huawei) valent tous 0x3D.
- **Huawei display eth-trunk** : l’échantillon colle tel quel l’exemple de la référence des commandes de Huawei. GigabitEthernet0/0/2, Selected (comme 0/0/3), lit 10111100 aux deux extrémités : 0x3D, agrégé, chaque extrémité émettant toutes les 30 secondes. Choisir GigabitEthernet0/0/4, Unselect, donne 10100000 et 10110000 : 0x05 et 0x0D, non agrégé, cette extrémité n’étant pas synchronisée et le partenaire n’étant pas encore en collecte ni en distribution.

## Ce que l’outil ne fait pas

Il ne communique avec aucun commutateur ni serveur : les valeurs sont les vôtres. Il ne calcule le hachage d’aucun constructeur hormis celui du pilote Linux, ni le choix du commutateur pour le trafic retour, ni les politiques encap, les fragments ou les protocoles autres que TCP et UDP sous `layer3+4`. Il ne décode pas une LACPDU entière, seulement les deux octets d’état (les ID système, les clés et les numéros de port d’une sortie Huawei collée sont affichés tels qu’imprimés, sans vérification), et il ne simule pas les machines d’état LACP. Pour voir les flux changer de membre quand vous en mettez un en panne, utilisez le lab de hachage de l’article [Agrégation de liens et LACP](/learn/link-aggregation-and-lacp).

## Partage des résultats

Sous le verdict, le bouton **Partager les résultats** crée, seulement quand vous appuyez dessus, un lien vers cette page qui contient, après le `#`, le mode et ses champs tels que saisis : `mode` (`link` ou `state`) toujours ; en mode Quel lien, `policy`, `order` (`little` ou `big`) et `members`, puis seulement les champs que lit la politique, quand ils sont saisis (`srcmac`, `dstmac`, `srcip`, `dstip`, `protocol`, `srcport`, `dstport`, `vlan`, `priority`), et `spread` et `count` quand une répartition est active ; en mode Indicateurs d’état, `format`, `actor`, et `partner` quand il est saisi ou, au format Huawei avec une sortie collée, `display` (la sortie, avec ses lignes) et `port` quand un port est choisi, à la place d’`actor` et de `partner`. Les champs que la politique ne lit pas, et ceux de l’autre mode, ne sont pas transmis. En mode Quel lien, la fenêtre contextuelle ajoute une mise en garde : les adresses MAC et IP et les ports peuvent décrire des hôtes d’un réseau privé, relisez-les donc avant d’envoyer le lien. Avec une sortie collée, elle ajoute une mise en garde qui lui est propre : la sortie nomme les ID système (adresses MAC) et les interfaces des commutateurs.

La [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986.txt) (section 3.5, consultée le 08/11/2026) précise que le fragment est séparé du reste de l’URI avant tout déréférencement (« separated from the rest of the URI prior to a dereference ») : ces valeurs ne sont donc pas envoyées au serveur à l’ouverture du lien ; elles restent dans la barre d’adresse et l’historique de la personne qui l’ouvre, et quiconque possède le lien peut les lire.

- **Longueur.** Un lien contient au plus 16 384 caractères, la limite que le site applique à toute valeur placée après le `#` ; une sortie collée d’au plus 8192 caractères y tient, et les autres champs sont bien plus courts.
- **Ouverture d’un lien.** Le mode et ses champs sont réglés comme le ferait une saisie (en mode Quel lien, un champ que la politique ne lit pas garde sa valeur, et une répartition absente désactive la répartition), et la page calcule. Un lien est ignoré s’il comporte un mode, une politique, un ordre, un protocole, un format ou un champ de répartition inconnus, un champ de l’autre mode ou un champ que la politique ne lit pas, s’il lui manque un champ obligatoire, ou s’il comporte un nombre de flux sans répartition ou l’inverse, un `display` ou un `port` hors du format Huawei, un `display` à côté d’un `actor` ou d’un `partner`, un `port` sans `display`, ou une valeur sur deux lignes (`display` excepté). Que le lien soit accepté ou non, les valeurs quittent ensuite aussitôt l’adresse de la page elle-même, sans aucune requête : un rechargement, un favori ou le bouton Partager de la page n’emporte donc rien que vous n’ayez choisi de partager.

## Provenance

Le moteur est une arithmétique de bits fixe, sans horloge, sans réseau et sans aléa. Ses vecteurs de référence (golden vectors, jeu `lacp-hash-and-state-reader-golden-2026-11-08b`) fixent chaque politique dans les deux ordres des octets pour 2 à 8 membres, les six flux du lab de l’article, IPv6 (avec une fin IPv4 en notation pointée), les trois notations MAC, les ports et les adresses à leurs limites, la politique VLAN avec et sans priorité, neuf répartitions (jusqu’à 4096 flux), chacun des 256 octets d’état comme acteur, 24 paires acteur et partenaire, les formes SNMP, Extreme et Arista, les exemples et les échantillons, les phrases qui portent les règles, et les refus. Chaque valeur attendue a été obtenue par une implémentation Python distincte, et non en exécutant ce moteur : le hachage à partir du code du pilote, avec les adresses et les ports lus par `struct.unpack` dans l’ordre des octets du processeur, et les états à partir de l’ordre des bits de la MIB et de la règle de la RFC 3417. Ses résultats big-endian concordent avec les vecteurs du lab de l’article, y compris le hachage que celui-ci calcule à la main. Le second jeu ajoute le PortState de Huawei : de nouveau chaque octet, sous forme de PortState, l’exemple de la référence des commandes de Huawei avec chaque membre choisi, des sorties avec des fins de ligne Windows, des lignes vides et des tabulations, des lignes sans en-têtes, une ligne ForceFwd et un port 10GE, chaque refus d’une sortie collée et ses limites ; leurs valeurs attendues proviennent d’un second modèle Python, qui lit un PortState comme la chaîne inversée et découpe les lignes sur les blancs. Les résultats little-endian du lab de l’article, que propose désormais son sélecteur d’ordre des octets, concordent avec ce moteur flux par flux.

## API

Le même moteur répond à `/api/v1/lacp-hash-and-state-reader` sur l’API HTTP du site ; le contrat figure sur la [page API](/api), qui indique aussi si ce site sert l’API.

- **Requête.** Un objet JSON. Quel lien : `{"mode": "link", "policy": "layer3+4", "byteOrder": "little", "members": 2, "srcIp": "192.0.2.10", "dstIp": "198.51.100.20", "protocol": "tcp", "srcPort": 50001, "dstPort": 873, "spread": {"field": "srcPort", "count": 64}}` ; `policy` (`layer2` par défaut), `byteOrder` (`little` par défaut), `protocol` (`tcp` par défaut), `vlan`, `priority` et `spread` sont facultatifs, et `srcMac` et `dstMac` sont exigés par `layer2` et `layer2+3` (`srcMac` seul par `vlan+srcmac`). Indicateurs d’état : `{"mode": "state", "format": "octet", "actor": "0x3F", "partner": "0x3F"}` ; `format` (`octet` par défaut) et `partner` sont facultatifs. Au format Huawei, `display` peut contenir toute la sortie de `display eth-trunk` à la place d’`actor` et de `partner`, avec `port` qui nomme le membre lu en détail.
- **Réponse, Quel lien.** `mode`, `policy`, `policyDefault`, `byteOrder`, `byteOrderMatters`, `members`, `family`, `etherType`, `used`, `formula`, `steps` (chacun avec `id` et `value`), `hash`, `hashDecimal`, `member`, `ifDown` (pour chaque membre qui tombe, le membre qu’utilise alors le flux), `ciscoValues`, `ciscoEven`, `spread` (`field`, `count`, `from`, `to`, `counts`, `min`, `max`, `even`, `first`, ou null) et `notes`.
- **Réponse, Indicateurs d’état.** `mode`, `format`, `formatDefault`, `actor` et `partner` (chacun avec `octet`, `hex`, `decimal`, `binary`, `snmp`, `extreme`, `huawei` et `bits`, huit éléments avec `bit`, `name`, `mask`, `set` et `text` ; `partner` vaut null s’il n’est pas fourni), `huawei` (null sauf si une sortie a été collée ; sinon `lagId`, `workingMode`, `hashArithmetic`, `systemPriority`, `systemId`, chacun null s’il n’est pas affiché, `members`, chacun avec `port`, `status`, `statusText`, `portType`, `portPri`, `portNo`, `portKey`, `weight`, `portState`, `hex`, `partner` et `verdict`, puis `port` et `portDefault`), `timers` (`actorTimeout`, `partnerTimeout`, `actorSends`, `partnerSends`, `periodic`), `status` (`bundled`, `bundled-this-end` ou `not-bundled`), `verdictText`, `findings` (chacun avec `id`, `level` et `text`) et `notes`.
- **Erreurs.** HTTP 400, `invalid_input`, avec le message du moteur, par exemple `"3D" looks hexadecimal: write it with 0x in front (0x3D), so it is not read as decimal.`.
