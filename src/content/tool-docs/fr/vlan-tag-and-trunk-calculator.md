## Ce que fait l’outil

Un VLAN (virtual local area network, réseau local virtuel) tient ses trames à l’écart de celles de tous les autres VLAN, et, sur une liaison qui en transporte plusieurs, chaque trame indique à quel VLAN elle appartient au moyen d’une étiquette IEEE 802.1Q de quatre octets. Cet outil répond, en deux modes, aux deux questions qui reviennent le plus souvent quand un trunk ne se comporte pas comme prévu :

- **Étiquette 802.1Q.** Collez en hexadécimal les octets d’une étiquette, ou d’un début de trame (MAC de destination, MAC source, puis les étiquettes). La page affiche le TPID, le PCP, le DEI et le VID de chaque étiquette, avec ses 32 bits dessinés octet par octet, le type de trafic du PCP et la façon dont il se décode selon les quatre sélections PCP, les étiquettes empilées (Q-in-Q, 802.1ad), ainsi que l’EtherType, la longueur ou ni l’un ni l’autre qui suit, nommé d’après la liste de l’IANA.
- **VLAN du trunk.** Collez les lignes du port trunk des deux extrémités d’une liaison, chacune dans la syntaxe de son constructeur : Cisco IOS XE, Juniper Junos, HPE Aruba AOS-CX, MikroTik RouterOS, Extreme Switch Engine, Extreme Fabric Engine, Arista EOS ou Huawei VRP, les huit constructeurs de la formation sur les commutateurs. La page indique ce que transporte chaque extrémité, ce qu’elle envoie étiqueté et non étiqueté, et, VLAN par VLAN et dans les deux sens, si une trame arrive dans le même VLAN, aboutit dans un autre, est supprimée, ou dépend d’un comportement que les pages consultées du constructeur ne précisent pas.

Tout est calculé dans votre navigateur.

## L’étiquette : ce que l’outil lit

Le format de l’étiquette figure dans la clause 9 de l’[IEEE P802.1ad/D2.4](https://www.ieee802.org/1/files/public/docs2004/802-1-ad-D2-4.pdf), le brouillon public IEEE 802.1 de 2004 qui contient le texte de 802.1Q tel qu’amendé. C’est un brouillon non approuvé ; l’édition actuelle, 802.1Q-2022, a le statut « Active Standard » auprès de l’[IEEE Standards Association](https://standards.ieee.org/ieee/802.1Q/10323/) mais n’est pas publique. L’outil lit donc le brouillon pour la structure et les tableaux que 802.1Q a conservés et, à côté, le [module YANG des types](https://raw.githubusercontent.com/YangModels/yang/main/standard/ieee/published/802.1/ieee802-dot1q-types.yang) actuel de l’IEEE (révision 2023-10-26).

- **TPID**, deux octets : 0x8100 est la C-TAG, « An 802.1Q Customer VLAN, using the 81-00 EtherType », et 0x88A8 la S-TAG, « An 802.1Q Service VLAN, using the 88-A8 EtherType originally introduced in 802.1ad, and incorporated into 802.1Q (2011) » (module YANG des types). 0x9100 est lu aussi comme une étiquette, uniquement parce que la [page de Juniper sur le bridging](https://www.juniper.net/documentation/us/en/software/junos/multicast-l2/topics/topic-map/bridging-and-vlans.html) indique « Junos OS switches support the TPID value 0x9100 for Q-in-Q » ; ce n’est pas un type d’étiquette 802.1Q, la liste de l’IANA ne le nomme pas, et la page précise qu’elle lit son TCI selon la structure 802.1Q sur la seule foi de cette page. Aucune autre valeur n’est lue comme une étiquette.
- **TCI**, deux octets : le PCP sur les trois premiers bits, puis un bit, puis le VID sur 12 bits (P802.1ad/D2.4, figure 9-1). Le PCP se trouve dans le premier octet : chaque champ de deux octets se lit donc avec son premier octet comme octet de poids fort, c’est-à-dire dans l’ordre big-endian, l’ordre réseau des octets, qu’explique l’article [Big-endian and little-endian: byte order explained](/learn/big-endian-and-little-endian).
- **PCP**, de 0 à 7. Avec la sélection par défaut, 8P0D, le PCP *n* correspond à la priorité *n* ; un port réglé sur 7P1D, 6P2D ou 5P3D lit certaines valeurs comme une autre priorité ou comme éligibles à la suppression (tableau 6-5), et la page affiche les quatre lectures. Le type de trafic est celui que le tableau G-2 donne pour la priorité : 1 Background (BK), 0 Best Effort (BE), 2 Excellent Effort (EE), 3 Critical Applications (CA), 4 Video (VI), 5 Voice (VO), 6 Internetwork Control (IC), 7 Network Control (NC). Background est placé à dessein en dessous de Best Effort : « the value 1 effectively communicates a lower priority than 0 » (annexe G.4). Le [guide QoS d’AOS-CX](https://arubanetworking.hpe.com/techdocs/AOS-CX/10.14/HTML/qos_4100i-6000-6100/Content/Chp_Overview/end-to-end-qos-beh.htm) de HPE Aruba donne aujourd’hui les mêmes huit types.
- **DEI**, un bit. Le [modèle de pont](https://raw.githubusercontent.com/YangModels/yang/main/standard/ieee/published/802.1/ieee802-dot1q-bridge.yang) actuel de l’IEEE l’appelle Drop Eligible Indicator : avec use-dei à True, un port marque la trame comme éligible à la suppression ; sinon, le DEI est transmis à zéro et ignoré à la réception (« the DEI shall be transmitted as zero and ignored on receipt »). Dans la C-TAG de 2004, ce même bit était le CFI, le Canonical Format Indicator (section 9.6) ; dans la S-TAG, il a toujours été le DE (section 9.7).
- **VID**, de 0 à 4095. Le tableau 9-2 donne un sens à trois valeurs : 0 est l’identifiant de VLAN nul (« The null VLAN ID »), une étiquette qui ne contient qu’une information de priorité (« contains only priority information ») ; 1 est la valeur de PVID par défaut qui sert à classer les trames à l’entrée (« The default PVID value used for classifying frames on ingress ») ; FFF (4095) est réservé à l’usage de l’implémentation (« Reserved for implementation use ») et ne doit pas être transmis dans un en-tête d’étiquette (« transmitted in a tag header »). La plage vlanid du module YANG va de 1 à 4094, et Juniper réserve aussi 0 et 4095 (« VLAN ID 0 is reserved for tagging the priority of frames », [802.1Q VLAN IDs](https://www.juniper.net/documentation/us/en/software/junos/multicast-l2/topics/concept/ethernet-802-1q-vlan-id-by-interface-type.html)). Une trame étiquetée pour la priorité aboutit dans le PVID du port qui la reçoit, « the VLAN-ID assigned to untagged frames or Priority-tagged frames received on this port » ([IEEE8021-Q-BRIDGE-MIB](https://www.ieee802.org/1/files/public/MIBs/IEEE8021-Q-BRIDGE-MIB-202211080000Z.mib)).

**Étiquettes empilées.** Les étiquettes se répètent jusqu’à un type qui n’est pas un TPID (huit au plus). Le provider bridging place la S-TAG à l’extérieur et la C-TAG du client à l’intérieur (« the MSDU of the associated frame can contain a Customer VLAN tag », section 9.7) : la page signale donc une S-TAG placée dans une C-TAG, ainsi que deux C-TAG à la suite, ce qui n’est pas un empilement 802.1ad et correspond aussi à la forme du double étiquetage (double tagging) que décrit l’[article sur les VLAN](/learn/vlans-and-8021q-trunking).

**Après les étiquettes.** [RFC 9542](https://www.rfc-editor.org/rfc/rfc9542.txt) (BCP 141, qui rend obsolète la RFC 7042), section 3 : les EtherTypes ont une valeur plancher (« are equal to or larger than 0x0600 »), une longueur doit rester sous un seuil pour ne pas être prise pour un EtherType (« must ... be less than 0x5DD, or it could be mistaken as an EtherType »), et l’EtherType d’encapsulation LLC peut tenir lieu de longueur (« the LLC encapsulation EtherType 0x8870 »). Ainsi, de 0x0000 à 0x05DC, la valeur se lit comme une longueur (une trame IEEE 802.3, suivie de LLC), de 0x05DD à 0x05FF comme ni l’un ni l’autre, et au-delà comme un EtherType, nommé comme le décrit la [liste de l’IANA](https://www.iana.org/assignments/ieee-802-numbers/ieee-802-numbers.xml) (dernière mise à jour le 03/11/2024 ; la ligne la plus étroite l’emporte quand deux lignes se chevauchent). L’IANA précise que cette liste contient des informations fournies sans vérification (« is contributed unverified information ») et que l’IEEE Registration Authority tient la liste publique ; une valeur que l’IANA ne liste pas est affichée comme non listée, jamais devinée.

**Adresses.** Quand les octets commencent par une MAC de destination, la page affiche les deux adresses avec le bit M de la RFC 9542 (« If it is a one, the address is groupcast (multicast or broadcast) ») et son bit X (adresse locale), section 2.1.1, signale les adresses de documentation de la RFC 9542 (00-00-5E-00-53-00 à -FF, 01-00-5E-90-10-00 à -FF, section 2.1.4), et avertit quand une adresse source a le bit M à 1.

**Point de départ des octets.** Auto lit comme une étiquette les octets qui commencent par 0x8100, 0x88A8 ou 0x9100, et comme un début de trame tout le reste à partir de 14 octets, en indiquant son choix ; les deux autres options imposent l’une ou l’autre lecture (une MAC de destination peut commencer par 81-00).

## Trunks : ce que signifient les lignes de chaque constructeur

Collez les lignes du port trunk telles que le commutateur les affiche ; les lignes qui ne concernent pas les VLAN du trunk sont listées comme non lues. Une simple liste comme `10,20,30-40` fonctionne aussi. Les règles de chaque constructeur proviennent de sa propre documentation, consultée le 8 novembre 2026 :

- **Cisco IOS XE** (Catalyst 9300 ; [VLAN trunks, 17.18](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-18/configuration_guide/vlan/b_1718_vlan_9300_cg/configuring_vlan_trunks.html) et la [référence des commandes 17.18](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-18/command_reference/b_1718_9300_cr/vlan_commands.html), consultées dans un navigateur, car le site de Cisco refuse les lectures automatisées ; la [référence des commandes 17.17](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-17/command_reference/b_1717_9300_cr/vlan_commands.html), consultée via WebFetch). `switchport trunk allowed vlan` accepte « all | none | [add | remove | except]vlan-atom [,vlan-atom...] » ; all désigne tous les VLAN et c’est la valeur par défaut (« specifies all VLANs from 1 to 4094. This is the default ») ; aucun espace n’est admis dans la liste (« Do not enter any spaces between comma-separated VLAN parameters or in hyphen-specified ranges ») ; la forme no rétablit la liste par défaut (« resets the list to the default list »). `switchport trunk native vlan` définit le VLAN natif pour envoyer et recevoir le trafic non étiqueté (« for sending and receiving untagged traffic »), avec une valeur par défaut (« VLAN 1 is the default native VLAN ID on the port »), et un paquet du VLAN natif part sans étiquette (« If a packet has a VLAN ID that is the same as the sending-port native VLAN ID, the packet is sent without a tag ») ; la liste autorisée regroupe les VLAN qui reçoivent et envoient du trafic étiqueté sur l’interface (« receive and send traffic on this interface in tagged format »). Les VLAN 1002 à 1005 sont réservés à Token Ring et à FDDI (« reserved for Token Ring and FDDI VLANs »), et l’équipement ne relaie pas ce trafic (« does not forward FDDI, FDDI-Net, TrCRF, or TrBRF traffic », [VLANs, 17.18](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-18/configuration_guide/vlan/b_1718_vlan_9300_cg/configuring_vlans.html)) ; la page les signale quand la liste les contient.
- **Juniper Junos avec ELS** ([bridging and VLANs](https://www.juniper.net/documentation/us/en/software/junos/multicast-l2/topics/topic-map/bridging-and-vlans.html) ; [Ethernet Switching User Guide](https://www.juniper.net/documentation/us/en/software/junos/multicast-l2/multicast-l2.pdf), 23 septembre 2026). `vlan members` accepte un VLAN, ou plusieurs entre `[` et `]`, par ID, par plage (`members 120-130`) ou par nom ; les lignes `set` successives s’ajoutent aux membres (l’exemple du guide lui-même se termine par `members [ 1 sales support ]`), et les noms se résolvent grâce aux lignes `set vlans NAME vlan-id N` collées avec elles. `native-vlan-id` définit le VLAN natif. Sans lui, un trunk reconnaît les paquets de contrôle non étiquetés, mais pas les paquets de données non étiquetés (« recognizes untagged control packets, but it does not recognize untagged data packets »), et l’interface logique doit être configurée avec le même ID de VLAN que le VLAN natif (« must be configured with the same VLAN ID as the native VLAN ID ») : un VLAN natif qui n’est pas membre ne reçoit donc rien de non étiqueté. `members all` est refusé : les pages consultées ne disent pas quels VLAN il représente sur ELS.
- **HPE Aruba AOS-CX** (10.16 Layer 2 Bridging Guide : [vlan trunk allowed](https://arubanetworking.hpe.com/techdocs/AOS-CX/10.16/HTML/l2_bridging_6300-6400/Content/Chp_vlans/vlan_cmds/vla-tru-all.htm), consultée via WebFetch et dans un navigateur, [vlan trunk native](https://arubanetworking.hpe.com/techdocs/AOS-CX/10.16/HTML/l2_bridging_6300-6400/Content/Chp_vlans/vlan_cmds/vla-tru-nat.htm) et [vlan trunk native tag](https://arubanetworking.hpe.com/techdocs/AOS-CX/10.16/HTML/l2_bridging_6300-6400/Content/Chp_vlans/vlan_cmds/vla-tru-nat-tag.htm), consultées dans un navigateur, car le site refuse les lectures automatisées ; les adresses de la référence des commandes citées auparavant pour les deux pages sur le VLAN natif répondent désormais 404 Not Found). La liste s’écrit ainsi : « a single ID, or a series of IDs separated by commas (2, 3, 4), dashes (2-4), or both (2-4,6) » ; all désigne tous les VLAN configurés sur le commutateur, y compris ceux qui le seront à l’avenir (« all the VLANs currently configured on the switch and any new VLANs that are configured in the future »), ce que l’outil compte comme 1 à 4094, en le précisant. Le VLAN natif a une valeur par défaut (« By default, VLAN ID 1 is assigned as the native VLAN ID »), et définir un VLAN natif fait exécuter `vlan trunk allowed all` au commutateur : pour n’autoriser que certains VLAN, il faut ensuite relancer la commande d’autorisation avec ces seuls VLAN (« To only allow specific VLANs on the trunk, issue the vlan trunk allowed command specifying only specific VLANs »). Une liste saisie après all la remplace ; une liste saisie après une liste s’y ajoute (« Multiple VLAN IDs can be assigned »), selon la lecture que fait l’outil des deux pages. `no vlan trunk allowed` retire des VLAN, et quand le dernier disparaît, le trunk transporte tous les VLAN définis sur le commutateur (« will trunk all the VLANs currently defined on the switch »). Avec `vlan trunk native ... tag`, les paquets entrants non étiquetés sont supprimés, sauf les BPDU (« Incoming packets that are untagged are dropped except for BPDUs »), et les paquets sortants sont étiquetés (« Egress packets are tagged »). Un VLAN natif absent de la liste autorisée n’est pas transporté : l’exemple de la page sur le VLAN natif est justement « Assigning native VLAN ID 20 to trunk interface 1/1/2 and then removing it from the list of allowed VLANs. (Only allow VLAN 10 on the trunk.) »
- **MikroTik RouterOS** ([manuel 7.24, bridge VLAN filtering](https://manual.mikrotik.com/docs/7.24/bridging-and-switching/)). Le `vlan-ids` de chaque entrée VLAN du bridge (« vlan-ids=100-115,120,122,128-130 »), avec `tagged=` ou `untagged=`, fait du port un membre étiqueté ou non étiqueté ; `pvid` (1 par défaut) indique à quel VLAN est affecté le trafic entrant non étiqueté (« specifies which VLAN the untagged ingress traffic is assigned to ») ; avec frame-types à sa valeur par défaut, admit-all, le port est ajouté automatiquement comme non étiqueté (« automatically added as untagged ») pour son PVID ; `frame-types=admit-only-vlan-tagged` sur le port n’admet que les trames étiquetées. L’outil lit chaque entrée collée comme une entrée qui liste le port trunk, et avertit quand le port sort non étiqueté dans plusieurs VLAN, ce que RouterOS déconseille dans ses propres avertissements.
- **Extreme Switch Engine** ([références des commandes 33.7.1](https://documentation.extremenetworks.com/Switch%20Engine%20v33.7.1%20Command%20References/downloads/Switch_Engine_33_7_1_Command_References.pdf)). `configure vlan NAME|ID add ports ... tagged|untagged` (« Default: Untagged. »), `delete ports`, et les noms issus de `create vlan NAME tag N` (étiquettes de 2 à 4094 : « tag 1 is assigned to the default VLAN, and tag 4095 is assigned to the management VLAN »). Le Default VLAN contient initialement tous les ports (« initially contains all ports ») et n’est étiqueté sur aucun (« is untagged on all ports »). Un port non étiqueté ne peut être membre que d’un seul VLAN (« Untagged ports can only be a member of a single VLAN ») et, avec `configure vlan untagged-ports auto-move` à sa valeur par défaut, inform, un ajout non étiqueté déplace le port hors de son ancien VLAN non étiqueté, avec un avis ; avec auto-move désactivé, l’outil refuse la ligne, comme le ferait le commutateur.
- **Extreme Fabric Engine** ([guide de l’utilisateur 9.4](https://documentation.extremenetworks.com/Fabric%20Engine%20v9.4%20User%20Guide/fe_9.4_ug_revacdev/content/documents/Switch_Operating_Systems/VOSS_and_Fabric_Engine/fabric_engine_user_guide/adding_or_removing_ports_in_a_vlan.shtml), [références des commandes 9.4](https://documentation.extremenetworks.com/Fabric%20Engine%20v9.4%20Command%20References/downloads/Fabric_Engine_9_4_Command_References.pdf)). `vlan members add|remove` accepte un seul ID de VLAN, de 1 à 4059, car le système réserve une plage à son usage interne (« the system reserves VLAN IDs 4060 to 4094 for internal use »), ainsi que la plage de 3500 à 3998 avec les boot flags vrf-scaling et spbm-config-mode. `default-vlan-id` et `untag-port-default-vlan` (« Untags the default VLAN for the port », désactivé par défaut) constituent le VLAN natif.

- **Arista EOS** ([EOS 4.37.0F User Manual, Virtual LANs](https://www.arista.com/en/um-eos/eos-virtual-lans-vlans), consulté dans un navigateur, car le site refuse les lectures automatisées). En mode trunk, l’interface peut être membre de plusieurs VLAN (« The interface may be a member of multiple VLANs, as configured by the switchport trunk allowed vlan command ») et le trafic non étiqueté est associé à son VLAN natif (« Untagged traffic is associated with the interface's native VLAN ») ; le mode par défaut est access, et l’outil lit les lignes collées comme celles d’un port trunk, et le signale quand `switchport mode trunk` manque. `switchport trunk allowed vlan` accepte une liste (« Valid v_range formats include number, range, or comma-delimited list of numbers and ranges »), `add`, `remove`, `except`, `all` ou `none` ; par défaut, les interfaces traitent le trafic étiqueté de tous les VLAN (« By default, interfaces handle tagged traffic for all VLANs »), et les formes no et default rétablissent all. `switchport trunk native vlan` accepte un VLAN (« The default native VLAN for all interfaces is VLAN 1 »), dont les trames sortent non étiquetées, sauf si le marquage de priorité en sortie envoie à leur place des trames étiquetées pour la priorité (« priority tagged Ethernet frames in place of untagged frames ») ; ses formes no et default rétablissent le VLAN natif par défaut du trunk (« restore vlan 1 as the trunk mode native VLAN »). Avec `tag`, l’interface supprime toutes les trames non étiquetées (« interface drops all untagged frames ») ; le manuel ne dit pas si les trames du VLAN natif lui-même sortent alors étiquetées : un VLAN natif présent dans la liste autorisée est donc marqué non confirmé dans ce sens. Un VLAN natif absent de la liste autorisée est lu comme non transporté, et la page indique sur quoi repose cette lecture : aucune phrase du manuel, mais l’exemple d’Arista lui-même, dont la liste autorisée 6-10 affiche « Trunking Native Mode VLAN: 1 (inactive) » là où d’autres exemples affichent « 1 (default) ».
- **Huawei VRP** (S5700 et S6700 V200R025C00 : la [référence des commandes, VLAN Configuration Commands](https://support.huawei.com/enterprise/en/doc/EDOC1100514211/834147df/vlan-configuration-commands), et le [guide de configuration Ethernet Switching, Adding and Removing VLAN Tags](https://support.huawei.com/enterprise/en/doc/EDOC1100514531/f9b8a34a/adding-and-removing-vlan-tags), tous deux consultés dans un navigateur, car le site refuse les lectures automatisées). `port link-type trunk` fait du port un trunk (le défaut est negotiation-desirable, et negotiation-auto sur le S5736-S). `port trunk allow-pass vlan` accepte des ID de VLAN séparés par des espaces, `to` pour une plage, au plus dix éléments par commande, ou `all` (« Adds a trunk interface to all VLANs ») ; lancer la commande plusieurs fois ajoute l’interface à tous les VLAN indiqués (« If you run the port trunk allow-pass vlan command multiple times in the same interface view, the interface is added to all the specified VLANs »), et la forme undo les retire. La valeur par défaut est la suivante : « By default, a trunk interface is in VLAN 1. » `port trunk pvid vlan` définit le VLAN par défaut (1 par défaut ; une ligne ultérieure le remplace, et la forme undo le ramène à sa valeur par défaut, « restores the default VLAN of a trunk interface to the default setting »), mais n’ajoute pas l’interface trunk à ce VLAN (« does not add the trunk interface to the default VLAN ») : une interface trunk ne relaie les trames du VLAN par défaut qu’une fois ajoutée à ce VLAN par la commande d’autorisation (« A trunk interface forwards frames with the default VLAN ID only after it is added to the default VLAN using the port trunk allow-pass vlan command »). Le tableau 4-2 du guide donne le reste : une trame non étiquetée prend l’ID du VLAN par défaut et est transmise quand ce VLAN est autorisé, supprimée quand il ne l’est pas ; une trame étiquetée n’est acceptée que si son VLAN est autorisé ; en sortie, les trames du VLAN par défaut partent non étiquetées et celles des autres VLAN autorisés, étiquetées. Une configuration qui nomme un VLAN inexistant ne prend pas effet (« If a specified VLAN does not exist, the configuration does not take effect ») : l’outil ne peut pas voir quels VLAN existent sur un commutateur ; il compte donc chaque VLAN que nomment les lignes, et le précise. `port trunk allow-pass only-vlan` est refusé, avec la raison : cette commande configure les VLAN qu’autorise une interface devenue trunk par négociation LNP (« configures VLANs allowed by the interface that is configured as a trunk interface through LNP negotiation »), après `port link-type negotiation`, alors que l’outil lit des trunks statiques.

## Trunks : comparaison des deux extrémités

Pour chaque VLAN de 1 à 4094 et dans chaque sens, l’extrémité émettrice envoie le VLAN non étiqueté quand c’est son VLAN natif (non étiqueté), étiqueté quand il figure dans sa liste, et pas du tout sinon. Une trame étiquetée aboutit dans le VLAN que nomme son étiquette quand l’extrémité réceptrice transporte ce VLAN, et elle est supprimée sinon. Une trame non étiquetée aboutit dans le VLAN natif de l’extrémité réceptrice, son PVID (selon la définition de la MIB de l’IEEE citée plus haut) : dans le même VLAN quand les deux VLAN natifs concordent, dans un autre quand ils diffèrent, et nulle part à une extrémité qui supprime les trames de données non étiquetées (Junos sans VLAN natif, AOS-CX avec un VLAN natif étiqueté, Arista avec `native vlan tag`, RouterOS n’admettant que les trames étiquetées) ou dont le VLAN natif n’est pas transporté (voir plus bas).

Le résultat liste les VLAN qui arrivent dans le même VLAN dans les deux sens, ceux qui ne passent que de A vers B ou que de B vers A, ceux qui aboutissent dans un autre VLAN et ceux qui ne sont pas confirmés, puis un tableau des séries de VLAN qui connaissent le même sort, et la lecture de chaque extrémité, ligne par ligne.

**VLAN natifs discordants.** Quand les deux extrémités placent les trames non étiquetées dans des VLAN différents, la page le signale avec l’avertissement de Cisco : si le VLAN natif d’une extrémité diffère de celui de l’autre, des boucles Spanning Tree peuvent en résulter (« spanning-tree loops might result ») ; il faut que le VLAN natif soit le même aux deux extrémités du trunk (« Make sure the native VLAN for an IEEE 802.1Q trunk is the same on both ends »).

**Un VLAN natif absent de la liste autorisée.** C’est le piège classique, et les constructeurs consultés ne disent pas tous la même chose. Sur AOS-CX, il n’est pas transporté (l’exemple de la page sur le VLAN natif, cité plus haut) ; sur Arista EOS, l’outil le lit comme non transporté d’après la sortie d’exemple d’Arista ; sur Huawei VRP, les trames du VLAN par défaut ne sont relayées qu’une fois l’interface ajoutée à ce VLAN (« only after it is added to the default VLAN ») ; sur Junos, l’interface doit être configurée avec le même ID de VLAN que le VLAN natif (« must be configured with the same VLAN ID as the native VLAN ID »). À ces extrémités, rien ne passe non étiqueté, et la page le signale en haut comme dans la lecture de l’extrémité.

**Non confirmé, jamais deviné.** Sur Cisco IOS XE et Fabric Engine, les pages consultées ne disent pas si un tel VLAN natif est transporté : la référence des commandes 17.18 et le guide VLAN de Cisco, dans chacune de leurs phrases sur le VLAN natif, se contentent de dire que la liste autorisée concerne le trafic étiqueté (« in tagged format ») et le VLAN natif, l’envoi et la réception du trafic non étiqueté (« sending and receiving untagged traffic »). La page marque ce VLAN comme non confirmé, explique pourquoi et suggère de l’ajouter à la liste. Il en va de même pour les arrivées non étiquetées sur un port Switch Engine non étiqueté dans aucun VLAN, sur un port Fabric Engine dont untag-port-default-vlan est désactivé, et pour la façon dont un VLAN natif autorisé sort d’un port Arista réglé sur `native vlan tag`. Le verdict n’est vert que si chaque VLAN envoyé traverse dans les deux sens dans son propre VLAN et que rien ne fait l’objet d’un avertissement.

## Ce que l’outil refuse, et pourquoi

- **Mode étiquette** : un texte qui n’est pas hexadécimal, un nombre impair de chiffres, plus de 128 octets ou de 4000 caractères, plus de huit étiquettes, une étiquette tronquée, un début de trame de moins de 14 octets, des octets dont on impose qu’ils commencent par un TPID alors qu’ils n’en ont pas, et un point de départ inconnu.
- **Mode trunk** : le VLAN 0 (« The null VLAN ID ... shall not be configured ») et le 4095 (réservé, tableau 9-2), les ID supérieurs à 4094 ou écrits avec des zéros initiaux, les plages inversées, les éléments de liste vides, les espaces dans une liste Cisco ou AOS-CX, les ID Fabric Engine à partir de 4060 et les listes dans ses commandes à VLAN unique, `default-vlan-id 0` (la plage l’autorise, mais la référence ne dit pas ce qu’il signifie), les options Fabric Engine que les pages ne décrivent pas, les noms de VLAN non résolus, un VLAN Switch Engine créé sans étiquette mais ajouté comme étiqueté, les étiquettes hors de la plage 2 à 4094, un VLAN RouterOS à la fois étiqueté et non étiqueté sur le port, un port Arista ou Huawei qui n’est pas un trunk (`switchport mode access`, `port link-type hybrid` et autres), une liste Arista avec des espaces, une liste Huawei avec des virgules ou des tirets, plus de dix éléments ou un `to` sans son second VLAN, le `port trunk allow-pass only-vlan` de Huawei (une commande destinée aux trunks négociés par LNP), une extrémité sans ligne de trunk, une extrémité de plus de 64 lignes, de 256 caractères par ligne ou de 4000 caractères, et un constructeur inconnu.

## Exemples commentés

Les exemples reprennent le lab VLAN du chapitre 2.3 de la formation ouverte [LAN Switch Operations and Maintenance](/materials/lan-switch-operations-and-maintenance), son bloc MODERN CLI B12 : les VLAN 10 USERS, 20 VOICE et 99 MGMT étiquetés sur le trunk, 999 comme VLAN natif, et des trames qui utilisent les adresses de documentation de la RFC 9542.

- **Étiquette** : `00 00 5e 00 53 01 00 00 5e 00 53 02 81 00 a0 14 08 00` est une trame de 00-00-5E-00-53-02 vers 00-00-5E-00-53-01 avec une C-TAG de TCI 0xA014 : PCP 5 (101, Voice), DEI 0, VID 20, le VLAN VOICE du lab ; puis l’EtherType 0x0800, que la liste de l’IANA décrit comme « Internet Protocol version 4 (IPv4) ». Avec 7P1D, 6P2D et 5P3D, ce même PCP 5 se décode en priorité 4.
- **Autres exemples** : une S-TAG de VID 100 autour d’une C-TAG de VID 10, puis IPv6 ; une étiquette de priorité (VID 0, PCP 5, puis ARP) ; le VID 4095 ; le TPID 0x9100 de Junos ; et une trame vers une adresse de groupe de documentation dont le champ de type vaut 0x002E, soit une longueur de 46 octets.
- **Trunk** : l’extrémité Cisco du lab (`switchport trunk allowed vlan 10,20,99`, `switchport trunk native vlan 999` et `switchport trunk allowed vlan add 999`) face à son extrémité Junos (`vlan members [ USERS VOICE MGMT ]` résolu en 10, 20 et 99, `native-vlan-id 999` et `vlan members 999`). Les VLAN 10, 20 et 99 arrivent étiquetés dans le même VLAN dans les deux sens, et le 999 non étiqueté.
- **Le lab chez deux autres constructeurs** : les lignes Switch Engine (l’ajout non étiqueté de NATIVE999 sort le port de Default, avec l’avis d’auto-move) face aux lignes RouterOS : 10, 20, 99 et 999 arrivent tous dans le même VLAN dans les deux sens. Il en va de même pour les lignes Arista (`switchport trunk native vlan 999`, puis `allowed vlan add 999`) face aux lignes Huawei (`port trunk pvid vlan 999`, `port trunk allow-pass vlan 999` et `undo port trunk allow-pass vlan 1`).
- **Le piège, chez quatre constructeurs** : deux exemples reprennent les lignes du lab sans 999 dans la liste autorisée. Cisco face à AOS-CX : 10, 20 et 99 passent, et 999 n’est pas confirmé côté Cisco et n’est pas transporté côté AOS-CX. Arista face à Huawei : 10, 20 et 99 passent, et 999 ne passe dans aucun sens, non transporté côté Arista (la sortie d’exemple d’Arista) et non relayé côté Huawei (le PVID n’a jamais été ajouté avec allow-pass). Les deux verdicts sont orange.
- **Une discordance** : une extrémité Cisco avec le VLAN natif 1 face à une extrémité AOS-CX avec le VLAN natif 10, toutes deux autorisant 1, 10 et 20 : le VLAN 20 passe ; les trames non étiquetées du VLAN 1 venant de Cisco aboutissent dans le VLAN 10, et les trames non étiquetées du VLAN 10 venant d’AOS-CX aboutissent dans le VLAN 1.

## Ce que l’outil ne fait pas

Il lit des lignes de configuration, pas un commutateur en fonctionnement : il suppose que chaque VLAN nommé existe sur les deux commutateurs, que la liaison est active et en trunk aux deux extrémités, et que rien d’autre (pruning, Spanning Tree, enregistrement des VLAN par MVRP) ne retire un VLAN. Il ne négocie pas le trunking (DTP), ne suit pas un VLAN à travers plus d’une liaison, ne traduit pas les VLAN et ne lit pas un fichier de capture entier : collez les premiers octets d’une trame. Le [lab sur les trunks](/learn/vlans-and-8021q-trunking) de l’article sur les VLAN suit une trame pas à pas à travers un trunk.

## Partage des résultats

Sous le verdict, le bouton **Partager les résultats** crée, seulement quand vous appuyez dessus, un lien vers cette page qui contient, après le `#`, les octets tels que saisis (`input`, et `start` quand il ne vaut pas auto) en mode étiquette, ou `mode=trunk` avec le constructeur et les lignes des deux extrémités tels que saisis (`avendor`, `aconfig`, `bvendor`, `bconfig`) en mode trunk. Les champs de l’autre mode n’y figurent pas. La fenêtre contextuelle ajoute une mise en garde : les octets d’une trame comprennent deux adresses MAC, qui identifient des équipements, et les lignes de trunk contiennent des noms d’interfaces et de VLAN, qui décrivent un réseau privé.

La [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (section 3.5, consultée le 08/11/2026) précise que le fragment est séparé du reste de l’URI avant tout déréférencement (« separated from the rest of the URI prior to a dereference ») : ces valeurs ne sont donc pas envoyées au serveur à l’ouverture du lien ; elles restent dans la barre d’adresse et l’historique de la personne qui l’ouvre, et quiconque possède le lien peut les lire.

- **Longueur.** Un lien contient au plus 16 384 caractères, la limite que le site applique à toute valeur placée après le `#`.
- **Ouverture d’un lien.** Le mode et ses champs sont définis comme le ferait une saisie (un start absent vaut auto), l’autre mode garde ses valeurs, et la page calcule. Un lien avec un mode, un start ou un constructeur inconnus (un constructeur est l’un des huit identifiants listés sous API), un champ de l’autre mode, un champ vide ou manquant, ou une valeur hors limites est ignoré. Que le lien soit accepté ou non, les valeurs quittent ensuite aussitôt l’adresse de la page, sans aucune requête.

## Provenance

Le moteur se résume à de l’arithmétique de bits, une consultation de table et de l’arithmétique d’ensembles, sans horloge, sans réseau et sans aléa. Il est livré avec 176 vecteurs de référence (golden vectors, jeu `vlan-tag-and-trunk-calculator-golden-2026-11-08b`) : 71 vecteurs calculés (33 lectures d’étiquettes et 38 comparaisons de trunks, exemples et exemples supplémentaires compris), 46 qui fixent les phrases portant les règles et les séries du tableau des sorts, 51 refus et 8 corps d’API. Chaque valeur attendue calculée a été obtenue par une implémentation Python distincte, et non en exécutant ce moteur : son propre analyseur hexadécimal et sa propre arithmétique de bits, sa propre lecture du XML de l’IANA, les tableaux 6-5 et G-2 ressaisis par PCP, et son propre analyseur pour chaque constructeur, avec des ensembles Python pour l’arithmétique des VLAN. Une vérification croisée de chacun de ses 1687 champs avec le moteur n’a trouvé aucune différence.

## API

Le même moteur répond à `/api/v1/vlan-tag-and-trunk-calculator` sur l’API HTTP du site ; le contrat se trouve sur la [page API](/api), qui indique aussi si ce site sert l’API.

- **Requête.** Un objet JSON. Étiquette : `{"mode": "tag", "input": "81 00 a0 14 08 00"}`, avec `start` (`auto`, `tpid` ou `mac`) facultatif. Trunk : `{"mode": "trunk", "a": {"vendor": "cisco-ios-xe", "config": "switchport trunk allowed vlan 10,20"}, "b": {"vendor": "aruba-aos-cx", "config": "vlan trunk allowed 10,20"}}` ; les constructeurs sont `cisco-ios-xe`, `juniper-junos`, `aruba-aos-cx`, `mikrotik-routeros`, `extreme-switch-engine`, `extreme-fabric-engine`, `arista-eos` et `huawei-vrp`.
- **Réponse, étiquette.** `mode`, `start`, `startAuto`, `octets`, `hex`, `destination` et `source` (`hex`, `colon`, `group`, `local`, `documentation`, ou null), `tags` (chacune : `index`, `offset`, `tpid`, `kind`, `name`, `tci`, `bits`, `pcp`, `pcpBits`, `acronym`, `trafficType`, `decodings`, `dei`, `vid`, `vidHex`, `vidBits`, `vidMeaning`, `notes`), `next` (`value`, `number`, `kind`, `name`, `text`, ou null), `after`, `verdict`, `warnings` et `notes`.
- **Réponse, trunk.** `mode`, `a` et `b` (chacune : `end`, `vendor`, `vendorName`, `allowed`, `allowedCount`, `allowedText`, `tagged`, `taggedText`, `untaggedOut`, `untaggedIn`, `untaggedInVlan`, `native`, `nativeConfirmed`, `allConfigured`, `read`, `notRead`, `warnings`, `notes`), `carried`, `carriedCount`, `carriedText`, `aOnly`, `aOnlyText`, `bOnly`, `bOnlyText`, `crossed`, `crossedText`, `unconfirmed`, `unconfirmedText`, `rows` (chacune : `from`, `to`, `ab` et `ba` avec `as`, `outcome` et `into`), `nativeMismatch`, `verdict`, `warnings` et `notes`. Les listes de VLAN sont des séries `[low, high]` et du texte comme `10,20,30-40`.
- **Erreurs.** HTTP 400, `invalid_input`, avec le message du moteur, par exemple `End B, line 2: port trunk allow-pass only-vlan applies only to an interface negotiated as a trunk: ...`.
