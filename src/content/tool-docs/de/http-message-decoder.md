## Was das Tool tut

Das Tool liest eine rohe HTTP/1.1-Nachricht, Anfrage oder Antwort, so, wie ein Mitschnitt, ein Proxy-Log, eine Ausgabe von `curl -v` oder ein Beispiel aus einem RFC sie liefert, und dekodiert sie, ohne etwas zu senden:

- **Die Startzeile.** Eine Anfragezeile wird als Methode, Anfrageziel und Version gelesen: die Methode anhand der Tabelle, die der [Vergleich der HTTP-Methoden](/tools/http-methods-comparison) verwendet (sicher, idempotent, definierende Spezifikation), das Ziel anhand der vier Formen aus RFC 9112, Abschnitt 3.2 (origin-form `/path`, absolute-form `scheme://host/path`, authority-form `host:port` für CONNECT, asterisk-form `*` für ein serverweites OPTIONS), die Version anhand von `HTTP-version = HTTP-name "/" DIGIT "." DIGIT`. Eine Statuszeile wird als Version, dreistelliger Code und Reason-Phrase gelesen; der Code wird in der Registry der Statuscodes der IANA nachgeschlagen, und die gesendete Reason-Phrase steht neben der aus der Registry, denn laut RFC 9110 sind Reason-Phrasen nur Empfehlungen („are only recommendations“), und ein Client „SHOULD ignore the reason-phrase content“.
- **Die Felder.** Jede Zeile `name: value` wird gegen die Registry der Feldnamen der IANA geprüft (permanent, veraltet, überholt; alles andere ist nicht registriert, und ein Präfix `X-` wird mit Verweis auf RFC 6648 vermerkt) und dem Teil der Spezifikation zugeordnet, der das Feld definiert: Framing (RFC 9112), Routing und Verbindung, Metadaten der Nachricht, Kontext von Anfrage und Antwort, Repräsentation, Content Negotiation, bedingte Anfragen, Range-Anfragen (RFC 9110, Abschnitte 6 bis 14), Caching (RFC 9111), Cookies (rfc6265bis), Sicherheitsrichtlinien, CORS und Fetch-Metadaten (die Spezifikationen Fetch und HTML der WHATWG, CSP, HSTS), WebSocket, Proxys und CDNs, WebDAV. Veraltete Zeilenfaltung wird zusammengeführt, Whitespace vor einem Doppelpunkt und wiederholte Singleton-Felder werden markiert, und HTTP-date-Werte werden gegen die drei Formate aus RFC 9110, Abschnitt 5.6.7 geprüft.
- **Das Framing.** Welche der acht Regeln aus RFC 9112, Abschnitt 6.3 entscheidet, wo der Body endet: eine Antwort, die keinen haben kann (HEAD, 1xx, 204, 304), ein CONNECT-Tunnel, Transfer-Encoding, das Content-Length übersteuert, chunked als letzte Kodierung, ein ungültiger Content-Length-Wert, ein gültiger, eine Anfrage ohne beides (Länge null), eine Antwort ohne beides (Lesen bis zum Schließen). Content-Length wird gegen `1*DIGIT` validiert, wiederholte Werte werden verglichen, und die angegebene Länge wird mit den tatsächlich eingefügten Oktetten verglichen. Ein Body in Chunks wird nach dem Algorithmus aus Abschnitt 7.1.3 dekodiert: Größe, Erweiterungen und Daten jedes Chunks, der last-chunk, die Trailer-Felder, die dekodierte Länge und alles, was nach dem Ende des Bodys übrig bleibt und was ein Empfänger als nächste Nachricht lesen würde.
- **Zugangsdaten und Cookies.** `Authorization` und `Proxy-Authorization` werden mit maskiertem Wert angezeigt; Zugangsdaten für Basic werden dekodiert, angezeigt wird aber nur die User-ID (RFC 7617: User-ID, ein Doppelpunkt und das Passwort, in Base64 kodiert; „not a secure method of user authentication“), und ein Bearer-Token in Form eines JWT wird an den [JWT-Decoder](/tools/jwt) übergeben, ohne im Link mitzureisen. `Cookie`-Paare werden mit maskierten Werten aufgelistet; jedes `Set-Cookie` wird auf Secure, HttpOnly, SameSite (standardmäßig Lax), die Anforderungen der Präfixe `__Secure-` und `__Host-`, den Vorrang von Max-Age vor Expires und das Format von Expires gelesen.
- **Übergaben.** Der Statuscode geht an [HTTP-Statuscodes erklärt](/tools/http-status-code-explainer), die Methode an den Vergleich der Methoden, die URL (sofern sie keine Query enthält) an den [URL-Inspektor](/tools/url-inspector), die Sicherheits-Header an die [Analyse der Sicherheits-Header](/tools/secure-headers) zur Bewertung und eine Anfrage an den [Übersetzer für HTTP-Anfragen](/tools/http-request-translator) für die Formen in curl, fetch, HTTPie, Python und PowerShell.

## Die Regeln

Achtundzwanzig Regeln, H1 bis H28, jede mit ihrem Satz belegt: die Startzeile (H1, H16, H17, H18, H24, H25), Host (H2), Syntax der Felder (H3, H4, H5, H20, H21, H22, H23, H28), Framing (H6, H7, H8, H9, H10, H11, H12, H13, H26), Zugangsdaten und Cookies (H14, H15), HTTP-Datumsangaben (H19) und Verbindungsoptionen (H27). Befunde werden nach Zeile aufgelistet und auf einer nummerierten Kopie der Nachricht markiert.

## Was das Tool bewusst nicht tut

- Es sendet nie, spielt nichts erneut ab, manipuliert nichts und fuzzt nicht: Es ist die Hälfte eines Inspektors, die nur dekodiert (D-53). Im [Übersetzer für HTTP-Anfragen](/tools/http-request-translator) wird aus einer Anfrage ein Befehl, den Sie selbst ausführen können.
- Es bewertet keine Sicherheits-Header und dekodiert keine JWTs selbst; die Tools, die das tun, sind einen Klick entfernt, und das Secret reist nie im Link mit.
- Es modelliert kein Framing von HTTP/2 oder HTTP/3: Diese übertragen Felder in binären Frames, und ein eingefügter Text davon ist bereits die Ausgabe eines Decoders.

## Ergebnisse teilen

Ganz oben in der Auswertung, unter der Zusammenfassung, erzeugt **Ergebnisse teilen** einen Link auf diese Seite, und zwar nur, wenn Sie die Schaltfläche wählen. Der Link enthält nach dem `#` die Nachricht mit maskierten Zugangsdaten, nie so, wie eingegeben: Die Bereiche maskieren Zugangsdaten und Cookies, doch die Codeansicht zeigt die Nachricht so, wie eingefügt. Das Popover nennt zuerst, was der Link enthält und wie viele Werte maskiert wurden, und bietet dann „Link kopieren“ und, sofern der Browser eines bietet, das Teilen-Menü an; die Adresse der Seite bleibt unverändert.

Was maskiert wird, damit die Seite, die den Link öffnet, dieselbe Nachricht liest:

- **`Authorization` und `Proxy-Authorization`** behalten ihr Schema ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110), Abschnitte 11.6.2 und 11.7.2); Basic behält seine User-ID, sodass die Seite den Benutzer weiterhin nennt ([RFC 7617](https://www.rfc-editor.org/rfc/rfc7617), Abschnitt 2); ein JWT behält seinen Protected Header, sodass die Seite es weiterhin als JWT kennzeichnet ([RFC 7519](https://www.rfc-editor.org/rfc/rfc7519), Abschnitt 1); Zugangsdaten nach AWS Signature Version 4 (`AWS4-HMAC-SHA256`) behalten den Umfang der Anmeldeinformationen (Credential Scope) und `SignedHeaders` und verlieren Zugriffsschlüssel-ID und Signatur, sodass Datum und Region lesbar bleiben ([Create a signed AWS API request](https://docs.aws.amazon.com/IAM/latest/UserGuide/create-signed-request.html), abgerufen am 01.11.2026); der Rest wird zu `REDACTED`.
- **`Cookie` und `Set-Cookie`**: Jeder Cookie-Wert wird Zeichen für Zeichen mit `*` gefüllt, sodass die Cookie-Tabelle dieselben Längen zeigt; Namen, Präfixe und Attribute bleiben ([RFC 6265](https://www.rfc-editor.org/rfc/rfc6265), Abschnitte 4.1.1 und 4.2.1).
- **Ein Feld, das wie ein Secret benannt ist** (`X-API-Key`), Passwort und geheime Parameter **des Anfrageziels** sowie ein Token in jedem anderen Wert (ein `Referer` oder eine `Location` mit einem Code) werden zu `REDACTED`. Eine gefaltete Fortsetzungszeile entfällt zusammen mit ihrem Feld.
- **Der Body**: JSON-Einträge und Formularparameter, die wie ein Secret benannt sind (`access_token` ([RFC 6750](https://www.rfc-editor.org/rfc/rfc6750), Abschnitte 2.2 und 2.3), `refresh_token`, `client_secret`, `password` und `code` ([RFC 6749](https://www.rfc-editor.org/rfc/rfc6749), Abschnitte 2.3.1, 4.1.2, 4.3.2 und 5.1), `code_verifier` ([RFC 7636](https://www.rfc-editor.org/rfc/rfc7636), Abschnitt 4.5) sowie jeder Name, der auf token, secret, password oder api key endet), werden Oktett für Oktett mit `*` gefüllt, sodass der Body seine Länge behält: `Content-Length` im Vergleich zum Body und jede Chunk-Größe lesen sich wie zuvor. Ein Trailer-Feld, das wie ein Secret benannt ist, wird ebenso gefüllt.

Die Share-Vektoren des Tools prüfen, dass die Seite, die den Link öffnet, dieselbe Nachricht liest: die Startzeile, die Felder, das Framing, die Schemata und User-IDs der Zugangsdaten, die Namen und Längen der Cookies, die Befunde und die Übergaben. Bleibt ein Schlüssel oder Token an einer Stelle, die kein Name kennzeichnet (ein privater Schlüssel in einem Body), gibt es keinen Link: Das Popover nennt die Zeile.

Laut [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (Abschnitt 3.5, abgerufen am 01.11.2026) ist das Fragment „separated from the rest of the URI prior to a dereference“, also vor der Dereferenzierung vom Rest der URI getrennt; daher wird die Kopie beim Öffnen des Links nicht an den Server gesendet. Sie bleibt in der Adressleiste und im Verlauf dessen, der den Link öffnet, und wer den Link hat, kann sie lesen.

- **Länge.** Insgesamt höchstens 16.384 Zeichen, die Grenze, die die Website für jeden Wert nach dem `#` setzt; ist der geteilte Inhalt länger, gibt es keinen Link, und das Popover nennt seine Länge.
- **Öffnen eines Links.** Die Kopie ersetzt den Inhalt des Feldes wie beim Einfügen, und die Seite dekodiert sie; es wird nichts gesendet oder erneut abgespielt. Danach verschwinden die Werte sofort aus der Adresse der Seite, ohne dass eine Anfrage gesendet wird; ein Neuladen oder die Schaltfläche „Teilen“ der Seite überträgt daher nichts.

## Grenzen

- Oktettzahlen sind UTF-8-Zählungen des eingefügten Texts; ein Body mit binärem Inhalt oder einem anderen Zeichensatz misst auf der Leitung anders, und beim Einfügen gehen oft Bytes am Ende verloren. Eine Abweichung bei Content-Length wird daher als Tatsache über den eingefügten Text gemeldet.
- Das Schema der URL einer Anfrage steht nicht in einer HTTP/1.1-Nachricht; wird die URL aus Host und einem Ziel in origin-form zusammengesetzt, wird `http` angenommen.
- Ob eine Antwort eine HEAD-Anfrage beantwortet, lässt sich aus der Antwort allein nicht erkennen; Regel 1 wird nur für 1xx, 204 und 304 angewendet.
- Feldwerte werden so angezeigt, wie sie geschrieben sind, außer Zugangsdaten und Cookies, die maskiert werden. Die Nachricht bleibt im Browser; ein Link zum Teilen wird geprüft, bevor er entsteht, weil eine Nachricht routinemäßig eine Sitzung enthält.
