## Was das Tool tut

Geben Sie dem Tool eine Route, also ein Präfix und das autonome System (AS), von dem sie ausgeht, und die Liste der Validated ROA Payloads (VRPs), gegen die Sie sie prüfen wollen, also der Daten, die ein Validator aus Route Origin Authorizations (ROAs) extrahiert, und es liefert den Validierungszustand der Route, wie RFC 6811 ihn definiert: Valid, Invalid oder NotFound. Es zeigt die Begründung VRP für VRP: welche VRPs das Präfix der Route abdecken, welche davon zu ihr passen und warum jeder abdeckende VRP, der nicht passt, scheitert. IPv4 und IPv6 werden beide behandelt, und das AS kann in asplain oder asdot geschrieben werden.

Das Tool ruft nichts ab. Dahinter stehen kein Repository der Resource Public Key Infrastructure (RPKI), kein Validator und kein Route Collector: Die VRPs sind die, die Sie einfügen, daher gilt die Antwort für diese Liste und für keine andere. Um eine Live-Route gegen die Live-RPKI zu prüfen, exportieren Sie die VRPs aus einem Validator, dem Sie vertrauen, und fügen Sie sie ein, oder verwenden Sie einen öffentlichen Dienst wie den Aufruf zur RPKI-Validierung von RIPEstat, den [der Artikel zur BGP-Sicherheit](/learn/bgp-and-the-routing-chokepoint) zeigt.

## Die Eingabe

Die Route ist eine Zeile: ein Präfix und sein Origin-AS, etwa `192.0.2.0/24 AS64496`, `2001:db8::/32 AS1.0` oder `192.0.2.0/24 64496`. RFC 6811 nimmt das Origin aus dem AS ganz rechts im AS_PATH, wenn der Pfad mit einer AS_SEQUENCE endet, verwendet das eigene AS des Routers, wenn der Pfad leer ist oder mit einem Konföderationssegment endet, und sonst den ausgezeichneten Wert NONE; schreiben Sie für diesen Fall `NONE` ([RFC 6811, Abschnitt 2](https://www.rfc-editor.org/rfc/rfc6811.txt)). Eine Route mit dem Origin AS 0 wird abgelehnt: RFC 7607 legt fest, dass ein solches UPDATE „MUST be considered as malformed“ und dass ein BGP-Speaker „MUST NOT originate or propagate a route with an AS number of zero“ ([RFC 7607, Abschnitt 2](https://www.rfc-editor.org/rfc/rfc7607.txt)); sie erreicht die Validierung also nie.

Die VRPs stehen je einer pro Zeile: ein Präfix, optional eine maxLength, dann das AS, getrennt durch Leerzeichen, Tabs oder Kommas, wie in `192.0.2.0/24 24 AS64496`. Die maxLength kann auch nach einem Bindestrich auf das Präfix folgen, `203.0.113.0/24-26`, so wie RFC 9319 eine ROA schreibt ([RFC 9319, Abschnitt 3](https://www.rfc-editor.org/rfc/rfc9319.txt)), und `AS 64496` mit Leerzeichen wird als ein AS gelesen. Trägt das AS sein Präfix `AS`, darf es an beliebiger Stelle in der Zeile stehen, daher funktioniert auch `AS64496,192.0.2.0/24,24`. Ein `#` leitet einen Kommentar ein, und Leerzeilen werden übersprungen. Eine Zeile ohne maxLength autorisiert nur genau das Präfix: „When the maxLength element is not present, the AS is only authorized to advertise the exact prefix“ ([RFC 9582, Abschnitt 4.3.2.2](https://www.rfc-editor.org/rfc/rfc9582.txt)). Eine maxLength, die kürzer als das Präfix ist oder länger als 32 bei IPv4 bzw. 128 bei IPv6, wird abgelehnt, weil derselbe Abschnitt verlangt, dass sie in diesem Bereich liegt („MUST be“). Präfixe mit gesetzten Bits jenseits ihrer Länge (`192.0.2.1/24`) werden abgelehnt, mit der Netzwerkadresse, die vermutlich gemeint war. Identische VRPs werden einmal gezählt.

Stattdessen können Sie eine Datei im Format Simplified Local Internet Number Resource Management with the RPKI (SLURM) einfügen: eine ganze Datei, ein Objekt mit `prefixAssertions` oder das Array selbst. Jede Assertion enthält `prefix` und `asn` und kann `maxPrefixLength` und `comment` enthalten ([RFC 8416, Abschnitt 3.4.1](https://www.rfc-editor.org/rfc/rfc8416.txt)); jeder andere Schlüssel wird abgelehnt, denn „JSON members that are not defined here MUST NOT be used in SLURM files“ (Abschnitt 3.1). Die `prefixFilters` einer Datei werden gezählt, aber nicht angewendet: Sie entfernen VRPs, die aus der RPKI-Validierung stammen, und „Locally Added Assertions MUST NOT be removed by output filtering“ (Abschnitt 3.2).

## Wie der Zustand bestimmt wird

Das Tool wendet die Definitionen von RFC 6811 wörtlich an. Ein VRP deckt eine Route ab, wenn „the VRP prefix length is less than or equal to the Route prefix length, and the VRP prefix address and the Route prefix address are identical for all bits specified by the VRP prefix length“. Er passt, wenn „the Route Prefix is Covered by that VRP, the Route prefix length is less than or equal to the VRP maximum length, and the Route Origin ASN is equal to the VRP ASN“. Dann gilt: „NotFound: No VRP Covers the Route Prefix.“, „Valid: At least one VRP Matches the Route Prefix.“ und „Invalid: At least one VRP Covers the Route Prefix, but no VRP Matches it.“ ([RFC 6811, Abschnitt 2](https://www.rfc-editor.org/rfc/rfc6811.txt)). Ein Treffer genügt, was immer die anderen VRPs sagen, und die Reihenfolge der Liste spielt keine Rolle.

Jeder VRP in der Tabelle erhält eines dieser Ergebnisse: Treffer; Anderes AS (er deckt ab und nennt ein anderes AS); Zu spezifisch (er deckt ab, und die Route ist länger als seine maxLength); beides zugleich; AS 0; Origin NONE; Deckt nicht ab; und Andere Adressfamilie, für einen IPv4-VRP gegenüber einer IPv6-Route oder umgekehrt. Ein Treffer, dessen VRP-Präfix kürzer als die Route ist, wird als über den maxLength-Bereich zustande gekommen gekennzeichnet.

## AS 0

Ein VRP mit AS 0 deckt ab wie jeder andere, kann aber nie passen: „no Route can be Matched by a VRP whose ASN is zero“ ([RFC 6811, Abschnitt 2](https://www.rfc-editor.org/rfc/rfc6811.txt)). So distanziert sich ein Inhaber von einem Block: Eine ROA mit AS 0 besagt, dass „the prefix described in the ROA, and any more specific prefix, should not be used in a routing context“ ([RFC 6483, Abschnitt 4](https://www.rfc-editor.org/rfc/rfc6483.txt)). Wenn nur VRPs mit AS 0 die Route abdecken, sagt das Tool das. Wenn ein anderer VRP ebenfalls passt, ist die Route Valid, weil eine ROA mit AS 0 „has a lower relative preference than any other ROA that has a routable AS as its subject“ (derselbe Abschnitt). Die maxLength eines VRP mit AS 0 ändert am Ergebnis nichts, wie RFC 6483 festhält; daher lässt das Tool VRPs mit AS 0 bei den Hinweisen zur maxLength aus.

## maxLength und RFC 9319

Jeder VRP, dessen maxLength länger als sein Präfix ist, erhält einen Hinweis mit der Anzahl der Präfixe, die er autorisiert, nämlich 2 hoch (maxLength minus Länge plus 1), minus 1: Ein /24 mit maxLength 26 autorisiert 7, das /24, zwei /25 und vier /26; das ist das eigene Beispiel von RFC 9582 ([RFC 9582, Abschnitt 4.3.2.2](https://www.rfc-editor.org/rfc/rfc9582.txt)). RFC 9319 bittet Betreiber, minimale ROAs zu veröffentlichen, und legt fest, dass sie „SHOULD avoid using the maxLength attribute in their ROAs, since its inclusion will usually make the ROA non-minimal“ ([RFC 9319, Abschnitt 5](https://www.rfc-editor.org/rfc/rfc9319.txt)); es erklärt, dass Präfixe, die eine ROA autorisiert, ihr AS aber nicht ankündigt, für einen sogenannten Forged-Origin-Sub-Prefix-Hijack angreifbar sind (Abstract und Abschnitt 3). Der Hinweis nennt den Bereich. Ob jedes Präfix darin tatsächlich angekündigt wird, kann nur der Betreiber sagen.

## Was das Tool nicht tut

Es validiert keine ROAs oder Zertifikate: VRPs sind per Definition das, was ein Validator nach dieser Arbeit erzeugt hat ([RFC 6811, Abschnitt 2](https://www.rfc-editor.org/rfc/rfc6811.txt)). Es wendet keine Richtlinie an: Was ein Router mit Invalid macht, ist Sache der Konfiguration des Betreibers, und „An implementation MUST NOT exclude a route from the Adj-RIB-In or from consideration in the decision process as a side effect of its validation state, unless explicitly configured to do so“ (derselbe Abschnitt). Und es prüft nur das Origin: „the complete path attestation against the AS_PATH attribute of a route is outside the scope“ der Origin-Validierung (Abschnitt 1).

## Durchgerechnete Beispiele

Mit dem einen VRP `192.0.2.0/24 24 AS64496`: `192.0.2.0/24 AS64496` ist Valid; `192.0.2.0/24 AS64497` ist Invalid (anderes AS); `192.0.2.128/25 AS64496` ist Invalid (zu spezifisch); `198.51.100.0/24 AS64497` ist NotFound; `192.0.2.0/24 NONE` ist Invalid. Mit `192.0.2.0/24 AS64496` und `192.0.2.0/24 AS64497` zusammen in der Liste ist `192.0.2.0/24 AS64497` Valid. Mit `203.0.113.0/24 32 AS0` allein ist `203.0.113.0/24 AS64496` Invalid; kommt `203.0.113.128/25 AS64497` hinzu, ist die Route `203.0.113.128/25 AS64497` Valid. Mit `203.0.113.0/24 26 AS64496` aus RFC 9582 sind das /24, `203.0.113.128/25` und `203.0.113.192/26` Valid, und `203.0.113.0/27` ist Invalid. Die ROA aus Anhang A von RFC 9582, AS 65536 für `2001:db8::/32`, macht `2001:db8::/32 AS65536` (in asdot `AS1.0`) Valid und `2001:db8:1::/48 AS65536` Invalid. Jedes dieser Beispiele ist ein Referenzvektor (Golden Vector).

## Ergebnisse teilen

Unter der Bewertung erzeugt **Ergebnisse teilen** einen Link auf diese Seite, und zwar nur, wenn Sie die Schaltfläche wählen. Der Link enthält die Route so, wie eingegeben (`#input=192.0.2.0%2F24+AS64496`), und die VRP-Liste so, wie eingegeben, als Zeilen oder SLURM-JSON (`&vrps=...`), und sonst nichts, auch nicht, welcher durchgerechnete Fall geladen war. Alles, was der Link enthält, steht nach dem `#`, und dieser Teil ist laut [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (Abschnitt 3.5, abgerufen am 27.10.2026) „separated from the rest of the URI prior to a dereference“, also vor der Dereferenzierung vom Rest der URI getrennt: Ein Browser sendet ihn beim Öffnen des Links nicht an den Server, aber er bleibt in der Adressleiste und im Verlauf dessen, der den Link öffnet, und wer den Link hat, kann ihn lesen.

- **Länge.** Ein Link enthält höchstens 16.384 Zeichen, die Grenze, die die Website für jeden Wert nach dem `#` setzt; ist der Inhalt länger, gibt es keinen Link, und das Popover nennt die Länge, die er hätte.
- **Öffnen eines Links.** Beide Felder werden wie beim Einfügen gefüllt, und die Seite bestimmt den Zustand anhand dieser Liste neu. Es wird nichts abgerufen, die Bewertung gilt also weiterhin nur für die eingefügten VRPs. Ein Link, dem einer der beiden Werte fehlt, wird ignoriert. Ob angenommen oder nicht, die Werte verschwinden danach sofort aus der Adresse der Seite, ohne dass eine Anfrage gesendet wird; ein Neuladen, ein Lesezeichen oder die Schaltfläche „Teilen“ der Seite überträgt daher nichts, was Sie nicht selbst teilen wollten.

## API

Dieselbe Engine beantwortet die Operation `/api/v1/rpki-origin-validation` der HTTP-API der Website, Feld für Feld beschrieben im OpenAPI-Vertrag auf der [API-Seite](/api), mit Beispielen aus den Referenzvektoren. Der Vertrag gibt auch an, ob diese Website die API bereitstellt.

- **Anfrage.** Ein JSON-Objekt mit `route` (der Routenzeile) und `vrps` (der VRP-Liste als Text, einer pro Zeile, oder SLURM-JSON als Text oder als JSON-Wert), etwa `{"route":"192.0.2.0/24 AS64497","vrps":"192.0.2.0/24 AS64496\n192.0.2.0/24 AS64497"}`.
- **Antwort.** `route` (`prefix`, `family`, `length`, `origin` und `originAsdot`), `state`, `vrpFormat`, `vrpCount`, `covering`, `matching`, `vrps` (jeder mit `index`, `line`, `prefix`, `length`, `maxLength`, `maxLengthGiven`, `asn`, `covers`, `relation` und bei einem Treffer `viaMaxLength`), `maxLengthNotes` (jeder mit `authorisedPrefixes` als Dezimalzahl in einer Zeichenfolge), `notes`, `duplicatesRemoved` und `slurmFiltersIgnored`. Für die obige Anfrage antwortet die API mit `state` `Valid`, `covering` 2 und `matching` 1, mit den Beziehungen `wrong-as` und `match`.
- **Fehler.** HTTP 400, `invalid_input`, mit der Meldung der Engine, zum Beispiel `maxLength 23 must be between the prefix length /24 and 32 (RFC 9582 section 4.3.2.2)` für den VRP `192.0.2.0/24 23 AS64496`.
