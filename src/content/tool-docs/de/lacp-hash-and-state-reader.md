## Was das Tool tut

Eine Link Aggregation Group (LAG) bündelt parallele Links zu einem, und mit dem Link Aggregation Control Protocol (LACP) einigen sich beide Enden darauf, welche Links dazugehören. Verhält sich ein Bündel falsch, stellen sich zwei Fragen: Auf welchem Member liegt dieser Flow, und was teilen sich die beiden Enden gegenseitig mit? Die Seite beantwortet beide, in zwei Modi:

- **Welcher Link.** Für einen Linux-Bond das Member, das einen Flow überträgt, ermittelt mit dem Transmit-Hash des Treibers selbst: jeder Zwischenwert, das Member, das der Flow nutzt, wenn jeweils eines der anderen Member ausfällt, und auf Wunsch, wie sich eine Reihe von Flows auf die Member verteilt. Für dieselbe Anzahl von Membern zeigt die Seite die Aufteilung, die Cisco für den Hash des Catalyst 6500/6000 dokumentiert; daraus geht hervor, warum 2, 4 und 8 Member den Datenverkehr gleichmäßig teilen und 3, 5, 6 und 7 nicht.
- **Zustands-Flags.** Die Zustandsoktette von Actor und Partner einer LACPDU (der LACP-Dateneinheit) oder die Flags, die ein show-Befehl ausgibt, Bit für Bit gelesen von LACP_Activity bis Expired, mit den daraus folgenden Timern und einer Bewertung für das Paar. Den PortState von Huawei können Sie so eingeben, wie `display eth-trunk` ihn ausgibt, oder die ganze Ausgabe einfügen; dann wird jede Member-Zeile gelesen.

Alles wird in Ihrem Browser berechnet.

## Warum nur der Linux-Hash berechnet wird

Wie ein Bündel Frames verteilt, bleibt jeder Implementierung überlassen. Das Managementmodul von IEEE 802.1AX selbst hält fest, dass eine Beschreibung des Verteilungsalgorithmus „could include information about the distribution algorithm in use“ und dass „The contents are vendor specific“ ([IEEE8023-LAG-MIB](https://www.ieee802.org/1/files/public/MIBs/IEEE8021-AX-MIB-202005290000Z.mib), dot3adAggDescription). Ein Member lässt sich nur dort berechnen, wo eine Implementierung ihren Hash vollständig veröffentlicht, und eine tut das: der Bonding-Treiber von Linux, dessen [HOWTO](https://docs.kernel.org/networking/bonding.html) jede Policy als Formel angibt und dessen Quellcode, [bond_main.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/net/bonding/bond_main.c), jedes Detail festlegt. Das Bonding von RouterOS bei MikroTik beschreibt dieselben Policy-Namen in Worten und verweist auf die Linux-Dokumentation ([MikroTik, Bonding](https://manual.mikrotik.com/docs/7.24/high-availability-solutions/bonding/)).

Die Switch-Hersteller dokumentieren, welche Felder in den Hash eingehen, nicht die Funktion; die Seite nennt die Felder daher und berechnet für diese Hersteller nichts:

- **Cisco.** Zum Catalyst 6500/6000 heißt es: „The Cisco-proprietary hash algorithm computes a value in the range 0 to 7“, und das Dokument gibt an, wie viele dieser Werte jeder Port annimmt, nicht den Hash ([Cisco, document 12023](https://www.cisco.com/c/en/us/support/docs/lan-switching/etherchannel/12023-4.html)). Der Leitfaden zum Catalyst 9300 listet die Load-Balance-Methoden auf, mit „The default is src-mac“, und beschreibt, dass der Switch einen Teil des Bitmusters aus den Adressen auf einen Zahlenwert reduziert: „part of the binary pattern that is formed from the addresses in the frame to a numerical value“ ([Cisco, Configuring EtherChannels, IOS XE 17.18](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-18/configuration_guide/lyr2/b_1718_lyr2_9300_cg/configuring_etherchannels.html)).
- **Juniper.** Der Hash verwendet Paketfelder „as well as on some internal values like source port ID and source device ID“ ([Juniper, Hashing Algorithms for LAG and ECMP](https://www.juniper.net/documentation/us/en/software/junos/interfaces-ethernet-switches/topics/topic-map/hashing-algoriths-lag-bundle-ecmp.html)), die niemand kennen kann, der ein Paket liest.
- **Arista.** „Hashing algorithm inputs varies by switch platform“ ([Arista EOS, Port Channels and LACP](https://www.arista.com/en/um-eos/eos-port-channels-and-lacp)).
- **HPE Aruba.** AOS-CX bietet l2-src-dst, l3-src-dst und l4-src-dst an, ohne die Funktion zu beschreiben ([AOS-CX 10.16, LACP configuration settings](https://arubanetworking.hpe.com/techdocs/AOS-CX/10.16/HTML/link_aggregation/Content/Chp_LAG/lac-cnf-set-10.htm)).
- **Extreme.** Switch Engine nennt xor, crc-16 und crc-32 als Hash-Algorithmen, nicht aber, wie die Felder für sie angeordnet werden ([Switch Engine 33.7.1 Command References](https://documentation.extremenetworks.com/Switch%20Engine%20v33.7.1%20Command%20References/downloads/Switch_Engine_33_7_1_Command_References.pdf), configure sharing address-based custom).
- **Huawei.** Die Befehlsreferenz für S5700 und S6700 listet die `load-balance`-Modi `dst-ip`, `dst-mac`, `src-ip`, `src-mac`, `src-dst-ip`, `src-dst-mac` und `enhanced profile` auf, nennt „The default load balancing mode is src-dst-ip“ und hält fest: „Load balancing is valid only for outgoing traffic; therefore, the load balancing modes for the interfaces at both ends of the link can be different“. Ist ein Modus gesetzt, gilt: „the hash factors used to calculate the outbound interface vary according to the packet type and device model“. Layer-2-Pakete fallen auf Quell- und Ziel-MAC-Adresse zurück; der S5736-S verwendet src-dst-ip mit Quell- und Zielport von TCP oder UDP, „regardless of whether you configure this parameter“, und unterstützt einen einzigen Load-Balancing-Modus für den ganzen Switch; und bei S5731-H, S5731-S, S5731S-S, S5731S-H, S5732-H, S6730-H, S6730S-H, S6730-S und S6730S-S gilt, gleich welcher der sechs Grundmodi konfiguriert ist: „packets are load balanced based on physical-layer source port numbers in the packets“. Die Funktion selbst ist nicht angegeben, daher wird für Huawei nichts berechnet; „You can run the display eth-trunk load-balance command to check the hash factors used when the outbound interface is calculated“ ([Huawei, Link Aggregation Commands, V200R025C00](https://support.huawei.com/enterprise/en/doc/EDOC1100514211/54c5f31b/link-aggregation-commands), im Browser abgerufen: Die Website verweigert automatisierte Abrufe).
- **Switch-Chips von MikroTik.** Ein Bond, der auf den Switch-Chip ausgelagert ist, hasht dort, und das Handbuch gibt dafür keine Formel an.

Um einen Switch selbst zu fragen, zeigt das Dokument 12023 von Cisco den Befehl `test etherchannel load-balance interface port-channel` des Catalyst 6500, der mit dem Port antwortet, den ein gegebenes Adresspaar nutzen würde.

## Welcher Link: die Eingaben

- **Transmit Hash Policy**: die `xmit_hash_policy`-Werte aus dem HOWTO, `layer2` (der Standard), `layer2+3`, `layer3+4` und `vlan+srcmac`. Das Formular zeigt nur die Felder, die die Policy liest.
- **Byte-Reihenfolge des Prozessors**: Little-Endian (der Standard) oder Big-Endian, für `layer2+3` und `layer3+4`. Ein 32-Bit-Wert belegt vier Bytes: Ein Big-Endian-Prozessor speichert sein höchstwertiges Byte an der niedrigsten Adresse, ein Little-Endian-Prozessor sein niedrigstwertiges. Von den Linux-Architekturen, die Debian aufführt, sind amd64, arm64, ppc64el, riscv64 und loong64 Little-Endian und s390x, ppc64, mips und sparc64 Big-Endian ([Debian Wiki, ArchitectureSpecificsMemo](https://wiki.debian.org/ArchitectureSpecificsMemo), im Browser abgerufen: Die Website verweigert automatisierte Abrufe). Der Artikel [Big-Endian und Little-Endian](/learn/big-endian-and-little-endian) erklärt die Byte-Reihenfolge ausführlich; wie sie diesen Hash verändert, steht unten bei den Regeln.
- **Member, die senden können**: 2 bis 8, nummeriert ab 0.
- **Quell- und Ziel-MAC** (`layer2`, `layer2+3`; `vlan+srcmac` liest nur die Quelle), in Schreibweise mit Doppelpunkten oder Bindestrichen oder in Cisco-Punktschreibweise.
- **Quell- und Ziel-IP-Adresse**, IPv4 oder IPv6, aus derselben Familie (bei jeder Policy außer `vlan+srcmac`; bei `layer2` bestimmen sie nur den EtherType).
- **Protokoll, Quellport und Zielport** (`layer3+4`): TCP oder UDP, Ports 0 bis 65535.
- **VLAN-ID und Priorität** (`vlan+srcmac`): eine VLAN-ID von 1 bis 4094 oder leer für einen ungetaggten Frame und eine Priorität von 0 bis 7; die MIBs von IEEE 802.1 lassen 0 und 4095 als VLAN-Kennungen nicht zu und geben Prioritäten als 0 bis 7 an ([IEEE8021-TC-MIB](https://www.ieee802.org/1/files/public/MIBs/IEEE8021-TC-MIB.mib), IEEE8021VlanIndex und IEEE8021PriorityValue).
- **Verteilung** (optional): ein Feld, das die Policy liest, vom eingegebenen Wert aus aufwärts variiert, über 1 bis 4096 Flows.

## Welcher Link: die Regeln

Die Formeln aus dem HOWTO, mit den Details, die der Quellcode festlegt:

```text
layer2:    hash = source MAC[5] XOR destination MAC[5] XOR packet type ID
layer2+3:  hash = source MAC[5] XOR destination MAC[5] XOR packet type ID
           hash = hash XOR source IP XOR destination IP
           hash = hash XOR (hash RSHIFT 16)
           hash = hash XOR (hash RSHIFT 8)
layer3+4:  hash = source port, destination port (as in the header)
           hash = hash XOR source IP XOR destination IP
           hash = hash XOR (hash RSHIFT 16)
           hash = hash XOR (hash RSHIFT 8)
           hash = hash RSHIFT 1
vlan+srcmac: hash = (vlan ID) XOR (source MAC vendor) XOR (source MAC dev)
```

und in jedem Fall gilt für den Hash: Er „is reduced modulo slave count“, wird also modulo der Anzahl der Member reduziert ([Linux bonding HOWTO](https://docs.kernel.org/networking/bonding.html), xmit_hash_policy).

- **Die Pakettyp-ID** ist der EtherType des Frames als Zahl: Der Treiber verknüpft `be16_to_cpu(ep->h_proto)` per XOR (bond_eth_hash), also 0x0800 für IPv4 und 0x86DD für IPv6 ([IANA, IEEE 802 Numbers](https://www.iana.org/assignments/ieee-802-numbers/ieee-802-numbers.txt)).
- **IPv6-Adressen** werden „first hashed using ipv6_addr_hash“ (HOWTO), also per XOR der vier 32-Bit-Wörter der Adresse zusammengefasst ([include/net/ipv6.h](https://raw.githubusercontent.com/torvalds/linux/master/include/net/ipv6.h)).
- **Die Byte-Reihenfolge des Prozessors.** Der Treiber verknüpft die Adressen per XOR so, wie `flow_get_u32_dst` und `flow_get_u32_src` sie liefern, als die rohen 32 Bit, die im Paket stehen, und kopiert die Ports mit `memcpy` aus einer Struktur, die den Quellport zuerst enthält ([include/net/flow_dissector.h](https://raw.githubusercontent.com/torvalds/linux/master/include/net/flow_dissector.h)). Ein Big-Endian-Prozessor liest diese Bytes mit dem höchstwertigen zuerst, und das ist die Formel des HOWTO, wie sie dasteht; ein Little-Endian-Prozessor liest sie andersherum und erhält einen anderen Hash. Welche Felder zählen, die beiden Faltungen, der Shift und das Modulo sind gleich. `layer2` und `vlan+srcmac` lesen einzelne Bytes oder setzen ihre Zahlen Byte für Byte zusammen, daher ändert die Byte-Reihenfolge sie nicht. Die Seite zeigt die beiden Wörter so, wie der gewählte Prozessor sie liest. Die Byte-Reihenfolge ändert das Member nur, wenn die Anzahl der Member keine Zweierpotenz ist. Die beiden Faltungen von `bond_ip_hash` (`hash ^= (hash >> 16); hash ^= (hash >> 8);`) hinterlassen im niedrigsten Byte das XOR der vier Bytes des Worts, das sich durch deren Umkehrung nicht ändert, und ein Modulo durch 2, 4 oder 8 liest nur Bits aus diesem Byte, auch nach dem Shift von `layer3+4`. Mit dieser Engine am 08.11.2026 für 4.000 zufällige Flows (zufällige IPv4-Adressen, MAC-Adressen und Ports) unter `layer2+3` und `layer3+4` mit jeder Anzahl von Membern von 2 bis 8 ausgeführt, wählten beide Reihenfolgen in allen 24.000 Fällen mit 2, 4 oder 8 Membern dasselbe Member und in 23.031 der 32.000 Fälle mit 3, 5, 6 oder 7 Membern ein anderes. Der Flow des Beispiels zeigt beides: Mit 2 oder 4 Membern nutzt er auf beiden Prozessoren Member 0 bzw. 2; mit 5 Membern Member 2 auf einem Little-Endian-Prozessor und Member 4 auf einem Big-Endian-Prozessor. Die Referenzvektoren (Golden Vectors) legen beide Fälle fest.
- **Das niedrigste Bit.** `layer3+4` lässt es am Ende fallen, laut Kommentar im Quellcode „to deal with the common even ports pattern“ (bond_ip_hash); zwei Ports, die sich nur im letzten Bit unterscheiden, landen daher meist auf demselben Member.
- **Das VLAN.** `vlan+srcmac` verknüpft `skb_vlan_tag_get(skb)` per XOR, also die gesamte Tag Control Information des Tags, `vlan_tci` ([include/linux/if_vlan.h](https://raw.githubusercontent.com/torvalds/linux/master/include/linux/if_vlan.h)); daher zählen die Prioritätsbits ebenso wie die VLAN-ID, und ein ungetaggter Frame zählt als 0. Die Seite setzt den Drop Eligible Indicator auf 0.
- **Welches Member.** Die Member, die senden können (im Modus 802.3ad die des aktiven Aggregators), stehen in der Reihenfolge in der Liste, in der sie dem Bond beigetreten sind (bond_update_slave_arr), und der Treiber nimmt `slaves->arr[hash % count]` (bond_xmit_3ad_xor_slave_get). Fällt ein Member aus, wird die Liste ohne es neu aufgebaut, und das Modulo läuft über ein Member weniger; die Seite zeigt daher für jedes Member der Reihe nach, wohin der Flow geht, wenn dieses ausfällt: Oft wechselt ein Flow, obwohl sein eigenes Member aktiv geblieben ist.
- **Ports.** `layer3+4` liest die Ports von nicht fragmentiertem TCP und UDP; „For fragmented TCP or UDP packets and all other IPv4 and IPv6 protocol traffic, the source and destination port information is omitted“ (HOWTO). Die Seite liest nur TCP und UDP.

**Die Aufteilung von Cisco.** Für die gewählte Anzahl von Membern zeigt die Seite außerdem die Tabelle, die das Dokument 12023 für den Catalyst 6500/6000 angibt, „the ratios of the values that each port accepts“: 4:4 für zwei Ports, 3:3:2 für drei, 2:2:2:2 für vier, 2:2:2:1:1 für fünf, 2:2:1:1:1:1 für sechs, 2:1:1:1:1:1:1 für sieben und je einen Wert für acht. Daher gilt: „you can only achieve perfect load balancing, even with random addresses, if you have two, four, or eight ports“. Die Seite zeigt jeden Anteil an den 8 Werten als Prozentsatz; das ist die dokumentierte Tabelle, keine Berechnung des Hashs von Cisco.

**Die Verteilung.** Mit einer Verteilung berechnet die Seite das Member jedes Flows der Reihe und zählt die Flows pro Member. Sie nennt die Verteilung gleichmäßig, wenn kein Member mehr als einen Flow mehr überträgt als ein anderes, und listet die Member der ersten 16 Flows auf; das zeigt Muster wie die Paare, die `layer3+4` aus aufeinanderfolgenden Quellports bildet.

**Jedes Ende hasht nur, was es sendet.** „Slave selection for outgoing traffic is done according to the transmit hash policy“ (HOWTO): Der Switch wählt das Member für den zurückkommenden Datenverkehr mit seinem eigenen Hash, den die Seite nicht berechnet.

## Zustands-Flags: die Eingaben

- **Schreibweise der Werte**:
  - **Oktett**: so, wie die LACPDU es überträgt, hexadezimal mit `0x` (`0x3D`, die Form der Spalte State in `show lacp neighbor` von Cisco, deren erwarteten Wert Cisco mit 0x3D angibt, [document 220367](https://www.cisco.com/c/fr_ca/support/docs/switches/catalyst-9300-series-switches/220367-troubleshoot-etherchannels-on-catalyst-9.html)), dezimal (`61`, wie Linux `port state` in /proc/net/bonding ausgibt, [bond_procfs.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/net/bonding/bond_procfs.c)) oder binär mit `0b`. Ein bloßes `3D` wird abgelehnt, damit es nie als Dezimalzahl gelesen wird.
  - **SNMP BITS**: `dot3adAggPortActorOperState` oder `dot3adAggPortPartnerOperState` so, wie SNMP sie zurückgibt, ein Oktett hexadezimal (mit oder ohne `0x`) oder acht Binärziffern mit `0b`.
  - **Extreme-Flags**: die acht Positionen von Switch Engine in der Reihenfolge ihrer Legende, „A-Activity, T-Timeout, G-Aggregation, S-Synchronization C-Collecting, D-Distributing, F-Defaulted, E-Expired“, ein Bindestrich für ein nicht gesetztes Bit, wie in ihrem Beispiel `A-GSCD--` (Switch Engine 33.7.1 Command References, show lacp member-port).
  - **Arista-Buchstaben**: die Legende von EOS, „A = Active, P = Passive; S=ShortTimeout, L=LongTimeout; G = Aggregable, I = Individual; s+=InSync, s-=OutOfSync; C = Collecting, X = state machine expired, D = Distributing, d = default neighbor state“, wie in ihrem Beispiel `ALGs+CD` ([Arista EOS](https://www.arista.com/en/um-eos/eos-port-channels-and-lacp)). Von jedem Paar ist ein Buchstabe erforderlich, C, X, D und d sind optional, jeder Buchstabe einmal, in beliebiger Reihenfolge.
  - **Huawei PortState**: die Spalte PortState von `display eth-trunk`, „eight bits, such as 10111100“, ausgegeben von Bit 1 bis Bit 8 ([Huawei, Link Aggregation Commands, V200R025C00](https://support.huawei.com/enterprise/en/doc/EDOC1100514211/54c5f31b/link-aggregation-commands), im Browser abgerufen: Die Website verweigert automatisierte Abrufe). Geben Sie den PortState von Actor und Partner ein oder fügen Sie die ganze Ausgabe ein: Die Seite liest jede Member-Zeile ihrer Tabelle Local (Port, Status, PortType, PortPri, PortNo, PortKey, PortState, Weight) und ihrer Tabelle Partner (Port, Systempriorität, System-ID, PortPri, PortNo, PortKey, PortState, unter einer Kopfzeile, die ebenfalls mit ActorPortName beginnt), ordnet sie nach Portnamen einander zu, zeigt die erkannten Kopfzeilen (LAG ID, WorkingMode, Hash arithmetic, System Priority, System ID) so, wie ausgegeben, und liest das gewählte Member im Detail, standardmäßig das erste. Zeilen werden an ihrer Form erkannt, daher dürfen die Wörter der Kopfzeile abweichen. `display eth-trunk` ohne Nummer listet jeden Trunk auf, jeweils eingeleitet von einer Zeile wie `Eth-Trunk10's state information is:`; die Seite liest den ersten Trunk mit Member-Zeilen, zeigt seinen Namen und meldet, dass andere ungelesen blieben.
- **Actor**: der Zustand des Endes, dessen Ausgabe Sie lesen.
- **Partner** (optional): der Zustand des Partners, wie dieses Ende ihn meldet, also das, was es zuletzt empfangen hat, oder seine Standardwerte, wenn Defaulted gesetzt ist.

`show lacp interfaces` von Juniper gibt die Flags als Wörter aus (Activity, Timeout, Aggr, Syn, Col, Dist, Def, Exp); lesen Sie sie ab und geben Sie das Oktett ein, oder vergleichen Sie sie mit der Bitliste der Seite.

## Zustands-Flags: die Regeln

**Die Bits.** IEEE 802.1AX selbst wird über das IEEE GET Program hinter einem IEEE-Konto angeboten ([IEEE SA, 802.1AX-2020](https://standards.ieee.org/ieee/802.1AX/6768/)) und wurde nicht gelesen. Das veröffentlichte MIB-Modul gibt die Reihenfolge an: „The first bit corresponds to bit 0 of the Actor_State (LACP_Activity), the second bit corresponds to bit 1 (Short_Timeout), the third bit corresponds to bit 2 (Aggregation)“ und so weiter bis „bit 7 (Expired)“ ([IEEE8023-LAG-MIB](https://www.ieee802.org/1/files/public/MIBs/IEEE8021-AX-MIB-202005290000Z.mib), dot3adAggPortActorAdminState). Der Linux-Treiber gibt denselben Bits ihren Platz im Oktett, von `LACP_STATE_LACP_ACTIVITY 0x1` bis `LACP_STATE_EXPIRED 0x80` ([include/uapi/linux/if_bonding.h](https://raw.githubusercontent.com/torvalds/linux/master/include/uapi/linux/if_bonding.h)); Bit 0 ist also das niedrigste Bit des Oktetts, und 0x3D bedeutet Activity, Aggregation, Synchronization, Collecting und Distributing.

**Die SNMP-Form.** Die MIB deklariert den Zustand als BITS, und SNMP sendet einen BITS-Wert mit „all the named bits ... commencing with the first bit and proceeding to the last bit, ... placed in bits 8 (high order bit) to 1 (low order bit) of the first octet“ ([RFC 3417](https://www.rfc-editor.org/rfc/rfc3417.txt), Abschnitt 8). LACP_Activity ist das erste benannte Bit, daher zeigt SNMP das Oktett bitumgekehrt: 0x3D auf der Leitung liest sich über SNMP als 0xBC. Die Seite zeigt jeden Zustand in beiden Formen.

**Der PortState von Huawei.** Huawei nummeriert die acht Zeichen von links als Bit 1 bis Bit 8. Die Tabelle von Huawei beschreibt Bit 1 als „Whether the member interface is an Actor. This bit has a fixed value 1“, Bit 2 als den Timeout (1 kurz, 0 lang; „By default, an Eth-Trunk member interface uses the long timeout interval (90s)“), Bit 3 als Erlaubnis, die Member-Schnittstelle zu aggregieren, Bit 4 als „added to the link aggregation group (LAG)“, Bit 5 und 6 als die Fähigkeit, LACPDUs zu empfangen bzw. zu senden, Bit 7 als LACPDUs mit Standardparameterwerten und Bit 8 als Receive State Machine des Actors im Zustand Expired. Das sind die Bits 0 (LACP_Activity) bis 7 (Expired) der MIB, das niedrigste zuerst geschrieben, also die Umkehrung des Oktetts in Binärschreibweise: `10111100` wie ausgegeben ist 0b00111101, 0x3D, der erwartete Wert von Cisco, und dieselben acht Ziffern wie der SNMP-BITS-Wert 0xBC in Binärschreibweise. Die Seite beschriftet jedes Bit mit beiden Nummern (Huawei-Bit 1 · Bit 0) und gibt jeden Zustand auch in der Form von Huawei an. Huawei formuliert Bit 5 und 6 über LACPDUs, wo die MIB Collecting und Distributing nennt; die Seite behält die Namen der MIB und die Bedeutungen von Juniper unten bei. Die Spalte Status verwendet die eigenen Wörter von Huawei: „Selected: A member interface in Selected state is active“, Unselect für eine inaktive und ForceFwd für eine, die „can forward Layer 2 traffic“. Im Beispiel von Huawei hat Eth-Trunk10 drei Member: GigabitEthernet0/0/2 und 0/0/3 sind Selected mit 10111100 an beiden Enden (0x3D, gebündelt), und GigabitEthernet0/0/4 ist Unselect mit 10100000 hier und 10110000 vom Partner (0x05 und 0x0D: dieses Ende nicht synchron, der Partner synchron, aber weder im Zustand Collecting noch Distributing).

**Was jedes Bit bedeutet**, nach `show lacp interfaces` von Juniper ([Juniper](https://www.juniper.net/documentation/us/en/software/junos/cli-reference/topics/ref/command/show-lacp-interfaces.html)):

| Bit | Name | Gesetzt | Nicht gesetzt |
|---|---|---|---|
| 0 | LACP_Activity | Aktiv: nimmt teil, „regardless of the partner's control value“ | Passiv: „not transmitting LAC PDUs unless its partner's control value is Active“ |
| 1 | LACP_Timeout | Kurzer (schneller) Timeout | Langer (langsamer) Timeout |
| 2 | Aggregation | Kann aggregieren | „operate only as an individual link“ |
| 3 | Synchronization | „allocated to the correct link aggregation group“, mit kompatiblem Aggregator und einer Identität, die „consistent with the system ID and operational key information transmitted“ ist | „not in the right aggregation“ |
| 4 | Collecting | Annahme eingehender Frames aktiviert | Nicht aktiviert |
| 5 | Distributing | Verteilung ausgehender Frames aktiviert | „currently disabled“ |
| 6 | Defaulted | Verwendet „the default operational partner information, administratively configured for the partner“ | Partnerinformationen „received in an LACP PDU“ |
| 7 | Expired | Die Receive Machine ist im Zustand Expired | Nicht Expired |

**Die Timer.** „In a fast timeout, PDUs are sent every second and in a slow timeout, PDUs are sent every 30 seconds. LACP timeout occurs when 3 consecutive PDUs are missed“, also nach 3 Sekunden oder 90 Sekunden (Juniper, wie oben); `lacp rate` von Cisco ergibt „the fast rate, once every 1 second“ und die normale Rate „every 30 seconds“ ([Cisco, Command Reference, IOS XE 17.18](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-18/command_reference/b_1718_9300_cr/layer_2_3_commands.html)); der LACP-Timeout von Extreme ist „either 90 seconds, long, or 3 seconds, short“, standardmäßig lang (configure sharing lacp timeout). Das Timeout-Bit ist eine Bitte an den Partner: `lacp_rate` von Linux ist die „rate in which we'll ask our link partner to transmit LACPDU packets“, standardmäßig langsam (30 Sekunden) (HOWTO). Im Treiber sendet ein Ende schnell, solange das Timeout-Bit seines Partners gesetzt ist, und sonst langsam, und es lässt seinen Partner nach seinem eigenen Bit ablaufen; ist keines der beiden Enden aktiv, gibt es überhaupt keine periodische Übertragung (ad_periodic_machine und ad_rx_machine, [bond_3ad.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/net/bonding/bond_3ad.c), dessen Konstanten `AD_FAST_PERIODIC_TIME 1`, `AD_SLOW_PERIODIC_TIME 30` und jeweils das Dreifache für die Timeouts sind). `lacp timeout` von Huawei: Mit `fast` beträgt das Intervall, in dem ein Eth-Trunk LACPDUs empfangen muss, 3 Sekunden, und „If fast is specified, the remote device sends an LACPDU every 1 second“; `slow`, der Standard, bedeutet 90 Sekunden und alle 30 Sekunden; ein `user-defined`-Wert reicht von 3 bis 90 Sekunden; die Einstellung „takes effect on all its member interfaces“, und „The timeout interval on the two ends can be different. To facilitate maintenance, you are advised to set the same timeout interval at both ends“ (Huawei, wie oben). Die Seite zeigt, wie oft jedes Ende sendet und nach welcher Zeit jedes das andere aufgibt.

**Die Bewertung.** Das Paar ist gebündelt, wenn beide Enden aggregierbar, synchron und im Zustand Collecting und Distributing sind, keines Defaulted oder Expired ist und mindestens eines aktiv ist. Liegt nur der Zustand des Actors vor, betrifft die Bewertung dieses Ende. Die Befunde, in dieser Reihenfolge:

- **Beide passiv**: „If both links are in passive mode, they won't exchange LACP packets, and the aggregated link won't be established“ ([Juniper, Aggregated Ethernet LACP](https://www.juniper.net/documentation/us/en/software/junos/interfaces-ethernet-switches/topics/topic-map/aggregated-ethernet-lacp-switches.html)); Cisco: Ein passiver Port „cannot form an EtherChannel with another port that is also in the passive mode“.
- **Expired** (dieses Ende oder vom Partner gemeldet): Bevor der Timer für den Zustand Current einmal abgelaufen war, kam keine LACPDU an; „If no LACP PDU is received before the timer for the Current state expires a second time, the state machine enters the Defaulted state“ (Juniper). Solange Expired gilt, setzt der Linux-Treiber den Timeout seines Partners auf kurz und sendet daher jede Sekunde.
- **Defaulted** (dieses Ende oder vom Partner gemeldet): keine LACPDU rechtzeitig empfangen; die Partnerwerte daneben sind Standardwerte, nicht das, was das andere Ende mitgeteilt hat.
- **Individuell**: Aggregation an einem der beiden Enden nicht gesetzt.
- **Nicht synchron**: Der Link ist nicht in der richtigen Aggregation. Ports bilden eine Aggregation, wenn sie „the same actor system ID, actor key, partner system ID, and partner key“ haben ([HPE Aruba, ArubaOS 8.11, LACP](https://arubanetworking.hpe.com/techdocs/Archived/AOS-8/ArubaOS_8.11.2_Web_Help/Content/arubaos-solutions/lacp/lacp-over.htm)); ein Member, das an einen anderen Switch oder dort an einen Port einer anderen Gruppe angeschlossen ist, zeigt daher eine System-ID oder einen Key des Partners, der von denen der anderen Member abweicht: Vergleichen Sie sie in den Partnerspalten des show-Befehls.
- **Synchron, aber nicht im Zustand Collecting und Distributing**: wird noch an den Aggregator angebunden oder wartet auf den Partner (die Mux-Zustände von Juniper zeigen, was zutrifft).
- **Unterschiedliche Timeouts**: Jedes Ende sendet mit der Rate, die das andere verlangt; ein stiller Ausfall wird daher in jeder Richtung nach einer anderen Zeit bemerkt.

## Was das Tool ablehnt, und warum

- **Welcher Link**: eine andere Policy als die vier (encap2+3 und encap3+4 können die inneren Header eines Tunnels lesen, die die Seite nicht übernimmt); eine andere Byte-Reihenfolge als little oder big; weniger als 2 oder mehr als 8 Member; ein fehlendes Feld, das die Policy liest; eine fehlerhafte MAC (verlangt sind sechs Oktette mit durchgehend einem Trennzeichen oder die Cisco-Punktschreibweise); eine IP-Adresse mit einem Oktett über 255, einer führenden Null, einer Präfixlänge oder einer Zone; Adressen aus zwei Familien; ein anderes Protokoll als TCP oder UDP; ein Port außerhalb von 0 bis 65535; eine VLAN-ID von 0 oder 4095 oder außerhalb von 1 bis 4094; eine Priorität außerhalb von 0 bis 7 oder eine Priorität bei einem ungetaggten Frame; eine Verteilung über ein Feld, das die Policy nicht liest (sie würde nichts verschieben), über mehr als 4096 Flows oder über den letzten Wert des Felds hinaus. Felder, die die Policy nicht liest, werden überhaupt nicht gelesen; ein veralteter Wert dort hält die Seite daher nicht auf.
- **Zustands-Flags**: ein Wert, der kein einzelnes Oktett ist (über 255, mehr als zwei Hexziffern oder mehr als acht Binärziffern); bloßes Hexadezimal ohne `0x`; acht Zeichen aus 0 und 1 in der Oktett-Form, die entweder ein unter dem falschen Format eingegebener PortState von Huawei oder Binärschreibweise ohne `0b` sind (die Meldung nennt beides); ein SNMP-Wert aus mehr als einem Oktett; eine Extreme-Zeichenfolge, die nicht aus acht Positionen mit dem richtigen Buchstaben oder einem Bindestrich besteht; Arista-Buchstaben, bei denen ein Paar fehlt, ein Buchstabe doppelt vorkommt oder ein Zeichen steht, das Arista nicht ausgibt; ein PortState von Huawei, der nicht aus acht Zeichen aus 0 und 1 besteht; eine eingefügte Ausgabe neben eingegebenen Werten; eine eingefügte Ausgabe ohne Member-Zeilen, mit einer Zeile, die wie eine Zeile von Local oder Partner beginnt, sich aber nicht als solche lesen lässt, mit zwei Zeilen für einen Port in derselben Tabelle oder mit einer Partner-Zeile, deren Port die Tabelle Local nicht aufführt; ein gewählter Port, den die Tabelle Local nicht aufführt.
- Jedes Feld hat höchstens 64 Zeichen, außer einer eingefügten Ausgabe: höchstens 8.192 Zeichen und 96 nicht leere Zeilen, wobei eine Zeile mit mehr als 200 Zeichen keine Tabellenzeile ist und nicht gelesen wird. Eine eingefügte Ausgabe wird nur im Format von Huawei gelesen.

## Durchgerechnete Beispiele

Der Kurs [Betrieb und Wartung von LAN-Switches](/materials/lan-switch-operations-and-maintenance), Kapitel 2.2, bündelt zwei Kabel, die Ports 47 und 48, und seine Herstellerfolien konfigurieren die schnelle LACP-Rate; Flows oder Adressen für das Bündel gibt er nicht an. Die Beispiele sind daher:

- **Welcher Link**: ein Bond mit zwei Membern, so wie das Lab des Kurses zwei Kabel bündelt, der den ersten Flow aus dem Lab des [Artikels unter „Lernen“](/learn/link-aggregation-and-lacp) überträgt, einen Backup-Datenstrom von 192.0.2.10, TCP-Port 50001, zu 198.51.100.20, TCP-Port 873, mit `layer3+4` auf einem Little-Endian-Prozessor. Die Ports lesen sich als 0x690351c3, die beiden Adressen als 0x0a0200c0 und 0x146433c6; nach dem XOR und den Faltungen ist der Hash 0x3b89385a, gerade, also überträgt ihn Member 0. Über die nächsten 64 Quellports übernehmen die beiden Member je 32 Flows, paarweise (0, 1, 1, 0, 0, 1, 1, 0 …), weil der letzte Shift das niedrigste Bit fallen lässt.
- **Die Auswertung aus dem Lab unter „Lernen“**: Derselbe Flow auf vier Membern und einem Big-Endian-Prozessor ergibt 0x62d3e15a und Member 2, den Wert, den das Lab von Hand ausrechnet.
- **layer2 zu einem Router**: Ist jeder Flow an die MAC des Routers adressiert, ergibt `layer2` 0x0000080b (0x01 XOR 0x0a XOR 0x0800) und für alle Member 3 von 4; variiert man stattdessen die Ziel-MAC über 256 Werte, verteilen sich die Flows mit 64 pro Member.
- **IPv6 über drei Member**: 2001:db8::10, TCP-Port 443, zu 2001:db8:1::20; die nächsten 300 Zielports ab 51000 landen mit 118, 91 und 91 auf den drei Membern, nicht mit je einem Drittel. Auch die von Cisco dokumentierte Aufteilung für drei Ports ist ungleichmäßig: 3:3:2 ihrer 8 Werte, 37,5 %, 37,5 % und 25 %.
- **Zustands-Flags**: 0x3F an beiden Enden: aktiv, kurzer Timeout, aggregierbar, synchron, Collecting und Distributing; gebündelt, jedes Ende sendet jede Sekunde und gibt nach 3 Sekunden auf. 0x3D an beiden Enden ist dasselbe mit der langsamen Rate, der von Cisco erwartete Wert. 68 und 0, wie /proc/net/bonding sie ausgibt, sind ein passiver Linux-Bond, der nichts empfangen hat, gegenüber einem Partnerzustand von 0, dem Standard des Treibers: beide passiv, Defaulted, nicht synchron. `A-GSCD--` (Extreme), `ALGs+CD` (Arista), 0xBC (SNMP) und `10111100` (Huawei) sind alle 0x3D.
- **display eth-trunk von Huawei**: Die Vorlage fügt das Beispiel aus der Befehlsreferenz von Huawei wörtlich ein. GigabitEthernet0/0/2, Selected (wie auch 0/0/3), liest sich an beiden Enden als 10111100: 0x3D, gebündelt, jedes Ende sendet alle 30 Sekunden. Wählt man GigabitEthernet0/0/4, Unselect, ergeben sich 10100000 und 10110000: 0x05 und 0x0D, nicht gebündelt, dieses Ende nicht synchron und der Partner noch nicht im Zustand Collecting und Distributing.

## Was das Tool nicht tut

Es kommuniziert mit keinem Switch und keinem Server: Die Werte stammen von Ihnen. Es berechnet keinen Hash eines Herstellers außer dem des Linux-Treibers, auch nicht die Wahl des Switches für den zurückkommenden Datenverkehr, die encap-Policies, Fragmente oder andere Protokolle als TCP und UDP unter `layer3+4`. Es dekodiert keine ganze LACPDU, nur die beiden Zustandsoktette (System-IDs, Keys und Portnummern einer eingefügten Ausgabe von Huawei werden so angezeigt, wie ausgegeben, und nicht geprüft), und es simuliert nicht die LACP-Zustandsautomaten. Um zu beobachten, wie Flows zwischen Membern wechseln, wenn eines ausfällt, verwenden Sie das Hashing-Lab im Artikel [Link-Aggregation und LACP](/learn/link-aggregation-and-lacp).

## Ergebnisse teilen

Unter der Bewertung erzeugt **Ergebnisse teilen** einen Link auf diese Seite, und zwar nur, wenn Sie die Schaltfläche wählen. Der Link enthält nach dem `#` den Modus und seine Felder so, wie eingegeben: immer `mode` (`link` oder `state`); im Modus „Welcher Link“ `policy`, `order` (`little` oder `big`) und `members`, dann nur die Felder, die die Policy liest, sofern eingegeben (`srcmac`, `dstmac`, `srcip`, `dstip`, `protocol`, `srcport`, `dstport`, `vlan`, `priority`), sowie `spread` und `count`, wenn eine Verteilung eingeschaltet ist; im Modus „Zustands-Flags“ `format`, `actor` und, sofern eingegeben, `partner`, oder im Format von Huawei mit eingefügter Ausgabe anstelle von `actor` und `partner` `display` (die Ausgabe, mit ihren Zeilen) und `port`, wenn einer gewählt ist. Felder, die die Policy nicht liest, und die des anderen Modus werden nicht übertragen. Im Modus „Welcher Link“ ergänzt das Popover einen Warnhinweis: MAC- und IP-Adressen und Ports können Hosts in einem privaten Netzwerk beschreiben, lesen Sie sie also, bevor Sie den Link senden. Bei einer eingefügten Ausgabe ergänzt es einen eigenen: Die Ausgabe nennt die System-IDs (MAC-Adressen) und die Schnittstellen der Switches.

Laut [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986.txt) (Abschnitt 3.5, abgerufen am 08.11.2026) ist das Fragment „separated from the rest of the URI prior to a dereference“, also vor der Dereferenzierung vom Rest der URI getrennt; daher werden diese Werte beim Öffnen des Links nicht an den Server gesendet. Sie bleiben in der Adressleiste und im Verlauf dessen, der den Link öffnet, und wer den Link hat, kann sie lesen.

- **Länge.** Ein Link enthält höchstens 16.384 Zeichen, die Grenze, die die Website für jeden Wert nach dem `#` setzt; eine eingefügte Ausgabe von bis zu 8.192 Zeichen passt hinein, und die anderen Felder sind weit kürzer.
- **Öffnen eines Links.** Der Modus und seine Felder werden so gesetzt, wie eine Eingabe sie setzen würde (im Modus „Welcher Link“ behält ein Feld, das die Policy nicht liest, seinen Wert, und eine fehlende Verteilung schaltet die Verteilung aus), und die Seite rechnet. Ein Link wird ignoriert, wenn er einen unbekannten Modus, eine unbekannte Policy, Reihenfolge, ein unbekanntes Protokoll, Format oder Verteilungsfeld enthält, ein Feld des anderen Modus oder eines, das die Policy nicht liest, wenn ein Pflichtfeld fehlt, wenn eine Anzahl ohne Verteilung steht oder umgekehrt, wenn `display` oder `port` außerhalb des Formats von Huawei steht, `display` neben `actor` oder `partner`, `port` ohne `display` oder ein Wert auf zwei Zeilen (außer bei `display`). Ob angenommen oder nicht, die Werte verschwinden danach sofort aus der Adresse der Seite, ohne dass eine Anfrage gesendet wird; ein Neuladen, ein Lesezeichen oder die Schaltfläche „Teilen“ der Seite überträgt daher nichts, was Sie nicht selbst teilen wollten.

## Herkunft

Die Engine ist feste Bitarithmetik ohne Uhr, ohne Netzwerk und ohne Zufall. Ihre Referenzvektoren (Satz `lacp-hash-and-state-reader-golden-2026-11-08b`) legen fest: jede Policy in beiden Byte-Reihenfolgen für 2 bis 8 Member, die sechs Flows des Labs unter „Lernen“, IPv6 (mit gepunktetem IPv4-Ende), die drei MAC-Schreibweisen, Ports und Adressen an ihren Grenzen, die VLAN-Policy mit und ohne Priorität, neun Verteilungen (bis zu 4096 Flows), jedes der 256 Zustandsoktette als Actor, 24 Paare aus Actor und Partner, die Formen für SNMP, Extreme und Arista, die Beispiele und Vorlagen, die Sätze, die die Regeln enthalten, und die Ablehnungen. Jeder erwartete Wert wurde von einer separaten Python-Implementierung abgeleitet, nicht durch Ausführen dieser Engine: der Hash aus dem Code des Treibers, wobei Adressen und Ports mit `struct.unpack` in der Byte-Reihenfolge des Prozessors gelesen werden, die Zustände aus der Bitreihenfolge der MIB und der Regel aus RFC 3417. Ihre Big-Endian-Ergebnisse stimmen mit den eigenen Vektoren des Labs unter „Lernen“ überein, einschließlich des Hashs, den es von Hand ausrechnet. Der zweite Satz ergänzt den PortState von Huawei: jedes Oktett noch einmal als PortState, das Beispiel aus der Befehlsreferenz von Huawei mit jedem Member als Auswahl, Ausgaben mit Windows-Zeilenenden, Leerzeilen und Tabulatoren, Zeilen ohne Kopfzeilen, eine ForceFwd-Zeile und einen 10GE-Port, jede Ablehnung einer eingefügten Ausgabe und ihre Grenzen; deren erwartete Werte stammen aus einem zweiten Python-Modell, das einen PortState als umgekehrte Zeichenfolge liest und die Zeilen an Whitespace aufteilt. Die Little-Endian-Ergebnisse des Labs unter „Lernen“, die dessen Schalter für die Byte-Reihenfolge jetzt anbietet, stimmen Flow für Flow mit dieser Engine überein.

## API

Dieselbe Engine beantwortet `/api/v1/lacp-hash-and-state-reader` in der HTTP-API der Website; der Vertrag steht auf der [API-Seite](/api), die auch angibt, ob diese Website die API bereitstellt.

- **Anfrage.** Ein JSON-Objekt. Welcher Link: `{"mode": "link", "policy": "layer3+4", "byteOrder": "little", "members": 2, "srcIp": "192.0.2.10", "dstIp": "198.51.100.20", "protocol": "tcp", "srcPort": 50001, "dstPort": 873, "spread": {"field": "srcPort", "count": 64}}`; `policy` (standardmäßig `layer2`), `byteOrder` (standardmäßig `little`), `protocol` (standardmäßig `tcp`), `vlan`, `priority` und `spread` sind optional, und `srcMac` und `dstMac` brauchen `layer2` und `layer2+3` (`vlan+srcmac` nur `srcMac`). Zustands-Flags: `{"mode": "state", "format": "octet", "actor": "0x3F", "partner": "0x3F"}`; `format` (standardmäßig `octet`) und `partner` sind optional. Im Format von Huawei kann `display` anstelle von `actor` und `partner` die ganze Ausgabe von `display eth-trunk` enthalten, wobei `port` das Member nennt, das im Detail gelesen wird.
- **Antwort, Welcher Link.** `mode`, `policy`, `policyDefault`, `byteOrder`, `byteOrderMatters`, `members`, `family`, `etherType`, `used`, `formula`, `steps` (jeder mit `id` und `value`), `hash`, `hashDecimal`, `member`, `ifDown` (für jedes ausfallende Member das Member, das der Flow dann nutzt), `ciscoValues`, `ciscoEven`, `spread` (`field`, `count`, `from`, `to`, `counts`, `min`, `max`, `even`, `first` oder null) und `notes`.
- **Antwort, Zustands-Flags.** `mode`, `format`, `formatDefault`, `actor` und `partner` (jeweils `octet`, `hex`, `decimal`, `binary`, `snmp`, `extreme`, `huawei` und `bits`, acht Einträge aus `bit`, `name`, `mask`, `set` und `text`; `partner` ist null, wenn nicht angegeben), `huawei` (null, sofern keine Ausgabe eingefügt wurde; sonst `lagId`, `workingMode`, `hashArithmetic`, `systemPriority`, `systemId`, jeweils null, wenn nicht ausgegeben, `members`, jedes mit `port`, `status`, `statusText`, `portType`, `portPri`, `portNo`, `portKey`, `weight`, `portState`, `hex`, `partner` und `verdict`, dann `port` und `portDefault`), `timers` (`actorTimeout`, `partnerTimeout`, `actorSends`, `partnerSends`, `periodic`), `status` (`bundled`, `bundled-this-end` oder `not-bundled`), `verdictText`, `findings` (jeder mit `id`, `level` und `text`) und `notes`.
- **Fehler.** HTTP 400, `invalid_input`, mit der Meldung der Engine, zum Beispiel `"3D" looks hexadecimal: write it with 0x in front (0x3D), so it is not read as decimal.`.
