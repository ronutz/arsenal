## Was das Tool tut

Fügen Sie eine Kommandozeile mit `openssl s_client` ein, den Text, den sie ausgegeben hat, oder beides, und das Tool erklärt sie. Jede Option wird anhand der Manpages von OpenSSL 3.5 gelesen, dem Release mit Langzeitsupport (unterstützt bis zum 8. April 2030); die Standardwerte, die gelten, weil eine Option fehlt, werden ausgeschrieben, jeder Block der Ausgabe wird erkannt und erklärt, und die Befunde, bei denen Handlungsbedarf besteht, stehen zuerst, die schwerwiegendsten ganz oben. Der Befehl kann in sein eigenes Feld oder in die erste Zeile des Ausgabefelds, genau so, wie ein Terminal ihn zeigt; das Tool trennt beides. Es liest nur Text: Es wird keine Verbindung aufgebaut und nichts aufgelöst, gesendet oder ausgeführt.

## Die Kommandozeile

Jede Option erscheint in ihrer Gruppe (Ziel, Servername, Verifizierung, Truststore, Protokollversionen, Cipher-Suiten und Gruppen, was s_client ausgibt, Sitzungen, Client-Zertifikat, STARTTLS und ALPN, OCSP-Stapling, Eingabeverarbeitung, DANE, PSK, Provider) mit ihrer Wirkung. Optionen werden so gelesen, wie der Optionsparser von OpenSSL selbst sie liest: `-name` und `--name` sind dieselbe Option, `--name=value` funktioniert, `--` beendet die Optionen, und danach darf ein Zielwort folgen. Eine Option, die nicht auf der Manpage von 3.5 steht, eine Option ohne ihren Wert und eine Option ohne Argument, die einen Wert erhält, werden markiert, denn s_client bricht bei jeder davon mit einem Usage-Fehler ab. `-ocsp_check_leaf` und `-ocsp_check_all` kamen mit OpenSSL 3.6: Das Tool erklärt sie, markiert sie mit „Nicht in OpenSSL 3.5“ und warnt, dass ein openssl 3.5 bei ihnen abbricht.

In den Standardwerten stecken die meisten Überraschungen, daher nennt das Tool die, die gelten:

- **Wohin die Verbindung geht.** Ohne `-connect` und ohne Zielwort verbindet sich s_client mit dem lokalen Host auf Port 4433. Ein Wert von `-connect` ohne Port behält diese 4433: `openssl s_client -connect example.com` spricht nicht mit Port 443. Laut BIO_parse_hostserv(3) lässt ein allein angegebener Host den Dienst unverändert, und s_client geht von 4433 aus.
- **Der als SNI gesendete Name.** Seit OpenSSL 1.1.1 wird ohne `-servername` der Host aus `-connect` als Server Name Indication gesendet, wenn er die Form eines DNS-Namens hat; ist er eine IP-Adresse, wird nichts gesendet (RFC 6066 erlaubt dort keine IP-Literale), und ohne jedes `-connect` wird „localhost“ gesendet. `-servername` sendet, was es erhält; `-noservername` sendet nichts.
- **Die Verifizierung hält den Handshake nie an.** Das Serverzertifikat wird immer geprüft und das Ergebnis ausgegeben, aber ohne `-verify_return_error` läuft der Handshake unabhängig vom Ergebnis weiter: Die Seite warnt, dass s_client jede Kette akzeptiert und dass eine echte Anwendung, die das täte, für einen Man in the Middle offen wäre. `-verify` schaltet die Verifizierung mit einer Tiefenbegrenzung ein und bricht trotzdem nicht ab.
- **Kein Hostname wird geprüft.** `-servername` wählt nur die SNI. s_client vergleicht das Zertifikat nur dann mit einem Namen, wenn `-verify_hostname`, `-verify_ip`, `-verify_email` oder DANE das verlangt; ohne eines davon sagt „Verify return code: 0 (ok)“ nichts darüber aus, ob das Zertifikat zur Website gehört.
- **Der Truststore.** Ohne `-CAfile`, `-CApath` oder `-CAstore` entscheidet der Standardspeicher des jeweiligen openssl-Builds. OpenSSL liefert keine eigenen Vertrauensanker mit; Linux-Distributionen verweisen es meist auf den Systemspeicher, weshalb derselbe Befehl auf einem Rechner verifizieren und auf einem anderen scheitern kann.
- **Protokollversionen.** Standardmäßig bietet der Client jede unterstützte Version an. `-tls1_2` und seine Geschwister erlauben nur eine Version und lassen sich nicht mit den Optionen `-no_*` kombinieren, die SSL_CONF_cmd(3) zugunsten von `-min_protocol` und `-max_protocol` als veraltet markiert. TLS 1.0 und 1.1 sind veraltet (RFC 8996) und werden ab Security Level 1 abgelehnt; wer sie erzwingen will, braucht daher außerdem einen Cipher-String mit `@SECLEVEL=0`, der alles erlaubt.
- **Cipher-Suiten und Gruppen.** `-cipher` setzt nur die Liste für TLS 1.2 und älter; Suiten für TLS 1.3 werden mit `-ciphersuites` gesetzt. Das Tool markiert jede der beiden, wenn die Versionsoptionen sie nutzlos machen. Ohne `-groups` verwendet OpenSSL 3.5 seine eingebaute Liste DEFAULT, die mit dem hybriden Post-Quanten-Verfahren X25519MLKEM768 beginnt und im ClientHello von TLS 1.3 zwei Key Shares sendet, X25519MLKEM768 und X25519 (SSL_CTX_set1_groups_list(3) und die Liste selbst in `ssl/t1_lib.c`).

Auch die Shell rund um den Befehl wird gelesen: `echo |` oder `</dev/null` vor s_client beenden seine Eingabe sofort, und die Seite weist darauf hin, dass ein nicht interaktiver Lauf dann zu früh schließen kann, besonders mit TLS 1.3; eine Pipe in `openssl x509` wird benannt. Secrets auf der Kommandozeile werden markiert: `-keylogfile` (ein Schlüssel-Log, mit dem Wireshark entschlüsseln kann), ein `pass:`-Passwort, das für `ps` sichtbar ist, und `-proxy_user` (Basic-Authentifizierung im Klartext zum Proxy).

## Die Ausgabe, Block für Block

Die Ausgabe wird Zeile für Zeile gelesen, und jede Zeile oder jeder Block erscheint mit Zeilennummern und Bedeutung. Was s_client ausgibt, beschreiben die Manpages nicht; das Layout wurde daher aus dem Quellcode von OpenSSL selbst am Git-Tag `openssl-3.5.9` gelesen. Zeilen, die nur OpenSSL 3.0 oder 3.6 ausgibt, werden ebenfalls gelesen, aus dem Quellcode an `openssl-3.0.13` und `openssl-3.6.5`; auch Ausgabe dieser Releases wird also erklärt:

- `Connecting to 127.0.0.1`: OpenSSL 3.5 gibt die Adresse, mit der es sich verbunden hat, auf der Standardfehlerausgabe aus, sobald die TCP-Verbindung offen ist (3.0 gab dort nichts aus);
- die Zeilen `depth=N` / `verify error:num=N:text` / `verify return:1` des Verifizierungs-Callbacks (Tiefe 0 ist das Zertifikat des Servers; OpenSSL geht vom Root-Zertifikat abwärts; `verify return:1` bedeutet, dass s_client sich entscheidet weiterzumachen). OpenSSL 3.5 schreibt Namen als `C=BR, O=Example Lab, CN=www.example.test`; 3.0 schrieb `C = BR, O = Example Lab, ...`;
- `CONNECTED(00000003)`, das nur besagt, dass die TCP-Verbindung offen ist (die Zahl ist der Dateideskriptor des Sockets);
- `Certificate chain`, die Zertifikate, wie der Server sie gesendet hat, mit `s:` Subject, `i:` Aussteller, `a:` Schlüssel- und Signaturalgorithmus und `v:` Gültigkeit; die Seite sagt dazu, dass es keine verifizierte Kette ist. In 3.5 lautet der Schlüssel `a:PKEY: RSA, 2048 (bit); sigalg: sha256WithRSAEncryption` oder bei einem Schlüssel auf elliptischen Kurven `EC, (prime256v1)`; 3.0 gab `rsaEncryption` und `RSA-SHA256` aus;
- `Server certificate` mit seinem PEM (mit `-showcerts` das PEM jedes Zertifikats) und den Zeilen `subject=` und `issuer=`;
- die Anforderung eines Client-Zertifikats, falls vorhanden, `Peer signing digest` und `Peer signature type`, das OpenSSL 3.5 als Namen des Signaturschemas der IANA angibt, etwa `rsa_pss_rsae_sha256` (3.0 gab `RSA-PSS` aus); dann der ephemere Schlüssel des Servers: `Peer Temp Key` in 3.5 oder `Negotiated TLS1.3 group`, wenn TLS 1.3 kein temporäres Schlüsselobjekt anzuzeigen hat, wie bei der hybriden Post-Quanten-Gruppe X25519MLKEM768, die zwei Peers mit OpenSSL 3.5 standardmäßig aushandeln (3.0 gab `Server Temp Key` aus);
- `SSL handshake has read N bytes and written M bytes` (0 gelesene Byte bedeuten, dass der Server nichts zurückgesendet hat);
- `Verification: OK` oder `Verification error: text` und `Verified peername`, wenn ein Hostname geprüft wurde;
- `New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384` (oder `Reused` bei einer wiederaufgenommenen Sitzung). Die Version in dieser Zeile ist die Version, die die Cipher-Suite zuerst definiert hat (SSL_CIPHER_get_version), nicht unbedingt die ausgehandelte: Eine Verbindung mit TLS 1.1 gibt `New, TLSv1.0, Cipher is ECDHE-RSA-AES256-SHA` aus. Die ausgehandelte Version steht in der Zeile `Protocol:`, die OpenSSL 3.5 danach ausgibt, und im Block SSL-Session;
- `Server public key is N bit`, die Zeile zur Neuaushandlung (`Secure Renegotiation IS supported` bis TLS 1.2; unter TLS 1.3, das keine Neuaushandlung kennt, gibt 3.5 „This TLS version forbids renegotiation.“ aus, wo 3.0 `IS NOT supported` ausgab), Komprimierung, ALPN, Early Data;
- `Verify return code: N (text)`, das abschließende Ergebnis der Verifizierung, mit seiner Bedeutung;
- der Block `SSL-Session`, Feld für Feld. Bei TLS 1.2 kommt er einmal, nach dem Handshake; bei TLS 1.3 einmal pro `Post-Handshake New Session Ticket arrived:`, weil der Server seine Tickets nach dem Handshake sendet (RFC 9846, Abschnitt 4.7.1). `Master-Key` (TLS 1.2) und `Resumption PSK` (TLS 1.3) sind Secrets der Sitzung;
- mit `-status` die OCSP-Zeile: `OCSP response: no response sent` (OpenSSL 3.5 und 3.0; 3.6 änderte sie in `no OCSP response received` oder unter TLS 1.3 in `OCSP responses: no responses sent`) oder die per Stapling gelieferte Antwort, ausgegeben zwischen zwei Zeilen aus `=`-Zeichen, aus der der Antwortstatus, Cert Status und das Fenster aus This Update und Next Update gelesen werden;
- die Kurzfassung von `-brief`, die Schritte von `-state` (`SSL_connect:...` und Alerts), die Nachrichten von `-msg` mit ihren Hex-Bytes, Lese- und Schreibvorgänge von `-debug`, Erweiterungen von `-tlsextdebug`, die Zeilen für Raw Public Keys nach RFC 7250 und Zeilen aus der Fehlerwarteschlange von OpenSSL, gelesen in dem Format, das ERR_print_errors(3) dokumentiert (Code, Bibliothek, Funktion, Grund, Datei und Zeile).

Alles andere, etwa eine HTTP-Antwort, die der Server nach dem Handshake gesendet hat, wird als Daten angezeigt und nie verworfen.

## Rückgabecodes der Verifizierung

Die Zahl in `verify error:num=N` und `Verify return code: N` ist ein Code vom Typ X509_V_ERR. openssl-verify(1) verweist für die Liste auf X509_STORE_CTX_get_error(3) und für die Nummern auf den Header `<openssl/x509_vfy.h>`. Das Tool kennt die 96 Codes von OpenSSL 3.5.9 (0 bis 95) mit ihrer Konstante, dem genauen ausgegebenen Text und einer verständlichen Auswertung, außerdem die sechs Codes, die OpenSSL 3.6 hinzugefügt hat (96 bis 101, fünf davon zu OCSP), markiert als nur in 3.6 vorhanden. Der Text in den Klammern stammt aus `crypto/x509/x509_txt.c`: Für die Codes 0 bis 94 ist er in 3.0.13 und 3.5.9 gleich, Code 95 (ein Raw Public Key, für dessen Vertrauen nichts konfiguriert ist) gibt es in 3.0.13 nicht, und 3.6 erweitert Code 9 zu „certificate is not yet valid or the system clock is incorrect“. Am häufigsten zu sehen: 0 ok, 10 abgelaufen, 18 ein selbstsigniertes Serverzertifikat, 19 ein selbstsigniertes Root-Zertifikat an der Spitze der Kette, dem der Client nicht vertraut, 20 ein Aussteller, der sich weder unter dem vom Server Gesendeten noch im Truststore findet, 21 ein einzelnes Zertifikat, das sich nicht verifizieren lässt, und 62 abweichender Hostname.

## Befunde

Die Befunde fügen die Auswertung zusammen. Die häufigsten: Die Verifizierung ist gescheitert (mit der Bedeutung des Codes), und der Handshake lief trotzdem weiter; ein fehlendes Zwischenzertifikat, ermittelt aus Fehler 20 oder 21 und der vom Server gesendeten Kette (das zuletzt gesendete Zertifikat nennt einen Aussteller, der nie gesendet wurde); ein nicht vertrauenswürdiges Root-Zertifikat, ein selbstsigniertes Zertifikat, ein abgelaufenes oder noch nicht gültiges, ein abweichender Name; eine Verifizierung, die ohne jede Prüfung des Hostnamens bestanden wurde; ein Handshake, der gescheitert ist oder nichts gelesen hat; ausgehandeltes TLS 1.0 oder 1.1; die Versionsfalle der Cipher-Zeile; NULL-, RC4-, Export-, DES-, 3DES- oder anonyme Suiten, RSA-Schlüsseltransport, DHE über endliche Körper und CBC-Suiten in TLS 1.2 (RFC 9325); eine Signatur mit SHA-1 oder MD5 in TLS 1.2 (RFC 9155); keine sichere Neuaushandlung oder kein Extended Master Secret in TLS 1.2 (RFC 9325, Abschnitt 3.5); eine Kette in falscher Reihenfolge oder mit eigenem Root-Zertifikat (RFC 9846, Abschnitt 4.5.1); OCSP nicht per Stapling geliefert oder mit dem Status good, revoked oder unknown (RFC 6960); eine Option, die OpenSSL 3.5 nicht hat; und Werte von Master-Key oder Resumption PSK, die vor dem Teilen der Ausgabe zu schwärzen sind.

## Beispiele

Die Schaltfläche „Beispiel“ lädt eine Aufzeichnung im Layout von OpenSSL 3.5: einen Server, der sein Zertifikat ohne das Zwischenzertifikat sendet, während der Client dem Root-Zertifikat über `-CAfile` vertraut. s_client gibt bei Tiefe 0 erst Fehler 20, dann 21 aus, schließt den Handshake trotzdem ab und endet mit „Verify return code: 21 (unable to verify the first certificate)“.

Die Referenzvektoren (Golden Vectors) sind neunzehn Aufzeichnungen gegen lokale Instanzen von `openssl s_server` und eine Wegwerf-Test-CA: TLS 1.3 mit vollständiger Kette, erzwungenes TLS 1.2 mit ALPN h2, TLS 1.1 auf Security Level 0, eine unbekannte CA, deren Server auch sein Root-Zertifikat sendet, ein selbstsigniertes Zertifikat, `-verify_return_error`, das den Handshake abbricht, `-showcerts`, `-brief`, `-status` mit und ohne per Stapling gelieferte Antwort, ein abweichender und ein passender Hostname, ein abgelaufenes Zertifikat (über `-attime`), `-state`, `-msg` und `-reconnect` in beiden Layouts. Jede ist ein echter Lauf vom 27. Oktober 2026 mit OpenSSL 3.5.9 an beiden Enden der Verbindung, gebaut aus dem offiziellen Quellcode-Release, nachdem dessen SHA-256 und Signatur geprüft waren. Zwei Peers mit 3.5.9 handeln unter TLS 1.3 die hybride Gruppe X25519MLKEM768 aus; diese Aufzeichnungen geben daher `Negotiated TLS1.3 group: X25519MLKEM768` aus, wo die mit TLS 1.2 `Peer Temp Key: X25519, 253 bits` ausgeben, und die Aufzeichnung mit `-msg` zeigt das ClientHello mit dem Key Share dieser Gruppe. Kurze Vektoren im Zeilenformat decken die Zeilen ab, die in keiner Aufzeichnung vorkommen, etwa die EC-Form von `a:PKEY`, das Layout von 3.0 und die OCSP-Zeilen, die nur 3.6 ausgibt, und sechsundzwanzig für die Tests geschriebene Kommandozeilen schreiben die Regeln des Befehlslesers fest. Neun Share-Vektoren schreiben Byte für Byte die Kopie fest, die ein Link von „Ergebnisse teilen“ enthält: die beiden Werte von Resumption PSK aus dem Beispiel, einen Master-Key von TLS 1.2, die sechs eines Laufs mit `-reconnect`, die vier Secrets der Kommandozeile, die Quellen, die bleiben, die Formen `--opt=value` und mit Fortsetzungszeile, einen Befehl oben im Ausgabefeld und die Passphrase eines anderen Befehls; für jeden liest die empfangende Seite dieselben Befunde, nur ohne den Befund zu ausgegebenen Secrets.

## Verwandte Tools und Lektüre

- **Die Zertifikate.** Fügen Sie die PEM-Blöcke, die `-showcerts` ausgibt, in den [Generator für Zertifikatsketten](/tools/cert-chain-builder) ein, der sie ordnet und ein fehlendes Zwischenzertifikat benennt, oder ein einzelnes Zertifikat in den [X.509-Zertifikatsdecoder](/tools/x509), um seine Felder und Erweiterungen zu lesen. Die Seite verlinkt beide neben der Kette, die sie zeigt.
- **Die Cipher-Suite.** Der [Cipher-Suite-Decoder](/tools/cipher) zerlegt die Suite aus der Zeile `Cipher is` in Schlüsselaustausch, Authentifizierung, Verschlüsselungsverfahren und MAC, mit ihrem Namen bei der IANA und ihrem Empfehlungsstatus.
- **Ein BIG-IP am anderen Ende.** Ist der Server ein virtueller Server auf einem BIG-IP, legt dessen client-ssl-Profil die Protokollversionen und Cipher-Suiten fest, auf die s_client trifft: [F5-SSL-Profile erklärt](/tools/f5-ssl-profile-explainer) liest das Profil und [F5-Cipher-Strings erklärt](/tools/f5-cipher-string-expander) seinen Cipher-String.
- **Eine Aufzeichnung teilen.** Schwärzen Sie die Secrets der Sitzung, bevor eine Aufzeichnung auf eine Folie oder in ein Ticket kommt. Die Secret-Prüfung von [Code als Bild](/tools/code-to-image) hat dafür keine Regel: Sie lässt eine Zeile `Resumption PSK:` von TLS 1.3 so, wie ausgegeben, und maskiert eine Zeile `Master-Key:` von TLS 1.2 nur, weil die Zeile die Form eines YAML-Schlüssels mit einem Namen hat, der nach einem Secret aussieht.
- **Lektüre.** [openssl s_client lesen](/learn/reading-openssl-s-client-output) geht durch, was der Befehl prüft und was die Ausgabe belegt, und [Zertifikatsketten](/learn/certificate-chains-order-anchors-and-what-breaks-them) erklärt die Kette hinter den Fehlern 20 und 21.

## Ergebnisse teilen

Unter den Befunden erzeugt **Ergebnisse teilen** einen Link auf diese Seite, und zwar nur, wenn Sie die Schaltfläche wählen. Der Link enthält nach dem `#` beide Felder, wobei jeder geheime Wert durch `[redacted]` ersetzt ist, nie so, wie eingefügt: jeder `Master-Key` und jeder `Resumption PSK` der Sitzungsblöcke, eine Passphrase, die als `pass:` an `-pass` oder `-proxy_pass` übergeben wird (oder in dieser Form irgendwo sonst im Text steht), der Schlüssel von `-psk` und das Passwort von `-srppass`. Das Popover nennt zuerst, was der Link enthält und wie viele Werte ersetzt wurden, und bietet dann „Link kopieren“ und, sofern der Browser eines bietet, das Teilen-Menü an; die Adresse der Seite bleibt unverändert.

Eine vollständige Ausgabe von s_client enthält fast immer eines der beiden Sitzungs-Secrets; deshalb enthält der Link eine Kopie statt des eingefügten Texts. Alles andere bleibt: Hostnamen, die Kette, die Quellen `env:`, `file:`, `fd:` und `stdin` einer Passphrase ([openssl-passphrase-options(1)](https://docs.openssl.org/3.5/man1/openssl-passphrase-options/), abgerufen am 27.10.2026, nennt nur die Form `pass:` als das Passwort selbst) und die Ticket-Bytes, die ohne ihr Secret keine Sitzung wiederaufnehmen können ([RFC 9846](https://www.rfc-editor.org/rfc/rfc9846), Abschnitte 4.7.1 und 4.3.11.2, abgerufen am 27.10.2026). Laut [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (Abschnitt 3.5, abgerufen am 27.10.2026) ist das Fragment „separated from the rest of the URI prior to a dereference“, also vor der Dereferenzierung vom Rest der URI getrennt; daher wird die Kopie beim Öffnen des Links nicht an den Server gesendet. Sie bleibt in der Adressleiste und im Verlauf dessen, der den Link öffnet, und wer den Link hat, kann sie lesen.

- **Länge.** Insgesamt höchstens 16.384 Zeichen, die Grenze, die die Website für jeden Wert nach dem `#` setzt; ist der geteilte Inhalt länger, gibt es keinen Link, und das Popover nennt seine Länge.
- **Öffnen eines Links.** Beide Felder füllen sich wie beim Einfügen (ein fehlendes wird geleert), und die Seite erklärt sie; wie immer wird keine Verbindung aufgebaut. Die Share-Vektoren prüfen, dass die empfangende Seite denselben Handshake liest: dieselben Befunde, nur ohne den Befund zu ausgegebenen Secrets. Danach verschwinden die Werte sofort aus der Adresse der Seite, ohne dass eine Anfrage gesendet wird; ein Neuladen oder die Schaltfläche „Teilen“ der Seite überträgt daher nichts.
- **Links von der seriellen Konsole.** Ein als `#input=` übergebener Bericht füllt das Ausgabefeld weiterhin genau wie bisher; „Ergebnisse teilen“ verwendet eigene Namen (`command`, `output`), sodass sich beides nie vermischt.

## API

Dieselbe Engine beantwortet die Operation `/api/v1/openssl-s-client-explainer` der HTTP-API der Website, beschrieben im OpenAPI-Vertrag auf der [API-Seite](/api), die auch angibt, ob diese Website die API bereitstellt. Schwärzen Sie Werte von Master-Key und Resumption PSK, bevor Sie Ausgabe irgendwohin senden, auch an diese API.

- **Anfrage.** Text: die Kommandozeile, die Ausgabe oder die Kommandozeile gefolgt von der Ausgabe.
- **Antwort.** `command` (null, wenn keiner gefunden wurde): `found`, `program`, `options` (jede mit `typed`, `name`, `value`, `known`, `group`, `text`, `dflt`, `since`, `deprecated`, `notIn35`, `problem`), `target` (`raw`, `from`, `host`, `port`, `portDefaulted`, `hostIsIp`), `sni` (`mode`, `value`, `text`), `stdinClosed`, `inputFrom`, `outputTo`, `absent` und `findings`. `output` (null, wenn es keine gab): `recognised`, `layout` (`full`, `brief` oder `unknown`), `lines`, `truncated`, `items` (jedes mit `kind`, `start`, `end`, `text`, `fields`, `connection`, `explain` und `detail`), `connections` (eine pro Handshake: Protokoll, Cipher-Suite, Verifizierung, Kette, Schlüssel, ALPN, OCSP, Tickets, ausgegebene Secrets, Fehlergründe) und `findings`. Dann `findings` (beide Listen zusammen, die schwerwiegendsten zuerst) und `splitFromOutput`. Jede Erklärung wird als `{"en": ..., "pt": ...}` geliefert; jeder Befund hat eine stabile `id`, eine `severity` (`high`, `warn` oder `info`) und die `source`, auf der er beruht.
- **Fehler.** Text, der weder ein Befehl noch eine Ausgabe von s_client ist, führt nicht zu einem HTTP-Fehler: Die Befunde nennen `noCommandFound` oder `notSClientOutput`.
