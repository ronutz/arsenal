# AFM-Regelkontexte und Treffer erklärt

Die Network Firewall von BIG-IP AFM (Advanced Firewall Manager) ist eine Hierarchie, und das Handbuch nennt ihre Reihenfolge klar: Richtlinien werden vom globalen Kontext über die Route Domain bis zum virtuellen Server oder zur Self IP verarbeitet, wobei Regeln für den Management-Port getrennt verarbeitet werden und überhaupt keine Richtlinie aufnehmen können. Der Satz, der über echte Ergebnisse entscheidet, steht direkt neben dieser Reihenfolge: Trifft Datenverkehr in einem Kontext auf eine Regel, wird deren Aktion angewendet, und der Datenverkehr wird im nächsten Kontext erneut verarbeitet. Die Aktion accept ist also eine Eintrittskarte bis zur nächsten Kontrolle, nicht durch das ganze Gebäude. Nur accept-decisively beendet den Durchlauf mit einem Ja, sinngemäß nach der Übersicht auf DevCentral: Das Paket wird zugelassen, und es findet keine weitere Verarbeitung in Kontexten statt. Bei drop wird stillschweigend verworfen; reject antwortet mit einem TCP-RST oder einer ICMP-Meldung Unreachable.

Fügen Sie Kontextdeklarationen, die Richtlinien, die sie durchsetzen, und eine Paketzeile ein, und der Durchlauf folgt dieser dokumentierten Reihenfolge, unabhängig von der Reihenfolge beim Einfügen. Jeder Kontext erscheint als Schritt: die erste zutreffende Regel, ihre Aktion und was die Aktion genau an dieser Stelle bedeutet. Richtlinien im Staging verhalten sich so, wie das Handbuch das Staging beschreibt: Der Treffer wird gemeldet, die Konnektivität bleibt unberührt. Rule-Lists werden an Ort und Stelle aufgelöst, entsprechend der Empfehlung, Richtlinien aus ihnen aufzubauen.

Zwei belegte Verhaltensweisen werden mechanisch durchgesetzt, statt nur nebenbei erwähnt zu werden. Die ICMP-Einschränkung, wörtlich aus dem Handbuch: „rules for ICMP or ICMPv6 cannot be created on a self IP or virtual server context“, und schmuggelt eine Rule-List doch eine hinein, gilt „such a rule will be ignored“; der Durchlauf überspringt diese Regeln in Edge-Kontexten und weist darauf hin. Und das Tool erfindet nie einen Standardwert: Beendet kein Kontext das Paket und wurde keine `default-action` deklariert, sagt der Durchlauf, dass das Ergebnis der Default Firewall Action des Geräts zufällt, statt zu raten, welchen Modus Sie betreiben.

Eine einzelne Richtlinie erhält das Audit nach den Definitionen des Systems selbst: Eine Regel, deren Kriterien vollständig von einer früheren Regel mit derselben Aktion abgedeckt werden, ist redundant, bei einer anderen Aktion steht sie im Konflikt, und der Sonderfall des Handbuchs wird berücksichtigt: accept und accept-decisively gelten als Konflikt, obwohl beide zulassen. Geolocation, FQDNs und Zeitpläne werden erkannt und gemeldet, aber nicht ausgewertet: Eine Regel, die sie verwendet, hält den Durchlauf mit einem ehrlichen „unbestimmt“ an, statt zu raten.

Alles läuft lokal; nichts, was Sie einfügen, verlässt die Seite, und es wird kein Gerät berührt.

## Ergebnisse teilen

Oberhalb der Auswertung erzeugt **Ergebnisse teilen** einen Link auf diese Seite, und zwar nur, wenn Sie die Schaltfläche wählen. Der Link enthält nach dem `#` das Feld so, wie eingegeben, und sonst nichts. Das Popover nennt zuerst, was der Link enthält, dann einen eigenen Warnhinweis: Eine Firewall-Richtlinie nennt Ihre Adressen, Kontexte und virtuellen Server; lesen Sie sie daher, bevor Sie den Link senden. Dann bietet es „Link kopieren“ und, sofern der Browser eines bietet, das Teilen-Menü an; die Adresse der Seite bleibt unverändert.

Diese Seite überspringt jeden Konfigurationsblock, den sie nicht erklärt, sodass auch eine ganze Konfigurationsdatei eine Auswertung erhält, und ein Link darauf würde alles enthalten, was darin steht. Solange der eingefügte Text eine geheime Einstellung enthält, gibt es daher keinen Link, und das Popover nennt die Einstellung: ein tmsh-Attribut namens `password`, `passphrase` oder `secret` oder eines, dessen Name darauf endet (`encrypted-password`, `proxy-ca-passphrase`, `shared-secret`), `bind-pw` oder `community-name`, gefolgt von einem anderen Wert als `none`; oder ein Header `Authorization` an beliebiger Stelle, etwa im `send`-String eines Monitors. Die [tmsh-Referenz von F5 für gtm monitor http](https://clouddocs.f5.com/cli/tmsh-reference/latest/modules/gtm/gtm_monitor_http.html) (abgerufen am 27.10.2026) führt `password` neben `send` auf, und [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110) (Abschnitt 11.6.2, abgerufen am 27.10.2026) definiert den Wert von Authorization als Zugangsdaten. Entfernen Sie diese Zeile, und wählen Sie die Schaltfläche erneut: Diese Seite zeigt diese Werte nie an, daher liest sich der Rest gleich.

Laut [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (Abschnitt 3.5, abgerufen am 27.10.2026) ist das Fragment „separated from the rest of the URI prior to a dereference“, also vor der Dereferenzierung vom Rest der URI getrennt; daher wird der Text beim Öffnen des Links nicht an den Server gesendet. Er bleibt in der Adressleiste und im Verlauf dessen, der den Link öffnet, und wer den Link hat, kann ihn lesen.

- **Länge.** Insgesamt höchstens 16.384 Zeichen, die Grenze, die die Website für jeden Wert nach dem `#` setzt; ist der geteilte Inhalt länger, gibt es keinen Link, und das Popover nennt seine Länge.
- **Öffnen eines Links.** Der Text füllt das Feld wie beim Einfügen, und die Seite liest ihn; es wird nichts gesendet. Danach verschwindet der Wert sofort aus der Adresse der Seite, ohne dass eine Anfrage gesendet wird; ein Neuladen oder die Schaltfläche „Teilen“ der Seite überträgt daher nichts.
