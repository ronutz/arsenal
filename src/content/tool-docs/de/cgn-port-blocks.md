## Was das Tool tut

Wenn ein Carrier-Grade NAT (CGN) eine öffentliche IPv4-Adresse unter vielen Teilnehmern aufteilt, wird eigentlich das 16-Bit-Portfeld dieser Adresse geteilt. Das Tool rechnet diese Aufteilung in drei Modi durch: Portblöcke (wie viele Blöcke und Teilnehmer eine Adresse und ein Pool fassen und wie viel Logging die Blöcke einsparen), die deterministische Zuordnung nach RFC 7422 (welche öffentliche Adresse und welche Ports eine interne Adresse erhält, und umgekehrt: von öffentlicher Adresse, Port und Zeit zurück zur internen Adresse) und das Port-Set eines Port Set Identifier (PSID) bei Mapping of Address and Port (MAP), wie MAP-E (RFC 7597) und MAP-T (RFC 7599) es berechnen. Alles ist Ganzzahlarithmetik in Ihrem Browser; Zeitpunkte sind Eingaben und werden nie von einer Uhr gelesen.

## Warum der nutzbare Bereich bei 1024 beginnt

Das Portfeld hat 65.536 Werte, und RFC 6335 teilt sie ein in „the System Ports, also known as the Well Known Ports, from 0-1023“, die User Ports von 1024 bis 49151 und die Dynamic Ports von 49152 bis 65535 ([RFC 6335, section 6](https://www.rfc-editor.org/rfc/rfc6335.txt)). Die Quellen, nach denen Portzuteilungen im CGN bemessen werden, beginnen alle oberhalb der System Ports: Der erste Zuteilungsschritt in RFC 7422 entfernt die reservierten Ports und legt fest: „At a minimum, the CGN SHOULD remove system ports [RFC6335] from the port candidate list“ ([RFC 7422, section 2](https://www.rfc-editor.org/rfc/rfc7422.txt)); der Offset in RFC 7597 ist standardmäßig 6, „as this excludes the system ports (0-1023)“ ([RFC 7597, section 5.1](https://www.rfc-editor.org/rfc/rfc7597.txt)); und RFC 6269 zitiert RFC 4787 mit der Aussage, dass „the use of port space (1024-65535) is safe“ für ausgehende Quellports ([RFC 6269, section 5](https://www.rfc-editor.org/rfc/rfc6269.txt)). Der nutzbare Standardbereich ist daher 1024 bis 65535, also 64.512 Ports pro Adresse. Sie können ihn ändern: Das Tool weist darauf hin, wenn Ihr Bereich System Ports enthält.

## Modus 1: Portblöcke

Eingaben: der öffentliche Pool (ein Präfix wie `192.0.2.0/24`, ein Bereich, eine einzelne Adresse oder nur eine Anzahl von Adressen), der nutzbare Portbereich, die Blockgröße in Ports, die Blöcke, die jeder Teilnehmer halten darf, und optional der Bedarf, als Anzahl von Teilnehmern oder als internes Präfix, aus dem die Teilnehmer nummeriert sind.

Ausgaben: nutzbare Ports pro Adresse, ganze Blöcke pro Adresse und die Ports, die kein ganzer Block abdeckt, Teilnehmer pro Adresse, Teilnehmer im ganzen Pool, das Portlimit pro Teilnehmer und, gemessen am Bedarf, wie viele Adressen gebraucht werden und ob der Pool sie fasst.

Eine Regel bestimmt die Zählung. RFC 6888 verlangt „Paired“ Address Pooling: „a CGN must use the same external IP address mapping for all sessions associated with the same internal IP address“ ([RFC 6888, section 3, REQ-2](https://www.rfc-editor.org/rfc/rfc6888.txt)). Alle Blöcke eines Teilnehmers liegen also auf einer Adresse, und die Teilnehmer pro Adresse sind die ganzen Blöcke pro Adresse geteilt durch die Blöcke pro Teilnehmer, abgerundet. Blockgröße mal Blöcke pro Teilnehmer ist das Limit pro Teilnehmer, das ein CGN laut REQ-4 unterstützen soll: „A CGN MUST support limiting the number of external ports (or, equivalently, 'identifiers' for ICMP) that are assigned per subscriber“.

Der Bereich zum Logging beziffert nur, was die RFCs beziffern. RFC 7422 nennt Log-Meldungen von „approximately 150 bytes long for NAT444 [NAT444] and 175 bytes for DS-Lite“ und „approximately 33,000 connections per day“ pro Haushalt, woraus es „approximately 5 MB per subscriber per day“ macht ([RFC 7422, section 1](https://www.rfc-editor.org/rfc/rfc7422.txt)); das Tool zeigt 33.000 Zeilen und 4.950.000 Byte (oder 5.775.000 mit DS-Lite-Meldungen), aus diesen beiden Werten berechnet. Laut RFC 7768 protokolliert die Blockzuteilung „only when blocks are allocated or deallocated“, „reducing log generation by a factor equal to the block size“ ([RFC 7768, section 2](https://www.rfc-editor.org/rfc/rfc7768.txt)); die Zeile für Blöcke teilt durch diesen Faktor. Es ist ein berechneter Wert, keine Messung: Die einzige Messung, die der RFC zitiert, sind 42,5 TB an Logs pro Sitzung gegenüber 40,6 GB mit Portblöcken, für 20.000 Teilnehmer über 60 Tage (Abschnitt 1).

## Modus 2: deterministische Zuordnung (RFC 7422)

RFC 7422 ersetzt das Übersetzungslog durch eine Funktion: „(External IP Address, Port Range) = function 1 (Internal IP Address)“ und „Internal IP Address = function 2 (External IP Address, Port Number)“ ([RFC 7422, section 2](https://www.rfc-editor.org/rfc/rfc7422.txt)). Seine Variablen sind der interne Bereich I, der externe Bereich O, das Kompressionsverhältnis C, der Faktor D für den dynamischen Pool, die maximale Portzahl pro Benutzer M, der Algorithmus A und die Liste R der reservierten Ports. Das Tool implementiert Algorithmus 0, Sequential, den das durchgerechnete Beispiel des RFC verwendet, Schritt für Schritt:

1. R (standardmäßig `0-1023`) aus der Liste der Kandidatenports entfernen.
2. Jeder internen Adresse 1/(C + D) der Kandidaten geben, abgerundet; „Any remaining ports are allocated to the dynamic pool.“
3. Sequential: Der erste Block geht an die erste interne Adresse, der zweite an die zweite und so weiter.
4. Ports über den Block eines Teilnehmers hinaus kommen aus dem dynamischen Pool, bis M, und „The CGN MUST log dynamically assigned port blocks“.

Der interne Bereich ist ein Präfix oder ein Bereich. Ein Präfix wird als seine Host-Adressen gezählt, so wie Abschnitt 2.3 sein Beispiel zählt: `198.51.100.0/28` ergibt die 14 Adressen `.1` bis `.14`, C ist also 14. C ist standardmäßig I geteilt durch O, aufgerundet; Sie können es festlegen. Hat O mehr als eine Adresse, füllt das Tool die externen Adressen der Reihe nach mit je C internen Adressen: Das Beispiel des RFC hat eine einzige externe Adresse und zeigt diesen Fall nicht, betrachten Sie es also als Aufteilung des Tools. Eine Liste reservierter Ports mit zusätzlichen Ports (`0-1023,5004,5060`) wird genau berücksichtigt, und ein Block, der einen reservierten Port überspannt, wird als zwei Bereiche angezeigt.

Vorwärtssuche: Eine interne Adresse ergibt ihre externe Adresse und ihren Portbereich. Rückwärtssuche: Eine externe Adresse und ein Port ergeben die interne Adresse, wenn der Port in einem vorab zugeteilten Block liegt; „dynamisch“, wenn er im dynamischen Pool liegt, wo nur das Log der dynamischen Blöcke antworten kann; „reserviert“, wenn er in R liegt; „nicht im Pool“, wenn die Adresse nicht in O liegt. Ein Zeitpunkt (UTC, auf die Sekunde, wie RFC 6302 es für Server-Logs empfiehlt) kann hinzukommen, und mit „gültig ab“ und „gültig bis“ gibt das Tool an, ob die eingegebene Konfiguration zu diesem Zeitpunkt galt. Die vier Zeitpunkte werden mit der Datums- und Uhrzeitauswahl des Browsers gesetzt und als UTC gelesen; jede Zahl auf den drei Tabs hat außerdem Pfeile nach oben und unten, die innerhalb der Bereiche bleiben, die das Tool annimmt. RFC 7422 begründet, warum das wichtig ist: Um einen Teilnehmer zu identifizieren, braucht man die zu diesem Zeitpunkt gültige Konfiguration, daher „the CGN MUST generate a record any time such variables are changed“ ([RFC 7422, section 3](https://www.rfc-editor.org/rfc/rfc7422.txt)). Das Tool schreibt diesen Eintrag im Format des RFC, Zeitstempel, internes Präfix und Maske, externes Präfix und Maske, D, M, A und R: Für die Felder des RFC selbst gibt es `[Wed Oct 11 14:32:52 2000]:198.51.100.0:28:192.0.2.0:32:2:5040:0:1-1023,5004,5060` aus.

Nicht implementiert: die Algorithmen 1 bis 5 (der RFC beschreibt Staggered, Round robin und Interlaced horizontally nur anhand von Beispielen, und 4 und 5 hängen von Schlüsseln oder Herstellern ab) sowie ein interner IPv6-Bereich (DS-Lite), den RFC 7422 erlaubt. Die interne Adresse ist das Ende der Arithmetik: Abschnitt 2.3 korreliert sie anschließend „with DHCP/PPP lease connection records“.

## Modus 3: MAP-Port-Sets (RFC 7597, RFC 7599)

MAP teilt eine Adresse ohne zentrales NAT, indem jedes Customer Edge (CE) ein festes Port-Set erhält. RFC 7597 schreibt einen Port als drei Felder, A (a Bit), die PSID (k Bit) und j (m Bit), mit a + k + m = 16 ([RFC 7597, section 5.1](https://www.rfc-editor.org/rfc/rfc7597.txt)). „For 'a' > 0, A MUST be larger than 0“, daher gehört der Portblock, in dem A gleich 0 ist, niemandem: Mit dem Standardwert a = 6 ist das 0 bis 1023, und „'a' = 4 will exclude ports 0-4095“. „The sharing ratio is 2^k. The number of ports assigned to the user is 2^(16 - k) - 2^m (excluded ports)“, jeder zusammenhängende Bereich enthält 2^m Ports, und „The interval between initial port numbers of successive contiguous ranges assigned to the same user is 2^(16 - a)“. MAP-T verwendet dieselben Regeln: Sein Anhang zur Portzuordnung verweist auf den von RFC 7597 ([RFC 7599, Appendix B](https://www.rfc-editor.org/rfc/rfc7599.txt)).

Eingaben: a, k und eine PSID (dezimal oder hexadezimal mit `0x`) und/oder ein Port. Ausgaben: m, das Teilungsverhältnis, die Ports pro Set, Länge und Abstand der Bereiche, der ausgeschlossene Block, jeder Bereich der PSID (bis zu 1.024 davon) und für einen Port die PSID, der er gehört, nach der Formel aus RFC 7597 „PSID = trunc((P modulo (R * M)) / M)“ (Anhang B), oder „ausgeschlossen“, wenn sein A gleich 0 ist. Mit a = 0 gibt es kein Feld A, und das ganze Port-Set ist ein einziger Bereich; RFC 7597 hält niedrige Ports dann heraus, „by putting a lower bound equal to ceil(N / M) on the allowed set of PSID values“ (Anhang B.1), und das Tool nennt diese Untergrenze für N = 1024.

## Durchgerechnete Beispiele

- Blöcke: `192.0.2.0/24` mit Blöcken von 300 Ports, der Größe des Beispielblocks „ports 2001~2300“ aus RFC 7768: 215 Blöcke pro Adresse mit 12 übrigen Ports, 55.040 Teilnehmer im Pool und 110 Log-Zeilen pro Teilnehmer und Tag statt 33.000.
- Deterministisch: das Beispiel aus RFC 7422, intern `198.51.100.0/28`, extern `192.0.2.1`, D = 2, M = 5040. C + D = 16, jede interne Adresse erhält 4.032 Ports, `198.51.100.1` hat 1024 bis 5055 und `198.51.100.14` hat 53440 bis 57471, der dynamische Pool ist 57472 bis 65535, und M erlaubt 1.008 weitere Ports pro Teilnehmer. Port 2001 ergibt rückwärts `198.51.100.1`; Port 58204 liegt im dynamischen Pool. Beide Suchen stammen aus dem RFC selbst.
- MAP: a = 6, k = 8, PSID `0x34`: 63 Bereiche zu 4 Ports, von 1232-1235 und 2256-2259 bis 63696-63699 und 64720-64723, insgesamt 252 Ports, das in Anhang A von RFC 7597 abgedruckte Port-Set. Port 1232 ergibt rückwärts die PSID `0x34`, wie Example 2 in Anhang A zeigt.

## Was das Tool nicht tut

Es teilt nichts zu, liest kein Log, kontaktiert kein Gerät und gibt keine Rechtsberatung. Wer welche Aufzeichnungen wie lange aufbewahren muss und wie eine rechtmäßige Anfrage beantwortet wird, hängt von der Rechtsordnung ab; der [Artikel zu CGNAT](/learn/cgnat-address-sharing-and-attribution) legt mit seinen Quellen dar, was RFC 6269, RFC 6302 und für Brasilien der Marco Civil da Internet vorgeben.

## Ergebnisse teilen

Unter den ersten Zahlen jedes Tabs erzeugt **Ergebnisse teilen** einen Link auf diese Seite, und zwar nur, wenn Sie die Schaltfläche wählen. Der Link enthält den geöffneten Tab und jedes darin eingegebene Feld, jeweils mit Namen (`#mode=map&offset=6&psidlength=8&psid=0x34`), und auf dem Tab für Portblöcke die Größe der Log-Meldung, wenn sie nicht NAT444 ist; die Felder der beiden anderen Tabs bleiben außen vor. Alles, was der Link enthält, steht nach dem `#`, und dieser Teil ist laut [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (Abschnitt 3.5, abgerufen am 27.10.2026) „separated from the rest of the URI prior to a dereference“, also vor der Dereferenzierung vom Rest der URI getrennt: Ein Browser sendet ihn beim Öffnen des Links nicht an den Server, aber er bleibt in der Adressleiste und im Verlauf dessen, der den Link öffnet, und wer den Link hat, kann ihn lesen.

- **Länge.** Ein Link enthält höchstens 16.384 Zeichen, die Grenze, die die Website für jeden Wert nach dem `#` setzt; die Felder eines Tabs sind weit kürzer.
- **Öffnen eines Links.** Der Tab öffnet sich, seine Felder übernehmen die Werte des Links (ein Feld, das der Link nicht enthält, wird geleert, sodass das Formular genau dem des Absenders entspricht), die anderen Tabs behalten ihre Werte, und die Seite rechnet. Ein Tab, ein Feld eines anderen Tabs oder eine Größe der Log-Meldung, die das Tool nicht kennt, führt dazu, dass der ganze Link ignoriert wird. Ob angenommen oder nicht, die Werte verschwinden danach sofort aus der Adresse der Seite, ohne dass eine Anfrage gesendet wird; ein Neuladen, ein Lesezeichen oder die Schaltfläche „Teilen“ der Seite überträgt daher nichts, was Sie nicht selbst teilen wollten.

## Herkunft

Jede Zahl stammt aus den unten genannten RFCs, heruntergeladen am 19.10.2026. Das Tool bringt 36 Referenzvektoren (Golden Vectors) mit (Satz `cgn-port-blocks/2026-10-19a`). Die Zahlen der RFCs selbst sind wörtlich festgelegt: die Tabelle mit vierzehn Zeilen aus RFC 7422, seine beiden Rückwärtssuchen und sein Konfigurationseintrag, das Port-Set für die PSID `0x34` aus RFC 7597, sein Beispiel von Port zu PSID und beide Beispiele aus Anhang B.2. Die übrigen werden aus der Regel berechnet, die sie nennen, und sagen das. Das verifizierte Erratum 5324 zu RFC 7599 korrigiert dessen Example 5 von PSID `0x20` auf `0x34`, die PSID, die zu den abgedruckten Ports passt; das verifizierte Erratum 4211 zu RFC 7422 korrigiert ein Zitat von „RFC 6292“ zu RFC 6269.

## API

Dieselbe Engine beantwortet die Operation `/api/v1/cgn-port-blocks` der HTTP-API der Website, Feld für Feld beschrieben im OpenAPI-Vertrag auf der [API-Seite](/api), mit Beispielen aus den Referenzvektoren. Der Vertrag gibt auch an, ob diese Website die API bereitstellt.

- **Anfrage.** Ein JSON-Objekt, das seinen Modus nennt. `{"mode":"blocks","pool":"192.0.2.0/24","blockSize":300}` mit optional `portRange`, `blocksPerSubscriber`, `subscribers` oder `inside` sowie `logFormat` (`nat444` oder `ds-lite`). `{"mode":"deterministic","inside":"198.51.100.0/28","outside":"192.0.2.1","dynamicFactor":2,"maxPorts":5040}` mit optional `reserved`, `compressionRatio`, `lookup`, `reverse` (`address`, `port`, `time`), `configFrom`, `configUntil` und `recordTime`. `{"mode":"map","offset":6,"psidLength":8,"psid":"0x34"}` mit optional `port`.
- **Antwort.** Das Ergebnis des Modus, wobei `mode` angibt, welcher es ist. Für `{"mode":"map","offset":6,"psidLength":8,"port":1232}` antwortet die API mit `reverse.psid` 52 und `reverse.psidHex` `0x34`; für die Anfrage aus RFC 7422 mit `reverse` Port 2001 antwortet sie mit `reverse.status` `deterministic` und `reverse.inside` `198.51.100.1`.
- **Fehler.** HTTP 400, `invalid_input`, mit der Meldung der Engine, zum Beispiel `with k = 8 the PSID must be 0 to 255` für die PSID 256.
