## Qué hace

Un grupo de agregación de enlaces (LAG, link aggregation group) agrupa enlaces paralelos en uno solo, y el protocolo de control de agregación de enlaces (LACP, Link Aggregation Control Protocol) permite que los dos extremos se pongan de acuerdo sobre qué enlaces pertenecen a él. Cuando un agregado se comporta mal surgen siempre dos preguntas: ¿por qué miembro va este flujo? y ¿qué se están diciendo los dos extremos? La página responde a las dos, en dos modos:

- **Qué enlace.** Para un bond de Linux, el miembro que lleva un flujo, calculado con el propio hash de transmisión del controlador: cada valor intermedio, el miembro que usa el flujo cuando cae cada uno de los demás miembros y, si lo pides, cómo se reparte una serie de flujos entre los miembros. Para el mismo número de miembros muestra el reparto que documenta Cisco para el hash de sus Catalyst 6500/6000, que explica por qué con 2, 4 y 8 miembros el tráfico se reparte de forma uniforme y con 3, 5, 6 y 7 no.
- **Flags de estado.** Los octetos de estado del actor y del partner de una LACPDU (la unidad de datos de LACP), o los flags que imprime un comando show, leídos bit a bit desde LACP_Activity hasta Expired, con los temporizadores que se derivan y un veredicto para la pareja. El PortState de Huawei se puede escribir tal como lo imprime `display eth-trunk`, o pegar la salida completa, y entonces se lee cada fila de miembro.

Todo se calcula en tu navegador.

## Por qué solo se calcula el hash de Linux

Cómo reparte las tramas un agregado se deja a cada implementación. El propio módulo de gestión de IEEE 802.1AX dice que una descripción del algoritmo de distribución “could include information about the distribution algorithm in use” (podría incluir información sobre el algoritmo de distribución en uso) y que “The contents are vendor specific” (el contenido depende del fabricante) ([IEEE8023-LAG-MIB](https://www.ieee802.org/1/files/public/MIBs/IEEE8021-AX-MIB-202005290000Z.mib), dot3adAggDescription). Solo se puede calcular un miembro cuando una implementación publica su hash completo, y una lo hace: el controlador de bonding de Linux, cuyo [HOWTO](https://docs.kernel.org/networking/bonding.html) da cada política como una fórmula y cuyo código fuente, [bond_main.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/net/bonding/bond_main.c), fija cada detalle. El bonding de RouterOS de MikroTik describe con palabras las mismas políticas, con los mismos nombres, y remite a la documentación de Linux ([MikroTik, Bonding](https://manual.mikrotik.com/docs/7.24/high-availability-solutions/bonding/)).

Los fabricantes de switches documentan qué campos entran en el hash, no la función, así que la página los nombra y no calcula nada para ellos:

- **Cisco.** En los Catalyst 6500/6000, “The Cisco-proprietary hash algorithm computes a value in the range 0 to 7” (el algoritmo de hash propietario de Cisco calcula un valor entre 0 y 7), y el documento da cuántos de esos valores acepta cada puerto, no el hash ([Cisco, documento 12023](https://www.cisco.com/c/en/us/support/docs/lan-switching/etherchannel/12023-4.html)). La guía de los Catalyst 9300 enumera los métodos de load-balance, con “The default is src-mac” (el predeterminado es src-mac), y dice que el switch reduce “part of the binary pattern that is formed from the addresses in the frame to a numerical value” (parte del patrón binario que forman las direcciones de la trama a un valor numérico) ([Cisco, Configuring EtherChannels, IOS XE 17.18](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-18/configuration_guide/lyr2/b_1718_lyr2_9300_cg/configuring_etherchannels.html)).
- **Juniper.** El hash usa campos del paquete “as well as on some internal values like source port ID and source device ID” (además de algunos valores internos, como el ID del puerto de origen y el ID del dispositivo de origen) ([Juniper, Hashing Algorithms for LAG and ECMP](https://www.juniper.net/documentation/us/en/software/junos/interfaces-ethernet-switches/topics/topic-map/hashing-algoriths-lag-bundle-ecmp.html)), que nadie que lea un paquete puede conocer.
- **Arista.** “Hashing algorithm inputs varies by switch platform” (las entradas del algoritmo de hash varían según la plataforma del switch) ([Arista EOS, Port Channels and LACP](https://www.arista.com/en/um-eos/eos-port-channels-and-lacp)).
- **HPE Aruba.** AOS-CX ofrece l2-src-dst, l3-src-dst y l4-src-dst sin describir la función ([AOS-CX 10.16, LACP configuration settings](https://arubanetworking.hpe.com/techdocs/AOS-CX/10.16/HTML/link_aggregation/Content/Chp_LAG/lac-cnf-set-10.htm)).
- **Extreme.** Switch Engine nombra xor, crc-16 y crc-32 como algoritmos de hash, pero no cómo se disponen los campos para ellos ([Switch Engine 33.7.1 Command References](https://documentation.extremenetworks.com/Switch%20Engine%20v33.7.1%20Command%20References/downloads/Switch_Engine_33_7_1_Command_References.pdf), configure sharing address-based custom).
- **Huawei.** La referencia de comandos de los S5700 y S6700 enumera los modos de `load-balance` `dst-ip`, `dst-mac`, `src-ip`, `src-mac`, `src-dst-ip`, `src-dst-mac` y `enhanced profile`, y dice que “The default load balancing mode is src-dst-ip” (el modo de balanceo de carga predeterminado es src-dst-ip) y que “Load balancing is valid only for outgoing traffic; therefore, the load balancing modes for the interfaces at both ends of the link can be different” (el balanceo de carga solo vale para el tráfico saliente, así que los modos de las interfaces de los dos extremos del enlace pueden ser distintos). Una vez fijado un modo, “the hash factors used to calculate the outbound interface vary according to the packet type and device model” (los factores de hash que se usan para calcular la interfaz de salida varían según el tipo de paquete y el modelo de dispositivo): los paquetes de capa 2 recurren a las direcciones MAC de origen y de destino; el S5736-S usa src-dst-ip con los puertos TCP o UDP de origen y de destino “regardless of whether you configure this parameter” (lo configures o no) y admite un solo modo de balanceo de carga para todo el switch; y en los S5731-H, S5731-S, S5731S-S, S5731S-H, S5732-H, S6730-H, S6730S-H, S6730-S y S6730S-S, sea cual sea el modo básico configurado de los seis, “packets are load balanced based on physical-layer source port numbers in the packets” (el balanceo de los paquetes se basa en los números de puerto de origen de capa física que llevan). La función en sí no se da, así que para Huawei no se calcula nada; “You can run the display eth-trunk load-balance command to check the hash factors used when the outbound interface is calculated” (puedes ejecutar el comando display eth-trunk load-balance para comprobar los factores de hash que se usan al calcular la interfaz de salida) ([Huawei, Link Aggregation Commands, V200R025C00](https://support.huawei.com/enterprise/en/doc/EDOC1100514211/54c5f31b/link-aggregation-commands), consultado en un navegador: el sitio rechaza las lecturas automatizadas).
- **Chips de switch de MikroTik.** Un bond descargado en el chip del switch calcula el hash allí, y el manual no da ninguna fórmula.

Para preguntárselo al propio switch, el documento 12023 de Cisco muestra el comando `test etherchannel load-balance interface port-channel` de los Catalyst 6500, que responde con el puerto que usaría un par de direcciones dado.

## Qué enlace: las entradas

- **Política de hash de transmisión**: los valores de `xmit_hash_policy` del HOWTO `layer2` (el predeterminado), `layer2+3`, `layer3+4` y `vlan+srcmac`. El formulario solo muestra los campos que lee la política.
- **Orden de bytes del procesador**: little-endian (el predeterminado) o big-endian, para `layer2+3` y `layer3+4`. Un valor de 32 bits ocupa cuatro bytes: un procesador big-endian guarda su byte más significativo en la dirección más baja, y uno little-endian, el menos significativo. De las arquitecturas Linux que enumera Debian, amd64, arm64, ppc64el, riscv64 y loong64 son little-endian, y s390x, ppc64, mips y sparc64 son big-endian ([Debian Wiki, ArchitectureSpecificsMemo](https://wiki.debian.org/ArchitectureSpecificsMemo), consultado en un navegador: el sitio rechaza las lecturas automatizadas). El artículo [Big-endian y little-endian](/learn/big-endian-and-little-endian) explica a fondo el orden de bytes; cómo cambia este hash está en las reglas de abajo.
- **Miembros que pueden transmitir**: de 2 a 8, numerados desde 0.
- **Dirección MAC de origen y de destino** (`layer2`, `layer2+3`; `vlan+srcmac` solo lee la de origen), en notación con dos puntos, con guiones o con puntos al estilo de Cisco.
- **Dirección IP de origen y de destino**, IPv4 o IPv6, de la misma familia (todas las políticas salvo `vlan+srcmac`; con `layer2` solo fijan el EtherType).
- **Protocolo, puerto de origen y puerto de destino** (`layer3+4`): TCP o UDP, puertos de 0 a 65535.
- **ID de VLAN y prioridad** (`vlan+srcmac`): un ID de VLAN de 1 a 4094, o en blanco para una trama sin etiquetar, y una prioridad de 0 a 7; las MIB de IEEE 802.1 no admiten 0 ni 4095 como identificadores de VLAN y dan las prioridades de 0 a 7 ([IEEE8021-TC-MIB](https://www.ieee802.org/1/files/public/MIBs/IEEE8021-TC-MIB.mib), IEEE8021VlanIndex e IEEE8021PriorityValue).
- **Reparto** (opcional): un campo de los que lee la política, que varía hacia arriba a partir del valor escrito, en una serie de 1 a 4096 flujos.

## Qué enlace: las reglas

Las fórmulas del HOWTO, con los detalles que fija su código fuente:

```text
layer2:    hash = source MAC[5] XOR destination MAC[5] XOR packet type ID
layer2+3:  hash = source MAC[5] XOR destination MAC[5] XOR packet type ID
           hash = hash XOR source IP XOR destination IP
           hash = hash XOR (hash RSHIFT 16)
           hash = hash XOR (hash RSHIFT 8)
layer3+4:  hash = source port, destination port (as in the header)
           hash = hash XOR source IP XOR destination IP
           hash = hash XOR (hash RSHIFT 16)
           hash = hash XOR (hash RSHIFT 8)
           hash = hash RSHIFT 1
vlan+srcmac: hash = (vlan ID) XOR (source MAC vendor) XOR (source MAC dev)
```

y en todos los casos el hash “is reduced modulo slave count” (se reduce módulo el número de miembros) ([Linux bonding HOWTO](https://docs.kernel.org/networking/bonding.html), xmit_hash_policy).

- **El ID de tipo de paquete** es el EtherType de la trama como número: el controlador hace el XOR de `be16_to_cpu(ep->h_proto)` (bond_eth_hash), así que 0x0800 para IPv4 y 0x86DD para IPv6 ([IANA, IEEE 802 Numbers](https://www.iana.org/assignments/ieee-802-numbers/ieee-802-numbers.txt)).
- **Las direcciones IPv6** pasan primero por ipv6_addr_hash (“first hashed using ipv6_addr_hash”, HOWTO), el XOR de las cuatro palabras de 32 bits de la dirección ([include/net/ipv6.h](https://raw.githubusercontent.com/torvalds/linux/master/include/net/ipv6.h)).
- **El orden de bytes del procesador.** El controlador hace el XOR de las direcciones tal como las devuelven `flow_get_u32_dst` y `flow_get_u32_src`, los 32 bits en bruto guardados en el paquete, y copia los puertos con `memcpy` desde una estructura que guarda primero el puerto de origen ([include/net/flow_dissector.h](https://raw.githubusercontent.com/torvalds/linux/master/include/net/flow_dissector.h)). Un procesador big-endian lee esos bytes empezando por el más significativo, que es la fórmula del HOWTO tal como está escrita; un procesador little-endian los lee al revés y obtiene un hash distinto. Qué campos cuentan, los dos plegados, el desplazamiento y el módulo son los mismos. `layer2` y `vlan+srcmac` leen bytes sueltos, o construyen sus números byte a byte, así que el orden de bytes no los cambia. La página muestra las dos palabras tal como las lee el procesador elegido. El orden de bytes solo cambia el miembro cuando el número de miembros no es una potencia de dos. Los dos plegados de `bond_ip_hash` (`hash ^= (hash >> 16); hash ^= (hash >> 8);`) dejan en el byte más bajo el XOR de los cuatro bytes de la palabra, que no cambia al invertirlos, y un módulo por 2, 4 u 8 solo lee bits de ese byte, también después del desplazamiento de `layer3+4`. Ejecutado en este motor el 2026-11-08 con 4000 flujos aleatorios (direcciones IPv4, direcciones MAC y puertos aleatorios) con `layer2+3` y `layer3+4` y con cada número de miembros de 2 a 8, los dos órdenes eligieron el mismo miembro en los 24.000 casos con 2, 4 u 8 miembros, y uno distinto en 23.031 de los 32.000 casos con 3, 5, 6 o 7. El flujo del Ejemplo muestra las dos cosas: con 2 o 4 miembros usa el miembro 0 o el 2 en cualquiera de los dos procesadores; con 5 miembros, el miembro 2 en un procesador little-endian y el miembro 4 en uno big-endian. Los vectores de referencia fijan los dos casos.
- **El bit más bajo.** `layer3+4` lo descarta al final; el comentario del código dice que es “to deal with the common even ports pattern” (para tratar el patrón habitual de puertos pares) (bond_ip_hash), así que dos puertos que solo difieren en su último bit suelen caer en el mismo miembro.
- **La VLAN.** `vlan+srcmac` hace el XOR de `skb_vlan_tag_get(skb)`, que es toda la información de control de la etiqueta, `vlan_tci` ([include/linux/if_vlan.h](https://raw.githubusercontent.com/torvalds/linux/master/include/linux/if_vlan.h)), así que los bits de prioridad cuentan además del ID de VLAN; una trama sin etiquetar cuenta como 0. La página toma el indicador de elegibilidad para descarte (DEI) como 0.
- **Qué miembro.** Los miembros que pueden transmitir (en modo 802.3ad, los del agregador activo) se enumeran en el orden en que se unieron al bond (bond_update_slave_arr), y el controlador toma `slaves->arr[hash % count]` (bond_xmit_3ad_xor_slave_get). Cuando cae un miembro, la lista se reconstruye sin él y el módulo se calcula con un miembro menos, así que la página muestra, para cada miembro por turno, adónde va el flujo si falla ese: a menudo un flujo se mueve aunque su propio miembro siga activo.
- **Puertos.** `layer3+4` lee los puertos de TCP y UDP sin fragmentar; “For fragmented TCP or UDP packets and all other IPv4 and IPv6 protocol traffic, the source and destination port information is omitted” (en los paquetes TCP o UDP fragmentados y en el resto del tráfico IPv4 e IPv6 se omite la información de puertos de origen y de destino) (HOWTO). La página solo lee TCP y UDP.

**El reparto documentado por Cisco.** Para el número de miembros elegido, la página muestra también la tabla que da el documento 12023 para los Catalyst 6500/6000, “the ratios of the values that each port accepts” (las proporciones de los valores que acepta cada puerto): 4:4 para dos puertos, 3:3:2 para tres, 2:2:2:2 para cuatro, 2:2:2:1:1 para cinco, 2:2:1:1:1:1 para seis, 2:1:1:1:1:1:1 para siete y un valor cada uno para ocho. De ahí que “you can only achieve perfect load balancing, even with random addresses, if you have two, four, or eight ports” (solo se consigue un balanceo de carga perfecto, incluso con direcciones aleatorias, con dos, cuatro u ocho puertos). La página muestra como porcentaje la parte de los 8 valores que corresponde a cada puerto; es la tabla documentada, no un cálculo del hash de Cisco.

**El reparto.** Con un reparto, la página calcula el miembro de cada flujo de la serie y los cuenta por miembro. Llama uniforme al reparto cuando ningún miembro lleva más de un flujo más que otro, y enumera los miembros de los 16 primeros flujos, lo que deja ver patrones como las parejas que forma `layer3+4` con puertos de origen consecutivos.

**Cada extremo solo calcula el hash de lo que envía.** “Slave selection for outgoing traffic is done according to the transmit hash policy” (la elección del miembro para el tráfico saliente se hace según la política de hash de transmisión) (HOWTO): el switch elige el miembro para el tráfico de vuelta con su propio hash, que la página no calcula.

## Flags de estado: las entradas

- **Cómo se escriben los valores**:
  - **Octeto**: tal como lo lleva la LACPDU, en hexadecimal con `0x` (`0x3D`, la forma de la columna State de `show lacp neighbor` de Cisco, cuyo valor esperado da Cisco como 0x3D, [documento 220367](https://www.cisco.com/c/fr_ca/support/docs/switches/catalyst-9300-series-switches/220367-troubleshoot-etherchannels-on-catalyst-9.html)), en decimal (`61`, como imprime Linux `port state` en /proc/net/bonding, [bond_procfs.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/net/bonding/bond_procfs.c)) o en binario con `0b`. Un `3D` a secas se rechaza, para que nunca se lea como decimal.
  - **SNMP BITS**: `dot3adAggPortActorOperState` o `dot3adAggPortPartnerOperState` tal como los devuelve SNMP, un octeto en hexadecimal (con `0x` o sin él) u ocho dígitos binarios con `0b`.
  - **Flags de Extreme**: las ocho posiciones de Switch Engine en el orden de su leyenda, “A-Activity, T-Timeout, G-Aggregation, S-Synchronization C-Collecting, D-Distributing, F-Defaulted, E-Expired”, con un guion para cada bit no activado, como en su muestra `A-GSCD--` (Switch Engine 33.7.1 Command References, show lacp member-port).
  - **Letras de Arista**: la leyenda de EOS, “A = Active, P = Passive; S=ShortTimeout, L=LongTimeout; G = Aggregable, I = Individual; s+=InSync, s-=OutOfSync; C = Collecting, X = state machine expired, D = Distributing, d = default neighbor state”, como en su muestra `ALGs+CD` ([Arista EOS](https://www.arista.com/en/um-eos/eos-port-channels-and-lacp)). Es obligatoria una letra de cada pareja; C, X, D y d son opcionales; cada letra va una sola vez, en cualquier orden.
  - **PortState de Huawei**: la columna PortState de `display eth-trunk`, “eight bits, such as 10111100” (ocho bits, como 10111100), impresa del Bit 1 al Bit 8 ([Huawei, Link Aggregation Commands, V200R025C00](https://support.huawei.com/enterprise/en/doc/EDOC1100514211/54c5f31b/link-aggregation-commands), consultado en un navegador: el sitio rechaza las lecturas automatizadas). Escribe el PortState del actor y el del partner, o pega la salida completa: la página lee cada fila de miembro de su tabla Local (puerto, Status, PortType, PortPri, PortNo, PortKey, PortState, Weight) y de su tabla Partner (puerto, prioridad de sistema, ID de sistema, PortPri, PortNo, PortKey, PortState, bajo una fila de encabezado que también empieza por ActorPortName), las empareja por nombre de puerto, muestra tal como se imprimen las líneas de encabezado que reconoce (LAG ID, WorkingMode, Hash arithmetic, System Priority, System ID) y lee en detalle el miembro que elijas, el primero de forma predeterminada. Las filas se reconocen por su forma, así que las palabras del encabezado pueden variar. `display eth-trunk` sin número enumera todos los trunks, cada uno abierto por una línea como `Eth-Trunk10's state information is:`; la página lee el primer trunk que tiene filas de miembro, muestra su nombre e indica que los demás se quedaron sin leer.
- **Actor**: el estado del extremo cuya salida estás leyendo.
- **Partner** (opcional): el estado del partner tal como lo indica ese extremo, que es lo último que recibió, o sus valores predeterminados cuando Defaulted está activado.

`show lacp interfaces` de Juniper imprime los flags como palabras (Activity, Timeout, Aggr, Syn, Col, Dist, Def, Exp); léelas y escribe el octeto, o compáralas con la lista de bits de la página.

## Flags de estado: las reglas

**Los bits.** El propio IEEE 802.1AX se ofrece a través del IEEE GET Program, detrás de una cuenta de IEEE ([IEEE SA, 802.1AX-2020](https://standards.ieee.org/ieee/802.1AX/6768/)), y no se consultó. Su módulo MIB publicado da el orden: “The first bit corresponds to bit 0 of the Actor_State (LACP_Activity), the second bit corresponds to bit 1 (Short_Timeout), the third bit corresponds to bit 2 (Aggregation)”, y así hasta “bit 7 (Expired)” (el primer bit corresponde al bit 0 de Actor_State, y así sucesivamente) ([IEEE8023-LAG-MIB](https://www.ieee802.org/1/files/public/MIBs/IEEE8021-AX-MIB-202005290000Z.mib), dot3adAggPortActorAdminState). El controlador de Linux da a esos mismos bits su lugar en el octeto, de `LACP_STATE_LACP_ACTIVITY 0x1` a `LACP_STATE_EXPIRED 0x80` ([include/uapi/linux/if_bonding.h](https://raw.githubusercontent.com/torvalds/linux/master/include/uapi/linux/if_bonding.h)), así que el bit 0 es el bit más bajo del octeto: 0x3D es Activity, Aggregation, Synchronization, Collecting y Distributing.

**La forma SNMP.** La MIB declara el estado como BITS, y SNMP envía un valor BITS con “all the named bits ... commencing with the first bit and proceeding to the last bit, ... placed in bits 8 (high order bit) to 1 (low order bit) of the first octet” (todos los bits con nombre, del primero al último, colocados en los bits 8, el de mayor orden, a 1, el de menor orden, del primer octeto) ([RFC 3417](https://www.rfc-editor.org/rfc/rfc3417.txt), sección 8). LACP_Activity es el primer bit con nombre, así que SNMP muestra el octeto con los bits invertidos: 0x3D en el cable se lee 0xBC a través de SNMP. La página muestra cada estado en las dos formas.

**El PortState de Huawei.** Huawei numera los ocho caracteres del Bit 1 al Bit 8 empezando por la izquierda. Su tabla describe el Bit 1 como “Whether the member interface is an Actor. This bit has a fixed value 1” (si la interfaz miembro es un actor; este bit vale siempre 1), el Bit 2 como el tiempo de espera (1 corto, 0 largo; “By default, an Eth-Trunk member interface uses the long timeout interval (90s)”, de forma predeterminada una interfaz miembro de un Eth-Trunk usa el tiempo de espera largo, 90 s), el Bit 3 como que permite agregar la interfaz miembro, el Bit 4 como que está “added to the link aggregation group (LAG)” (añadida al grupo de agregación de enlaces), los Bits 5 y 6 como que puede recibir y enviar LACPDU, el Bit 7 como que las LACPDU llevan valores de parámetros predeterminados y el Bit 8 como que la máquina de estados de recepción del actor está en el estado Expired. Son los bits 0 (LACP_Activity) a 7 (Expired) de la MIB, escritos empezando por el más bajo, que es el orden inverso del octeto en binario: `10111100` tal como se imprime es 0b00111101, 0x3D, el valor esperado de Cisco, y los mismos ocho dígitos que el valor SNMP BITS 0xBC escrito en binario. La página etiqueta cada bit con los dos números (Bit 1 · bit 0) y da también cada estado en la forma de Huawei. Huawei formula los Bits 5 y 6 en términos de LACPDU donde la MIB nombra Collecting y Distributing; la página conserva los nombres de la MIB y los significados de Juniper que hay más abajo. La columna Status usa las palabras de Huawei: “Selected: A member interface in Selected state is active” (una interfaz miembro en estado Selected está activa), Unselect para una inactiva y ForceFwd para una que “can forward Layer 2 traffic” (puede reenviar tráfico de capa 2). En el ejemplo de Huawei, Eth-Trunk10 tiene tres miembros: GigabitEthernet0/0/2 y 0/0/3 están en Selected con 10111100 en los dos extremos (0x3D, agrupados), y GigabitEthernet0/0/4 está en Unselect con 10100000 aquí y 10110000 desde el partner (0x05 y 0x0D: este extremo sin sincronizar, y el partner sincronizado, pero sin Collecting ni Distributing).

**Qué significa cada bit**, según `show lacp interfaces` de Juniper ([Juniper](https://www.juniper.net/documentation/us/en/software/junos/cli-reference/topics/ref/command/show-lacp-interfaces.html)):

| Bit | Nombre | Activado | Desactivado |
|---|---|---|---|
| 0 | LACP_Activity | Activo: participa “regardless of the partner's control value” (sea cual sea el valor de control del partner) | Pasivo: “not transmitting LAC PDUs unless its partner's control value is Active” (no transmite LACPDU salvo que el valor de control de su partner sea Active) |
| 1 | LACP_Timeout | Tiempo de espera corto (rápido) | Tiempo de espera largo (lento) |
| 2 | Aggregation | Puede agregarse | “operate only as an individual link” (funciona solo como enlace individual) |
| 3 | Synchronization | “allocated to the correct link aggregation group” (asignado al grupo de agregación de enlaces correcto), con un agregador compatible y una identidad “consistent with the system ID and operational key information transmitted” (coherente con el ID de sistema y la clave operativa transmitidos) | “not in the right aggregation” (no está en la agregación correcta) |
| 4 | Collecting | Recepción de las tramas entrantes habilitada | No habilitada |
| 5 | Distributing | Distribución de las tramas salientes habilitada | “currently disabled” (deshabilitada en este momento) |
| 6 | Defaulted | Usa “the default operational partner information, administratively configured for the partner” (la información operativa predeterminada del partner, configurada administrativamente) | Información del partner “received in an LACP PDU” (recibida en una LACPDU) |
| 7 | Expired | La máquina de recepción está en el estado Expired | No ha vencido |

**Los temporizadores.** “In a fast timeout, PDUs are sent every second and in a slow timeout, PDUs are sent every 30 seconds. LACP timeout occurs when 3 consecutive PDUs are missed” (con el tiempo de espera rápido, las PDU se envían cada segundo, y con el lento, cada 30 segundos; el tiempo de espera de LACP se agota cuando se pierden 3 PDU consecutivas), es decir, 3 segundos o 90 segundos (Juniper, como arriba); `lacp rate` de Cisco da “the fast rate, once every 1 second” (la tasa rápida, una vez por segundo) y la tasa normal “every 30 seconds” (cada 30 segundos) ([Cisco, Command Reference, IOS XE 17.18](https://www.cisco.com/c/en/us/td/docs/switches/lan/catalyst9300/software/release/17-18/command_reference/b_1718_9300_cr/layer_2_3_commands.html)); el tiempo de espera de LACP de Extreme es “either 90 seconds, long, or 3 seconds, short” (de 90 segundos, el largo, o de 3 segundos, el corto), largo de forma predeterminada (configure sharing lacp timeout). El bit Timeout es una petición al partner: `lacp_rate` de Linux es la “rate in which we'll ask our link partner to transmit LACPDU packets” (la tasa a la que pediremos a nuestro partner que transmita LACPDU), lenta (30 segundos) de forma predeterminada (HOWTO). En el controlador, un extremo envía con la tasa rápida mientras el bit Timeout de su partner está activado, y con la lenta en caso contrario, y da por perdido a su partner según su propio bit; cuando ningún extremo es activo, no hay ninguna transmisión periódica (ad_periodic_machine y ad_rx_machine, [bond_3ad.c](https://raw.githubusercontent.com/torvalds/linux/master/drivers/net/bonding/bond_3ad.c), cuyas constantes son `AD_FAST_PERIODIC_TIME 1`, `AD_SLOW_PERIODIC_TIME 30` y el triple de cada una para los tiempos de espera). `lacp timeout` de Huawei: con `fast`, el intervalo en el que un Eth-Trunk tiene que recibir LACPDU es de 3 segundos y “If fast is specified, the remote device sends an LACPDU every 1 second” (con fast, el dispositivo remoto envía una LACPDU cada segundo); `slow`, el predeterminado, es de 90 segundos y cada 30 segundos; un valor `user-defined` va de 3 a 90 segundos; la configuración “takes effect on all its member interfaces” (se aplica a todas sus interfaces miembro), y “The timeout interval on the two ends can be different. To facilitate maintenance, you are advised to set the same timeout interval at both ends” (el tiempo de espera puede ser distinto en los dos extremos; para facilitar el mantenimiento, se recomienda poner el mismo en ambos) (Huawei, como arriba). La página muestra con qué frecuencia envía cada extremo y tras cuánto tiempo da por perdido al otro.

**El veredicto.** La pareja está agrupada cuando los dos extremos son agregables, están sincronizados, en Collecting y en Distributing, ninguno está en Defaulted ni en Expired y al menos uno es activo. Con solo el estado del actor, el veredicto se refiere a ese extremo. Los hallazgos, por orden:

- **Ambos pasivos**: “If both links are in passive mode, they won't exchange LACP packets, and the aggregated link won't be established” (si los dos enlaces están en modo pasivo, no intercambian paquetes LACP y el enlace agregado no se establece) ([Juniper, Aggregated Ethernet LACP](https://www.juniper.net/documentation/us/en/software/junos/interfaces-ethernet-switches/topics/topic-map/aggregated-ethernet-lacp-switches.html)); Cisco: un puerto pasivo “cannot form an EtherChannel with another port that is also in the passive mode” (no puede formar un EtherChannel con otro puerto que también esté en modo pasivo).
- **Expired** (en este extremo, o indicado por el partner): no llegó ninguna LACPDU antes de que el temporizador del estado Current venciera una vez; “If no LACP PDU is received before the timer for the Current state expires a second time, the state machine enters the Defaulted state” (si no se recibe ninguna LACPDU antes de que el temporizador del estado Current venza por segunda vez, la máquina de estados pasa al estado Defaulted) (Juniper). Mientras está en Expired, el controlador de Linux pone en corto el Timeout de su partner, así que envía cada segundo.
- **Defaulted** (en este extremo, o indicado por el partner): no se recibió ninguna LACPDU a tiempo; los valores del partner que aparecen a su lado son predeterminados, no lo que dijo el extremo remoto.
- **Individual**: Aggregation desactivado en alguno de los dos extremos.
- **Sin sincronizar**: el enlace no está en la agregación correcta. Los puertos forman una agregación cuando tienen “the same actor system ID, actor key, partner system ID, and partner key” (el mismo ID de sistema del actor, la misma clave del actor, el mismo ID de sistema del partner y la misma clave del partner) ([HPE Aruba, ArubaOS 8.11, LACP](https://arubanetworking.hpe.com/techdocs/Archived/AOS-8/ArubaOS_8.11.2_Web_Help/Content/arubaos-solutions/lacp/lacp-over.htm)), así que un miembro cableado a otro switch, o a un puerto de otro grupo de ese switch, muestra un ID de sistema o una clave del partner distintos de los de los demás miembros: compáralos en las columnas del partner del comando show.
- **Sincronizado, pero sin Collecting ni Distributing**: todavía se está asociando al agregador, o espera al partner (los estados mux de Juniper indican cuál de las dos cosas).
- **Tiempos de espera distintos**: cada extremo envía a la tasa que le pide el otro, así que un fallo silencioso se detecta tras un tiempo distinto en cada sentido.

## Qué rechaza y por qué

- **Qué enlace**: una política que no sea una de las cuatro (encap2+3 y encap3+4 pueden leer los encabezados internos de un túnel, que la página no acepta); un orden de bytes que no sea little ni big; menos de 2 o más de 8 miembros; que falte un campo que lee la política; una dirección MAC mal formada (seis octetos, un mismo separador en toda ella, o la notación con puntos de Cisco); una dirección IP con un octeto mayor que 255, un cero a la izquierda, una longitud de prefijo o una zona; direcciones de dos familias; un protocolo que no sea TCP ni UDP; un puerto fuera del intervalo de 0 a 65535; un ID de VLAN de 0 o 4095, o fuera del intervalo de 1 a 4094; una prioridad fuera del intervalo de 0 a 7, o una prioridad en una trama sin etiquetar; un reparto sobre un campo que la política no lee (no movería nada), de más de 4096 flujos, o que pase del último valor del campo. Los campos que la política no lee no se leen en absoluto, así que un valor antiguo en ellos no detiene la página.
- **Flags de estado**: un valor que no sea un octeto (mayor que 255, de más de dos dígitos hexadecimales o de ocho dígitos binarios); hexadecimal a secas sin `0x`; ocho caracteres 0 y 1 en la forma de octeto, que son o bien un PortState de Huawei escrito con el formato equivocado, o bien binario sin su `0b` (el mensaje nombra las dos cosas); un valor SNMP de más de un octeto; una cadena de Extreme que no sean ocho posiciones con la letra correcta o un guion; letras de Arista a las que les falte una pareja, con una letra repetida o con un carácter que Arista no imprime; un PortState de Huawei que no sean ocho caracteres 0 y 1; una salida pegada junto con valores escritos; una salida pegada sin filas de miembro, con una línea que empieza como una fila Local o Partner pero no se lee como tal, con dos filas para un mismo puerto en la misma tabla, o con una fila Partner cuyo puerto no incluye la tabla Local; un puerto elegido que la tabla Local no incluye.
- Cada campo tiene como máximo 64 caracteres, salvo una salida pegada: como máximo 8192 caracteres y 96 líneas que no estén en blanco; una línea de más de 200 caracteres no es una fila y no se lee. Una salida pegada solo se lee en el formato de Huawei.

## Ejemplos resueltos

El curso [LAN Switch Operations and Maintenance](/materials/lan-switch-operations-and-maintenance), en su capítulo 2.2, agrupa dos cables, los puertos 47 y 48, y las diapositivas del fabricante configuran la tasa rápida de LACP; no da flujos ni direcciones para el agregado. Así que los Ejemplos son:

- **Qué enlace**: un bond de dos miembros, igual que el laboratorio del curso agrupa dos cables, que lleva el primer flujo del laboratorio del [artículo de Aprender](/learn/link-aggregation-and-lacp), un flujo de copia de seguridad desde 192.0.2.10, puerto TCP 50001, hasta 198.51.100.20, puerto TCP 873, con `layer3+4` en un procesador little-endian. Los puertos se leen como 0x690351c3, y las dos direcciones como 0x0a0200c0 y 0x146433c6; tras el XOR y los plegados, el hash es 0x3b89385a, par, así que lo lleva el miembro 0. En los 64 puertos de origen siguientes, los dos miembros toman 32 flujos cada uno, por parejas (0, 1, 1, 0, 0, 1, 1, 0...), porque el último desplazamiento descarta el bit más bajo.
- **La lectura del laboratorio de Aprender**: el mismo flujo con cuatro miembros y un procesador big-endian da 0x62d3e15a y el miembro 2, el valor que el laboratorio calcula a mano.
- **layer2 hacia un router**: con todos los flujos dirigidos a la dirección MAC del router, `layer2` da 0x0000080b (0x01 XOR 0x0a XOR 0x0800) y el miembro 3 de 4 para todos ellos; si en cambio se varía la dirección MAC de destino en 256 valores, se reparten 64 por miembro.
- **IPv6 en tres miembros**: 2001:db8::10, puerto TCP 443, hacia 2001:db8:1::20; los 300 puertos de destino siguientes a partir de 51000 caen 118, 91 y 91 en los tres miembros, no un tercio exacto cada uno. El reparto documentado por Cisco para tres puertos también es desigual: 3:3:2 de sus 8 valores, 37,5 %, 37,5 % y 25 %.
- **Flags de estado**: 0x3F en los dos extremos: activo, tiempo de espera corto, agregable, sincronizado, en Collecting y en Distributing; agrupado, con cada extremo enviando cada segundo y dando por perdido al otro tras 3 segundos. 0x3D en los dos es lo mismo con la tasa lenta, el valor esperado de Cisco. 68 y 0, tal como los imprime /proc/net/bonding, son un bond de Linux pasivo que no ha oído nada frente a un estado del partner de 0, el valor predeterminado del controlador: ambos pasivos, Defaulted, sin sincronizar. `A-GSCD--` (Extreme), `ALGs+CD` (Arista), 0xBC (SNMP) y `10111100` (Huawei) son todos 0x3D.
- **display eth-trunk de Huawei**: la muestra pega, literalmente, el ejemplo de la referencia de comandos de Huawei. GigabitEthernet0/0/2, en Selected (como 0/0/3), lee 10111100 en los dos extremos: 0x3D, agrupado, con cada extremo enviando cada 30 segundos. Si eliges GigabitEthernet0/0/4, en Unselect, lee 10100000 y 10110000: 0x05 y 0x0D, no agrupado, con este extremo sin sincronizar y el partner todavía sin Collecting ni Distributing.

## Qué no hace

No habla con ningún switch ni servidor: los valores son tuyos. No calcula el hash de ningún fabricante salvo el del controlador de Linux, ni la elección del switch para el tráfico de vuelta, ni las políticas encap, los fragmentos o los protocolos distintos de TCP y UDP con `layer3+4`. No decodifica una LACPDU entera, solo los dos octetos de estado (los ID de sistema, las claves y los números de puerto de una salida de Huawei pegada se muestran tal como se imprimen, sin comprobarlos), y no simula las máquinas de estados de LACP. Para ver cómo se mueven los flujos entre miembros cuando haces caer uno, usa el laboratorio de hash del artículo [Agregación de enlaces y LACP](/learn/link-aggregation-and-lacp).

## Compartir resultados

Debajo del veredicto, **Compartir resultados** genera un enlace a esta página, solo cuando lo presionas, que lleva después del `#` el modo y sus campos tal como se escribieron: `mode` (`link` o `state`) siempre; en el modo de enlace, `policy`, `order` (`little` o `big`) y `members`, y después solo los campos que lee la política, si se escribieron (`srcmac`, `dstmac`, `srcip`, `dstip`, `protocol`, `srcport`, `dstport`, `vlan`, `priority`), y `spread` y `count` cuando hay un reparto activado; en el modo de estado, `format`, `actor` y `partner` si se escribió, o, en el formato de Huawei con una salida pegada, `display` (la salida, con sus líneas) y `port` si se eligió uno, en lugar de `actor` y `partner`. No se llevan los campos que la política no lee ni los del otro modo. En el modo de enlace, la ventana emergente añade una advertencia: las direcciones MAC e IP y los puertos pueden describir hosts de una red privada, así que léelos antes de enviar el enlace. Con una salida pegada añade una propia: la salida nombra los ID de sistema de los switches (direcciones MAC) y sus interfaces.

Según el [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986.txt) (sección 3.5, consultado el 2026-11-08), el fragmento queda “separated from the rest of the URI prior to a dereference” (separado del resto del URI antes de resolverlo), así que estos valores no se envían al servidor cuando se abre el enlace; se quedan en la barra de direcciones y en el historial de quien lo abra, y cualquiera que tenga el enlace puede leerlos.

- **Longitud.** Un enlace lleva como máximo 16.384 caracteres, el límite que el sitio aplica a todo valor después del `#`; una salida pegada de hasta 8192 caracteres cabe, y los demás campos son mucho más cortos.
- **Al abrir un enlace.** El modo y sus campos se establecen como lo haría la escritura (en el modo de enlace, un campo que la política no lee conserva su valor, y si falta el reparto, el reparto se desactiva), y la página calcula. Se ignora un enlace con un modo, una política, un orden, un protocolo, un formato o un campo de reparto desconocidos, con un campo del otro modo o uno que la política no lee, sin un campo obligatorio, con un recuento sin reparto o al revés, con un `display` o un `port` fuera del formato de Huawei, con un `display` junto a un `actor` o un `partner`, con un `port` sin `display`, o con un valor en dos líneas (salvo `display`). Se acepte o no, los valores salen después de la propia dirección de la página al instante, sin ninguna solicitud, así que al recargar, con un marcador o con el propio botón Compartir de la página no se lleva nada que no hayas decidido compartir.

## Procedencia

El motor es aritmética de bits fija, sin reloj, sin red y sin aleatoriedad. Sus vectores de referencia (conjunto `lacp-hash-and-state-reader-golden-2026-11-08b`) fijan cada política en los dos órdenes de bytes con 2 a 8 miembros, los seis flujos del laboratorio de Aprender, IPv6 (con una cola IPv4 con puntos), las tres notaciones de direcciones MAC, puertos y direcciones en sus límites, la política de VLAN con prioridad y sin ella, nueve repartos (de hasta 4096 flujos), cada uno de los 256 octetos de estado como actor, 24 parejas de actor y partner, las formas SNMP, Extreme y Arista, los Ejemplos y las muestras, las frases que recogen las reglas y los rechazos. Cada valor esperado se obtuvo con una implementación en Python independiente, no ejecutando este motor: el hash, a partir del código del controlador, con las direcciones y los puertos leídos con `struct.unpack` en el orden de bytes del procesador; los estados, a partir del orden de bits de la MIB y de la regla del RFC 3417. Sus resultados big-endian coinciden con los propios vectores del laboratorio de Aprender, incluido el hash que calcula a mano. El segundo conjunto añade el PortState de Huawei: de nuevo cada octeto como PortState, el ejemplo de la referencia de comandos de Huawei con cada miembro elegido, salidas con finales de línea de Windows, líneas en blanco y tabulaciones, filas sin encabezados, una fila ForceFwd y un puerto 10GE, y cada rechazo de una salida pegada con sus límites; sus valores esperados proceden de un segundo modelo en Python que lee un PortState como la cadena invertida y separa las filas por los espacios en blanco. Los resultados little-endian del laboratorio de Aprender, que su opción de orden de bytes ofrece ahora, coinciden flujo a flujo con este motor.

## API

El mismo motor responde a `/api/v1/lacp-hash-and-state-reader` en la API HTTP del sitio; el contrato está en la [página de la API](/api), que también indica si este sitio sirve la API.

- **Solicitud.** Un objeto JSON. Qué enlace: `{"mode": "link", "policy": "layer3+4", "byteOrder": "little", "members": 2, "srcIp": "192.0.2.10", "dstIp": "198.51.100.20", "protocol": "tcp", "srcPort": 50001, "dstPort": 873, "spread": {"field": "srcPort", "count": 64}}`; `policy` (`layer2` de forma predeterminada), `byteOrder` (`little` de forma predeterminada), `protocol` (`tcp` de forma predeterminada), `vlan`, `priority` y `spread` son opcionales, y `srcMac` y `dstMac` los necesitan `layer2` y `layer2+3` (`vlan+srcmac` solo necesita `srcMac`). Flags de estado: `{"mode": "state", "format": "octet", "actor": "0x3F", "partner": "0x3F"}`; `format` (`octet` de forma predeterminada) y `partner` son opcionales. En el formato de Huawei, `display` puede llevar la salida completa de `display eth-trunk` en lugar de `actor` y `partner`, con `port` para nombrar el miembro que se lee en detalle.
- **Respuesta, qué enlace.** `mode`, `policy`, `policyDefault`, `byteOrder`, `byteOrderMatters`, `members`, `family`, `etherType`, `used`, `formula`, `steps` (cada uno con `id` y `value`), `hash`, `hashDecimal`, `member`, `ifDown` (para cada miembro que cae, el miembro que pasa a usar el flujo), `ciscoValues`, `ciscoEven`, `spread` (`field`, `count`, `from`, `to`, `counts`, `min`, `max`, `even`, `first`, o null) y `notes`.
- **Respuesta, flags de estado.** `mode`, `format`, `formatDefault`, `actor` y `partner` (cada uno con `octet`, `hex`, `decimal`, `binary`, `snmp`, `extreme`, `huawei` y `bits`, ocho elementos con `bit`, `name`, `mask`, `set` y `text`; `partner` es null cuando no se da), `huawei` (null salvo que se haya pegado una salida; si no, `lagId`, `workingMode`, `hashArithmetic`, `systemPriority`, `systemId`, cada uno null cuando no se imprime, `members`, cada uno con `port`, `status`, `statusText`, `portType`, `portPri`, `portNo`, `portKey`, `weight`, `portState`, `hex`, `partner` y `verdict`, y después `port` y `portDefault`), `timers` (`actorTimeout`, `partnerTimeout`, `actorSends`, `partnerSends`, `periodic`), `status` (`bundled`, `bundled-this-end` o `not-bundled`), `verdictText`, `findings` (cada uno con `id`, `level` y `text`) y `notes`.
- **Errores.** HTTP 400, `invalid_input`, con el mensaje del motor, por ejemplo `"3D" looks hexadecimal: write it with 0x in front (0x3D), so it is not read as decimal.`.
