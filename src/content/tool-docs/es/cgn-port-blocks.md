## Qué hace

Cuando un NAT de nivel de operador (CGN, carrier-grade NAT) comparte una dirección IPv4 pública entre muchos abonados, lo que se comparte es el campo de puerto de 16 bits de esa dirección. Esta herramienta hace la aritmética de ese reparto en tres modos: bloques de puertos (cuántos bloques y abonados caben en una dirección y en un pool, y cuántos logs ahorran los bloques), asignación determinista tal como la define el RFC 7422 (qué dirección pública y qué puertos recibe una dirección interna, y a la inversa: de una dirección pública, un puerto y una hora a la dirección interna) y el conjunto de puertos de un identificador de conjunto de puertos (PSID, Port Set Identifier) de la asignación de dirección y puerto (MAP, Mapping of Address and Port), tal como lo calculan MAP-E (RFC 7597) y MAP-T (RFC 7599). Todo es aritmética entera que se ejecuta en tu navegador; las horas son datos de entrada, nunca se leen de un reloj.

## Por qué el rango utilizable empieza en 1024

El campo de puerto tiene 65.536 valores, y el RFC 6335 los divide en “the System Ports, also known as the Well Known Ports, from 0-1023”, los User Ports, de 1024 a 49151, y los Dynamic Ports, de 49152 a 65535 ([RFC 6335, sección 6](https://www.rfc-editor.org/rfc/rfc6335.txt)). Todas las fuentes que dimensionan las asignaciones de puertos de un CGN empiezan por encima de los System Ports: el primer paso de asignación del RFC 7422 quita los puertos reservados y dice “At a minimum, the CGN SHOULD remove system ports [RFC6335] from the port candidate list” ([RFC 7422, sección 2](https://www.rfc-editor.org/rfc/rfc7422.txt)); el desplazamiento (offset) del RFC 7597 vale 6 de forma predeterminada “as this excludes the system ports (0-1023)” ([RFC 7597, sección 5.1](https://www.rfc-editor.org/rfc/rfc7597.txt)); y el RFC 6269 cita el RFC 4787 para decir que “the use of port space (1024-65535) is safe” para los puertos de origen salientes ([RFC 6269, sección 5](https://www.rfc-editor.org/rfc/rfc6269.txt)). Por eso, el rango utilizable predeterminado va del 1024 al 65535, 64.512 puertos por dirección. Puedes cambiarlo: la herramienta avisa cuando tu rango conserva System Ports.

## Modo 1: bloques de puertos

Entradas: el pool público (un prefijo como `192.0.2.0/24`, un rango, una dirección o simplemente un número de direcciones), el rango de puertos utilizable, el tamaño de bloque en puertos, los bloques que puede tener cada abonado y, opcionalmente, la demanda, como número de abonados o como el prefijo interno del que se numeran los abonados.

Salidas: puertos utilizables por dirección, bloques completos por dirección y los puertos que no cubre ningún bloque completo, abonados por dirección, abonados en todo el pool, el límite de puertos por abonado y, frente a la demanda, cuántas direcciones hacen falta y si el pool las tiene.

Una regla condiciona el recuento. El RFC 6888 exige la agrupación de direcciones de tipo “Paired”: “a CGN must use the same external IP address mapping for all sessions associated with the same internal IP address” (un CGN debe usar la misma dirección IP externa para todas las sesiones de una misma dirección IP interna) ([RFC 6888, sección 3, REQ-2](https://www.rfc-editor.org/rfc/rfc6888.txt)). Así que todos los bloques de un abonado están en una misma dirección, y los abonados por dirección son los bloques completos por dirección divididos entre los bloques por abonado, redondeado hacia abajo. El tamaño de bloque multiplicado por los bloques por abonado es el límite por abonado que REQ-4 pide que admita un CGN: “A CGN MUST support limiting the number of external ports (or, equivalently, 'identifiers' for ICMP) that are assigned per subscriber”.

El panel de logs solo cuantifica lo que cuantifican los RFC. El RFC 7422 indica mensajes de log de “approximately 150 bytes long for NAT444 [NAT444] and 175 bytes for DS-Lite” y “approximately 33,000 connections per day” por hogar, que convierte en “approximately 5 MB per subscriber per day” ([RFC 7422, sección 1](https://www.rfc-editor.org/rfc/rfc7422.txt)); la herramienta muestra 33.000 líneas y 4.950.000 bytes (o 5.775.000 con mensajes DS-Lite), calculados a partir de esas dos cifras. El RFC 7768 dice que la asignación por bloques registra “only when blocks are allocated or deallocated” (solo al asignar o liberar bloques), “reducing log generation by a factor equal to the block size” (lo que reduce el volumen de logs en un factor igual al tamaño de bloque) ([RFC 7768, sección 2](https://www.rfc-editor.org/rfc/rfc7768.txt)); la fila de bloques divide por ese factor. Es una cifra calculada, no una medición: la única medición que cita el RFC son 42,5 TB de logs por sesión frente a 40,6 GB con bloques de puertos, para 20.000 abonados durante 60 días (sección 1).

## Modo 2: asignación determinista (RFC 7422)

El RFC 7422 sustituye el log de traducciones por una función: “(External IP Address, Port Range) = function 1 (Internal IP Address)” y “Internal IP Address = function 2 (External IP Address, Port Number)” ([RFC 7422, sección 2](https://www.rfc-editor.org/rfc/rfc7422.txt)). Sus variables son el rango interno I, el rango externo O, la relación de compresión C, el factor del pool dinámico de direcciones D, el máximo de puertos por usuario M, el algoritmo A y la lista de puertos reservados R. La herramienta implementa el algoritmo 0, Sequential, el que usa el ejemplo resuelto del RFC, paso a paso:

1. Quita R (de forma predeterminada `0-1023`) de la lista de puertos candidatos.
2. Da a cada dirección interna 1/(C + D) de los candidatos, redondeado hacia abajo; “Any remaining ports are allocated to the dynamic pool.” (los puertos restantes van al pool dinámico).
3. Sequential: el primer bloque va a la primera dirección interna, el segundo a la segunda, y así sucesivamente.
4. Los puertos que exceden el bloque de un abonado salen del pool dinámico, hasta M, y “The CGN MUST log dynamically assigned port blocks”.

El rango interno es un prefijo o un rango. Un prefijo se cuenta por sus direcciones de host, como cuenta la sección 2.3 su ejemplo: `198.51.100.0/28` da las 14 direcciones de `.1` a `.14`, así que C es 14. C vale de forma predeterminada I dividido entre O, redondeado hacia arriba; puedes fijarlo. Cuando O tiene más de una dirección, la herramienta rellena las direcciones externas por orden, C direcciones internas en cada una: el ejemplo del RFC tiene una sola dirección externa y no muestra este caso, así que tómalo como la disposición propia de la herramienta. Una lista de reservados con puertos adicionales (`0-1023,5004,5060`) se respeta exactamente, y un bloque que abarca un puerto reservado se muestra como dos rangos.

Búsqueda directa: una dirección interna da su dirección externa y su rango de puertos. Búsqueda inversa: una dirección externa y un puerto dan la dirección interna cuando el puerto está en un bloque preasignado; “dinámico” cuando está en el pool dinámico, donde solo puede responder el log de bloques dinámicos; “reservado” cuando está en R; “fuera del pool” cuando la dirección no está en O. Puede acompañarla una fecha y hora (en UTC, al segundo, como recomienda el RFC 6302 para los logs de servidor), y con “vigente desde” y “vigente hasta” la herramienta indica si la configuración que introdujiste estaba en vigor en ese momento. Las cuatro fechas y horas se fijan con el selector de fecha y hora del navegador y se leen como UTC; cada número de las tres pestañas tiene además flechas arriba y abajo que no salen de los rangos que acepta la herramienta. El RFC 7422 explica por qué importa: para identificar a un abonado hace falta la configuración vigente en ese momento, así que “the CGN MUST generate a record any time such variables are changed” ([RFC 7422, sección 3](https://www.rfc-editor.org/rfc/rfc7422.txt)). La herramienta escribe ese registro con el formato del RFC (marca de tiempo, prefijo interno y máscara, prefijo externo y máscara, D, M, A y R): para los campos del propio RFC imprime `[Wed Oct 11 14:32:52 2000]:198.51.100.0:28:192.0.2.0:32:2:5040:0:1-1023,5004,5060`.

No se implementan los algoritmos 1 a 5 (el RFC solo describe con ejemplos Staggered, Round robin e Interlaced horizontally, y el 4 y el 5 dependen de claves o de fabricantes) ni un rango interno IPv6 (DS-Lite), que el RFC 7422 permite. La dirección interna es el final de la aritmética: la sección 2.3 la correlaciona después “with DHCP/PPP lease connection records” (con los registros de concesiones DHCP/PPP).

## Modo 3: conjuntos de puertos MAP (RFC 7597, RFC 7599)

MAP comparte una dirección sin un NAT central, dando a cada equipo del lado del cliente (CE, customer edge) un conjunto fijo de puertos. El RFC 7597 escribe un puerto como tres campos, A (a bits), el PSID (k bits) y j (m bits), con a + k + m = 16 ([RFC 7597, sección 5.1](https://www.rfc-editor.org/rfc/rfc7597.txt)). “For 'a' > 0, A MUST be larger than 0”, así que el bloque de puertos en el que A es 0 no pertenece a nadie: con el valor predeterminado a = 6 es del 0 al 1023, y “'a' = 4 will exclude ports 0-4095”. “The sharing ratio is 2^k. The number of ports assigned to the user is 2^(16 - k) - 2^m (excluded ports)”, cada rango contiguo tiene 2^m puertos y “The interval between initial port numbers of successive contiguous ranges assigned to the same user is 2^(16 - a)”. MAP-T usa las mismas reglas: su apéndice de asignación de puertos remite al del RFC 7597 ([RFC 7599, apéndice B](https://www.rfc-editor.org/rfc/rfc7599.txt)).

Entradas: a, k y un PSID (decimal, o hexadecimal con `0x`), un puerto o ambos. Salidas: m, la relación de compartición, los puertos por conjunto, la longitud y el intervalo de los rangos, el bloque excluido, todos los rangos del PSID (hasta 1024) y, para un puerto, el PSID al que pertenece, según la fórmula del RFC 7597 “PSID = trunc((P modulo (R * M)) / M)” (apéndice B), o “excluido” cuando su A es 0. Con a = 0 no hay campo A y todo el conjunto de puertos es un único rango; el RFC 7597 deja entonces fuera los puertos bajos “by putting a lower bound equal to ceil(N / M) on the allowed set of PSID values” (apéndice B.1), y la herramienta da ese límite para N = 1024.

## Ejemplos resueltos

- Bloques: `192.0.2.0/24` con bloques de 300 puertos, el tamaño del bloque de ejemplo del RFC 7768, “ports 2001~2300”: 215 bloques por dirección con 12 puertos sobrantes, 55.040 abonados en el pool y 110 líneas de log por abonado al día en lugar de 33.000.
- Determinista: el ejemplo del RFC 7422, interno `198.51.100.0/28`, externo `192.0.2.1`, D = 2, M = 5040. C + D = 16, cada dirección interna recibe 4032 puertos, `198.51.100.1` tiene del 1024 al 5055 y `198.51.100.14`, del 53440 al 57471, el pool dinámico va del 57472 al 65535 y M permite 1008 puertos más por abonado. El puerto 2001 se resuelve a la inversa en `198.51.100.1`; el puerto 58204 está en el pool dinámico. Las dos búsquedas son las del propio RFC.
- MAP: a = 6, k = 8, PSID `0x34`: 63 rangos de 4 puertos, desde 1232–1235 y 2256–2259 hasta 63696–63699 y 64720–64723, 252 puertos en total, el conjunto de puertos impreso en el apéndice A del RFC 7597. El puerto 1232 se resuelve a la inversa en el PSID `0x34`, como muestra el ejemplo 2 del apéndice A.

## Qué no hace

No asigna nada, no lee ningún log ni contacta con ningún dispositivo, y no da asesoramiento legal. Quién debe conservar qué registros, durante cuánto tiempo y cómo se responde a una solicitud legal depende de la jurisdicción; el [artículo sobre CGNAT](/learn/cgnat-address-sharing-and-attribution) expone lo que dicen el RFC 6269, el RFC 6302 y, para Brasil, el Marco Civil da Internet, con sus fuentes.

## Compartir resultados

Debajo de las primeras cifras de cada pestaña, **Compartir resultados** genera un enlace a esta página, solo cuando lo presionas, que lleva la pestaña abierta y cada campo escrito en ella, cada uno por su nombre (`#mode=map&offset=6&psidlength=8&psid=0x34`), y, en la pestaña de bloques de puertos, el tamaño del mensaje de log cuando no es NAT444; los campos de las otras dos pestañas no se incluyen. Todo lo que lleva el enlace va después del `#`, que el [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (sección 3.5, consultado el 2026-10-27) describe como “separated from the rest of the URI prior to a dereference” (separado del resto del URI antes de resolverlo): el navegador no lo envía al servidor cuando se abre el enlace, pero se queda en la barra de direcciones y en el historial de quien lo abra, y cualquiera que tenga el enlace puede leerlo.

- **Longitud.** Un enlace lleva como máximo 16.384 caracteres, el límite que el sitio aplica a todo valor después del `#`; los campos de una pestaña son mucho más cortos.
- **Al abrir un enlace.** Se abre la pestaña, sus campos pasan a ser los del enlace (un campo que el enlace no lleva se vacía, así que el formulario es exactamente el de quien lo envió), las otras pestañas conservan sus valores y la página calcula. Una pestaña, un campo de otra pestaña o un tamaño de mensaje de log que la herramienta no tiene hace que se ignore el enlace entero. Se acepte o no, los valores salen después de la propia dirección de la página al instante, sin ninguna solicitud, así que al recargar, con un marcador o con el propio botón Compartir de la página no se lleva nada que no hayas decidido compartir.

## Procedencia

Cada número sale de los RFC que se citan abajo, descargados el 19 de octubre de 2026. La herramienta incluye 36 vectores de referencia (conjunto `cgn-port-blocks/2026-10-19a`). Los números de los propios RFC se fijan al pie de la letra: la tabla de catorce filas del RFC 7422, sus dos búsquedas inversas y su registro de configuración, el conjunto de puertos del RFC 7597 para el PSID `0x34`, su ejemplo de puerto a PSID y los dos ejemplos del apéndice B.2. Los demás se calculan a partir de la regla que nombran, y así lo indican. La errata verificada 5324 del RFC 7599 corrige su ejemplo 5, del PSID `0x20` al `0x34`, el PSID que coincide con los puertos impresos; la errata verificada 4211 del RFC 7422 corrige una cita de “RFC 6292” por RFC 6269.

## API

El mismo motor responde a la operación `/api/v1/cgn-port-blocks` de la API HTTP del sitio, detallada campo por campo en el contrato OpenAPI de la [página de la API](/api), con ejemplos tomados de los vectores de referencia. El contrato también indica si este sitio sirve la API.

- **Solicitud.** Un objeto JSON que nombra su modo. `{"mode":"blocks","pool":"192.0.2.0/24","blockSize":300}` con `portRange`, `blocksPerSubscriber`, `subscribers` o `inside` opcionales, y `logFormat` (`nat444` o `ds-lite`). `{"mode":"deterministic","inside":"198.51.100.0/28","outside":"192.0.2.1","dynamicFactor":2,"maxPorts":5040}` con `reserved`, `compressionRatio`, `lookup`, `reverse` (`address`, `port`, `time`), `configFrom`, `configUntil` y `recordTime` opcionales. `{"mode":"map","offset":6,"psidLength":8,"psid":"0x34"}` con un `port` opcional.
- **Respuesta.** El resultado del modo, con `mode` indicando cuál. Para `{"mode":"map","offset":6,"psidLength":8,"port":1232}`, la API responde `reverse.psid` 52 y `reverse.psidHex` `0x34`; para la solicitud del RFC 7422 con el puerto 2001 en `reverse`, responde `reverse.status` `deterministic` y `reverse.inside` `198.51.100.1`.
- **Errores.** HTTP 400, `invalid_input`, con el mensaje del motor, por ejemplo `with k = 8 the PSID must be 0 to 255` para el PSID 256.
