## Qué hace

Pega un ID token de OpenID Connect o el documento `.well-known/openid-configuration` de un proveedor, y la herramienta lo decodifica. En un ID token lee los claims de identidad principales, los claims de perfil estándar y los hashes de vinculación, y ejecuta una serie de comprobaciones de seguridad. En un documento de descubrimiento presenta los endpoints y las capacidades del proveedor. Detecta automáticamente cuál de los dos pegaste, y todo se ejecuta en tu navegador.

## OIDC en un párrafo

OpenID Connect es una capa de identidad construida sobre OAuth 2.0. OAuth responde “qué puede hacer esta aplicación”; OIDC añade “y quién es el usuario”. Lo consigue haciendo que el proveedor emita un **ID token**, un JWT firmado que afirma quién inició sesión, junto con el token de acceso de OAuth. Como un ID token es un JWT, la herramienta lo decodifica con el mismo núcleo de JWT que se usa en otras partes del sitio y después lo interpreta con el significado específico de OIDC.

## El ID token y sus comprobaciones

Los claims principales identifican el token: `iss` (quién lo emitió), `sub` (el identificador estable del usuario), `aud` (el cliente para el que se emitió) y los claims de tiempo. Por encima de ellos, OIDC añade claims que conviene entender: `nonce`, un valor que genera el cliente y que el proveedor devuelve tal cual para poder detectar un token reutilizado (replay); `at_hash` y `c_hash`, que vinculan el ID token al token de acceso y al código de autorización para que no se puedan intercambiar; `amr`, los métodos de autenticación usados (valores como `pwd`, `otp` o `mfa`, registrados en el RFC 8176); y claims de perfil estándar como `name` y `email`. Las comprobaciones de seguridad de la herramienta miran exactamente lo que miraría un cliente cuidadoso: que estén los claims obligatorios, que el algoritmo de firma sea sólido y no `none` ni uno débil, que haya un nonce y que la audiencia sea la que esperas.

## El documento de descubrimiento

El documento `.well-known/openid-configuration` es la forma en que un proveedor se anuncia. Enumera los endpoints que necesita un cliente (authorization, token, userinfo y el `jwks_uri`, donde están las claves de firma), los scopes y los tipos de respuesta que admite, los algoritmos con los que firmará los ID tokens y los métodos de code challenge de PKCE que acepta. Leerlo te dice de un vistazo qué admite un proveedor y si anuncia protecciones actuales como PKCE con `S256`.

## Uso

Pega un ID token para decodificar sus claims y ver la evaluación de seguridad, o pega un documento de descubrimiento para leer los endpoints y las capacidades de un proveedor. La decodificación es una lectura pura de lo que contiene el token o el documento; no contacta con el proveedor.

## Compartir resultados

Debajo de las insignias y los hallazgos, **Compartir resultados** genera un enlace a esta página, solo cuando lo presionas. Lo que lleva después del `#` depende de lo que pegaste, y su ventana emergente lo dice antes de que se copie nada; después ofrece Copiar enlace y, si el navegador lo tiene, el menú Compartir del sistema; la dirección de la página no cambia.

- **Un ID token.** El enlace lleva su encabezado y sus claims: los dos primeros segmentos exactamente como los pegaste, seguidos de un segmento de firma vacío (`header.payload.`), y una marca que indica que el token pegado tenía firma. Nunca lleva la firma, ni el token tal como lo pegaste. Un ID token es un JWT que el token endpoint devuelve junto a un token de acceso al portador ([OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html), secciones 2 y 3.1.3.3, consultado el 2026-11-01), y sin su firma la copia no es un token que acepte ningún verificador ([RFC 7515](https://www.rfc-editor.org/rfc/rfc7515), sección 5.2, consultado el 2026-11-01: cuando ninguna firma se valida, “the JWS MUST be considered invalid”, el JWS debe considerarse no válido). La ventana emergente añade una precaución: los claims nombran a una persona, así que léelos antes de enviar el enlace. Si el miembro `jwk` de un encabezado contiene material de clave privada, no hay enlace.
- **Un documento de descubrimiento.** El enlace lo lleva tal como lo escribiste: un proveedor tiene que publicarlo en `/.well-known/openid-configuration` ([OpenID Connect Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html), sección 4, consultado el 2026-11-01), así que es público. Si lo pegado también contiene una credencial, como suele ocurrir con el propio archivo de configuración de una aplicación, no hay enlace, y la ventana emergente nombra el miembro: `client_secret` ([RFC 7591](https://www.rfc-editor.org/rfc/rfc7591), sección 3.2.1), `registration_access_token` ([RFC 7592](https://www.rfc-editor.org/rfc/rfc7592), sección 3), `access_token` o `refresh_token` ([RFC 6749](https://www.rfc-editor.org/rfc/rfc6749), sección 5.1), `id_token` (OpenID Connect Core 1.0, sección 3.1.3.3) o una JWK con miembros privados ([RFC 7518](https://www.rfc-editor.org/rfc/rfc7518), sección 6), todos consultados el 2026-11-01. La página nunca muestra esos miembros, pero un enlace con lo pegado sí los llevaría; quítalos y vuelve a presionar.

Según el [RFC 3986](https://www.rfc-editor.org/rfc/rfc3986) (sección 3.5, consultado el 2026-11-01), el fragmento queda “separated from the rest of the URI prior to a dereference” (separado del resto del URI antes de resolverlo), así que los valores no se envían al servidor cuando se abre el enlace; se quedan en la barra de direcciones y en el historial de quien lo abra, y cualquiera que tenga el enlace puede leerlos.

- **Longitud.** Como máximo 16.384 caracteres en total, el límite que el sitio aplica a todo valor después del `#`; si lo compartido es más largo, no hay enlace, y la ventana emergente indica su longitud.
- **Al abrir un enlace.** El valor rellena el cuadro y la página lo decodifica como un pegado: los mismos claims, los mismos tiempos y los mismos hallazgos para un token (su insignia lo muestra firmado si el de quien lo envió lo estaba, con una nota de que la firma se dejó fuera del enlace) y los mismos endpoints y capacidades para un documento. No se descarga nada: la página nunca llama al `jwks_uri` ni a ningún endpoint. Un token entero, un documento que contiene una credencial o cualquier cosa que la página rechace se ignora. En cualquier caso, el valor sale de la dirección de la página al instante, sin ninguna solicitud, así que al recargar, o con el propio botón Compartir de la página, no se lleva nada.
